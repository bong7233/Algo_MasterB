# X-7 부동소수점의 함정

::: lead
`0.1 + 0.2 == 0.3`이 왜 거짓인지 답할 수 있는가. 답할 수 있어야, 좌표를 실수로 받을 수밖에 없는 문제에서 `==`를 쓰지 않는 이유도 설명할 수 있다.
:::

## 1. 문제

[X-5](#/x-5)와 [X-6](#/x-6)은 좌표를 끝까지 정수로 유지해서 CCW의 부호 비교를 정수 연산으로 끝냈다. 그런데 입력이 애초에 정수가 아닌 경우가 실무에는 흔하다. GPS 좌표, 센서가 측정한 거리, 물리 시뮬레이션이 계산해 낸 위치는 전부 실수다.

시뮬레이션 루프를 하나 짠다고 하자. 로봇이 초당 `0.1`m씩 전진하고, 누적 이동 거리가 정확히 `1.0`m가 되면 정지한다.

```python
distance = 0.0
while distance != 1.0:
    distance += 0.1
```

이 코드는 멈추지 않는다. `0.1`을 열 번 더한 값이 `1.0`과 **정확히 같지 않기** 때문이다. 두 로봇이 같은 지점에 도달했는지, 계산한 넓이 두 개가 같은 값인지, 반복문이 목표값에 "도달"했는지를 실수로 비교하는 자리마다 이 문제가 똑같이 나타난다.

## 2. 아이디어

### 2.1 이진 부동소수점이 십진 소수를 못 담는 이유

십진법에서 `1/3`은 `0.333...`으로 끝나지 않는다. 분모 `3`이 십진법의 밑인 `10 = 2 × 5`의 소인수가 아니기 때문이다. 이진법도 같은 사정을 겪는다. 컴퓨터의 실수(`float`, `double`)는 **2의 거듭제곱의 합**으로만 값을 표현한다 — $1.1_2 = 1 + 1/2$, $1.01_2 = 1 + 1/4$처럼, 소수점 아래 각 자리가 $2^{-1}, 2^{-2}, 2^{-3}, \ldots$의 계수다.

`0.1`은 십진분수로 $1/10$이다. $10 = 2 \times 5$이고 $5$가 2의 거듭제곱이 아니므로, $1/10$을 이진 소수로 적으면 `0.0001100110011...`처럼 `0011`이 무한히 반복된다. 유한한 비트(`double`은 가수부 52비트)로는 이 무한 반복을 어느 자리에서 자를 수밖에 없고, **잘린 값은 `0.1`과 정확히 같지 않다.** 컴퓨터에 저장된 `0.1`은 이미 `0.1`이 아니라 그것과 가장 가까운 이진 소수다.

$0.5 = 1/2$, $0.25 = 1/4$처럼 분모가 2의 거듭제곱인 값은 예외적으로 정확히 담긴다. `0.1`, `0.2`, `0.3`은 전부 담기지 않는다. `0.1 + 0.2`를 계산하면 "이미 근사된 0.1"과 "이미 근사된 0.2"를 더한 값이 나오고, 그 결과를 반올림한 값이 "이미 근사된 0.3"과 우연히 같아야 할 이유가 없다. **`0.1 + 0.2 != 0.3`은 버그가 아니라 이진 부동소수점의 정의 그 자체다.**

### 2.2 오차는 연산마다 쌓인다

근사 오차 하나는 작다 — `double`은 유효숫자가 십진수로 약 15~17자리다. 문제는 **연산을 반복할 때마다 그 작은 오차가 다음 연산의 입력에 그대로 실려 들어간다**는 데 있다. `0.1`을 열 번 더하면 매 덧셈마다 반올림이 한 번씩 더 끼고, 그 결과가 `1.0`에서 미세하게 벗어난다. 시뮬레이션이 수만 스텝을 도는 실시간 제어 루프라면, 이 미세한 오차가 스텝마다 누적되어 무시할 수 없는 크기로 자란다.

**크기가 커지면 오차도 커진다.** `double`의 유효숫자가 약 15~17자리라는 것은 절대적인 소수점 자릿수가 아니라 **유효숫자** 개수라는 뜻이다. 값이 $10^{16}$ 근처면 표현 가능한 가장 작은 차이(ULP, unit in the last place)가 이미 `2` 정도로 벌어진다 — 그 크기에서는 `1`을 더해도 반올림되어 사라진다. 절대 오차 기준을 하나 정해 모든 크기의 값에 똑같이 적용할 수 없는 이유가 여기서 나온다.

### 2.3 EPS를 어떻게 정하는가

`==` 대신 **"충분히 가까우면 같다고 본다"**는 판정을 쓴다. 여기서 EPS(epsilon, 허용 오차)를 어떻게 잡느냐가 갈린다.

**절대오차** $|a - b| < \varepsilon$은 단순하지만 크기에 둔감하다. $\varepsilon = 10^{-9}$로 고정하면, 값이 `1` 근처일 때는 적당하지만 값이 $10^{16}$ 근처일 때는 그 오차 범위 안에 있는 서로 다른 값이 사실상 없다시피 해서(2.1에서 본 ULP가 이미 $10^{-9}$보다 크므로) 기준이 무의미해진다. 반대로 값이 $10^{-15}$처럼 아주 작을 때는 $10^{-9}$가 오히려 너무 커서, 진짜 다른 값도 같다고 오판한다.

**상대오차** $\dfrac{|a-b|}{\max(|a|,|b|)} < \varepsilon$은 크기에 비례해서 허용 범위가 늘어나므로 이 문제를 피한다. 다만 $a, b$가 둘 다 `0`에 가까우면 분모가 `0`에 가까워져 오차가 폭발적으로 커 보이는 역효과가 있다.

실무에서는 **둘을 같이 쓴다.** "절대오차 기준을 통과하거나, 상대오차 기준을 통과하면 같다고 본다." 값이 `0` 근처일 때는 절대오차가 안전망 역할을 하고, 값이 클 때는 상대오차가 기준을 자동으로 늘려 준다.

### 2.4 정수로 우회할 수 있으면 그것이 최선이다

EPS 비교는 **어쩔 수 없을 때 쓰는 차선책**이다. [X-5](#/x-5)의 CCW가 좌표를 정수로 유지해서 `cross > 0`, `cross == 0`을 오차 없이 정수로 판정했던 것을 떠올려 보라. 그 판정에는 EPS가 필요 없었다 — 애초에 근사가 끼어들 자리가 없었기 때문이다.

입력이 정수 좌표거나, 정수로 변환해도 문제가 요구하는 정밀도를 잃지 않는다면(예: 좌표가 소수점 둘째 자리까지만 의미 있다면 `100`을 곱해 정수로 바꾼다), **그 변환을 먼저 하는 것이 EPS를 튜닝하는 것보다 항상 안전하다.** EPS는 "이 문제에서 이 정도 오차는 같다고 봐도 되는가"라는 판단을 코드 밖에서 사람이 매번 해야 하고, 그 판단이 틀리면 조용히 틀린 답을 낸다. 정수 비교는 그 판단 자체가 필요 없다.

| 6 | 0.59999999999999998 | 예 — `0.6`보다 **작은** 근사 |

스텝 3에서 이미 `0.3`과 다른 값이 저장된다. 이 오차는 이후 계속 실려 다니다가, 스텝 6부터는 `0.6`보다 작은 값으로 굳어진다(스텝 6~9의 끝자리가 전부 `9`로 도배되는 것이 "약간 모자란다"는 뜻이다).

스텝 10의 값 `0.99999999999999989`는 `1.0`과 **다르다.** `while distance != 1.0`은 이 값이 `1.0`이 되기를 기다리는데, 부동소수 덧셈이 만들어내는 값은 정확히 `1.0`을 지나치거나 못 미친 채로 계속 다른 값만 만들어낼 수 있다 — 이 예제에서는 근처까지 왔지만 정확히 맞아떨어지지 않았다. 종료 조건을 `!=`로 짜면 최악의 경우 무한 루프다.
:::

## 4. 구현

### 4.1 오차 관찰

::: dual
```python title="부동소수 오차 관찰"
s = 0.0
for i in range(1, 11):
    s += 0.1
    print(i, f"{s:.17f}")

print(0.1 + 0.2 == 0.3)
```
```cpp title="부동소수 오차 관찰"
#include <cstdio>

int main() {
    double s = 0.0;
    for (int i = 1; i <= 10; i++) {
        s += 0.1;
        printf("%d %.17f\n", i, s);
    }
    printf("%s\n", (0.1 + 0.2 == 0.3) ? "True" : "False");
    return 0;
}
```
:::

```console
1 0.10000000000000001
2 0.20000000000000001
3 0.30000000000000004
4 0.40000000000000002
5 0.50000000000000000
6 0.59999999999999998
7 0.69999999999999996
8 0.79999999999999993
9 0.89999999999999991
10 0.99999999999999989
False
```

**복잡도:** 시간 $O(n)$ — 덧셈을 $n$번 반복한다. 공간 $O(1)$ — 누산 변수 하나.

두 언어의 출력이 소수점 17자리까지 **완전히 같다.** Python의 `float`과 C++의 `double`이 둘 다 IEEE 754 배정밀도(64비트)를 쓰기 때문이다 — 오차의 크기와 발생 지점은 언어가 아니라 **표현 방식 자체**가 결정한다.

### 4.2 EPS 비교 — 절대오차와 상대오차를 함께

::: dual
```python title="EPS 비교 함수"
def almost_equal(a, b, rel_tol=1e-9, abs_tol=1e-12):
    diff = abs(a - b)
    return diff <= max(rel_tol * max(abs(a), abs(b)), abs_tol)


print(0.1 + 0.2 == 0.3)
print(almost_equal(0.1 + 0.2, 0.3))

big_a, big_b = 1e16, 1e16 + 1
print(big_a == big_b)
print(almost_equal(big_a, big_b))
```
```cpp title="EPS 비교 함수"
#include <cstdio>
#include <cmath>
#include <algorithm>
using namespace std;

bool almost_equal(double a, double b, double rel_tol = 1e-9, double abs_tol = 1e-12) {
    double diff = fabs(a - b);
    return diff <= max(rel_tol * max(fabs(a), fabs(b)), abs_tol);
}

int main() {
    printf("%s\n", (0.1 + 0.2 == 0.3) ? "True" : "False");
    printf("%s\n", almost_equal(0.1 + 0.2, 0.3) ? "True" : "False");

    double big_a = 1e16, big_b = 1e16 + 1;
    printf("%s\n", (big_a == big_b) ? "True" : "False");
    printf("%s\n", almost_equal(big_a, big_b) ? "True" : "False");
    return 0;
}
```
:::

```console
False
True
True
True
```

`big_a == big_b`가 `True`인 것은 `almost_equal`이 관대해서가 아니다. **`1e16 + 1`을 계산하는 순간 그 덧셈 자체가 반올림되어 `1e16`과 똑같은 비트로 저장됐다** — §2.2에서 짚은 ULP가 이 크기에서 이미 `2`에 가깝기 때문이다. `almost_equal`을 쓰든 안 쓰든 이 두 값은 이미 같은 값으로 저장되어 있다. **비교 함수는 저장된 값이 다를 때만 관용을 베풀 수 있다 — 저장 자체가 정보를 지운 경우는 비교로 되돌릴 수 없다.**

**복잡도:** 시간 $O(1)$, 공간 $O(1)$ — 뺄셈·나눗셈·비교 몇 번뿐이다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 표준 라이브러리 지원 | `math.isclose(a, b, rel_tol=1e-9, abs_tol=0.0)`가 같은 절대·상대오차 조합을 표준으로 제공한다 | 표준 라이브러리에 대응 함수가 없다. 위 `almost_equal`처럼 직접 짜거나 프로젝트마다 관용적인 EPS 비교 함수를 둔다 |

📖 `math.isclose(a, b, *, rel_tol=1e-9, abs_tol=0.0)` — 상대오차와 절대오차를 함께 검사해 두 실수가 "충분히 가깝다"고 판정한다. $O(1)$.
   기본값 `abs_tol=0.0`은 **`0`과의 비교에는 상대오차만으로 항상 실패한다**는 뜻이다(분모가 `0`이라 상대오차 자체가 정의되지 않는다). `0` 근처 값을 비교해야 하면 `abs_tol`을 반드시 지정해야 한다.
   쓰는 곳: 반복문 종료 조건, 두 계산 결과의 일치 확인, [VII-4 실수 이분 탐색과 종료 조건](#/vii-4)의 구간 폭 판정.
   C++ 대응: 없음. 위 `almost_equal`을 직접 두거나 프로젝트 공통 유틸리티에 넣는다.

::: pitfall
- **EPS 하나를 정해 모든 크기의 값에 그대로 쓴다.** §2.3에서 본 대로 절대오차만 쓰면 큰 값에서는 기준이 무의미해지고 작은 값에서는 기준이 너무 크다. 값의 크기 범위가 넓은 문제에서는 절대·상대오차를 함께 검사한다.
- **`0`과의 비교에 상대오차만 쓴다.** 분모가 `0`에 가까워지며 상대오차가 정의를 잃는다. `abs_tol`을 같이 둬서 `0` 근처를 절대오차로 받친다.
- **좌표가 정수로 들어오는데도 습관적으로 EPS 비교부터 쓴다.** [X-5](#/x-5), [X-6](#/x-6)처럼 정수로 남겨 둘 수 있는 계산까지 실수로 바꾼 뒤 EPS로 비교하면, 없어도 될 오차를 스스로 만드는 것이다. 정수 우회가 가능한지부터 확인한다.
:::

## 5. 어디에 쓰이는가

**금융 계산은 통화의 최소 단위(센트, 원)를 정수로 다뤄 이 문제 자체를 피한다.** 결제 시스템이 금액을 `float`로 들고 있으면 `0.1 + 0.2`류의 오차가 누적되어 장부의 합계가 실제 거래 합과 미세하게 어긋나는 사고로 이어질 수 있다. 금액을 "원 단위 정수" 또는 "센트 단위 정수"로 저장하고 화면에 표시할 때만 소수점을 붙이면, 사칙연산 전체가 정수 연산이 되어 반올림 오차가 원천적으로 사라진다.

**게임 엔진은 물리 연산이 만든 실수 좌표를 주기적으로 격자에 스냅한다.** 캐릭터나 오브젝트의 위치를 매 프레임 부동소수 물리 계산으로 갱신하면 미세한 오차가 계속 쌓이고, 오래 실행될수록 원래는 정렬돼 있어야 할 오브젝트들이 눈에 띄게 어긋난다. 일정 주기로 좌표를 가장 가까운 격자 값으로 반올림(스냅)해서 오차가 무한정 누적되는 것을 막는다.

## 요약

- 이진 부동소수점은 2의 거듭제곱의 합으로만 값을 표현한다. `0.1`처럼 분모가 2의 거듭제곱이 아닌 십진 소수는 유한 비트로 정확히 담을 수 없어 근사값으로 저장된다.
- `0.1 + 0.2 != 0.3`은 버그가 아니라 이 표현 방식의 정의 그 자체다 — 계산 경로가 다르면 반올림되는 지점이 달라 다른 비트가 저장된다.
- 오차는 연산을 반복할 때마다 누적된다. 값의 크기가 커지면 표현 가능한 최소 간격(ULP)도 커져, 절대오차 기준 하나로는 모든 크기를 감당할 수 없다.
- EPS 비교는 절대오차와 상대오차를 함께 쓴다 — 절대오차는 `0` 근처를 받치고, 상대오차는 큰 값에서 기준을 자동으로 늘린다.
- Python `math.isclose`가 이 조합을 표준으로 제공한다. C++은 표준에 없어 직접 짠다.
- **정수로 우회할 수 있으면 EPS 비교보다 그것이 항상 우선이다.** [X-5](#/x-5)와 [X-6](#/x-6)이 좌표를 정수로 유지해 CCW를 정수 부호 비교로 끝낸 것이 이 원칙의 실천이었다.
- 금융 계산은 통화의 최소 단위를 정수로 다뤄, 게임 엔진은 좌표를 주기적으로 격자에 스냅해 오차 누적을 원천적으로 막는다.
