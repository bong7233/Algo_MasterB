# 0-11 손추적(dry run) 방법론

::: lead
코드를 실행하지 않고, 종이 위에서 그 코드가 무엇을 하는지 정확히 아는 방법.
:::

## 1. 문제

이분 탐색은 열 줄이다. 읽으면 전부 이해된다. 그런데 직접 짜면 셋 중 하나가 일어난다. 답이 하나 어긋나거나, 배열 범위를 벗어나거나, 프로그램이 끝나지 않는다. 채점기가 돌려주는 것은 `틀렸습니다` 한 줄뿐이다.

흔한 대응은 조금 고쳐서 다시 제출하는 것이다. `<`를 `<=`로, `mid`를 `mid+1`로, `hi`를 `n-1`로 바꿔 본다. 네 군데를 각각 두 가지로 바꾸면 조합이 열여섯 개다. 하나가 우연히 통과해도 그것은 통과했을 뿐 이해된 것이 아니다.

디버거를 붙이면 되지 않느냐는 반문이 나온다. 붙일 수 없는 자리가 셋 있다.

- **면접과 화이트보드.** 실행 환경이 없다. 종이 위에서 코드가 옳다는 것을 설명해야 한다.
- **실시간·동시성 코드.** 브레이크포인트는 타이밍을 바꾼다. 멈춰 세우는 순간 재현되던 경합 조건이 사라진다. 이 현상은 [XI-3 락과 락프리](#/xi-3)에서 다시 다룬다.
- **재현되지 않는 입력.** 10만 개 중 하나에서만 깨진다면, 그 하나를 찾기 전까지 디버거는 붙일 자리가 없다.

더 근본적인 이유가 있다. ==디버거는 코드가 무엇을 하는지 보여주지만, 무엇을 해야 하는지는 보여주지 않는다.== 화면의 `lo = 3`이 옳은지 틀린지는 결국 사람이 판단한다. 그 판단의 근거를 만드는 것이 손추적이다.

"읽으면 이해되는데 못 짠다"는 상태의 정체도 여기 있다. 읽을 때는 **코드가 상태를 대신 들고 있다.** 짤 때는 그 상태를 전부 머리가 들어야 한다. 읽기는 실행 모델 없이도 되지만 쓰기는 안 된다. 손추적은 그 모델을 종이에 외부화해 훈련하는 절차다.

비용은 싸다. 이분 탐색은 원소가 100만 개여도 20스텝, 여섯 개면 세 스텝이다. **표 세 줄이 열여섯 번의 제출을 대체한다.**

## 2. 아이디어

손추적은 상태 표를 그리는 일이고, 표를 그린다는 것은 세 가지를 결정한다는 뜻이다. 무엇을 열로 둘지, 언제 한 줄을 찍을지, 언제 멈출지.

### 2.1 무엇을 관찰할 것인가

변수를 전부 열로 만들면 표가 죽는다. 열이 열두 개면 채우다 지치고, 채워도 무엇이 이상한지 안 보인다. 남길 것은 세 부류뿐이다.

**첫째, 경계 변수.** **불변식**이 걸려 있는 변수다. 불변식은 특정 지점에서 항상 참이어야 하는 명제다. 반열림 이분 탐색이라면 "답은 항상 `[lo, hi)` 안에 있다"가 불변식이고 `lo`와 `hi`가 경계 변수다. BFS라면 "큐 안의 정점들은 거리 순으로 정렬되어 있다"가 불변식이고 큐가 경계다.

**둘째, 측도.** 매 반복 반드시 줄어드는 음이 아닌 정수량이다. 이분 탐색에서는 폭 `hi - lo`가 측도다. 0 밑으로 못 내려가는데 매번 줄어드니 무한히 돌 수 없다. 반대로 **측도가 줄지 않는 반복이 한 번이라도 있으면 무한 루프에 빠질 수 있다.**

**셋째, 판정에 쓰인 파생값.** `mid`, `a[mid]`, 비교 결과다. 없으면 왜 그쪽으로 갔는지 재구성할 수 없다.

**불변식이 정확성을 맡고 측도가 종료를 맡는다.** 알고리즘이 옳다는 말은 이 둘이 모두 성립한다는 뜻이고, 손추적 표는 그것을 한 화면에서 확인하는 장치다.

::: note
열을 고르는 일이 손추적의 절반이다. ==열을 못 고르겠다면 그 알고리즘을 아직 이해하지 못한 것이다.== 실패가 아니라 신호다. 코드를 더 들여다볼 것이 아니라 "이 루프가 매 바퀴 지켜야 하는 명제"를 한 문장으로 먼저 적으라는 뜻이다.
:::

### 2.2 언제 한 줄을 찍을 것인가

스냅샷 지점은 **루프 머리 한 곳으로 고정한다.** 불변식은 루프 머리에서 참인 명제이지 중간에서 참인 명제가 아니다. `lo`는 갱신했는데 `hi`는 아직인 시점을 적으면 그 줄은 어떤 불변식도 만족하지 않는 유령 상태가 된다. 표가 거짓말을 시작하는 지점이 대개 여기다.

재귀 함수라면 찍는 자리는 **함수 진입 직후**이고, 열에는 인자와 깊이를 둔다. 반환값은 별도 열로 두고 되돌아올 때 채운다. [III-1 재귀 사고법](#/iii-1)에서 호출 트리로 확장된다.

### 2.3 언제 멈출 것인가

세 줄만 채우고 덮는 습관은 손추적의 효과를 거의 다 버린다. **끝까지 간다.** 측도가 0이 되고 루프 조건이 거짓이 되는 줄까지다.

오프바이원은 거의 항상 마지막 한 줄에서 드러난다. 중간 스텝은 웬만한 구현이 다 통과한다. `lo`와 `hi`가 붙는 순간에 한쪽이 하나 어긋나거나 조건이 `<=`여서 한 바퀴를 더 도는 것이 그 자리에서 나온다. 표의 마지막 줄은 곧 반환값의 의미를 적는 줄이다.

### 2.4 표의 모양

```text nolines
  step | lo | hi | width | mid | a[mid] | branch
  -----+----+----+-------+-----+--------+-----------
     0 |  0 |  6 |     6 |   3 |      5 | hi = mid
     1 |  0 |  3 |     3 |   1 |      3 | lo = mid+1
     2 |    |    |       |     |        |
          ^            ^                    ^
          |            |                    +-- 갱신: 어느 쪽 절반을 버렸는가
          |            +----------------------- 측도: 반드시 단조 감소한다
          +------------------------------------ 경계: 불변식이 걸려 있는 변수
```

왼쪽 세 덩어리가 전부다. 경계가 불변식을 지키는지, 측도가 줄어드는지, 갱신 규칙이 방금 검사한 원소를 제대로 처리했는지 본다. 세 번째가 오프바이원을 잡는다. **`mid`를 검사했으면 반드시 어느 한쪽에서 사라져야 한다.** 양쪽 다 남기면 구간이 줄지 않고, 다 버리면 답을 건너뛴다.

### 2.5 어떤 입력으로 추적할 것인가

크기는 **답이 나오는 최소 크기의 두 배** 정도가 좋다. 원소 여섯 개면 세 스텝을 돌아 갈림길이 양쪽 다 나온다. 세 개면 한쪽 분기만 밟고 끝나 반쪽만 검증된다.

값의 배치는 셋을 돌린다.

1. **답이 중간에 있는 입력.** 정상 경로.
2. **답이 맨 끝에 있는 입력.** 오른쪽 경계가 닫힘인지 열림인지가 여기서 갈린다.
3. **답이 없는 입력.** 루프가 빈 구간에서 어떻게 끝나고 무엇을 돌려주는지가 여기서 정해진다.

중복 원소를 하나 섞는 것도 값싸다. `a = [1, 3, 3, 5, 7, 9]`에서 `3`이 둘인 이유가 그것이다. "첫 위치"와 "마지막 다음 위치"를 구분하는 구현인지가 여기서만 드러난다.

### 2.6 손추적이 잡지 못하는 것

::: widget complexity-plot {"n":1000000,"curves":["n","n log n","n^2","2^n"],"budget":100000000}
:::

위젯은 N이 커질 때 $O(n)$, $O(n \log n)$, $O(n^2)$, $O(2^n)$이 로그 축에서 얼마나 벌어지는지와 "1초 안에 되는 선"이 어디를 지나는지를 보인다. 슬라이더를 밀면 $O(n^2)$이 그 선을 넘는 지점이 나오고, $O(2^n)$은 훨씬 왼쪽에서 넘어가 있다.

이 그림이 여기 있는 이유는 **손추적의 한계를 긋기 위해서다.** 손추적은 정확성 도구이지 성능 도구가 아니다. 원소 여섯 개를 따라가서는 100만 개에서 시간 초과인지 알 수 없다. 성능은 [0-9 N 범위로 알고리즘 역산하기](#/0-9)의 절차로 판단한다.

::: tip
순서가 있다. **역산이 먼저, 손추적이 나중이다.** 역산으로 후보를 정하고 그 구현을 손으로 따라간다. 뒤집으면 시간 초과가 확정된 코드를 정성껏 검증하는 일이 생긴다.
:::

::: hist
손추적은 새 기법이 아니다. 한 번의 실행에 대기 시간이 길던 시절에는 기계에 넣기 전 종이로 검증하는 것이 표준 절차였고, 그 이름이 desk checking이다. 기계가 싸지면서 "일단 돌려 보고 고친다"가 자리를 대신했다.

그 시절의 명제 하나는 지금도 유효하다. Dijkstra는 1970년의 노트에서 테스트가 버그의 존재를 보일 수는 있어도 부재를 보일 수는 없다고 적었다. 실행은 넣어 본 입력에 대해서만 말하고, 불변식과 측도는 넣어 보지 않은 입력에 대해서도 말한다.
:::

## 3. 손으로 따라가기

::: trace
입력: `a = [1, 3, 3, 5, 7, 9]`, `x = 5`. 구할 것은 `a[i] >= 5`를 만족하는 **가장 왼쪽 인덱스** `i`.

불변식: 답은 항상 반열림 구간 `[lo, hi)` 안에 있다. 시작은 `lo = 0`, `hi = 6`, 루프 조건은 `lo < hi`.
갱신 규칙: `mid = lo + (hi - lo) // 2`. `a[mid] >= 5`이면 `hi = mid`, 아니면 `lo = mid + 1`.

| 스텝 | lo | hi | width | mid | a[mid] | a[mid] >= 5 | 갱신 |
|---|---|---|---|---|---|---|---|
| 0 | 0 | 6 | 6 | 3 | 5 | 예 | hi = 3 |
| 1 | 0 | 3 | 3 | 1 | 3 | 아니오 | lo = 2 |
| 2 |  |  |  |  |  |  |  |
| 3 |  |  |  |  |  |  |  |

세 가지를 확인하라.

- [ ] `width` 열이 매 스텝 **실제로** 줄어드는가
- [ ] 루프가 멈추는 순간 `lo`와 `hi`는 얼마인가
- [ ] 그때의 `lo`가 정말 답인가. 불변식이 폭 0인 구간에서 무엇을 뜻하는가
:::

::: answer
| 스텝 | lo | hi | width | mid | a[mid] | a[mid] >= 5 | 갱신 |
|---|---|---|---|---|---|---|---|
| 0 | 0 | 6 | 6 | 3 | 5 | 예 | hi = 3 |
| 1 | 0 | 3 | 3 | 1 | 3 | 아니오 | lo = 2 |
| 2 | 2 | 3 | 1 | 2 | 3 | 아니오 | lo = 3 |
| 3 | 3 | 3 | 0 | — | — | — | `lo < hi`가 거짓, 종료 |

답은 `lo = 3`이고 `a[3] = 5`가 맞다.

`width` 열이 `6 → 3 → 1 → 0`으로 매 스텝 엄격히 줄었다. 이것이 이 루프가 반드시 끝난다는 증거다.

마지막 질문의 핵심은 폭 0인 구간에서 불변식이 무엇을 뜻하느냐다. `[3, 3)`은 빈 구간이다. "답이 이 안에 있다"가 참이려면 답은 그 **왼쪽 끝 위치**, 즉 `lo`여야 한다. 반열림으로 짜면 `lo`와 `hi`가 만나는 지점이 곧 답이라 보정할 것이 없다. 닫힌 구간이면 `lo`인지 `lo+1`인지를 매번 다시 생각해야 한다. ==구간 표기를 반열림으로 통일하는 것이 오프바이원에 대한 가장 값싼 방어다.==

**이제 규칙 하나만 바꿔 같은 표를 다시 채워 보라.** `lo = mid + 1` 대신 `lo = mid`로 두면:

| 스텝 | lo | hi | width | mid | a[mid] | a[mid] >= 5 | 갱신 |
|---|---|---|---|---|---|---|---|
| 0 | 0 | 6 | 6 | 3 | 5 | 예 | hi = 3 |
| 1 | 0 | 3 | 3 | 1 | 3 | 아니오 | lo = 1 |
| 2 | 1 | 3 | 2 | 2 | 3 | 아니오 | lo = 2 |
| 3 | 2 | 3 | 1 | 2 | 3 | 아니오 | lo = 2 |
| 4 | 2 | 3 | 1 | 2 | 3 | 아니오 | lo = 2 |

스텝 3에서 `width`가 1로 멈춘다. `mid`가 `lo`와 같아지는 순간 `lo = mid`는 아무것도 바꾸지 않고, 표는 같은 줄을 영원히 반복한다. **무한 루프가 실행 없이 표 다섯 줄에서 잡혔다.** 이것이 측도를 열로 두는 이유다.
:::

## 4. 구현

손추적 표를 그대로 코드로 옮기면 추적 로그가 된다. 열 이름이 곧 출력 필드이고 출력 지점이 곧 루프 머리다. 표를 먼저 그렸다면 무엇을 찍을지 고민할 일이 없다.

::: dual
```python title="lower_bound — 손추적 표를 코드가 대신 찍게 하기"
def lower_bound(a, x):
    lo, hi = 0, len(a)          # 불변식: 답은 항상 [lo, hi) 안에 있다
    step = 0
    while lo < hi:              # 측도: hi - lo 가 매 반복 반드시 줄어든다
        mid = lo + (hi - lo) // 2
        print(f"step={step} lo={lo} hi={hi} width={hi - lo} mid={mid} a[mid]={a[mid]}")
        if a[mid] >= x:
            hi = mid            # mid 는 조건을 만족하므로 후보로 남긴다
        else:
            lo = mid + 1        # mid 는 조건을 만족하지 못하므로 버린다
        step += 1
    print(f"done lo={lo} hi={hi} width={hi - lo}")
    return lo


a = [1, 3, 3, 5, 7, 9]
ans = lower_bound(a, 5)
print("answer =", ans)
```
```cpp title="lower_bound — 손추적 표를 코드가 대신 찍게 하기"
#include <iostream>
#include <vector>
using namespace std;

int lower_bound(const vector<int>& a, int x) {
    int lo = 0, hi = (int)a.size();   // 불변식: 답은 항상 [lo, hi) 안에 있다
    int step = 0;
    while (lo < hi) {                 // 측도: hi - lo 가 매 반복 반드시 줄어든다
        int mid = lo + (hi - lo) / 2;
        cout << "step=" << step << " lo=" << lo << " hi=" << hi
             << " width=" << hi - lo << " mid=" << mid << " a[mid]=" << a[mid] << "\n";
        if (a[mid] >= x)
            hi = mid;                 // mid 는 조건을 만족하므로 후보로 남긴다
        else
            lo = mid + 1;             // mid 는 조건을 만족하지 못하므로 버린다
        step += 1;
    }
    cout << "done lo=" << lo << " hi=" << hi << " width=" << hi - lo << "\n";
    return lo;
}

int main() {
    vector<int> a = {1, 3, 3, 5, 7, 9};
    int ans = lower_bound(a, 5);
    cout << "answer = " << ans << "\n";
    return 0;
}
```
:::

두 구현의 출력은 한 글자도 다르지 않다.

```console
step=0 lo=0 hi=6 width=6 mid=3 a[mid]=5
step=1 lo=0 hi=3 width=3 mid=1 a[mid]=3
step=2 lo=2 hi=3 width=1 mid=2 a[mid]=3
done lo=3 hi=3 width=0
answer = 3
```

**복잡도:** 시간 $O(\log n)$ — 매 반복 폭 `hi - lo`가 절반 이하로 줄고 폭이 0이면 끝나므로, 반복 횟수는 폭을 1까지 반으로 접는 횟수인 $\log_2 n$을 넘지 않는다. 공간 $O(1)$ — 재귀 없이 정수 변수 네 개만 쓴다.

상수도 말해 둔다. $O(\log n)$은 $n = 10^6$에서 20회지만 **각 스텝이 배열의 전혀 다른 곳을 찌른다.** 위치가 매번 절반씩 뛰어 캐시 라인이 재사용되지 않으므로 초반 스텝은 사실상 매번 캐시 미스다. 같은 20회라도 연속 접근 20회와 비용이 다르다. 이 차이는 [0-6 C++ 컨테이너 세트](#/0-6)에서 다룬다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 정수 나눗셈 | `//`는 항상 내림. 음수에서 `-1 // 2 == -1` | `/`는 0 방향 절삭. `-1 / 2 == 0` |
| `(lo + hi)` 오버플로 | 임의 정밀도라 발생하지 않는다 | `int` 범위를 넘을 수 있다. `lo + (hi - lo) / 2`로 쓰는 이유 |
| 배열 길이 타입 | `len(a)`는 `int` | `a.size()`는 부호 없는 `size_t`. 부호 있는 값과 섞으면 비교가 뒤집힌다 |
| 표준 대응 | `bisect.bisect_left(a, x)` | `std::lower_bound(a.begin(), a.end(), x)` |

::: danger
`mid = (lo + hi) / 2`는 C++에서 실제 장애를 만드는 코드다. `lo`와 `hi`가 20억 근처면 합이 `int` 범위를 넘어 음수가 되고, 음수 인덱스로 배열을 읽는다. 정의되지 않은 동작이라 크래시할 수도, 조용히 쓰레기 값을 읽을 수도 있다.

`mid = lo + (hi - lo) / 2`로 쓰면 뺄셈이 먼저라 중간값이 커지지 않는다. **Python에서는 두 표기가 동등하지만 같은 습관을 양쪽에 들여 두는 편이 안전하다.** 언어를 오갈 때 무너지는 것은 지식이 아니라 습관이다. 오버플로는 [0-5 C++ 입출력과 기본 타입](#/0-5)에 있다.
:::

::: warn
추적 출력은 **디버깅용이지 제출용이 아니다.** 채점기는 표준 출력을 정답과 비교하므로 로그 한 줄이 섞이면 알고리즘이 맞아도 오답이다. 지우는 것을 잊는 사고가 잦다면 `sys.stderr` / `cerr`로 보내라. 표준 에러는 채점 대상이 아니다.
:::

::: perf
추적 출력을 켠 채로 큰 입력을 돌리는 것은 방법이 아니다. 정렬된 배열 $n = 10^6$에 질의 10만 번이면 한 질의가 약 20스텝이라 로그가 약 200만 줄이다. 전부 `/dev/null`로 버렸는데도 이렇다.

| | 추적 없이 | 추적 출력 | 배수 |
|---|---|---|---|
| Python 3.13 | 0.45초 | 1.47초 | 3.3배 |
| C++17 `-O2` | 0.018초 | 0.65초 | 36배 |

> (Linux x86-64 / CPython 3.13 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 측정 스크립트는 `tools/bench/dry_run_trace_cost.py` 와 `.cpp` 다.)

C++ 쪽 배수가 큰 것이 핵심이다. 계산이 이미 0.018초로 끝나므로 계측 코드가 전체를 지배한다. **알고리즘이 빠를수록 로그가 프로그램이 된다.** 손추적이 입력을 여섯 개로 줄이는 데서 시작하는 이유가 이것이다.
:::

버그가 있는 쪽도 같은 형식으로 남긴다. 앞 절의 정답 상자에서 무한 루프를 만든 변형이다.

```python title="무한 루프에 빠지는 버전 (조각)" {2,4-5}
while lo < hi:
    mid = lo + (hi - lo) // 2
    if a[mid] >= x:
        hi = mid       # ✅ mid 는 조건을 만족하므로 후보로 남긴다
    else: lo = mid     # ❌ mid 는 조건을 만족하지 않는데도 버리지 않았다
```

정수 나눗셈이 내림이라 `mid`는 폭이 1일 때 항상 `lo`와 같아지고, 그 순간 `lo = mid`는 아무 일도 하지 않는다. **이 버그는 폭이 1이 되기 전까지 드러나지 않는다.** 표를 끝까지 채우라는 §2.3이 겨냥하는 것이 이 종류다.

무한 루프를 <kbd>Ctrl</kbd>+<kbd>C</kbd>로 끊었을 때 마지막 로그가 같은 값을 반복하고 있다면, 원인은 거의 항상 측도가 줄지 않는 갱신 규칙이다.

::: pitfall
- **`mid`를 양쪽 다 남긴다.** `hi = mid`와 `lo = mid`를 함께 쓰면 폭 1에서 멈춘다.
- **구간 표기를 섞는다.** `hi = len(a)`로 시작해 놓고 `while lo <= hi`를 쓰면 첫 반복부터 `a[len(a)]`를 읽는다. 반열림이면 `<`, 닫힌 구간이면 `hi = len(a) - 1`에 `<=`다. 표기는 하나로 통일한다.
- **끝난 뒤의 값을 확인하지 않는다.** `x`가 모든 원소보다 크면 `lo == len(a)`가 되고 그대로 `a[lo]`를 읽으면 터진다. 반환값을 쓰기 전에 범위 검사를 넣어라.
- **관찰 대상을 잘못 고른다.** `width`를 빼면 무한 루프가 표에서 보이지 않는다. 측도 열은 선택이 아니다.
- **중간 상태를 표에 적는다.** `lo`만 갱신하고 `hi`는 아직인 시점을 남기면 그 줄은 어떤 불변식도 만족하지 않는다. 찍는 자리는 루프 머리 하나다.
:::

::: deep
이 형식은 즉흥적인 요령이 아니라 프로그램 검증의 표준 도구를 축소한 것이다. Hoare가 1969년에 제시한 논리에서 루프의 정확성은 사전조건, 불변식, 사후조건으로 서술된다. 루프 조건이 거짓이 된 시점에 성립하는 "불변식 ∧ ¬루프조건"이 곧 사후조건이어야 한다.

이분 탐색에 대입하면 불변식은 "답은 `[lo, hi)` 안에 있다", 루프 조건의 부정은 `lo == hi`다. 둘을 결합하면 "답은 폭 0인 구간의 위치, 즉 `lo`"가 나온다. **`lo`를 돌려주면 된다는 결론이 코드를 보지 않고 논리만으로 나온다.** 종료는 측도가 담당한다.

실전에서 값어치를 하는 것은 증명이 아니라 **문서화**다. 루프 위에 불변식 한 줄을 주석으로 적어 두면 반년 뒤 고치는 사람이 무엇을 깨면 안 되는지 안다.
:::

## 5. 어디에 쓰이는가

**코드 리뷰가 손추적이다.** 리뷰어가 루프 앞에서 멈춰 "`i`가 `n-1`까지 가나 `n`까지 가나"를 묻는 것은 머릿속에서 표를 두어 줄 채우는 일이다. 코멘트가 "이상한 것 같은데요"에서 "`n=1`이면 이 루프는 한 번도 안 돕니다"로 바뀌는 순간, 표의 마지막 줄을 실제로 채워 봤다는 뜻이다.

**로그 필드 설계가 관찰 대상 선택과 같은 문제다.** 운영 중인 시스템에서 무엇을 로그로 남길지 정하는 일은 어떤 변수를 열로 둘지 정하는 일과 같다. 전부 찍으면 디스크가 차고 정작 필요한 줄을 못 찾는다. 남길 것은 불변식이 깨졌는지 판정할 수 있는 최소 필드다. 큐 길이, 처리 지연, 재시도 횟수가 그 자리에 온다. [XI-7 이벤트 루프와 백프레셔](#/xi-7)에서 다시 쓰인다.

**단위 테스트의 케이스 표가 손추적의 마지막 줄이다.** §2.5에서 고른 세 입력은 그대로 테스트 케이스 세 개가 된다. 확인한 것을 테스트로 고정하면 같은 확인을 다시 손으로 하지 않아도 된다. 제어 주기가 1밀리초인 루프처럼 브레이크포인트 자체가 동작을 바꾸는 코드에는 이 경로 말고 대안이 없다.

## 6. 이 유형을 알아보는 법

손추적이 필요한 코드에는 표식이 있다.

::: classify
- 신호어: "정확히 K번", "이상/이하", "포함한다/포함하지 않는다", "가장 왼쪽의", "처음으로 ~가 되는 시점"
- 제약조건: 구간이 반열림인지 닫힘인지 지문이 명시하지 않을 때. 인덱스가 1부터 시작하는 입력. 원소가 1개일 수 있는 입력. 답이 없을 수 있는 입력
- 혼동 주의: 경계가 흔들리는 것과 알고리즘 선택이 틀린 것은 다른 문제다. 손추적은 앞쪽만 고친다. 유형 자체를 잘못 잡은 경우는 [I-5 오분류 사례집](#/i-5)으로 간다
- 반례 함정: 원소 1개, 답이 맨 끝, 답이 아예 없음. 이 세 입력에서만 깨지는 구현이 대부분이고, 중간 크기 입력만 돌려 보면 전부 통과한다
:::

::: interview
경계가 있는 루프를 화이트보드에 짜게 한 뒤 이어지는 질문은 대개 둘이다.

**"이 루프가 무한 루프에 빠지지 않는 이유를 설명해 보세요."**
답변 뼈대는 측도다. 매 반복 엄격히 줄어드는 음이 아닌 정수량을 지목한다. "구간 폭 `hi - lo`가 매 반복 최소 1 줄고 0 밑으로는 못 갑니다. 따라서 최대 초기 폭만큼만 돌고 끝납니다." "테스트해 봤는데 잘 돌았습니다"는 답이 아니다.

**"이 함수가 옳은 값을 돌려준다는 것을 어떻게 압니까."**
답변 뼈대는 불변식이다. 루프 머리에서 항상 참인 명제를 한 문장으로 말하고, 거기에 루프 조건의 부정을 결합해 무엇이 나오는지 보인다. "답은 항상 `[lo, hi)` 안에 있고, 루프가 끝나면 `lo == hi`이므로 답은 `lo`입니다."

두 답변 모두 코드를 다시 읽지 않고 나온다.
:::

## 연습

::: quiz
전부 경계 조건이 본체인 유형이다. **코드를 짜기 전에 손추적 표부터 그려라.**

**1. 백준 1920 수 찾기 (실버 4)** — https://www.acmicpc.net/problem/1920
- 신호: "존재하는지 알아내시오" + N과 M이 각각 10만. 선형 탐색이면 100억이라 넘는다.
- 상태: 탐색 구간 `[lo, hi)` 하나.
- 자료구조: 정렬된 배열. 순서만 필요하고 삽입·삭제가 없어 트리나 해시를 쓸 이유가 없다.

**2. 백준 10816 숫자 카드 2 (실버 4)** — https://www.acmicpc.net/problem/10816
- 신호: 존재 여부가 아니라 "몇 개인지"를 묻는다. 개수를 세는 것은 경계 두 개의 차다.
- 상태: 같은 값이 놓인 구간의 왼쪽 끝과 오른쪽 끝 다음 위치. `upper_bound - lower_bound`가 답이다.
- 자료구조: 정렬 배열 + 두 종류의 경계 탐색. 해시로도 풀리지만 훈련 가치는 두 경계의 차이를 손으로 확인하는 데 있다.

**3. 백준 2805 나무 자르기 (실버 2)** — https://www.acmicpc.net/problem/2805
- 신호: "절단기에 설정할 수 있는 높이의 최댓값". 답 자체가 수이고 "높이 H면 M 이상인가"라는 판정이 H에 대해 단조롭다.
- 상태: 답의 후보 구간 `[lo, hi)`. 배열 인덱스가 아니라 **답의 값**을 이분 탐색한다.
- 자료구조: 배열과 누적 합계용 정수. 합이 20억을 넘어 C++에서는 `long long`이 필수다. [VII-3 매개변수 탐색](#/vii-3)에서 다룬다.

**4. 손추적 과제.** `a = [2, 4, 4, 4, 8]`, `x = 4`로 위의 `lower_bound`를 끝까지 표로 채워라. 이어서 `a[mid] >= x`를 `a[mid] > x`로만 바꾸고 같은 표를 다시 채워라. 두 표는 어디서 갈라지고, 두 결과의 차는 무엇을 뜻하는가.

::: answer
`a[mid] >= x`인 원본은 `lo = 1`에서 끝난다. `a[1] = 4`가 4 이상인 첫 위치다.

`a[mid] > x`로 바꾸면 `4`들은 조건을 만족하지 못해 `lo = mid + 1`로 전부 버려지고, 루프는 `lo = 4`에서 끝난다. `a[4] = 8`이 4보다 큰 첫 위치다.

두 표는 `mid`가 값 `4`를 가리키는 첫 스텝에서 갈라진다. 원본은 `hi = mid`로 왼쪽을 남기고, 변형은 `lo = mid + 1`로 오른쪽으로 간다.

두 결과의 차 `4 - 1 = 3`이 배열 안 `4`의 개수다. 이것이 곧 `upper_bound - lower_bound`이고 2번 문제의 답이다. **부등호 하나가 "첫 위치"와 "마지막 다음 위치"를 가르고, 두 값의 차가 개수를 준다.** 세 결과가 같은 표에서 나온다는 것이 이 과제의 요점이다.
:::
:::

## 요약

- 손추적은 코드를 실행하지 않고 상태 표를 채워 실행 모델을 검증하는 절차다. "읽으면 이해되는데 못 짠다"는 상태를 겨냥한다.
- 열로 둘 것은 셋뿐이다. 불변식이 걸린 **경계 변수**, 매 반복 줄어드는 **측도**, 판정에 쓰인 **파생값**.
- **불변식이 정확성을 맡고 측도가 종료를 맡는다.** 측도가 줄지 않는 반복이 하나라도 있으면 무한 루프다.
- 스냅샷은 **루프 머리 한 곳**에서만 찍고, 표는 **측도가 0이 되는 줄까지** 채운다. 오프바이원은 마지막 줄에서 드러난다.
- 입력은 답이 중간에 있는 것, 맨 끝에 있는 것, 아예 없는 것 세 가지를 돌린다.
- 구간 표기는 한 함수 안에서 **반열림 `[lo, hi)` 하나로 통일한다.** 폭이 `hi - lo`이고 빈 구간이 `lo == hi` 하나로 표현되는 것이 오프바이원을 줄인다.
- 손추적은 정확성 도구다. 성능은 [0-9 N 범위로 알고리즘 역산하기](#/0-9)의 역산으로 판단하고, 역산을 먼저 한다.
