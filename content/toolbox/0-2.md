# 0-2 Python 입출력과 기본 타입

::: lead
알고리즘이 맞는데 시간 초과가 나는 자리는 대개 입출력이고, 답이 이상한 자리는 대개 리스트 초기화다.
:::

## 1. 문제

정수 100만 개를 읽어 합을 구하는 문제가 있다. 복잡도는 $O(n)$이고, 이보다 나은 방법은 없다. 그런데 다음 코드가 시간 초과로 떨어진다.

```python title="시간 초과가 나는 코드 (조각)"
n = int(input())
total = 0
for _ in range(n):
    total += int(input())
print(total)
```

알고리즘을 아무리 들여다봐도 고칠 곳이 없다. 고칠 곳은 알고리즘이 아니라 `input()`이다. 이 한 줄을 바꾸면 통과한다.

같은 종류의 사고가 하나 더 있다. 3×2 격자를 만들어 한 칸만 바꿨는데 두 줄이 함께 바뀐다.

```python title="답이 이상한 코드 (조각)"
grid = [[0] * 3] * 2
grid[0][0] = 9
print(grid)          # [[9, 0, 0], [9, 0, 0]]  <- 두 행이 같이 바뀌었다
```

둘 다 알고리즘 지식으로는 잡히지 않는다. **언어가 실제로 무엇을 하는지**를 알아야 잡힌다. 이 챕터가 그 자리다.

## 2. 입력이 병목이 되는 지점

### 2.1 얼마나 차이 나는가

정수 100만 줄(약 3.9MB)을 읽어 합을 구하는 데 걸리는 시간이다.

::: perf
| 방식 | 시간 | 배수 |
|---|---|---|
| `input()` | 1.105초 | 기준 |
| `sys.stdin.readline` | 0.289초 | **3.8배 빠름** |
| `sys.stdin.buffer.read().split()` | 0.331초 | 3.3배 빠름 |
| (참고) C++ `cin` 기본값 | 0.186초 | |
| (참고) C++ `cin` + `sync_with_stdio(false)` | 0.062초 | |

> (Linux x86-64 / CPython 3.13 / g++ 13 `-O2` 실측, 3회 실행의 최솟값. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 측정 스크립트는 `tools/bench/py_input_readline.py` 다.)

제한 시간이 1초인 문제에서 1.105초와 0.289초는 통과와 실패다. **알고리즘을 한 글자도 안 고치고 0.8초가 사라진다.**
:::

### 2.2 왜 느린가

"`input()`은 개행을 떼고 `readline`은 안 떼니까 그만큼 느리다"는 설명이 흔하다. 측정하면 틀렸다는 것이 바로 나온다. 읽기만 하고 계산은 빼서 순수 비용만 남긴 것이다.

::: perf
| 하는 일 | 시간 |
|---|---|
| `readline()` 만 | 0.127초 |
| `readline().rstrip()` | 0.172초 |
| `input()` | 0.945초 |

> (같은 환경·같은 스크립트의 `[분해]` 절.)

개행을 떼는 비용은 0.045초다. **전체 차이 0.82초 중 5%밖에 설명하지 못한다.** 나머지 0.77초는 `input()` 자신의 호출 비용이다.
:::

::: deep
`input()`이 하는 일은 한 줄 읽기가 아니다. 호출될 때마다 다음을 한다.

1. **`sys.stdin`과 `sys.stdout`을 이름으로 찾는다.** 사용자가 이 둘을 다른 객체로 갈아 끼웠을 수 있으므로 캐시할 수 없다.
2. **둘이 터미널인지 검사한다.** 터미널이면 대화형 편집(방향키·히스토리)을 지원하는 경로로 가고, 파이프나 파일이면 일반 경로로 간다. 이 판정을 **매 호출** 한다.
3. 프롬프트 인자가 있으면 출력하고 버퍼를 비운다.
4. 한 줄을 읽고, 끝의 개행을 뗀다.
5. 빈 결과면 `EOFError`를 던진다. `readline`은 이때 빈 문자열 `''`을 돌려준다.

`readline`은 이 중 4번만 한다. 그것도 파일 객체의 메서드를 미리 이름으로 붙잡아 두면(`rl = sys.stdin.readline`) 속성 조회조차 반복하지 않는다.

`input()`이 이렇게 설계된 이유는 **대화형 셸을 위한 함수**이기 때문이다. 사람이 한 줄 치고 기다리는 상황에서 매 호출 몇 마이크로초는 아무 의미가 없다. 100만 번 부르는 것은 이 함수의 용도가 아니다.
:::

### 2.3 표준 관용구

::: dual
```python title="빠른 입출력 — n개의 (a, b)를 읽어 a*b의 합"
import sys
input = sys.stdin.readline          # 왜: 이름을 바꿔 두면 기존 코드를 그대로 쓴다

n = int(input())
total = 0
for _ in range(n):
    a, b = map(int, input().split())
    total += a * b
print(total)
```
```cpp title="빠른 입출력 — n개의 (a, b)를 읽어 a*b의 합"
#include <iostream>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);   // 왜: C 표준 입출력과의 동기화를 끊는다
    cin.tie(nullptr);                   // 왜: cin 앞에서 cout 을 자동으로 비우지 않는다

    int n;
    cin >> n;
    long long total = 0;
    for (int i = 0; i < n; i++) {
        long long a, b;
        cin >> a >> b;
        total += a * b;
    }
    cout << total << "\n";
    return 0;
}
```
:::

입력 `3 / 2 3 / 4 5 / 1000000 1000000`에 대해 두 코드 모두 `1000000000026`을 출력한다.

**복잡도:** 시간 $O(n)$ — 줄마다 상수 번의 읽기·분해·변환이므로 줄 수에 비례한다. 공간 $O(1)$ — 한 줄씩 처리하고 버리므로 입력 전체를 들고 있지 않는다. 다만 상수가 크다. 위 실측에서 보듯 같은 $O(n)$ 안에서 방식에 따라 4배가 갈린다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 느린 기본값의 정체 | `input()`의 대화형 처리 | `cin`의 C 입출력 동기화 |
| 해제 방법 | `sys.stdin.readline`으로 교체 | `sync_with_stdio(false)` |
| 부작용 | 개행이 남는다 | `printf`와 `cout`을 섞어 쓰면 순서가 깨진다 |
| 누적 합의 타입 | `int`가 알아서 커진다 | `long long`을 직접 써야 한다 |

::: danger
`input = sys.stdin.readline`은 **내장 함수를 가리는(shadowing) 코드**다. 코딩테스트에서는 표준 관용구이고 안전하지만, 그 이유는 제출 파일이 한 개이고 수명이 5분이기 때문이다.

여러 사람이 고치는 코드에서 같은 일을 하면 `input()`을 부르는 다른 모든 코드의 동작이 조용히 바뀐다. 개행이 남는 것과 EOF에서 예외 대신 `''`이 나오는 것, 둘 다 조용한 변화다. 실무 코드에서는 `readline = sys.stdin.readline`처럼 **다른 이름**을 쓴다.
:::

### 2.4 출력도 같은 병목이다

입력만 고치고 출력을 방치하면 절반만 고친 것이다. 100만 줄을 쓰는 세 가지 방식이다.

::: perf
| 방식 | 시간 | 배수 |
|---|---|---|
| `print(x)`를 100만 번 | 1.438초 | 기준 |
| `sys.stdout.write` | 0.726초 | 2.0배 빠름 |
| `'\n'.join(...)`으로 한 번에 | 0.178초 | **8.1배 빠름** |

> (같은 환경·같은 스크립트. 출력은 `/dev/null`로 버려 디스크 비용을 뺀 순수 계산 비용이다.)
:::

`print()`가 느린 이유는 `input()`과 같은 계열이다. 호출마다 인자를 문자열로 바꾸고, 구분자와 끝 문자를 붙이고, 파일 객체를 찾아 쓴다. **한 번에 몰아서 쓰면 이 비용이 100만분의 1로 준다.**

```python title="출력 몰아쓰기 (조각)"
import sys

ans = [i * i for i in range(5)]

# ❌ 줄마다 부른다
for x in ans:
    print(x)

# ✅ 한 번에 만들어 한 번에 쓴다
sys.stdout.write('\n'.join(map(str, ans)) + '\n')
```

::: warn
몰아쓰기에는 메모리 대가가 있다. 출력이 100만 줄이면 그 문자열 전체를 메모리에 들고 있어야 한다. 출력이 수천만 줄이라면 적당한 크기로 끊어 쓰거나 `sys.stdout.write`를 반복하는 쪽이 낫다. **시간과 공간을 바꾸는 거래**이지 공짜가 아니다.
:::

## 3. 개행과 분해

### 3.1 `readline`은 개행을 남긴다

`sys.stdin.readline()`이 돌려주는 것은 **줄바꿈 문자를 포함한** 문자열이다. 이 사실이 어디서 문제가 되고 어디서 안 되는지가 갈린다.

```python title="개행이 어디서 문제가 되는가 (조각)"
line = sys.stdin.readline()      # '41\n'
int(line) + 1                    # 42     <- int() 는 앞뒤 공백·개행을 무시한다

name = sys.stdin.readline()      # 'kim\n'
name == "kim"                    # False  <- 문자열 비교는 개행을 무시하지 않는다
name.rstrip() == "kim"           # True

row = sys.stdin.readline()       # ' 10  20   30 \n'
row.split()                      # ['10', '20', '30']   <- split() 도 알아서 버린다
```

규칙은 하나로 정리된다. **숫자로 바꾸거나 `split()`을 거치면 개행은 저절로 사라진다. 문자열을 그대로 쓸 때만 `rstrip()`이 필요하다.**

::: pitfall
- **격자를 읽을 때.** `grid.append(input())`으로 읽으면 각 행 끝에 `'\n'`이 붙어 열 개수가 하나씩 많아진다. `input().rstrip()`으로 읽어야 `'#.#.'`이 네 글자다.
- **`rstrip()`과 `rstrip('\n')`은 다르다.** 인자 없는 `rstrip()`은 공백도 뗀다. 뒤쪽 공백이 의미를 갖는 입력이라면 `rstrip('\n')`을 써야 한다.
- **줄 끝이 `\r\n`인 입력.** Windows에서 만든 파일이 그렇다. `rstrip()`은 `\r`도 떼지만 `rstrip('\n')`은 `\r`을 남긴다. 이때 `int()`는 통과하고 문자열 비교만 조용히 실패한다.
:::

### 3.2 `map`과 `split`

한 줄에 여러 수가 있을 때의 표준 관용구다.

📖 `str.split()` — 문자열을 공백 기준으로 잘라 리스트로 만든다. $O(n)$, n은 문자열 길이.
　 인자 없이 부르면 **연속된 공백을 하나로 보고 앞뒤 공백을 버린다.** `split(' ')`는 다르다 — 공백 하나마다 자르므로 빈 문자열이 생긴다.
　 쓰는 곳: 거의 모든 입력 처리. C++ 대응: `cin >>`가 공백 구분을 알아서 한다.

📖 `map(f, iterable)` — 각 원소에 `f`를 적용하는 **지연 반복자**를 돌려준다. 리스트가 아니다.
　 리스트가 필요하면 `list(map(...))`로 감싼다. 한 번만 순회할 것이면 감싸지 않는 편이 빠르고 메모리도 덜 쓴다.
　 쓰는 곳: 입력 파싱 전반. C++ 대응: 없다. `cin >>`가 타입에 맞춰 직접 변환한다.

```python title="입력 형태별 관용구 (조각)"
a, b = map(int, input().split())          # 한 줄에 두 수
arr = list(map(int, input().split()))     # 한 줄에 n개
mat = [list(map(int, input().split()))    # n줄 x m열 정수 격자
       for _ in range(n)]
grid = [input().rstrip() for _ in range(n)]   # n줄 문자 격자
data = sys.stdin.buffer.read().split()    # 전체를 한 번에 (줄 구분 무시)
```

마지막 줄은 **줄 구분이 의미 없을 때** 쓴다. 입력 전체를 한 번의 시스템 호출로 읽고 공백 단위로 자른다. 줄 수가 매우 많고 줄바꿈 위치가 상관없는 문제에서 가장 빠르다. 대신 입력 전체가 메모리에 올라온다.

::: tip
`sys.stdin.buffer`는 **바이트**를 읽는다. `sys.stdin`이 유니코드 디코딩을 거치는 것과 달리 그 단계가 없어서 빠르다. 대신 나오는 원소가 `b'10'` 같은 바이트열이다. `int()`는 바이트열도 받으므로 정수 입력에는 문제가 없지만, 문자열로 쓰려면 `.decode()`가 필요하다.
:::

## 4. 다차원 리스트 초기화

### 4.1 `[[0]*n]*m`이 부수는 것

§1의 두 번째 사고로 돌아온다.

```python title="같은 행을 m번 가리킨다"
n, m = 3, 2

bad = [[0] * n] * m
bad[0][0] = 9
print(bad)                    # [[9, 0, 0], [9, 0, 0]]
print(bad[0] is bad[1])       # True   <- 같은 객체다

good = [[0] * n for _ in range(m)]
good[0][0] = 9
print(good)                   # [[9, 0, 0], [0, 0, 0]]
print(good[0] is good[1])     # False
```

`*`는 **원소를 복사하지 않는다. 참조를 복사한다.** `[[0]*n] * m`은 리스트 하나를 만들고 그것을 가리키는 포인터를 m개 늘어놓는다. 그래서 `bad[0]`과 `bad[1]`은 같은 객체이고, 한쪽을 고치면 다른 쪽도 고쳐진다.

```text nolines
   bad = [ ptr, ptr ]                good = [ ptr, ptr ]
            |    |                            |     |
            +----+                            |     +--> [0, 0, 0]
            |                                 +-------> [0, 0, 0]
            v
          [9, 0, 0]                        <- 서로 다른 객체 2개
```

`[[0]*n for _ in range(m)]`은 **표현식을 m번 실행**한다. `[0]*n`이 m번 평가되므로 매번 새 리스트가 생긴다.

::: danger
1차원에서는 이 함정이 드러나지 않는다. `[0] * n`은 완벽히 안전하다. `0`이 불변 객체라 공유되어도 아무 문제가 없기 때문이다.

그래서 `[0] * n`으로 성공한 경험이 `[[0] * n] * m`으로 그대로 확장된다. **얕은 복사가 문제가 되는 것은 원소가 가변일 때뿐이고, 리스트는 가변이다.** 같은 이유로 `[[]] * n`, `[{}] * n`, `[set()] * n`이 전부 같은 사고를 낸다.

증상이 고약하다. 격자를 채우는 도중까지는 멀쩡해 보이고, 값이 여러 행에 번지기 시작한 뒤에야 이상해진다. 그때는 이미 알고리즘을 의심하고 있다.
:::

### 4.2 어느 쪽을 쓸 것인가

::: dual
```python title="2차원 격자 만들기 — m행 n열을 0으로"
n, m = 4, 3

grid = [[0] * n for _ in range(m)]
grid[1][2] = 7

for row in grid:
    for x in row:
        print(x, end=' ')
    print()
```
```cpp title="2차원 격자 만들기 — m행 n열을 0으로"
#include <iostream>
#include <vector>
using namespace std;

int main() {
    int n = 4, m = 3;

    vector<vector<int>> grid(m, vector<int>(n, 0));
    grid[1][2] = 7;

    for (const auto& row : grid) {
        for (int x : row) cout << x << ' ';
        cout << '\n';
    }
    return 0;
}
```
:::

**복잡도:** 시간 $O(nm)$ — 칸 하나마다 한 번 초기화하므로 칸 수에 비례한다. 공간 $O(nm)$ — 정수 nm개와 행 포인터 m개. Python 쪽은 여기에 더해 **각 칸이 객체 참조**라 실제 메모리가 C++의 `vector<vector<int>>`보다 여러 배 크다. 이 차이는 [0-3 Python 내장 자료구조의 실제 비용](#/0-3)에서 다룬다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 얕은 복사 함정 | `[[0]*n]*m`이 행을 공유한다 | `vector`는 값 복사라 함정이 없다 |
| 안전한 표기 | `[[0]*n for _ in range(m)]` | `vector<vector<int>>(m, vector<int>(n, 0))` |
| 원소 접근 비용 | 참조를 따라가므로 캐시 미스가 잦다 | 행 안은 연속 메모리 |
| 범위 밖 인덱스 | `IndexError` 예외 | 정의되지 않은 동작 |

::: tip
행 수가 매우 많거나 성능이 급하면 **1차원 리스트를 2차원처럼 쓰는 방법**이 있다. `flat = [0] * (n * m)`으로 잡고 `flat[r * n + c]`로 접근한다. 참조를 한 번만 따라가므로 메모리도 적고 캐시에도 유리하다. 인덱스 계산을 직접 해야 하는 것이 대가다.
:::

## 5. 정수는 넘치지 않는다

### 5.1 자릿수 제한이 없다

Python의 `int`는 **임의 정밀도**다. 값이 커지면 자릿수를 더 쓴다. 오버플로가 존재하지 않는다.

::: dual
```python title="큰 수 — 20억 두 개를 더하고 곱한다"
a = 2_000_000_000
b = 2_000_000_000
print("a + b =", a + b)
print("a * b =", a * b)
```
```cpp title="큰 수 — 20억 두 개를 더하고 곱한다"
#include <iostream>
using namespace std;

int main() {
    int a = 2000000000;
    int b = 2000000000;
    cout << "a + b = " << a + b << "\n";
    cout << "a * b = " << (long long)a * b << "\n";
    return 0;
}
```
:::

**여기서 두 출력이 갈린다.** 의도적이다.

```console
Python:  a + b = 4000000000            a * b = 4000000000000000000
C++   :  a + b = -294967296            a * b = 4000000000000000000
```

`a + b`가 C++에서 음수다. `int`는 약 21억까지라 40억이 들어가지 않는다. 부호 있는 정수의 오버플로는 **정의되지 않은 동작**이고, 위 값은 이 컴파일러·이 최적화 수준에서 관측된 결과일 뿐 보장된 값이 아니다. `a * b` 쪽이 맞은 것은 한쪽을 `long long`으로 올려 곱셈 자체를 64비트로 했기 때문이다. 상세는 [0-5 C++ 입출력과 기본 타입](#/0-5)에 있다.

**복잡도:** 덧셈은 자릿수 $d$에 대해 $O(d)$ — 자리마다 한 번씩 더하고 올림을 넘긴다. 곱셈은 교과서 방식이면 $O(d^2)$다. C++의 `int` 연산은 $d$가 고정이라 $O(1)$이다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 최댓값 | 없다 (메모리까지) | `int` 약 21억, `long long` 약 922경 |
| 오버플로 | 발생하지 않는다 | 부호 있는 타입은 **정의되지 않은 동작** |
| 정수 하나의 크기 | 28바이트부터 시작해 자란다 | `int` 4바이트, `long long` 8바이트 고정 |
| 연산 비용 | 자릿수에 비례 | 자릿수와 무관하게 상수 |
| 나눗셈 | `//`는 내림 (`-7 // 2 == -4`) | `/`는 0 방향 절삭 (`-7 / 2 == -3`) |

### 5.2 그 편의의 값

공짜가 아니다. 정수 하나가 객체이고, 크기가 자란다.

::: perf
| 값 | `sys.getsizeof` |
|---|---|
| `0`, `1`, `2^30 - 1` | 28바이트 |
| `2^30` | 32바이트 |
| `2^63 - 1`, `2^64` | 36바이트 |
| `2^1000` | 160바이트 |

곱셈 20만 번에 걸리는 시간이다.

| 피연산자 크기 | 시간 | 30비트 대비 |
|---|---|---|
| 30비트 | 0.010초 | 기준 |
| 64비트 | 0.013초 | 1.3배 |
| 1024비트 | 0.348초 | **34.6배** |
| 8192비트 | 4.81초 | **478배** |

> (Linux x86-64 / CPython 3.13 실측. 측정 스크립트는 `tools/bench/py_bigint_cost.py` 다.)
:::

읽는 법이 중요하다. **64비트까지는 사실상 공짜다.** 코딩테스트에서 다루는 값은 거의 전부 이 구간이라, "Python은 큰 수 연산이 느리다"는 걱정은 대개 근거가 없다. 비용이 드러나는 것은 **1024비트를 넘어가는 진짜 큰 수**이고, 그런 값이 나오는 곳은 조합론·거듭제곱·팩토리얼이다.

덧셈은 더 완만하다. 같은 스크립트에서 30비트와 1024비트의 덧셈 차이는 1.4배에 그친다. 자릿수 비용보다 인터프리터의 반복 비용이 크기 때문이다.

::: note
오버플로가 없다는 것이 값어치를 하는 자리가 있다. `math.factorial(2000)`은 5,736자리 정수를 0.0002초에 정확히 돌려준다. C++에서 같은 것을 하려면 큰 수 라이브러리를 직접 짜야 한다. `unsigned long long`은 **21!에서 이미 넘친다.**

모듈러 거듭제곱과 조합론은 [X-3 모듈러 연산과 분할 정복 거듭제곱](#/x-3), [X-4 조합론 기초](#/x-4)에서 다룬다. 거기서 Python은 `pow(a, b, m)`이라는 3인자 내장 함수로 끝난다.
:::

::: warn
CPython 3.11부터 **큰 정수를 문자열로 바꾸는 데 자릿수 제한**이 걸렸다. 기본값은 4,300자리이고, 넘으면 `ValueError`가 난다.

```python title="이 한 줄이 실제로 예외를 던진다"
str(2 ** 100000)     # ValueError: Exceeds the limit (4300 digits)...
```

2진수를 10진수로 바꾸는 것은 진법이 서로의 거듭제곱이 아니라 자릿수 전체를 건드리는 작업이고, 교과서적 알고리즘은 자릿수의 제곱에 비례한다. 악의적 입력으로 서비스를 멈출 수 있어 기본 제한이 생겼다. 푸는 방법은 `sys.set_int_max_str_digits(n)`이다.

다만 3.13의 실제 증가율은 제곱보다 훨씬 완만하다. 같은 스크립트 실측에서 `2^800000`(0.052초)과 `2^1600000`(0.113초)의 비는 2.2배다. 제곱이면 4배여야 한다.
:::

**1. 예측.** 다음 각각의 출력을 적어라. 돌리기 전에 적는 것이 요점이다.
```python
a = [[0] * 2] * 2
b = [[0] * 2 for _ in range(2)]
a[0][0] = 1
b[0][0] = 1
print(a, b, a[0] is a[1], b[0] is b[1])
```

**2. 백준 15552 빠른 A+B (브론즈 4)** — https://www.acmicpc.net/problem/15552
- 신호: 지문이 대놓고 "입출력 방식이 느리면 시간초과"라고 알려 준다. 유일하게 입출력 자체가 주제인 문제다.
- 상태: 없다. 한 줄 읽어 한 줄 쓰는 것이 전부다.
- 자료구조: 없다. 대신 §2.3과 §2.4를 둘 다 적용해야 한다. 입력만 고치고 출력을 `print` 반복으로 두면 절반만 고친 것이다.

**3. 백준 10951 A+B - 4 (브론즈 2)** — https://www.acmicpc.net/problem/10951
- 신호: "입력의 마지막 줄이 언제인지 주어지지 않는다". 몇 줄인지 모른 채 EOF까지 읽어야 한다.
- 상태: 없다. 다만 **종료 조건**이 상태다.
- 자료구조: 없다. §2.2의 5번이 핵심이다. `input()`은 EOF에서 `EOFError`를 던지고 `readline`은 빈 문자열을 돌려준다. 어느 쪽을 쓰느냐에 따라 루프를 끝내는 코드가 완전히 달라진다.

**4. 백준 2338 긴 자리 계산 (브론즈 5)** — https://www.acmicpc.net/problem/2338
- 신호: 입력이 100자리 정수다. C++이면 큰 수 덧셈·뺄셈·곱셈을 직접 짜야 한다.
- 상태: 없다.
- 자료구조: Python에서는 `int`가 그대로 답이다. §5.1이 그대로 값어치를 하는 자리이고, 같은 문제의 두 언어 난도가 얼마나 벌어지는지 보는 데 의미가 있다.

::: answer
**1.** `[[1, 1... ` 이 아니다. 정확히는 이렇다.

```console
[[1, 0], [1, 0]] [[1, 0], [0, 0]] True False
```

`a`는 행을 공유하므로 `a[0][0] = 1`이 두 행에 동시에 보인다. `a[0] is a[1]`이 `True`인 것이 그 증거다. `b`는 리스트 컴프리헨션이 `[0] * 2`를 두 번 평가해 서로 다른 객체를 만들었다.

**3의 보충.** 두 방식의 종료 코드는 이렇게 갈린다. 어느 쪽도 틀리지 않지만 **섞으면 틀린다.**

```python title="EOF까지 읽는 두 가지 방법 (조각)"
import sys

# readline: 빈 문자열이 EOF 신호
while True:
    line = sys.stdin.readline()
    if not line:
        break

# input(): 예외가 EOF 신호
while True:
    try:
        line = input()
    except EOFError:
        break
```

`input = sys.stdin.readline`으로 이름만 바꿔 두고 아래쪽 `try/except` 구조를 그대로 쓰면 **예외가 영원히 안 나서 무한 루프**가 된다. §2.3의 `::: danger`가 겨냥한 사고가 이것이다.
:::
:::

## 요약

- `input()`은 대화형 셸용 함수다. 호출마다 스트림을 찾고 터미널인지 검사한다. 100만 줄에서 `sys.stdin.readline`보다 **3.8배 느리고**, 그 차이의 95%는 개행 제거가 아니라 호출 비용 자체다.
- 출력도 같다. `print()` 반복은 `'\n'.join`으로 몰아쓰기보다 **8.1배 느리다.** 입력만 고치는 것은 절반만 고치는 것이다.
- `readline`은 개행을 남긴다. **`int()`와 `split()`은 알아서 무시하고, 문자열을 그대로 쓸 때만 `rstrip()`이 필요하다.** 격자 입력이 대표적인 자리다.
- `[[0]*n]*m`은 행 하나를 m번 가리킨다. `*`는 참조를 복제하지 실제 값을 복제하지 않는다. **`[[0]*n for _ in range(m)]`을 쓴다.** 1차원 `[0]*n`이 안전한 것은 `0`이 불변이기 때문이지 `*`가 안전해서가 아니다.
- Python 정수는 임의 정밀도라 오버플로가 없다. C++에서 같은 코드가 `int` 오버플로로 음수를 내는 자리에서 Python은 그냥 맞는다. **64비트까지는 비용도 사실상 없다.** 1024비트를 넘어야 곱셈이 34배로 벌어진다.
- 큰 정수를 `str()`로 바꿀 때 4,300자리 기본 제한이 있다. `sys.set_int_max_str_digits`로 푼다.
