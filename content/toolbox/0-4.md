# 0-4 Python 표준 라이브러리 세트

::: lead
알고리즘을 짜는 데 실제로 쓰이는 표준 라이브러리 전부와, `sort()`가 이미 정렬된 입력을 알아보는 방법.
:::

## 1. 문제

[0-3](#/0-3)이 남긴 결론은 "이 연산은 비싸다"였다. 그러면 무엇을 쓸 것인가. 답의 대부분은 이미 표준 라이브러리에 있고, 문제는 **있는 줄 모르고 다시 짜는 것**이다.

다시 짜면 둘을 잃는다. **시간**과 **정확성**이다. 표준 라이브러리의 상당수는 C로 구현되어 있어 복잡도가 같아도 상수가 자릿수로 갈리고, 이분 탐색을 직접 짜면 경계 조건에서 틀린다([0-11](#/0-11)이 그 이야기다).

```python title="같은 O(n log n), 다른 결과 (조각)"
sorted(data)[:100]           # 0.180초
heapq.nsmallest(100, data)   # 0.013초   <- 14배 빠르다
```

그런데 정반대의 함정도 있다. **표준 라이브러리라고 다 빠르지는 않다.** `functools.cmp_to_key`는 같은 정렬을 2.5배 느리게 만든다. 무엇이 왜 빠른지 알아야 고를 수 있다.

이 챕터는 그 목록이고, 마지막 절은 `sort()` 안에서 실제로 무슨 일이 벌어지는지다.

## 2. `heapq` — 최솟값만 필요할 때

전체를 정렬할 필요 없이 **가장 작은 것 하나**만 반복해서 꺼내는 상황이 있다. 다익스트라, 이벤트 시뮬레이션, 작업 스케줄러가 전부 그렇다.

📖 `heapq.heappush(heap, item)` — 최소 힙에 원소 삽입. $O(\log n)$.
　 리스트를 힙으로 취급하는 함수 모음이다. 별도 타입이 아니라 **그냥 `list`**이고, `heap[0]`이 항상 최솟값이다.
　 쓰는 곳: 다익스트라([V-1](#/v-1)), 최소 신장 트리의 프림([IX-4](#/ix-4)), 실시간 스케줄러([XI-5](#/xi-5)).
　 C++ 대응: `std::priority_queue` — 이쪽은 **최대 힙이 기본**이다. 반대다.

📖 `heapq.heappop(heap)` — 최솟값을 꺼내 돌려준다. $O(\log n)$.
📖 `heapq.heapify(a)` — 기존 리스트를 제자리에서 힙으로 만든다. **$O(n)$**이다.
📖 `heapq.nsmallest(k, iterable)` / `nlargest(k, iterable)` — 가장 작은/큰 k개. $O(n \log k)$.

::: dual
```python title="최소 힙 — 넣은 순서와 무관하게 작은 것부터"
import heapq

heap = []
for x in (5, 1, 8, 3):
    heapq.heappush(heap, x)

while heap:
    print(heapq.heappop(heap), end=' ')
print()
```
```cpp title="최소 힙 — 넣은 순서와 무관하게 작은 것부터"
#include <iostream>
#include <queue>
#include <vector>
using namespace std;

int main() {
    // 왜 greater<int> 인가: priority_queue 는 최대 힙이 기본이다.
    // heapq 와 같은 최소 힙으로 맞추려면 비교자를 뒤집어야 한다.
    priority_queue<int, vector<int>, greater<int>> heap;
    for (int x : {5, 1, 8, 3}) {
        heap.push(x);
    }

    while (!heap.empty()) {
        cout << heap.top() << ' ';
        heap.pop();
    }
    cout << '\n';
    return 0;
}
```
:::

두 코드 모두 `1 3 5 8`을 출력한다.

**복잡도:** `heappush`/`heappop`이 각각 시간 $O(\log n)$ — 완전 이진 트리의 높이가 $\log n$이고, 삽입은 새 잎에서 뿌리 방향으로, 삭제는 뿌리에서 잎 방향으로 한 층씩만 교환하기 때문이다. 공간 $O(n)$ — 배열 하나뿐이고 포인터가 없다. 내부는 [II-8 힙과 우선순위 큐](#/ii-8)에 있다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 기본 방향 | **최소 힙 고정** | **최대 힙 기본** |
| 뒤집는 법 | 값에 `-1`을 곱해 넣는다 | 비교자를 `greater<T>`로 준다 |
| 타입 | 별도 타입 없음. `list`를 함수로 다룬다 | `priority_queue`라는 독립 타입 |
| 최솟값 보기 | `heap[0]` | `heap.top()` |
| 임의 원소 접근 | `heap[i]`로 가능 (의미는 없다) | 불가능 |

::: warn
`heapq`에 튜플을 넣으면 **첫 원소로 비교하고, 같으면 다음 원소로 넘어간다.** 다익스트라에서 `(거리, 정점)` 순서로 넣는 이유다. `(정점, 거리)`로 뒤집으면 정점 번호로 정렬되어 전혀 다른 알고리즘이 된다.

두 번째 원소가 비교 불가능한 객체이면 첫 원소가 같을 때 `TypeError`가 난다. `(거리, 카운터, 객체)`처럼 절대 겹치지 않는 정수를 중간에 끼워 넣는다.
:::

::: perf
| 하는 일 | 시간 | 복잡도 |
|---|---|---|
| 50만 개에서 최소 100개 — `sorted(data)[:100]` | 0.180초 | $O(n \log n)$ |
| 50만 개에서 최소 100개 — `heapq.nsmallest(100, data)` | 0.013초 | $O(n \log k)$, **14배 빠름** |
| 50만 개로 힙 만들기 — `heapify` | 0.020초 | $O(n)$ |
| 50만 개로 힙 만들기 — `heappush` 50만 번 | 0.050초 | $O(n \log n)$, 2.5배 느림 |

> (Linux x86-64 / CPython 3.13 실측. 측정 스크립트는 `tools/bench/py_stdlib_ops.py` 다.)
:::

`heapify`가 $O(n)$인 것은 직관에 어긋나 보인다. 이유는 **대부분의 원소가 깊은 곳에 있고 깊은 원소는 내려갈 거리가 짧기 때문**이다. 잎 절반은 아예 움직이지 않는다. 층별로 (노드 수 × 내려갈 거리)를 더하면 수렴하는 급수가 되어 $O(n)$이다.

## 3. `bisect` — 정렬된 배열에서의 위치

📖 `bisect.bisect_left(a, x)` — 정렬된 `a`에서 `x`를 넣어도 정렬이 유지되는 **가장 왼쪽** 위치. $O(\log n)$.
　 `x`가 이미 있으면 **첫 번째 `x`의 인덱스**다. 그래서 존재 여부 검사에도 쓴다.
　 쓰는 곳: [VII-2 lower_bound/upper_bound](#/vii-2), LIS의 $O(n \log n)$ 풀이([VIII-6](#/viii-6)), 좌표 압축([VI-5](#/vi-5)).
　 C++ 대응: `std::lower_bound` — 이름만 다르고 의미가 같다.

📖 `bisect.bisect_right(a, x)` (별칭 `bisect`) — **가장 오른쪽** 위치. 즉 마지막 `x`의 다음 칸.
📖 `bisect.insort(a, x)` — 정렬을 유지하며 삽입. 위치 찾기는 $O(\log n)$이지만 **삽입 자체가 $O(n)$**이다.

::: dual
```python title="개수 세기 — 정렬 배열에서 x가 몇 개인가"
import bisect

a = [1, 3, 3, 3, 7, 9]
x = 3

lo = bisect.bisect_left(a, x)
hi = bisect.bisect_right(a, x)
print(lo, hi, hi - lo)

bisect.insort(a, 5)
print(*a)
```
```cpp title="개수 세기 — 정렬 배열에서 x가 몇 개인가"
#include <algorithm>
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> a = {1, 3, 3, 3, 7, 9};
    int x = 3;

    int lo = lower_bound(a.begin(), a.end(), x) - a.begin();
    int hi = upper_bound(a.begin(), a.end(), x) - a.begin();
    cout << lo << ' ' << hi << ' ' << hi - lo << '\n';

    a.insert(upper_bound(a.begin(), a.end(), 5), 5);
    for (size_t i = 0; i < a.size(); i++) cout << a[i] << " \n"[i + 1 == a.size()];
    return 0;
}
```
:::

두 코드 모두 `1 4 3`과 `1 3 3 3 5 7 9`를 출력한다. **두 경계의 차가 개수**다.

**복잡도:** 탐색은 시간 $O(\log n)$ — 매 비교마다 후보 구간의 폭이 절반으로 줄고, 폭 1까지 접는 횟수가 $\log_2 n$이다. 공간 $O(1)$. 다만 `insort`는 전체가 $O(n)$이다 — 위치는 $O(\log n)$에 찾지만 삽입이 뒤쪽 원소를 전부 밀기 때문이다([0-3](#/0-3) §2.3).

::: perf
20만 개 배열에 20만 번 질의한 시간이다.

| | 시간 |
|---|---|
| `bisect.bisect_left` | 0.143초 |
| 손으로 짠 선형 탐색 | 1,019초 (400회 실측 후 환산) |
| | **7,145배 느림** |

> (같은 환경·같은 스크립트.)
:::

::: danger
`insort`를 루프에서 n번 부르면 전체가 $O(n^2)$이다. **$\log n$인 것은 위치 찾기뿐이고 삽입은 여전히 선형이다.**

정렬 상태를 유지하며 계속 삽입해야 한다면 답은 `bisect`가 아니라 균형 트리([II-9](#/ii-9))나 [XV-5 스킵 리스트](#/xv-5)다. 다만 정렬이 다 끝난 뒤에만 조회한다면 **전부 넣고 마지막에 한 번 `sort()`** 하는 것이 거의 항상 낫다.
:::

## 4. `collections`

### 4.1 `deque`

[0-3](#/0-3) §2.3에서 다뤘다. 양끝 $O(1)$, 인덱싱 $O(n)$, 빈 객체가 760바이트다. BFS의 큐는 예외 없이 이것을 쓴다.

📖 `deque(iterable, maxlen=None)` — `maxlen`을 주면 **고정 크기 링 버퍼**가 된다. 꽉 찬 상태에서 한쪽에 넣으면 반대쪽이 밀려 나간다.
　 최근 N개만 들고 있는 이동 평균에 그대로 쓰인다. 이 구조 자체는 [XI-1 링 버퍼](#/xi-1)의 주제다.

### 4.2 `defaultdict`

📖 `collections.defaultdict(factory)` — 없는 키를 읽으면 `factory()`를 불러 만들어 넣는다.
　 `d[k] += 1`이나 `d[k].append(x)`를 `if k not in d` 없이 쓸 수 있다.
　 쓰는 곳: 인접 리스트 만들기([IV-1](#/iv-1)), 그룹핑. C++ 대응: `std::map`/`unordered_map`은 **없는 키를 읽으면 기본값으로 자동 생성**한다 — Python의 `dict`와 달리 원래 그렇게 동작한다.

```python title="인접 리스트 (조각)"
from collections import defaultdict

graph = defaultdict(list)
for u, v in edges:
    graph[u].append(v)      # graph[u] 가 없어도 빈 리스트가 자동으로 생긴다
    graph[v].append(u)
```

::: danger
`defaultdict`는 **읽기만 해도 키를 만든다.**

```python
d = defaultdict(int)
if d[5] > 0:        # 읽었을 뿐인데
    pass
print(len(d))       # 1   <- 키 5가 생겼다
```

그래프 순회 중 `if graph[v]`로 검사하면 방문하지도 않은 정점이 계속 생겨 순회 대상이 늘어난다. 존재만 확인할 때는 `if v in graph`를 쓴다. `in`은 키를 만들지 않는다.

C++의 `map`도 `m[k]`로 읽으면 같은 일이 일어난다. 이쪽은 `m.count(k)`를 쓴다. **두 언어가 같은 함정을 공유하는 드문 지점**이다.
:::

### 4.3 `Counter`

📖 `collections.Counter(iterable)` — 원소별 등장 횟수를 담은 `dict`의 하위 클래스. 만드는 데 $O(n)$.
　 없는 키를 읽으면 `KeyError` 대신 **0**을 준다. 단, `defaultdict`와 달리 **키를 만들지는 않는다.**
　 `most_common(k)`는 상위 k개를 준다. 내부에서 힙을 쓴다.
　 쓰는 곳: 빈도 문제 전반, 애너그램 판정, [II-6 해시](#/ii-6). C++ 대응: 없다. `map<T,int>`로 직접 센다.

::: dual
```python title="단어 빈도 세기"
from collections import Counter

words = ["ab", "cd", "ab", "ef", "cd", "ab"]
cnt = Counter(words)

for w, c in sorted(cnt.items()):
    print(w, c)
print("top:", cnt.most_common(1)[0][0], cnt.most_common(1)[0][1])
```
```cpp title="단어 빈도 세기"
#include <iostream>
#include <map>
#include <string>
#include <vector>
using namespace std;

int main() {
    vector<string> words = {"ab", "cd", "ab", "ef", "cd", "ab"};
    map<string, int> cnt;                     // map 은 키 정렬을 유지한다
    for (const string& w : words) cnt[w]++;   // 없는 키는 0 으로 만들어진다

    for (const auto& [w, c] : cnt) {
        cout << w << ' ' << c << '\n';
    }
    string best;
    int bestc = 0;
    for (const auto& [w, c] : cnt) if (c > bestc) { best = w; bestc = c; }
    cout << "top: " << best << ' ' << bestc << '\n';
    return 0;
}
```
:::

두 코드 모두 `ab 3 / cd 2 / ef 1 / top: ab 3`을 출력한다.

**복잡도:** 세기는 시간 $O(n)$ — 원소마다 해시 한 번과 갱신 한 번이다. `most_common(k)`는 $O(n \log k)$ — 크기 k짜리 힙을 유지하며 n개를 훑는다. 인자 없이 부르면 전체 정렬이라 $O(n \log n)$이다. 공간 $O(u)$ — u는 서로 다른 원소의 수.

| 언어 차이 | Python | C++ |
|---|---|---|
| 없는 키 읽기 | `Counter`는 0, `dict`는 `KeyError` | `map`은 0을 **만들어** 넣는다 |
| 키 순서 | 삽입 순서 (정렬하려면 `sorted`) | `map`은 정렬 유지, `unordered_map`은 무순서 |
| 상위 k개 | `most_common(k)` 내장 | 직접 훑거나 `nth_element` |

::: perf
100만 개의 빈도를 세는 세 가지 방법이다.

| 방식 | 시간 |
|---|---|
| `Counter(data)` | 0.078초 |
| `d[x] = d.get(x, 0) + 1` | 0.109초 (1.4배 느림) |
| `defaultdict(int)`에 `+= 1` | 0.119초 (1.5배 느림) |

> (같은 환경·같은 스크립트.)

차이가 작다. `Counter`를 쓰는 이유는 속도보다 **의도가 드러나고 `most_common`이 딸려 오기 때문**이다. 세면서 다른 일도 같이 해야 한다면 직접 루프를 도는 편이 낫고, 1.4배는 그 자유를 사는 값으로 싸다.
:::

## 5. `itertools`와 `functools`

### 5.1 조합 생성

📖 `itertools.permutations(iterable, r)` — 길이 r의 **순열**을 사전순으로 생성. 총 $P(n,r)$개.
📖 `itertools.combinations(iterable, r)` — 길이 r의 **조합**. 총 $C(n,r)$개.
📖 `itertools.product(*iterables, repeat=k)` — 곱집합. 중첩 `for`문을 평평하게 만든다.
　 전부 **지연 생성**이다. 리스트를 미리 만들지 않으므로 메모리가 $O(r)$이다.
　 쓰는 곳: 완전탐색([III-2](#/iii-2)), 외판원 순회의 브루트포스 대조([VIII-9](#/viii-9)).
　 C++ 대응: `std::next_permutation`만 있다. 조합은 직접 짜거나 비트마스크([III-3](#/iii-3))를 쓴다.

```python title="4방향 델타를 곱집합으로 (조각)"
from itertools import product, combinations

for dr, dc in ((-1, 0), (1, 0), (0, -1), (0, 1)):
    pass

# 중첩 for 3개를 한 줄로
for a, b, c in product(range(3), repeat=3):
    pass

# n개 중 2개 고르기 — 이중 루프의 i < j 를 대신한다
for i, j in combinations(range(5), 2):
    pass
```

::: warn
`permutations(range(10))`은 362만 개지만 `permutations(range(13))`은 62억 개라 절대 끝나지 않는다. **생성기라서 메모리는 안 터지고 시간만 무한히 간다.** 쓰기 전에 개수를 먼저 계산하라. [0-9 N 범위로 알고리즘 역산하기](#/0-9)의 표가 그 판단을 준다.
:::

### 5.2 `lru_cache`

📖 `functools.lru_cache(maxsize=None)` — 함수의 인자별 반환값을 캐시하는 데코레이터.
　 인자가 **해시 가능해야** 한다. 리스트를 인자로 받는 함수에는 못 붙인다 — 튜플로 바꿔 받아야 한다.
　 쓰는 곳: 메모이제이션 DP 전반([VIII-2](#/viii-2)). C++ 대응: 없다. `map`이나 배열로 직접 만든다.

```python title="메모이제이션 (조각)"
from functools import lru_cache
import sys

sys.setrecursionlimit(10 ** 6)      # 왜: 기본 재귀 한도가 1000이라 금방 넘는다

@lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)
```

::: perf
| | 시간 | 함수 호출 수 |
|---|---|---|
| `fib(30)` 캐시 없음 | 0.161초 | 1,664,079회 |
| `fib(30)` `lru_cache` | 0.0001초 | **31회** |
| | **1,422배 빠름** | |

> (같은 환경·같은 스크립트.)
:::

호출 수를 보라. 지수가 선형이 됐다. 캐시가 하는 일은 **같은 부분문제를 두 번 풀지 않는 것**이고, 그것이 DP의 정의다. 이 관계는 [VIII-2](#/viii-2)에서 정면으로 다룬다.

::: pitfall
- **`maxsize=None`이 아니면 캐시가 쫓겨난다.** DP에서는 전부 남겨야 하므로 `None`을 준다. 이름의 LRU가 그 축출 정책이고, 정책 자체는 [XV-9 캐시 교체 정책](#/xv-9)의 주제다.
- **재귀 깊이.** 기본 한도 1,000을 `sys.setrecursionlimit`으로 올려도 실제 스택이 부족하면 인터프리터가 죽는다. 안전한 답은 반복문으로 바꾸는 것이다([0-10](#/0-10)).
- **인자가 가변이면 못 쓴다.** 인자를 키로 쓰므로 해시 가능해야 한다. `tuple(grid)` 같은 변환이 필요하고, 그 비용이 캐시 이득을 넘을 수도 있다.
:::

### 5.3 `cmp_to_key`

📖 `functools.cmp_to_key(cmpfunc)` — 두 값을 받아 음수/0/양수를 돌려주는 **비교 함수**를 `key=`용 객체로 바꾼다. `key=`로 표현할 수 없는 순서 규칙에만 쓴다.

::: perf
20만 개를 정렬하는 두 방법이다.

| | 시간 |
|---|---|
| `key=lambda p: (p[0], -p[1])` | 0.360초 |
| `key=cmp_to_key(비교함수)` | 0.914초 (**2.5배 느림**) |

> (같은 환경·같은 스크립트.)
:::

복잡도는 둘 다 $O(n \log n)$이다. **차이는 전부 상수다.** `key=`는 원소마다 키를 한 번만 만들어 두지만, `cmp_to_key`는 비교할 때마다 Python 함수를 호출한다. 비교 횟수가 $n \log n$이니 호출도 그만큼이다.

**그래서 `key=`로 표현 가능하면 언제나 `key=`를 쓴다.** 내림차순은 값에 `-`를 붙이거나 `reverse=True`를 주고, 여러 기준이면 튜플로 묶는다. 숫자가 아니라 `-`를 못 붙이는 경우가 `cmp_to_key`가 필요한 거의 유일한 자리다.

## 7. 정렬 — Timsort 안에서 무슨 일이 벌어지는가

### 7.1 비교 정렬의 하한은 무작위 입력에 대한 것이다

"비교 기반 정렬은 $O(n \log n)$보다 빠를 수 없다"는 명제는 맞다. 다만 그것은 **최악의 경우**에 대한 명제이고, 실제 입력은 무작위가 아닌 경우가 많다.

::: perf
원소 200만 개를 `list.sort()`로 정렬한 시간과, 20만 개에서 실제로 일어난 **비교 횟수**다.

| 입력 모양 | 시간 (200만) | 비교 횟수 (20만) |
|---|---|---|
| 무작위 | 0.923초 | 3,263,435 |
| 이미 오름차순 | 0.019초 (**×0.02**) | **199,999** |
| 이미 내림차순 | 0.023초 (×0.03) | **199,999** |
| 앞뒤 절반씩 정렬 | 0.036초 (×0.04) | 399,999 |
| 99% 정렬 + 1% 흐트러짐 | 0.102초 (×0.11) | 547,260 |
| 전부 같은 값 | 0.008초 (×0.01) | 199,999 |
| (참고) $n \log_2 n$ | | 3,520,000 |

> (Linux x86-64 / CPython 3.13 실측. 측정 스크립트는 `tools/bench/py_timsort.py` 다.)
:::

무작위 입력의 비교 횟수 326만은 $n \log_2 n = 352$만에 거의 딱 붙는다. **이론이 맞았다.**

그런데 이미 정렬된 입력은 **199,999회**, 정확히 $n - 1$이다. 인접한 쌍을 한 번씩만 비교하고 끝났다는 뜻이고 이것은 $O(n)$이다. 내림차순도, 전부 같은 값도 똑같다.

이런 성질을 **적응적(adaptive)** 이라고 부른다. Timsort는 적응적이라 실전 데이터에서 이론값보다 훨씬 빠르다.

### 7.2 런 — 이미 정렬된 조각을 찾는다

::: deep
Timsort의 출발점은 하나다. **실제 데이터에는 이미 정렬된 구간이 섞여 있다.** 로그는 시간순이고, 병합된 두 파일은 각각 정렬되어 있다.

그래서 Timsort는 배열을 왼쪽부터 훑으며 **런(run)**, 즉 이미 정렬된 최대 구간을 찾는다.

- **오름차순 런**: `a[i] <= a[i+1]`이 이어지는 동안 늘린다.
- **내림차순 런**: `a[i] > a[i+1]`이 이어지는 동안 늘리고, 찾은 뒤 **제자리에서 뒤집는다.**

내림차순 입력이 오름차순만큼 빠른 이유가 이것이다. 한 번 훑어 전체가 하나의 내림차순 런임을 확인하고($n-1$번 비교), 뒤집고, 끝난다.

여기서 **엄격한** 부등호가 중요하다. 내림차순 런은 `>`로만 잇는다. 같은 값을 내림차순 런에 넣으면 뒤집을 때 순서가 바뀌어 **안정성이 깨지기** 때문이다. 그래서 `[3, 3, 3]`은 오름차순 런(`<=`)으로 잡히고, 전부 같은 값인 입력이 $n-1$번에 끝나는 것도 이 때문이다.

**minrun.** 런이 짧으면 병합할 조각이 너무 많아진다. 그래서 최소 길이 `minrun`을 정하고, 찾은 런이 그보다 짧으면 뒤쪽 원소를 **이진 삽입 정렬**로 밀어 넣어 채운다. 짧은 배열에서는 삽입 정렬이 실제로 가장 빠르다.

`minrun`은 32 이상 64 이하로 잡되 **`n / minrun`이 2의 거듭제곱에 가깝도록** 계산한다. 병합을 균형 잡히게 하기 위해서다 — 길이가 심하게 다른 두 런을 병합하면 짧은 쪽 원소가 여러 번 복사된다.
:::

### 7.3 병합 불변식 — 스택을 균형 있게 유지한다

::: deep
런들을 찾는 대로 스택에 쌓는다. 그리고 스택 꼭대기의 세 런 X, Y, Z(Z가 가장 아래)에 대해 **두 불변식**을 강제한다.

```text nolines
   run stack (top is right)
   ... | Z | Y | X |
         |   |   +-- most recent
         |   +------ |Y| > |X|
         +---------- |Z| > |Y| + |X|
```

불변식이 깨지면 그 자리에서 병합해 다시 세운다. 목적이 둘이다.

**첫째, 병합의 균형.** $|Z| > |Y| + |X|$는 인접한 런의 크기가 지수적으로 커지도록 강제한다. 병합이 항상 비슷한 크기끼리 일어나 전체가 $O(n \log n)$에 머문다.

**둘째, 스택 깊이의 상한.** 크기가 지수적으로 커지므로 쌓이는 런의 수가 $\log n$을 넘지 않는다.

::: hist
이 불변식에는 유명한 후일담이 있다. 2015년, 형식 검증 도구로 Java의 Timsort를 검사하던 연구진이 **꼭대기 세 개만 검사해서는 불변식을 완전히 보장하지 못한다**는 것을 발견했다. 특정 런 길이 조합에서 아래쪽 불변식이 깨진 채 남고, 그러면 미리 잡아 둔 스택 배열이 넘친다. CPython과 Java 모두 수정됐다.

의미가 있는 것은 이 사실이다. **세계에서 가장 많이 실행된 정렬 코드 중 하나에 남아 있던 버그를, 테스트가 아니라 불변식의 형식적 검증이 찾아냈다.** [0-11 손추적 방법론](#/0-11)이 불변식을 열로 두라고 하는 이유가 같은 자리에 있다.
:::
:::

### 7.4 갤러핑 — 한쪽이 계속 이기면 건너뛴다

::: deep
두 런을 병합할 때 보통은 양쪽 머리를 하나씩 비교해 작은 쪽을 가져온다. 그런데 한쪽이 **연달아** 이기는 상황이 있다. 두 런의 값 범위가 거의 겹치지 않으면 그렇다.

이때 하나씩 비교하는 것은 낭비다. 그래서 Timsort는 한쪽이 연속으로 7번 이기면(`MIN_GALLOP`) **갤러핑 모드**로 전환한다. 상대 런에서 1, 3, 7, 15, ... 칸씩 지수적으로 건너뛰며 넘어설 지점을 찾고, 찾으면 그 안을 이분 탐색한다. 한 번에 여러 원소를 통째로 옮긴다.

효과는 재 보면 바로 나온다. 원소 20만 개를 두 런으로 만들어 병합시킨 것이다.

| 두 런의 관계 | 총 비교 횟수 |
|---|---|
| 값 범위가 겹치지 않음 (한쪽이 연달아 이김) | **200,042** |
| 지퍼처럼 한 번씩 번갈아 이김 | 399,999 |

> (같은 환경·같은 스크립트의 `갤러핑` 절.)

읽는 법이 중요하다. 런 두 개를 찾는 데만 이미 199,998번이 든다. 그러니 **병합에 실제로 쓰인 비교는 위쪽이 44번, 아래쪽이 200,001번**이다.

원소 20만 개를 44번 비교로 병합했다. 지수 탐색이 하는 일이 이것이다. 아래쪽은 매번 승자가 바뀌어 연승이 7에 도달하지 못하므로 갤러핑이 아예 발동하지 않는다.

갤러핑이 공짜는 아니다. 발동했다 이득이 없으면 `MIN_GALLOP` 문턱을 올려 다음부터 덜 시도하고, 잘 맞으면 낮춘다. **입력에 맞춰 스스로 조정하는 이 부분**이 Timsort를 적응적으로 만드는 두 번째 장치다.
:::

### 7.5 안정성

::: dual
```python title="안정 정렬 — 같은 키의 원래 순서가 보존된다"
data = [("b", 1), ("a", 2), ("b", 3), ("a", 4)]

data.sort(key=lambda p: p[0])

for name, idx in data:
    print(name, idx)
```
```cpp title="안정 정렬 — 같은 키의 원래 순서가 보존된다"
#include <algorithm>
#include <iostream>
#include <string>
#include <vector>
using namespace std;

int main() {
    vector<pair<string, int>> data = {{"b", 1}, {"a", 2}, {"b", 3}, {"a", 4}};

    // 왜 stable_sort 인가: std::sort 는 안정성을 보장하지 않는다.
    // Python 의 sort 와 같은 결과를 얻으려면 이쪽을 써야 한다.
    stable_sort(data.begin(), data.end(),
                [](const auto& x, const auto& y) { return x.first < y.first; });

    for (const auto& [name, idx] : data) {
        cout << name << ' ' << idx << '\n';
    }
    return 0;
}
```
:::

두 코드 모두 `a 2 / a 4 / b 1 / b 3`을 출력한다. **원래 순서 그대로다.**

**복잡도:** 시간 최악 $O(n \log n)$ — 병합 불변식이 런 크기를 지수적으로 유지해 병합 단계가 $\log n$번이고 각 단계가 $O(n)$이다. 최선 $O(n)$ — 입력이 하나의 런이면 훑기 한 번으로 끝난다. 공간 $O(n)$ — 병합용 임시 버퍼가 필요하다. 실제로는 두 런 중 짧은 쪽만 복사하므로 $O(n/2)$이지만 표기는 $O(n)$이다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 기본 정렬 | `sort()` = Timsort, **안정** | `std::sort` = introsort, **불안정** |
| 안정 정렬 | 기본이 이미 안정 | `std::stable_sort`를 따로 쓴다 |
| 추가 메모리 | 항상 $O(n)$ | `sort`는 $O(\log n)$, `stable_sort`는 $O(n)$ |
| 적응성 | 정렬된 입력에서 $O(n)$ | introsort는 적응적이지 않다 |
| 순서 지정 | `key=` 또는 `reverse=` | 비교자 람다 |

::: danger
안정성이 **결과를 바꾸는** 자리가 있다. 두 기준으로 정렬할 때 안정 정렬이면 **약한 기준으로 먼저, 강한 기준으로 나중에** 두 번 정렬하는 것이 통한다. 나중 정렬이 앞 정렬의 결과를 보존하기 때문이다.

C++에서 같은 습관으로 `std::sort`를 두 번 부르면 조용히 틀린다. 결과는 여전히 "정렬되어" 있어서 눈으로는 안 보이고 채점기에서만 드러난다. **한 번에 튜플로 비교하는 것이 두 언어 모두에서 안전하다.**

`std::sort`가 안정성을 포기한 대가로 받은 것은 $O(\log n)$의 추가 메모리와 작은 상수다. 상세는 [0-7 C++ 알고리즘 함수 세트](#/0-7)에 있다.
:::

- 자료구조: 리스트와 `key=lambda p: (p[1], p[0])`. §5.3이 요점이다 — **`cmp_to_key`를 쓸 이유가 없고**, 튜플 키가 더 짧고 2.5배 빠르다.

**3. 백준 1181 단어 정렬 (실버 5)** — https://www.acmicpc.net/problem/1181
- 신호: "길이가 짧은 것부터, 같으면 사전 순, **중복은 제거**".
- 상태: 없다. 중복 제거와 정렬 키 두 개.
- 자료구조: `set`으로 중복을 없애고 `sorted(key=lambda w: (len(w), w))`. **`set`의 순회 순서를 믿으면 안 된다**([0-3](#/0-3) §4.3)가 여기서 실제로 문제가 된다.

**4. 측정 과제.** `tools/bench/py_timsort.py`를 돌려 비교 횟수 표를 직접 뽑아라. "앞뒤 절반씩 정렬" 입력이 정확히 399,999회인 이유를 §7.2와 §7.4로 설명하라. 그리고 "무작위"만 $n \log_2 n$에 붙는 이유를 말하라.

::: answer
**4.** 입력은 `[0..99999] + [0..99999]`이므로 런이 두 개다.

- **런 탐지**: 각 런에서 $100{,}000 - 1$번씩, 합쳐서 199,998번.
- **병합**: 두 런의 값 범위가 **완전히 겹치므로** 승자가 계속 바뀐다. 7연승이 나오지 않아 원소마다 정직하게 비교한다. 약 200,001번.

합이 399,999다. §7.4의 "지퍼처럼 맞물린 두 런"과 같은 수인 것이 우연이 아니다 — 둘 다 갤러핑이 발동하지 않는 배치다. 대조군인 "값 범위가 겹치지 않는 두 런"은 런 탐지 199,998번이 똑같이 들고 **병합만 44번**으로 끝났다. 갈린 것은 알고리즘이 아니라 **두 런의 값 배치**다.

$n \log_2 n$에 붙는 것이 무작위뿐인 이유는 그 하한이 **정보이론적 한계**이기 때문이다. n개의 순열은 $n!$가지이고 비교 한 번이 1비트를 주므로, 어느 순열인지 특정하려면 $\log_2(n!) \approx n \log_2 n$번이 필요하다.

이미 정렬된 입력에는 이 논증이 적용되지 않는다. 후보가 $n!$가지가 아니기 때문이다. Timsort는 $n-1$번의 비교로 "이건 이미 정렬됨"을 확인하고 정렬을 **아예 하지 않는다.** 하한을 깬 것이 아니라 하한이 걸리는 상황이 아닌 것이다.
:::
:::

## 요약

- `heapq`는 **최소 힙 고정**이고 C++의 `priority_queue`는 **최대 힙 기본**이다. 부호가 반대다. `heapify`는 $O(n)$이라 `heappush` 반복보다 2.5배 빠르고, 상위 k개는 `nsmallest`가 전체 정렬보다 14배 빠르다.
- `bisect`는 $O(\log n)$이지만 **`insort`는 $O(n)$이다.** 두 경계의 차가 개수다.
- `defaultdict`는 **읽기만 해도 키를 만든다.** 존재 확인은 `in`으로 한다. C++의 `map[k]`도 같은 함정이다. `Counter`는 직접 세는 것보다 1.4배 빠를 뿐이고, 쓰는 이유는 속도가 아니라 의도와 `most_common`이다.
- `lru_cache`는 지수를 선형으로 바꾼다. `fib(30)`의 호출이 166만 회에서 **31회**가 된다. 반대로 `cmp_to_key`는 같은 $O(n \log n)$을 **2.5배 느리게** 만든다. `key=`로 표현 가능하면 언제나 `key=`다.
- Timsort는 **적응적**이다. 이미 정렬된 200만 개를 무작위의 **1/50 시간**에 정렬하고 비교 횟수가 정확히 $n-1$이다. 내림차순도 같다 — 하나의 런으로 찾아 뒤집기 때문이다.
- 내부 장치는 셋이다. **런**(이미 정렬된 구간을 찾고 짧으면 삽입 정렬로 채운다), **병합 불변식**($|Z| > |Y|+|X|$, $|Y| > |X|$로 균형과 스택 깊이를 보장), **갤러핑**(한쪽이 7연승하면 지수 탐색으로 건너뛴다). 갤러핑이 걸리면 20만 개 병합이 **44번 비교**로 끝난다.
- Python의 `sort()`는 안정, C++의 `std::sort`는 불안정이다. 두 번 정렬해 두 기준을 거는 습관은 Python에서만 통한다. **한 번에 튜플로 비교하는 것이 양쪽 모두에서 안전하다.**
