# 0-10 언어별 상수와 TLE 대응

::: lead
같은 알고리즘이 Python과 C++에서 몇 배 벌어지는가, 그리고 그 배수를 언제 코드로 줄이고 언제 언어로 줄이는가.
:::

## 1. 문제

$O(n \log n)$ 알고리즘을 맞게 짰다. C++로 낸 사람은 통과했고 Python으로 낸 같은 코드는 시간 초과다. 여기서 두 가지 결론이 나오는데 둘 다 틀렸다.

첫째, "Python은 100배 느리니까 어차피 안 된다." 둘째, "언어 탓이 아니라 내 코드가 나쁘다."

배수는 하나가 아니기 때문이다. 같은 환경에서 워크로드만 바꿔 재면 **2.7배에서 106배까지** 나온다. 어느 쪽 끝에 서 있느냐에 따라 해야 할 일이 정반대다. 3배짜리 자리에서 언어를 갈아타는 것은 헛수고이고, 100배짜리 자리에서 코드를 다듬는 것도 헛수고다.

그래서 먼저 재야 한다.

## 2. 배수는 하나가 아니다

같은 일을 두 언어에서 같은 구조로 짜고 잰 결과다.

::: perf
| 워크로드 | Python 3.13 | g++ 13 `-O2` | 배수 |
|---|---|---|---|
| DP 갱신 `dp[j] = max(dp[j], ...)` 1회 | 137.0 ns | 1.29 ns | **106×** |
| 재귀 `fib(30)` 전체 | 0.147 s | 0.0025 s | 59× |
| 연속 배열 접근 `s += a[i]` 1회 | 59.4 ns | 1.23 ns | 48× |
| 함수 호출 1회 | 72.7 ns | 1.55 ns | 47× |
| 무작위 배열 접근 `s += a[idx[i]]` 1회 | 507.0 ns | 15.74 ns | 32× |
| 문자 100만 개 누적 (각 언어 최선) | 0.0537 s | 0.0018 s | 30× |
| 정렬 $10^6$개 | 0.369 s | 0.077 s | **4.8×** |
| 해시 조회 1회 (100만 키) | 507.0 ns | 135.70 ns | **3.7×** |
| 정수 100만 개 입력 (각 언어 최선) | 0.305 s | 0.093 s | 3.3× |
| 100만 줄 출력 (각 언어 최선) | 0.173 s | 0.063 s | **2.7×** |

> (Linux x86-64 / CPython 3.13 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 측정 스크립트는 `tools/bench/ops_budget.py|.cpp` 와 `tools/bench/lang_constant.py|.cpp` 다.)
:::

표를 위에서 아래로 읽으면 규칙이 하나 보인다. **인터프리터가 직접 도는 루프일수록 배수가 크고, 일을 라이브러리에 넘길수록 배수가 작다.**

DP 갱신은 인덱스 계산, 비교, 대입이 전부 Python 바이트코드다. 한 바퀴마다 인터프리터가 명령을 열 개 남짓 해석한다. 배수 106배가 그 값이다.

정렬은 반대다. `list.sort()`는 호출 한 번이고, 그 뒤의 비교와 이동은 전부 CPython의 C 코드가 한다. 인터프리터는 시작할 때 한 번 관여하고 끝이다. 배수 4.8배가 그 값이다.

::: note
==Python이 느린 것은 표준 라이브러리가 아니라 인터프리터 루프다.== 이 한 문장이 이 챕터의 전부다. 최적화의 방향이 여기서 나온다. **루프를 줄이는 것이 아니라 루프를 라이브러리 안으로 옮기는 것이 Python 최적화다.**

C++에서는 반대다. 라이브러리 호출이 이미 기계어라 옮길 곳이 없다. C++의 최적화는 메모리 접근 패턴과 할당 횟수를 손보는 쪽이다.
:::

## 3. 배수를 코드로 줄이는 네 자리

### 3.1 입출력

$n \ge 10^6$이면 읽는 시간이 계산 시간을 넘긴다. 정수 100만 개를 읽는 데 걸린 시간이다.

::: perf
| Python | 초 | | C++ | 초 |
|---|---|---|---|---|
| `input()` | 1.181 | | `cin` (기본) | 0.367 |
| `sys.stdin.readline` | 0.305 | | `cin` + `sync_with_stdio(false)` | 0.093 |
| `sys.stdin.buffer.read().split()` | 0.367 | | `scanf` | 0.115 |

100만 줄 출력:

| Python | 초 | | C++ | 초 |
|---|---|---|---|---|
| `print()` 줄마다 | 1.486 | | `cout << endl` | 0.382 |
| `sys.stdout.write` + `join` | 0.173 | | `cout << '\n'` | 0.063 |
| | | | `printf` | 0.067 |

> (같은 환경 실측. 별도 프로세스에서 측정해 프로세스 기동 시간이 포함되어 있다. 측정 스크립트는 `tools/bench/lang_constant.py` 와 `.cpp` 다.)
:::

**같은 언어 안에서 3.9배와 4.0배가 공짜로 있다.** 언어를 바꿔서 얻는 3.3배보다 크다. 시간 초과가 났을 때 알고리즘을 의심하기 전에 여기부터 본다.

📖 `sys.stdin.readline()` — 표준 입력에서 개행까지 한 줄을 읽어 문자열로 돌려준다. 개행 문자가 **포함된 채** 온다. `int()`는 앞뒤 공백을 무시하므로 정수 변환에는 그대로 써도 되지만, 문자열로 쓸 때는 `.rstrip()`이 필요하다.
   `input()`보다 빠른 이유는 프롬프트 처리와 인코딩 협상 계층을 건너뛰기 때문이다. 자세한 내부는 [0-2 Python 입출력과 기본 타입](#/0-2)에 있다.
   쓰는 곳: 입력이 $10^5$줄을 넘는 모든 문제.
   C++ 대응: `cin >> x` — 단, `ios_base::sync_with_stdio(false)`를 먼저 부르지 않으면 위 표의 0.367초 쪽이다.

::: danger
`ios_base::sync_with_stdio(false)`를 부른 뒤에는 `scanf`/`printf`와 `cin`/`cout`을 **섞어 쓰면 안 된다.** 동기화를 껐다는 것은 두 버퍼가 따로 논다는 뜻이고, 출력 순서가 뒤섞인다. 로컬에서는 멀쩡하다가 채점기에서 깨지는 경로가 이것이다.

`cin.tie(nullptr)`도 같은 종류다. 이것을 끄면 입력 전에 출력이 자동으로 비워지지 않는다. 대화형 문제(입력과 출력을 주고받는 문제)에서는 **끄면 안 된다.** 끄고 나서 직접 `flush`를 부르거나, 대화형에서는 아예 손대지 않는다.
:::

### 3.2 재귀

`fib(30)`은 논리 호출이 2,692,537회다. Python 0.147초, C++ 0.0025초로 59배다. 호출 하나당 Python 72.7 ns, C++ 1.55 ns다.

Python의 함수 호출이 비싼 이유는 프레임 객체를 만들고, 인자를 묶고, 예외 처리 상태를 쌓기 때문이다. C++은 인자를 레지스터에 넣고 `call` 명령 하나다. 게다가 `-O2`는 `fib`의 두 재귀 호출 중 하나를 반복문으로 바꿔 실제 기계어 호출 횟수를 절반으로 줄인다. **컴파일러가 알고리즘을 조금 바꾼다.**

깊이 한계도 다르다.

::: perf
| | Python 3.13 | C++ (`ulimit -s` 8MB) |
|---|---|---|
| 기본 한계 | `sys.getrecursionlimit()` = 1,000 | 스택이 찰 때까지 |
| 한계 + 100 | `RecursionError` | — |
| 깊이 200,000 | `setrecursionlimit(300000)` 후 통과 | 통과 |

> (같은 환경 실측. `tools/bench/lang_constant.py` 와 `.cpp`.)
:::

::: deep
CPython 3.12부터 순수 Python 함수의 재귀는 **C 스택을 쓰지 않는다.** 프레임이 힙에 있는 청크로 관리되어 `setrecursionlimit`만 올리면 깊이 20만이 실제로 통과한다. 3.11 이하에서는 같은 코드가 세그멘테이션 폴트로 죽었다 — 인터프리터의 `RecursionError`를 피해 한계를 올리면 그다음에 OS의 스택 한계에 부딪혔기 때문이다.

그래도 `setrecursionlimit`을 크게 올리는 것은 안전한 조치가 아니다. C 확장이 끼어드는 경로(예: `__repr__`가 재귀 호출되는 자료구조)는 여전히 C 스택을 쓴다. **깊이가 $10^5$을 넘는 DFS는 반복으로 바꾸는 것이 맞다.** 변환 방법은 [IV-2 DFS](#/iv-2)에 있다.
:::

### 3.3 문자열 누적

Python의 `s += "x"` 100만 회가 0.0649초, `"".join(...)`이 0.0537초로 1.2배 차이밖에 안 났다. 교과서가 말하는 $O(n^2)$이 나오지 않았다.

::: deep
CPython에는 문자열 `+=`에 대한 특수 최적화가 있다. 좌변 문자열의 참조 카운트가 1이고 그 결과를 같은 이름에 다시 대입하는 형태이면, 새 객체를 만드는 대신 **버퍼를 그 자리에서 늘린다.** 그래서 이 특정 패턴만 상환 $O(n)$이 된다.

조건이 깨지면 그대로 $O(n^2)$이다. 다른 이름이 같은 문자열을 참조하고 있거나, 리스트 원소에 누적하거나(`parts[i] += x`), CPython이 아닌 구현이면 최적화가 걸리지 않는다.

==특정 구현의 최적화에 복잡도를 맡기지 마라.== `join`은 어디서나 $O(n)$이고 조건이 없다. C++에서도 같은 논리로 `reserve`를 먼저 부르면 재할당이 사라져 1.8배 빨라진다(0.0032초 → 0.0018초). 예측 가능한 쪽을 쓰는 것이 규율이다.
:::

### 3.4 자료구조 선택

배수 표의 아래쪽 세 줄(정렬 4.8배, 해시 3.7배, 입출력 2.7배)이 알려 주는 것은 이것이다. **Python에서 할 일은 안쪽 루프를 라이브러리 호출로 바꾸는 것이다.**

| 손으로 짠 루프 | 라이브러리로 옮긴 형태 | 어디에 |
|---|---|---|
| 최솟값 찾는 `for` | `min(a)` | [0-3](#/0-3) |
| 정렬 직접 구현 | `a.sort(key=...)` | [II-7](#/ii-7) |
| 이분 탐색 직접 구현 | `bisect.bisect_left` | [0-4](#/0-4) |
| 카운팅 `for` | `collections.Counter` | [0-4](#/0-4) |
| 누적 합 `for` | `itertools.accumulate` | [VI-4](#/vi-4) |
| 앞쪽 삽입·삭제 | `collections.deque` | [II-5](#/ii-5) |

억지로 밀어 넣으라는 말은 아니다. 판단 기준은 하나다. **그 루프가 안쪽 루프이고 $10^6$번 이상 도는가.** 바깥 루프를 라이브러리로 바꿔 봐야 얻는 것이 없다.

## 4. 손으로 따라가기

배수 표를 그대로 쓰면 "이 코드가 Python에서 몇 초일지"를 코드를 돌리기 전에 낼 수 있다. 계산의 형태는 항상 같다. **연산 횟수 × 단가.**

::: trace
문제: 정점 $V = 10^5$, 간선 $E = 3 \times 10^5$인 그래프에서 다익스트라. 시간 제한 2초.

다익스트라의 연산은 세 종류다([V-1](#/v-1)). 각각 §2 표의 어느 줄에 해당하는지 정하고 시간을 채워라.

| 연산 | 횟수 | 어느 단가인가 | Python (ns) | Python 소계 | C++ (ns) | C++ 소계 |
|---|---|---|---|---|---|---|
| 힙 push/pop ($\log$ 포함) | $E \log E \approx 5.5 \times 10^6$ | 무작위 접근 | 507.0 | 2.79 s | 15.74 | 0.087 s |
| 인접 리스트 순회 | $2E = 6 \times 10^5$ | 연속 접근 | 59.4 | 0.036 s | 1.23 | 0.001 s |
| 거리 배열 갱신 | $E = 3 \times 10^5$ |  |  |  |  |  |
| 입력 읽기 |  |  |  |  |  |  |
| **합계** | | | | | | |

- [ ] 거리 갱신은 `dist[v]`를 정점 번호로 찌른다. 어느 단가인가
- [ ] 입력은 간선 $3 \times 10^5$줄, 즉 정수 $9 \times 10^5$개다. §3.1 표에서 각 언어의 최선을 가져오라
- [ ] 합계를 낸 뒤, 2초 제한을 어느 쪽이 통과하는가
:::

::: answer
| 연산 | 횟수 | 어느 단가인가 | Python (ns) | Python 소계 | C++ (ns) | C++ 소계 |
|---|---|---|---|---|---|---|
| 힙 push/pop | $5.5 \times 10^6$ | 무작위 접근 | 507.0 | 2.79 s | 15.74 | 0.087 s |
| 인접 리스트 순회 | $6 \times 10^5$ | 연속 접근 | 59.4 | 0.036 s | 1.23 | 0.001 s |
| 거리 배열 갱신 | $3 \times 10^5$ | 무작위 접근 | 507.0 | 0.152 s | 15.74 | 0.005 s |
| 입력 읽기 | 정수 $9 \times 10^5$개 | §3.1 최선 | — | 0.275 s | — | 0.084 s |
| **합계** | | | | **3.25 s** | | **0.18 s** |

**거리 갱신은 무작위 접근이다.** 정점 번호에 순서가 없어 `dist[v]`가 배열 어디를 찌를지 예측되지 않는다. 인접 리스트 순회는 반대로 한 정점의 이웃이 메모리에 붙어 있어 연속 접근이다. ==같은 배열 인덱싱인데 접근 패턴이 달라 단가가 8.5배 갈린다.==

입력은 §3.1의 100만 개 기준을 0.9배 해서 Python 0.275초, C++ 0.084초다.

2초 제한에서 C++은 0.18초로 여유롭고 Python은 3.25초로 초과다. **1.6배가 모자란다.**

여기서 나오는 판단이 중요하다. 3.25초 대 2초는 자릿수 문제가 아니다. 힙 연산이 전체의 86%를 차지하므로 여기만 줄이면 된다. 실제로 `heapq`는 C 구현이라 push/pop 자체는 빠르고, 비용의 상당 부분은 튜플 생성과 비교에서 나온다. 거리를 상위 비트에, 정점 번호를 하위 비트에 넣어 **정수 하나로 힙에 넣으면** 튜플 할당과 원소별 비교가 사라진다. 이런 종류의 손질로 1.6배는 대체로 회수된다.

**106배가 모자란 상황이었다면 얘기가 다르다.** 그때는 언어를 바꾸는 것이 유일한 길이다. 판단 기준을 다음 절에서 정리한다.
:::

## 5. 구현

같은 계산을 반복하지 않도록 두 언어의 "빠른 입출력 골격"을 하나로 고정해 둔다. 이것을 매번 새로 떠올리는 것은 순손실이다.

::: dual
```python title="빠른 입출력 골격 — 정수 n개를 읽어 합을 낸다"
import sys


def main():
    data = sys.stdin.buffer.read().split()   # 전부 한 번에 읽고 공백으로 쪼갠다
    n = int(data[0])
    total = 0
    for i in range(1, n + 1):
        total += int(data[i])                # 필요한 것만 그때 정수로 바꾼다
    out = []
    out.append(str(total))
    out.append(str(total * 2))
    sys.stdout.write("\n".join(out) + "\n")  # 줄마다 print 하지 않는다


main()
```
```cpp title="빠른 입출력 골격 — 정수 n개를 읽어 합을 낸다"
#include <iostream>
#include <string>
#include <vector>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);        // C 표준 입출력과의 동기화를 끊는다
    cin.tie(nullptr);                        // 입력 전 자동 flush 를 끈다
    int n;
    cin >> n;
    long long total = 0;                     // int 로 두면 넘칠 수 있다
    for (int i = 0; i < n; ++i) {
        long long x;
        cin >> x;
        total += x;
    }
    vector<string> out;
    out.push_back(to_string(total));
    out.push_back(to_string(total * 2));
    string buf;
    for (auto& s : out) buf += s + "\n";
    cout << buf;                             // 줄마다 endl 을 쓰지 않는다
    return 0;
}
```
:::

**복잡도:** 시간 $O(n)$ — 입력 토큰마다 정수 변환 한 번, 덧셈 한 번이므로 토큰 수에 비례한다. 공간 $O(n)$ — Python 쪽은 `split()`이 토큰 전부를 바이트열 리스트로 들고 있어 입력 크기에 비례하는 메모리를 쓴다. C++ 쪽은 한 번에 하나씩 읽어 $O(1)$이다. **이 차이가 Python에서 메모리 초과를 만드는 자리다.** 입력이 수백 MB면 `readline` 반복으로 바꾼다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 통째로 읽기 | `sys.stdin.buffer.read().split()` — 가장 빠르지만 메모리를 입력 크기만큼 쓴다 | 대응이 필요 없다. `cin`이 이미 버퍼링한다 |
| 줄 단위 | `sys.stdin.readline` — 메모리 $O(1)$, 이 워크로드에서는 오히려 더 빨랐다(0.305 s vs 0.367 s) | `getline(cin, s)` |
| 개행 | `readline`은 개행을 포함해 돌려준다 | `cin >> x`는 공백을 건너뛴다 |
| 출력 모으기 | `"\n".join(out)` | `string buf`에 누적. `reserve`를 부르면 더 빠르다 |
| 위험한 단축 | 없음 | `sync_with_stdio(false)` 후 `printf` 혼용 금지, 대화형에서 `tie(nullptr)` 금지 |
| 정수 크기 | 임의 정밀도라 합이 넘치지 않는다 | `int` 합은 넘친다. `long long` 필수([0-5](#/0-5)) |

::: pitfall
- **`sys.stdin.buffer.read()`를 대화형 문제에 쓴다.** EOF까지 기다리므로 영원히 멈춘다.
- **`readline`으로 읽고 `.rstrip()`을 잊는다.** 문자열 비교가 개행 때문에 전부 실패한다.
- **출력을 모으다 메모리를 넘긴다.** 출력이 수천만 줄이면 `join`할 리스트 자체가 크다. 그때는 적당한 크기로 나눠 흘려보낸다.
- **C++에서 `endl`을 습관으로 쓴다.** `endl`은 개행 + `flush`다. 100만 줄에서 0.382초 대 0.063초, 6배다.
- **입력 형식을 잘못 가정한다.** 한 줄에 여러 정수가 오는데 `readline`을 정수 하나로 읽으면 토큰이 밀린다. `split()`으로 통일하는 편이 안전하다.
:::

## 6. 언제 언어를 갈아탈 것인가

배수를 코드로 줄이는 데에도 한계가 있다. 판단 순서를 고정해 둔다.

```text nolines
  1. 입출력을 고쳤는가                       -> 최대 4배, 공짜
  2. 안쪽 루프를 라이브러리로 옮겼는가       -> 최대 30배, 코드 몇 줄
  3. 알고리즘의 복잡도가 최선인가            -> 자릿수, 재설계
  4. 그래도 모자라면                         -> 언어를 바꾼다
```

1번과 2번을 건너뛰고 4번으로 가는 것이 가장 흔한 낭비다. 반대로 **1~3을 다 했는데 여전히 10배가 모자라면 더 다듬어도 나오지 않는다.**

::: tip
언어를 바꿔야 하는 신호는 구체적이다.

- **안쪽 루프가 순수 산술이고 $10^7$번 이상 돈다.** DP 갱신, 시뮬레이션 스텝, 격자 순회가 여기다. 배수가 100배 쪽 끝이다.
- **재귀 호출이 $10^6$번 이상이다.** 호출당 72.7 ns면 $10^7$회에 0.7초다.
- **라이브러리로 옮길 수 있는 부분이 이미 없다.** 남은 것이 전부 인터프리터가 직접 도는 코드다.

반대로 **바꿔도 소용없는 신호**도 있다.

- 시간의 대부분이 정렬이나 해시에 있다. 배수가 4배 언저리라 언어를 바꿔도 4배다.
- 복잡도가 한 단계 높다. $O(n^2)$을 C++로 옮겨 봐야 $O(n^2)$이다. **언어는 상수를 바꾸고 알고리즘은 지수를 바꾼다.**
:::

::: note
**PyPy에 대해.** PyPy는 CPython과 다른 Python 구현이고, 추적 JIT 컴파일러가 뜨거운 루프를 기계어로 바꾼다. 그래서 위 표에서 **배수가 큰 줄들, 즉 순수 Python 루프가 지배하는 워크로드에서만 크게 이득이 난다.** 반대로 정렬·해시·입출력처럼 이미 C가 하는 일은 바꿀 것이 없고, JIT 예열 시간과 더 큰 메모리 사용이 붙어 오히려 불리해질 수 있다.

이 레포의 기준 환경(§1-3)에는 PyPy가 없다. **그래서 이 챕터의 모든 수치는 CPython 3.13이고, PyPy 수치는 싣지 않는다.** 재현할 수 없는 숫자를 적는 것보다 없는 편이 낫다.

판단 기준만 적어 둔다. **채점기가 PyPy를 제공하고, 병목이 순수 Python 루프이고, 메모리 제한에 여유가 있으면** 후보다. 병목이 라이브러리 호출이거나 메모리가 빠듯하면 후보가 아니다. 어느 쪽인지는 프로파일이 말해 준다 — §4의 계산을 항목별로 해 보면 어디에 시간이 몰려 있는지가 나온다.
:::

::: interview
**"Python으로 짜셨는데 성능이 걱정되지 않습니까."** 실무 면접에서 자주 나오고, "느리다고 알고 있습니다"는 답이 아니다.

답의 뼈대는 **배수가 워크로드에 따라 다르다**는 사실이다. "인터프리터가 직접 도는 루프는 50~100배지만, 정렬이나 해시처럼 C 구현으로 내려가는 부분은 3~5배입니다. 그래서 병목이 어디인지에 따라 판단이 달라집니다. 프로파일을 떠서 뜨거운 루프가 순수 Python이면 그 부분만 C 확장이나 다른 언어로 내리고, 라이브러리 호출이면 언어를 바꿀 이유가 없습니다."

**"그러면 언제 다른 언어를 씁니까."** 위의 4단계를 그대로 말하면 된다. 숫자를 근거로 순서를 정했다는 것이 답의 핵심이지 특정 언어에 대한 선호가 아니다.
:::

## 7. 어디에 쓰이는가

**혼합 언어 시스템의 경계가 이 표에서 결정된다.** 수치 계산 라이브러리, 머신러닝 프레임워크, 데이터 처리 도구가 전부 같은 형태를 하고 있다 — 얇은 Python 층이 배열 하나를 통째로 넘기고, 무거운 루프는 C나 포트란이 돈다. 이 구조가 나온 이유가 §2의 표다. **경계를 어디에 그을지는 "루프를 몇 번 도는가"로 정해진다.**

같은 판단이 서비스 코드에도 있다. 요청 처리는 Python으로 두고 초당 수백만 번 도는 정합 루프만 확장 모듈로 내리는 구조가 표준이다. 전부 내리면 개발 속도를 잃고, 아무것도 안 내리면 처리량을 잃는다.

**제어 소프트웨어의 언어 분리도 같다.** 주기가 밀리초인 제어 루프는 C++이고, 그 위의 임무 관리와 설정은 Python인 구조가 흔하다. 경계선은 취향이 아니라 **주기 안에 들어오는가**로 그어진다. 100Hz 루프의 10밀리초 예산에 72.7 ns짜리 호출이 $10^5$번 들어가면 7.3밀리초로 예산의 73%다.

## 8. 이 판단이 필요한 신호

::: classify
- 신호어: "시간 초과", "$N \le 10^6$", "$10^7$번의 연산", 채점 결과의 "1.9초 / 2초"처럼 아슬아슬한 통과
- 제약조건: 안쪽 루프의 반복 횟수가 $10^6$을 넘는 모든 코드. 재귀 호출이 $10^6$을 넘는 코드. 입력 줄 수가 $10^5$을 넘는 코드
- 혼동 주의: 복잡도가 틀린 것과 상수가 큰 것은 다른 문제다. 앞쪽은 언어를 바꿔도 안 되고 뒤쪽은 언어를 바꾸면 된다. 어느 쪽인지는 [0-9](#/0-9)의 두 배 실험이 가른다 — **지수가 예상보다 크면 알고리즘 문제이고, 지수는 맞는데 절대 시간이 크면 상수 문제다**
- 반례 함정: 시간 초과를 전부 언어 탓으로 돌리는 것. 실제로는 입출력 방식 하나로 4배가 나오는 경우가 가장 많다. 반대로 라이브러리 호출이 지배하는 코드를 언어만 바꿔 다시 짜는 것도 같은 종류의 실패다
:::

## 연습

::: quiz
전부 **"어디에 시간이 있는가"를 먼저 계산하는** 훈련이다. 코드를 고치기 전에 §4의 표를 그려라.

**1. 백준 11003 최솟값 찾기 (플래티넘 5)** — https://www.acmicpc.net/problem/11003
- 신호: $N \le 5{,}000{,}000$. 입력 정수만 500만 개다. §3.1 표에서 Python의 최선이 100만 개에 0.305초이므로 **읽기만 1.5초**다. 알고리즘을 정하기 전에 입출력 방식이 정해진다.
- 상태: 크기 $L$의 창 안에서 최솟값. 창이 밀릴 때마다 다시 훑으면 $O(NL)$이라 탈락이고, 덱에 후보만 남기면 각 원소가 한 번 들어가고 한 번 나와 $O(N)$이다.
- 자료구조: `collections.deque` / `std::deque`. 인덱스를 넣고 값으로 비교한다. **Python에서 이 루프는 순수 인터프리터라 배수가 50배 쪽이다.** 출력도 500만 개라 `join`이 필수다. [VI-3 투 포인터와 슬라이딩 윈도우](#/vi-3).

**2. 백준 1753 최단경로 (골드 4)** — https://www.acmicpc.net/problem/1753
- 신호: $V \le 20{,}000$, $E \le 300{,}000$. §4의 손추적이 그대로 이 문제다.
- 상태: `dist[v]` 배열 하나와 우선순위 큐. 큐에 들어가는 것은 (거리, 정점) 쌍이고, 꺼낸 거리가 현재 `dist`보다 크면 버린다.
- 자료구조: `heapq` / `priority_queue`. **Python에서 튜플 대신 정수 하나로 인코딩하면 힙 비교가 싸진다.** 그 판단의 근거가 §4의 소계 표다. [V-1 다익스트라](#/v-1).

**3. 백준 2447 별 찍기 - 10 (골드 5)** — https://www.acmicpc.net/problem/2447
- 신호: $N \le 3^7 = 2187$. 출력이 $2187^2 \approx 4.8 \times 10^6$자다. 계산은 가볍고 **출력이 전부다.**
- 상태: 재귀로 $(r, c)$가 별인지 판정하거나, 크기를 3배씩 키우며 격자를 조립한다. 어느 쪽이든 결과는 문자 격자 하나다.
- 자료구조: 문자 배열. 줄마다 `print`하면 2187줄이라 견디지만, 문자마다 `+=`로 붙이면 §3.3의 최적화 조건을 벗어나 $O(n^2)$이 될 수 있다. **줄을 리스트에 모아 `join` 한 번**이 안전하다. [III-1 재귀 사고법](#/iii-1).

**4. 계산 과제.** $N = 10^6$인 배열에서 $O(N \log N)$ 정렬 한 번과 $O(N)$ 순회 세 번을 하는 코드가 있다. §2 표의 단가로 Python과 C++의 예상 시간을 각각 내고, 1초 제한을 통과하는지 판정하라. 순회는 전부 연속 접근이다.

::: answer
**정렬.** §2 표에 $n = 10^6$ 정렬의 실측이 있다. Python 0.369초, C++ 0.077초다.

**순회 세 번.** $3 \times 10^6$회, 연속 접근 단가다.
- Python: $3 \times 10^6 \times 59.4\,\text{ns} = 0.178$초
- C++: $3 \times 10^6 \times 1.23\,\text{ns} = 0.004$초

**합계.** Python 0.547초, C++ 0.081초. 둘 다 1초를 통과한다.

여기서 볼 것은 **비중이 뒤집혀 있다는 점**이다. Python은 정렬이 67%, 순회가 33%다. C++은 정렬이 95%다. 즉 ==Python에서 이 코드를 빠르게 만들려면 순회를 손봐야 하고, C++에서는 손볼 것이 없다.== 같은 코드인데 최적화 대상이 다르다.

그리고 입력을 빠뜨리지 않았는지 확인하라. $10^6$개를 읽는 데 Python 0.305초, C++ 0.093초가 더 붙는다. 합계가 Python 0.852초로 1초에 바짝 붙는다. **입출력을 계산에 넣지 않는 것이 §4 손추적에서 가장 자주 나오는 누락이다.**
:::
:::

## 요약

- **배수는 하나가 아니다.** 같은 환경 실측에서 2.7배(출력)부터 106배(DP 갱신)까지 나온다.
- 규칙은 하나다. **인터프리터가 직접 도는 루프일수록 배수가 크고, 일을 라이브러리에 넘길수록 작다.** Python이 느린 것은 표준 라이브러리가 아니라 인터프리터 루프다.
- 입출력만 고쳐도 같은 언어 안에서 Python 3.9배, C++ 4.0배가 나온다. **언어를 바꿔서 얻는 3.3배보다 크다.**
- 재귀는 호출당 Python 72.7 ns, C++ 1.55 ns다. 깊이도 다르다 — Python 기본 한계는 1,000이고 올려야 쓸 수 있다.
- 순서를 지킨다. **입출력 → 라이브러리로 옮기기 → 복잡도 재설계 → 언어 교체.** 앞의 셋을 건너뛰고 언어부터 바꾸는 것이 가장 흔한 낭비다.
- **언어는 상수를 바꾸고 알고리즘은 지수를 바꾼다.** $O(n^2)$은 어느 언어로 옮겨도 $O(n^2)$이다.
- PyPy는 순수 Python 루프가 병목일 때만 후보다. 이 레포 환경에 없으므로 **수치는 싣지 않고 판단 기준만 남긴다.**
