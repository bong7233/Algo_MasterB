# 0-3 Python 내장 자료구조의 실제 비용

::: lead
`list`, `dict`, `set`, `tuple`, `str`이 메모리에서 실제로 어떻게 생겼고, 어느 연산이 조용히 $O(n)$인가.
:::

## 1. 문제

큐가 필요해서 리스트를 썼다. 뒤에 넣고 앞에서 꺼낸다. 논리적으로 완벽하다.

```python title="시간 초과가 나는 BFS (조각)"
queue = [start]
while queue:
    cur = queue.pop(0)      # 앞에서 꺼낸다
    for nxt in graph[cur]:
        queue.append(nxt)   # 뒤에 넣는다
```

정점이 10만 개면 이 코드는 통과하지 못한다. `append`는 $O(1)$인데 `pop(0)`은 $O(n)$이기 때문이다. **둘 다 "원소 하나를 다루는 연산"으로 보이는데 비용이 다르다.** 코드만 봐서는 어느 쪽이 어느 쪽인지 알 수 없다.

같은 종류의 함정이 문자열에도 있다.

```python title="답을 만드는 두 가지 방법 (조각)"
s = ""
for x in items:
    s += str(x)         # 이게 위험한가?
```

"문자열은 불변이니 매번 전체를 복사한다. 그러니 $O(n^2)$이다"라는 설명이 널리 퍼져 있다. **측정하면 절반만 맞다.** 어느 절반이 맞는지 아는 것이 이 챕터의 목적이다.

내장 자료구조는 이름이 짧고 문법이 편해서 비용이 없는 것처럼 보인다. 비용은 전부 있고, 다만 보이지 않을 뿐이다.

## 2. `list` — 연속된 포인터 배열

### 2.1 무엇이 연속인가

Python의 `list`는 연결 리스트가 아니다. **포인터의 연속 배열**이다. 이름이 오해를 부른다.

```text nolines
   a = [10, 20, 30]

   list 객체      ob_size = 3
                  allocated = 4        <- 실제로 잡아 둔 슬롯
                  ob_item ---+
                             |
                             v
   포인터 배열   [ ptr, ptr, ptr, --- ]
                    |    |    |     ^
                    |    |    |     +-- 남는 슬롯 1개
                    v    v    v
   정수 객체       10   20   30        <- 각각 28바이트짜리 객체
```

두 가지가 따라온다. **인덱싱이 $O(1)$이다** — 시작 주소에 `i * 8`을 더하면 끝난다. 그리고 **원소는 값이 아니라 참조다** — 정수 하나가 28바이트 객체이고 리스트는 그 주소만 들고 있다.

📖 `sys.getsizeof(obj)` — 객체 자신이 차지하는 바이트 수. $O(1)$.
　 **참조하는 다른 객체의 크기는 포함하지 않는다.** 리스트라면 헤더와 포인터 배열의 크기이고, 원소 객체들의 크기는 빠져 있다.
　 쓰는 곳: 메모리 제한이 걸린 문제의 진단. C++ 대응: `sizeof`는 정적 크기만 준다 — `vector`의 `sizeof`는 원소 수와 무관하게 24바이트다.

### 2.2 언제 커지는가

리스트는 꽉 찰 때마다 더 큰 배열을 새로 잡고 통째로 옮긴다. 그 시점을 `getsizeof`의 계단이 그대로 드러낸다.

::: perf
빈 리스트에 `append`를 반복하며 크기가 바뀌는 순간만 찍은 것이다. 빈 리스트의 헤더는 56바이트이고, 포인터 하나는 8바이트다.

| 원소 수 | `getsizeof` | 확보된 슬롯 | 직전 대비 |
|---|---|---|---|
| 1 | 88 | 4 | +4 |
| 5 | 120 | 8 | +4 |
| 9 | 184 | 16 | +8 |
| 17 | 248 | 24 | +8 |
| 33 | 376 | 40 | +8 |
| 41 | 472 | 52 | +12 |
| 77 | 792 | 92 | +16 |
| 109 | 1080 | 128 | +20 |
| 173 | 1656 | 200 | +28 |

> (Linux x86-64 / CPython 3.13 실측. 측정 스크립트는 `tools/bench/py_list_growth.py` 다.)
:::

읽는 법이 있다. **슬롯 수의 증가폭 자체가 늘어난다.** 4 → 8 → 16 → 24 → 40 → 52 → 92 → 128 → 200이다. 두 배씩은 아니고 대략 1.125배씩 늘린다.

::: deep
CPython의 과할당 규칙은 새 크기를 `n + (n >> 3) + 6` 근처로 잡고 4나 8의 배수로 맞추는 식이다. `n >> 3`이 곧 12.5%다.

두 배로 늘리지 않는 이유가 있다. 두 배 정책은 원소가 100만 개일 때 200만 개짜리 배열을 잡아 절반을 놀린다. 12.5%면 낭비가 훨씬 적다. 대신 재할당 횟수가 늘어난다.

그런데도 `append`가 **분할 상환 $O(1)$**인 것은 변하지 않는다. 증가폭이 현재 크기에 비례하기 때문이다. 크기 $n$까지 가는 동안의 총 복사량이 $n$에 비례하는 등비급수라 원소 하나당 상수로 나뉜다. 증가폭이 상수(예: 매번 +8)라면 이야기가 달라진다 — 재할당 횟수가 $n/8$번이고 총 복사량이 $O(n^2)$이 된다. **비율로 늘리는가 상수로 늘리는가가 갈림길이다.**

`list.append`의 상수를 더 줄이고 싶으면 크기를 미리 아는 경우 `[0] * n`으로 한 번에 잡는다. 재할당이 0번이다. C++의 `reserve`에 해당하고, 그쪽은 [0-6 C++ 컨테이너 세트](#/0-6)에 있다.
:::

### 2.3 앞쪽 연산이 $O(n)$인 이유

연속 배열이라는 사실에서 곧바로 나온다. **앞에 넣으려면 뒤의 모든 원소를 한 칸씩 밀어야 한다.**

```text nolines
   insert(0, 99)

   before   [ 10, 20, 30, 40, -- ]
                 \    \    \    \        <- n개를 전부 오른쪽으로 옮긴다
                  v    v    v    v
   after    [ 99, 10, 20, 30, 40 ]
```

`deque`는 다른 구조다. 고정 크기 블록들을 양방향 연결 리스트로 엮어 두고, 양 끝 블록에만 손을 댄다. 그래서 양쪽 끝이 $O(1)$이다. 대신 **인덱싱이 $O(n)$**이다 — 블록을 세어 가야 한다.

::: perf
| 연산 (10만 회) | 시간 | 배수 |
|---|---|---|
| `list.insert(0, x)` | 1.326초 | 기준 |
| `deque.appendleft(x)` | 0.0075초 | **177배 빠름** |
| `list.append(x)` | 0.0053초 | 248배 빠름 |
| `list.pop(0)` | 0.738초 | 기준 |
| `deque.popleft()` | 0.0045초 | **165배 빠름** |

정말 $O(n^2)$인지 확인하려면 n을 두 배로 늘려 보면 된다.

| n | `insert(0, x)` 총 시간 | 직전 대비 |
|---|---|---|
| 25,000 | 0.081초 | |
| 50,000 | 0.327초 | ×4.0 |
| 100,000 | 1.325초 | ×4.0 |
| 200,000 | 5.873초 | ×4.4 |

> (같은 환경·같은 스크립트.)

**n이 2배가 될 때 시간이 4배다.** 이것이 $O(n^2)$의 정의다. 복잡도 표기를 실측으로 확인하는 가장 값싼 방법이 이 표다.
:::

📖 `collections.deque([iterable])` — 양쪽 끝 삽입·삭제가 $O(1)$인 양방향 큐.
　 `append`, `appendleft`, `pop`, `popleft`가 전부 $O(1)$. 대신 `d[i]` 인덱싱이 $O(n)$이고 슬라이싱은 아예 안 된다.
　 쓰는 곳: BFS의 큐([IV-3](#/iv-3)), 슬라이딩 윈도우([VI-3](#/vi-3)), 명령 버퍼([II-5](#/ii-5)).
　 C++ 대응: `std::deque` — 이쪽은 인덱싱도 $O(1)$이다. 구조가 다르다.

::: warn
`deque`가 언제나 낫다는 뜻이 아니다. **빈 `deque`는 760바이트, 빈 `list`는 56바이트다.** 작은 컨테이너를 수만 개 만드는 상황이라면 이 차이가 지배한다.

판단 기준은 하나다. **앞쪽에 손을 대는가.** 뒤에서만 넣고 빼면(스택) `list`가 낫다. 앞뒤 양쪽을 쓰면(큐) `deque`다. 중간에 자주 넣고 뺀다면 둘 다 답이 아니고 자료구조를 다시 골라야 한다.
:::

::: pitfall
- **`list.pop()`과 `list.pop(0)`은 완전히 다른 연산이다.** 인자 없는 쪽은 $O(1)$, `0`을 주는 쪽은 $O(n)$이다. 글자 하나 차이로 복잡도가 바뀐다.
- **`del a[0]`도 `a.pop(0)`과 같은 비용이다.** 문법이 달라도 하는 일이 같다.
- **`a.remove(x)`는 $O(n)$이다.** 값을 찾느라 한 번 훑고, 지운 뒤 밀면서 또 훑는다.
- **`x in a`는 리스트에서 $O(n)$이다.** `set`에서는 $O(1)$이다. 문법이 똑같아서 가장 놓치기 쉽다(§4.4).
:::

## 3. `tuple` — 불변이라 얻는 것

`tuple`은 크기가 고정된 `list`다. 차이가 셋 있다.

::: perf
| 원소 수 | `list` | `tuple` |
|---|---|---|
| 0 | 56 | 40 |
| 1 | 72 | 48 |
| 1,000 | 8,056 | 8,040 |

> (같은 환경, `tools/bench/py_dict_set_resize.py` 의 마지막 절.)
:::

**첫째, 조금 작다.** 여유 슬롯을 잡지 않으므로 딱 필요한 만큼이다. 1,000개에서 16바이트 차이니 크지는 않다.

**둘째, 해시 가능하다.** 이게 진짜 이유다. `dict`의 키와 `set`의 원소가 되려면 해시 가능해야 하고, 리스트는 안 된다.

```python title="좌표를 키로 쓰기 (조각)"
visited = set()
visited.add((3, 4))          # ✅ 튜플은 된다
# visited.add([3, 4])        # ❌ TypeError: unhashable type: 'list'
```

격자 문제에서 방문 표시를 `set`으로 할 때 이 성질이 필수다. 다만 격자가 작으면 2차원 리스트가 더 빠르다 — 해시 계산이 없기 때문이다.

**셋째, 의도를 드러낸다.** 튜플이면 "이건 안 바뀐다"가 코드에 적힌다. 좌표 `(r, c)`, 간선 `(비용, 정점)` 같은 것이 그렇다.

::: danger
불변인 것은 **튜플 자신**이지 그 안의 객체가 아니다.

```python title="마지막 줄은 실제로 예외를 던진다"
t = ([1, 2], 3)
t[0].append(9)      # 된다. 튜플이 가리키는 리스트는 가변이다
print(t)            # ([1, 2, 9], 3)
hash(t)             # TypeError: unhashable type: 'list'
```

리스트를 품은 튜플은 해시할 수 없다. 좌표를 `set`에 넣다가 이 예외가 나면 원소 중에 리스트가 섞인 것이다.
:::

## 4. `dict`와 `set` — 개방 주소법

### 4.1 충돌을 어떻게 처리하는가

해시 테이블은 키를 해시해 그 값으로 슬롯을 정한다. 두 키가 같은 슬롯을 원하면 **충돌**이다. 처리 방식은 크게 둘이다.

- **체이닝** — 슬롯마다 연결 리스트를 달고 충돌한 키를 이어 붙인다.
- **개방 주소법** — 다른 빈 슬롯을 찾아 옮겨 간다. 테이블 밖으로 나가지 않는다.

**CPython은 개방 주소법을 쓴다.** 슬롯 배열 하나만 있고 곁가지가 없어 캐시에 유리하다. 대신 테이블이 꽉 차면 빈 슬롯을 찾는 탐색이 길어져 급격히 느려진다. 그래서 채움률에 상한을 두고, 넘으면 테이블을 키운다.

::: perf
`getsizeof`의 계단이 그 시점이다.

| `dict` 원소 수 | 바이트 | | `set` 원소 수 | 바이트 |
|---|---|---|---|---|
| 5 | 224 | | 5 | 728 |
| 6 | 352 | | 19 | 2,264 |
| 11 | 632 | | 77 | 8,408 |
| 22 | 1,168 | | 307 | 32,984 |
| 43 | 2,264 | | 1,229 | 131,288 |
| 86 | 4,688 | | 4,915 | 524,504 |
| 171 | 9,304 | | 19,661 | 2,097,368 |
| 342 | 18,512 | | | |

> (같은 환경, `tools/bench/py_dict_set_resize.py`.)
:::

`dict`가 커지는 지점은 6 → 11 → 22 → 43 → 86 → 171 → 342로 **매번 약 2배**다. 슬롯이 8개일 때 6번째 원소에서, 16개일 때 11번째에서 커진다. 8의 2/3이 5.33이고 16의 2/3이 10.67이다. **채움률 2/3이 상한이다.**

`set`이 커지는 지점은 5 → 19 → 77 → 307 → 1,229로 **매번 약 4배**다. 상한도 다르다 — 슬롯 8개에 5번째, 32개에 19번째에서 커지므로 **3/5가 상한**이고, 늘릴 때는 네 배로 늘린다.

계단의 모양이 다르니 어느 쪽이 더 큰지는 **계단의 어디에 서 있느냐**에 달렸다. 원소 5개면 `set`이 728바이트, `dict`가 224바이트로 `set`이 세 배 넘게 크다. 원소 1,000개면 `set`이 32,984바이트, `dict`가 36,952바이트로 뒤집힌다. 어느 한쪽이 항상 작다는 규칙은 없다.

::: deep
리사이즈는 **테이블을 새로 잡고 모든 키를 다시 넣는 것**이다. 슬롯 위치가 테이블 크기의 나머지로 정해지므로 크기가 바뀌면 위치가 전부 바뀐다. 비용이 $O(n)$이다.

그런데도 `d[k] = v`가 **분할 상환 $O(1)$**인 것은 리스트와 같은 논리다. 크기가 배수로 늘어나므로 리사이즈 사이의 간격이 지수적으로 벌어지고, 총 재삽입 비용이 등비급수로 $O(n)$에 머문다. 원소 하나당 상수다.

같은 이유로 **크기를 미리 알면 미리 만드는 편이 낫다.** `dict.fromkeys(keys)`나 `set(iterable)`은 원소 수를 알고 시작하므로 중간 리사이즈를 건너뛴다.

이 계보는 여기서 끝나지 않는다. 테이블이 메모리에 안 들어가면 [XV-8 일관성 해싱](#/xv-8)의 문제가 되고, 원소가 있는지만 알면 될 때는 [XV-4 블룸 필터](#/xv-4)로 공간을 줄인다. 해시 테이블 자체의 전모는 [II-6 해시](#/ii-6)에 있다.
:::

### 4.2 해시가 무너지면 어떻게 되는가

$O(1)$은 **해시가 고르게 흩어진다는 전제** 위에 있다. 전제가 깨지면 어떻게 되는지는 재 볼 수 있다. 모든 키의 해시를 같은 값으로 만든 클래스로 4,000개를 넣는다.

::: perf
| | 시간 |
|---|---|
| 정상 해시 | 0.00028초 |
| 모든 키의 해시가 동일 | 0.787초 |
| | **2,793배 느림** |

> (같은 환경, `tools/bench/py_dict_set_resize.py`.)
:::

전부 한 슬롯을 원하니 삽입할 때마다 빈 자리를 찾아 훑는다. 삽입 하나가 $O(n)$이고 전체가 $O(n^2)$이다. **$O(1)$이 $O(n)$으로 바뀌었다.**

::: note
이것이 이론적 우려만은 아니다. 웹 서버가 요청 파라미터를 `dict`에 담을 때, 공격자가 해시가 충돌하도록 계산된 키를 수만 개 보내면 서버 한 대가 CPU를 다 쓴다. **해시 DoS**라고 부른다.

방어는 **해시 시드 무작위화**다. Python은 프로세스가 뜰 때마다 무작위 시드를 정해 문자열 해시에 섞는다. 공격자가 충돌 키를 미리 계산할 수 없다.

부작용이 하나 따라온다. `hash("abc")`는 **실행할 때마다 다른 값**이다. 재현이 필요하면 `PYTHONHASHSEED` 환경 변수로 고정한다. 문자열을 해시해 무언가를 결정하는 코드가 어제와 다르게 동작한다면 원인이 대개 이것이다.
:::

### 4.3 순회 순서

`dict`는 **삽입 순서를 유지한다.** Python 3.7부터 언어 명세다.

```python title="순회 순서 (조각)"
d = {}
for k in ("banana", "apple", "cherry"):
    d[k] = 1
list(d)                  # ['banana', 'apple', 'cherry']   <- 삽입 순서

del d["apple"]
d["apple"] = 1
list(d)                  # ['banana', 'cherry', 'apple']   <- 지웠다 넣으면 맨 뒤로
```

`set`은 다르다. **순서 보장이 없다.**

```python title="set 의 순서는 보장이 아니다 (조각)"
s = set()
for k in ("banana", "apple", "cherry"):
    s.add(k)
list(s)                  # ['cherry', 'apple', 'banana']   <- 삽입 순서가 아니다

list(set(range(10)))     # [0, 1, 2, ..., 9]   <- 정렬되어 보인다. 우연이다
```

::: danger
마지막 줄이 함정이다. `set(range(10))`은 정렬된 것처럼 나온다. **작은 정수의 해시가 자기 자신이기 때문**이다. `hash(7) == 7`이라 7번 슬롯에 들어가고, 순회하면 슬롯 순서대로 나온다.

이걸 보고 "`set`은 정렬해서 준다"로 배우면 다음 셋 중 하나에서 무너진다.

- 원소가 문자열이면 순서가 뒤죽박죽이다(위의 `banana` 예).
- 정수라도 테이블 크기보다 큰 값이 섞이면 나머지 연산 때문에 순서가 깨진다.
- 같은 코드가 실행할 때마다 다른 순서를 낸다(§4.2의 해시 시드).

**정렬이 필요하면 `sorted(s)`라고 쓴다.** $O(n \log n)$을 내는 대신 보장을 산다. 순서에 의존하는 코드가 "내 컴퓨터에서는 되는데"가 되는 전형적인 경로가 이것이다.
:::

### 4.4 포함 검사는 어디에 넣느냐가 전부다

`x in a`는 리스트와 집합에서 **문법이 완전히 같고 비용이 완전히 다르다.**

::: perf
20만 개짜리 컨테이너에 2,000번 포함 검사를 한 시간이다.

| | 시간 |
|---|---|
| `x in set` | 0.00079초 |
| `x in list` | 1.834초 |
| | **2,311배 느림** |

> (같은 환경, `tools/bench/py_dict_set_resize.py`.)
:::

`list` 쪽은 원소를 하나씩 비교하므로 $O(n)$이고, `set` 쪽은 해시로 슬롯을 한 번에 찾으므로 $O(1)$이다. 루프 안에 있으면 $O(n^2)$과 $O(n)$의 차이가 된다.

::: tip
**방문 배열을 `list`로 두고 `if nxt not in visited`를 쓰는 것**이 이 사고의 가장 흔한 형태다. BFS가 통과하지 못하는 두 번째 이유이고(첫 번째는 §2.3의 `pop(0)`), 둘 다 코드만 보면 멀쩡하다.

`visited`는 `set`으로 두거나, 정점 번호가 0부터 연속이면 `[False] * n` 불리언 리스트로 둔다. 후자가 더 빠르다 — 해시 계산조차 없이 인덱싱 한 번이다.
:::

## 5. `str` — 불변성의 대가

### 5.1 널리 퍼진 설명과 실측

문자열은 불변이다. `s += t`는 `s`를 고치는 것이 아니라 **새 문자열을 만들어 `s`가 그것을 가리키게 하는 것**이다. 그러면 매번 전체를 복사하니 루프에서 $O(n^2)$이라는 결론이 나온다.

재 보면 이렇다.

::: perf
10글자 조각을 이어 붙인다.

| 방식 | 5만 개 | 10만 개 | 20만 개 |
|---|---|---|---|
| `s += t` (참조 1개) | 0.0042초 | 0.0086초 | 0.0165초 |
| `s += t` (참조 2개) | 1.100초 | 4.756초 | 18.199초 |
| `''.join(parts)` | 0.0026초 | 0.0052초 | 0.0104초 |
| `io.StringIO` | 0.0035초 | 0.0066초 | 0.0130초 |

> (Linux x86-64 / CPython 3.13 실측. 측정 스크립트는 `tools/bench/py_str_concat.py` 다.)
:::

두 줄이 1,000배 넘게 갈린다. **같은 `s += t`인데 그렇다.** 그리고 그 위쪽 줄은 `join`과 겨우 1.6배 차이다.

증가율을 보면 정체가 나온다. 조각 수가 2배가 될 때 위쪽은 1.9배(선형), 아래쪽은 3.8배(제곱)다.

### 5.2 무엇이 갈랐는가

::: deep
CPython에는 문자열 이어 붙이기에 대한 특수한 최적화가 있다. `s = s + t` 또는 `s += t`를 실행할 때, **왼쪽 문자열의 참조 수가 1이면** 새 객체를 만들지 않고 기존 버퍼를 `realloc`으로 늘려 뒤에 이어 붙인다.

참조 수가 1이라는 것은 **`s`라는 이름 말고 그 문자열을 가리키는 것이 없다**는 뜻이고, 그러면 제자리에서 고쳐도 아무도 눈치채지 못한다. 불변성은 관측 가능한 성질에 대한 약속이지 메모리에 대한 약속이 아니다.

이 조건이 깨지는 순간이 두 번째 줄이다. 벤치마크는 `keep = s`로 참조를 하나 더 만들어 이 경로를 막았다. 실제 코드에서 조건이 깨지는 경우는 이렇다.

- 리스트나 딕셔너리에 중간 결과를 같이 담을 때
- 함수에 넘기는 등으로 참조가 살아 있을 때
- 다른 구현(PyPy 등)에서 돌릴 때 — **이 최적화는 CPython 구현 세부사항이지 언어 명세가 아니다**

::: warn
그래서 결론은 "`+=`를 써도 된다"가 아니다. **`+=`는 조건부로 빠르고, 그 조건은 코드에 안 보인다.** 한 줄 추가로 1,000배가 되는 코드는 위험하다.

`''.join(parts)`은 조건이 없다. 전체 길이를 먼저 재고 한 번에 잡아 한 번에 복사하므로 항상 $O(n)$이다. **보장된 것을 쓴다.**
:::
:::

### 5.3 표준 관용구

::: dual
```python title="조각을 모아 한 줄 만들기"
parts = []
for i in range(5):
    parts.append(str(i * i))

s = ' '.join(parts)
print(s)
print(len(s))
```
```cpp title="조각을 모아 한 줄 만들기"
#include <iostream>
#include <string>
#include <vector>
using namespace std;

int main() {
    vector<string> parts;
    for (int i = 0; i < 5; i++) {
        parts.push_back(to_string(i * i));
    }

    string s;
    for (size_t i = 0; i < parts.size(); i++) {
        if (i) s += ' ';
        s += parts[i];
    }
    cout << s << "\n";
    cout << s.size() << "\n";
    return 0;
}
```
:::

두 코드 모두 `0 1 4 9 16`과 `10`을 출력한다.

**복잡도:** 시간 $O(L)$ — L은 결과 전체 길이다. `join`은 조각들의 길이를 먼저 합해 버퍼를 한 번 잡고 각 조각을 한 번씩 복사하므로 전체 복사량이 L이다. 공간 $O(L)$ — 결과 버퍼 하나. 조각들을 담은 리스트가 따로 L만큼 더 든다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 가변성 | `str`은 불변 | `std::string`은 가변 |
| 이어 붙이기 | `+=`는 참조 수에 따라 갈린다 | `+=`는 항상 제자리 추가 (분할 상환 $O(1)$) |
| 표준 방법 | `''.join(parts)` | 루프로 `+=`, 또는 `reserve` 후 추가 |
| 한 글자 | 길이 1인 `str` | `char` — 다른 타입이다 |

C++의 `std::string`은 가변이라 이 함정이 없다. `+=`가 `vector`처럼 과할당된 버퍼에 덧붙이므로 분할 상환 $O(1)$이다. **Python에서 위험한 관용구가 C++에서는 표준 관용구**인 드문 지점이다.

::: pitfall
- **`s[0] = 'x'`는 안 된다.** `TypeError`다. 문자열의 한 글자를 바꾸려면 `list(s)`로 풀어 고치고 `''.join()`으로 되돌린다.
- **`s.replace(...)`는 새 문자열을 만든다.** 원본은 그대로다. `s.replace('a','b')`만 쓰고 결과를 안 받으면 아무 일도 일어나지 않는다.
- **`+` 두 개짜리는 아무 문제 없다.** `a + b + c`처럼 고정된 개수를 붙이는 것은 루프가 아니라서 $O(n^2)$이 될 수 없다. 위험한 것은 **루프 안의 누적**뿐이다.
- **`s in t`는 부분 문자열 검사다.** 리스트의 `in`과 의미가 다르다. 비용은 최악 $O(|s| \times |t|)$이고, 진짜 문자열 검색은 [IX-7 문자열 매칭](#/ix-7)의 KMP다.
:::

## 6. 한 장 요약표

| 연산 | `list` | `deque` | `dict` / `set` | `str` |
|---|---|---|---|---|
| 인덱싱 `a[i]` | $O(1)$ | $O(n)$ | — | $O(1)$ |
| 키 조회 `d[k]` | — | — | $O(1)$ 평균 | — |
| 뒤에 추가 | $O(1)$ 분할상환 | $O(1)$ | $O(1)$ 분할상환 | 조건부 |
| 앞에 추가 | **$O(n)$** | $O(1)$ | — | — |
| 뒤에서 제거 | $O(1)$ | $O(1)$ | — | — |
| 앞에서 제거 | **$O(n)$** | $O(1)$ | — | — |
| 포함 검사 `x in c` | **$O(n)$** | $O(n)$ | $O(1)$ 평균 | $O(nm)$ |
| 값으로 제거 | $O(n)$ | $O(n)$ | $O(1)$ | — |
| 길이 `len` | $O(1)$ | $O(1)$ | $O(1)$ | $O(1)$ |
| 정렬 | $O(n \log n)$ | — | — | — |

굵은 칸이 사고가 나는 자리다. 셋 다 **문법이 짧아서 싸 보인다**는 공통점이 있다.

## 연습

::: quiz
전부 자료구조 선택이 본체인 문제다. 코드를 짜기 전에 **어느 연산이 몇 번 일어나는지**를 먼저 세어라.

**1. 백준 10845 큐 (실버 4)** — https://www.acmicpc.net/problem/10845
- 신호: `push`, `pop`, `front`, `back`이 명령으로 들어온다. 명령이 1만 개다.
- 상태: 큐 하나. 앞과 뒤 양쪽에 손을 댄다.
- 자료구조: `deque`다. `list`로 `pop(0)`을 쓰면 $O(n^2)$이고, 명령 1만 개면 아슬아슬하게 통과할 수도 있다. **통과 여부와 무관하게 §2.3의 표를 보고 골라라** — 명령이 10배가 되는 순간 갈린다.

**2. 백준 1764 듣보잡 (실버 4)** — https://www.acmicpc.net/problem/1764
- 신호: "듣지도 보지도 못한 사람". 두 명단의 교집합이고 각각 50만이다.
- 상태: 두 집합.
- 자료구조: `set` 두 개와 `&` 연산. `list`에 담고 이중 루프를 돌면 2,500억 번이라 §4.4의 2,311배가 그대로 나타난다. 출력이 사전순이라 마지막에 `sorted()`가 필요하고, **`set`의 순서를 믿으면 안 되는 이유**(§4.3)가 바로 여기서 드러난다.

**3. 백준 1927 최소 힙 (실버 2)** — https://www.acmicpc.net/problem/1927
- 신호: "가장 작은 값을 출력하고 배열에서 제거". 연산이 10만 번이다.
- 상태: 아직 안 꺼낸 수들의 모음. 전체 정렬이 아니라 **최솟값만** 필요하다.
- 자료구조: 힙이다. 매번 `sorted()`를 부르면 $O(n^2 \log n)$이고, `min()` + `remove()`도 $O(n^2)$이다. 힙은 [0-4](#/0-4)의 `heapq`이고 내부는 [II-8](#/ii-8)에 있다.

**4. 측정 과제.** `tools/bench/py_list_growth.py`의 마지막 절을 참고해, `s += t`를 참조 1개와 2개 각각으로 n을 2배씩 늘려 가며 재라. 어느 쪽이 2배, 어느 쪽이 4배로 늘어나는가. 그 배수가 각각 무슨 복잡도를 뜻하는가.

::: answer
**4.** 참조 1개는 n이 2배일 때 시간이 약 **2배**로 는다. 선형, 즉 $O(n)$이다. `realloc`으로 제자리 확장이 되므로 조각마다 상수 작업이다.

참조 2개는 약 **4배**로 는다. 제곱, 즉 $O(n^2)$이다. 매번 새 버퍼를 잡고 이미 만들어진 부분 전체를 복사하므로, 총 복사량이 $10 + 20 + 30 + \cdots$이라 $n^2$에 비례한다.

§5.1의 실측이 정확히 이 모양이다. 20만 개에서 0.0165초와 18.199초, 1,100배 차이다. **차이를 만든 것은 알고리즘이 아니라 참조 수 한 개**이고, 그래서 `join`을 쓴다.

n을 2배로 늘려 시간 배수를 보는 것은 복잡도 표기를 실측으로 검증하는 일반적인 방법이다. 2배면 $O(n)$, 4배면 $O(n^2)$, 8배면 $O(n^3)$이고, 2배보다 조금 크면 $O(n \log n)$이다.
:::
:::

## 요약

- `list`는 **포인터의 연속 배열**이다. 인덱싱이 $O(1)$인 것과 앞쪽 삽입이 $O(n)$인 것이 같은 사실에서 나온다.
- 리스트는 꽉 차면 약 **12.5%씩** 키운다. 두 배가 아닌데도 `append`가 분할 상환 $O(1)$인 것은 증가폭이 **현재 크기에 비례**하기 때문이다. 상수로 늘리면 $O(n^2)$이 된다.
- `insert(0, x)`는 `deque.appendleft`보다 **177배**, `pop(0)`은 `popleft`보다 **165배** 느리다. n을 2배로 늘리면 시간이 4배가 되는 것으로 $O(n^2)$을 확인할 수 있다.
- `dict`와 `set`은 **개방 주소법**이고 채움률이 각각 2/3, 3/5를 넘으면 커진다. 리사이즈는 $O(n)$이지만 배수로 늘어 분할 상환 $O(1)$이 유지된다.
- 해시가 전부 충돌하면 $O(1)$이 $O(n)$이 된다. 실측 **2,793배**다. 해시 시드 무작위화가 그 방어이고, 그래서 `hash("abc")`는 실행마다 다르다.
- `dict`는 삽입 순서를 유지하지만 **`set`은 순서 보장이 없다.** `set(range(10))`이 정렬되어 보이는 것은 작은 정수의 해시가 자기 자신이라서 생기는 우연이다. 정렬이 필요하면 `sorted()`라고 쓴다.
- `x in list`는 $O(n)$, `x in set`은 $O(1)$이다. **문법이 같고 비용이 2,311배 다르다.**
- `s += t`는 참조 수가 1일 때만 빠르다. 참조가 하나 더 생기면 **1,100배 느려지고** $O(n^2)$이 된다. 조건이 코드에 안 보이므로 `''.join()`을 쓴다.

**다음 절**: [0-4 Python 표준 라이브러리 세트](#/0-4) — 이 비용들을 우회하는 도구 상자. `heapq`, `bisect`, `Counter`, 그리고 `sort()`가 이미 정렬된 입력을 알아보는 방법.
