# 0-5 C++ 입출력과 기본 타입

::: lead
같은 알고리즘을 짰는데 C++에서 시간 초과가 나거나 답이 음수로 나오는 두 가지 이유.
:::

## 1. 문제

정수 100만 개를 읽어 합을 구한다. 알고리즘은 $O(n)$이고 더 줄일 것이 없다. 그런데 다음 두 줄짜리 차이로 실행 시간이 네 배 갈린다.

```cpp title="같은 알고리즘, 다른 시간 (조각)" {2,3}
int main() {
    ios_base::sync_with_stdio(false);   // 이 두 줄이 있고 없고
    cin.tie(nullptr);                   // 0.38초와 0.09초가 갈린다
    ...
}
```

같은 프로그램이 합을 `int`에 담으면 답도 틀린다. 100만 개의 값이 각각 10억 근처면 합은 $10^{15}$이고 `int`에는 안 들어간다. 채점기는 **틀렸습니다**를 돌려주고, 어디가 틀렸는지는 말해 주지 않는다.

두 사고 모두 알고리즘의 문제가 아니다. **언어의 기본값을 모르는 데서 나온다.** 이 절은 그 기본값을 하나씩 연다.

## 2. cin은 왜 느린가

📖 `ios_base::sync_with_stdio(false)` — C++ 스트림(`cin`/`cout`)과 C 스트림(`scanf`/`printf`)의 버퍼 공유를 끊는다.
   `main` 첫 줄에서, **첫 입출력 전에** 한 번만 부른다.
   쓰는 곳: 입력이 큰 모든 문제. 특히 [IV-1 그래프 표현](#/iv-1)처럼 간선을 수십만 줄 읽는 유형.
   Python 대응: 없다. Python은 `sys.stdin.readline`으로 함수 자체를 바꾼다([0-2](#/0-2)).

📖 `cin.tie(nullptr)` — `cin`이 읽기 전에 `cout`을 자동으로 flush 하던 연결을 끊는다.
   읽기와 쓰기를 **번갈아** 하는 프로그램에서만 효과가 있다.
   쓰는 곳: 질의를 하나 읽고 답을 하나 출력하는 유형.

기본 상태의 `cin`은 C의 `stdin` 버퍼와 **한 글자 단위로 보조를 맞춘다.** 표준이 그렇게 요구한다. `scanf`와 `cin >>`를 아무렇게나 섞어 써도 읽는 순서가 소스 순서와 같아야 하기 때문이다. 이 보장을 지키려면 C++ 스트림이 자기 버퍼를 채워 놓을 수 없다. 문자마다 C 쪽 버퍼를 들여다봐야 한다.

`sync_with_stdio(false)`는 그 보장을 포기한다. 그 순간 `cin`은 **자기 버퍼를 통째로 채워 놓고** 거기서 파싱한다. 시스템 콜 횟수가 아니라 **글자당 간접 호출 횟수**가 줄어드는 것이 속도의 정체다.

::: perf
정수 100만 개(각 10자리 이하)를 읽어 합을 구하는 데 걸린 시간.

| 방식 | 시간 | 기본 대비 |
|---|---|---|
| `cin` (기본) | 0.379초 | 1.0배 |
| `cin` + `sync_with_stdio(false)` + `tie(nullptr)` | 0.094초 | **4.0배 빠름** |
| `scanf` | 0.120초 | 3.2배 빠름 |
| Python `input()` | 1.047초 | |
| Python `sys.stdin.readline` | 0.193초 | |

읽기와 쓰기를 **번갈아** 하면(1개 읽고 1개 쓰기 × 100만) `tie`가 따로 드러난다.

| 방식 | 시간 |
|---|---|
| 동기화 해제, `tie` 그대로 | 0.835초 |
| 동기화 해제 + `tie(nullptr)` | 0.167초 |

> (Linux x86-64 / CPython 3.13 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 측정 스크립트는 `tools/bench/cpp_io_sync.cpp`, `tools/bench/cpp_io_sync_py.py`, `tools/bench/cpp_io_tie.cpp` 이고 러너는 `tools/bench/cpp_io_sync_run.sh` 다.)

주목할 것은 **동기화를 끈 `cin`이 `scanf`보다 빠르다**는 점이다. `scanf`는 매 호출마다 형식 문자열 `"%d"`를 런타임에 해석하지만 `cin >> x`는 `x`의 타입이 컴파일 시점에 정해져 그 해석이 없다.
:::

::: danger
`sync_with_stdio(false)` 뒤에 `printf`와 `cout`을 섞으면 **출력 순서가 무너진다.** 소스에 적힌 순서대로

```cpp title="동기화를 끈 뒤 두 스트림을 섞는다 (조각)"
printf("printf: 1\n"); cout << "cout: 2\n";
printf("printf: 3\n"); cout << "cout: 4\n";
```

를 실행한 실제 출력은 이렇다.

```console
cout: 2
cout: 4
printf: 1
printf: 3
```

두 스트림이 각자 버퍼를 들고 있다가 프로그램이 끝날 때 따로 비우기 때문이다. 파일로 리다이렉트해도 같다. ==동기화를 껐으면 출력은 한쪽으로 통일한다.== 재현 코드는 `tools/bench/cpp_io_tie.cpp mix` 다.
:::

::: warn
`sync_with_stdio(false)`는 **첫 입출력보다 먼저** 불러야 한다. 이미 읽기 시작한 뒤에 부르면 표준이 동작을 정의하지 않는다. 그리고 이 설정은 `cin`에만 걸리는 것이 아니라 C++ 스트림 전체에 걸린다.

멀티스레드에서 `cout`을 여러 스레드가 쓰는 코드에도 손대지 마라. 동기화를 끄면 스트림 접근이 스레드 안전에서 벗어난다. 이 문제는 [XI-3 락과 락프리](#/xi-3)에서 다룬다.
:::

## 3. `endl`은 개행이 아니다

`endl`은 개행 문자를 넣고 **거기서 버퍼를 비운다**(flush). flush는 커널에 쓰기를 요청하는 일이다. 줄마다 하면 줄마다 시스템 콜이다.

::: perf
정수 100만 줄을 파일로 출력한 시간.

| 방식 | 시간 | 배수 |
|---|---|---|
| `cout << i << endl` | 0.674초 | 10.1배 |
| `cout << i << '\n'` | 0.067초 | 1.0배 |

> (Linux x86-64 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 측정 스크립트는 `tools/bench/cpp_endl_flush.cpp`. 출력을 `/dev/null`이 아니라 실제 파일로 보냈다 — `/dev/null`은 커널이 쓰기를 버려서 flush 비용이 실제보다 작게 나온다.)
:::

그렇다고 `endl`이 쓸모없는 것은 아니다. **버퍼에 있는 출력은 프로그램이 비정상 종료하면 사라진다.** 크래시 직전에 찍은 로그가 화면에 안 남는 원인이 대개 이것이다. 대화형으로 서버와 주고받는 문제, 그리고 죽을 수 있는 코드의 진단 출력에는 flush가 필요하다.

**규칙은 단순하다. 기본은 `'\n'`, flush가 필요한 자리에만 `endl`이나 `cout.flush()`.** `"\n"`(큰따옴표)보다 `'\n'`(작은따옴표)이 낫다 — 앞은 문자열이라 널 종료를 찾아 길이를 재고 뒤는 문자 하나다.

## 4. 빠른 입력의 관용구

두 언어의 기본 입력이 왜 느린지는 원인이 다르다. C++은 **동기화**, Python은 **줄마다 만들어지는 객체와 프롬프트 처리**다. 고치는 방법도 다르다.

::: dual
```python title="정수 n개를 읽어 합 구하기 — 빠른 입력"
import sys

def main():
    data = sys.stdin
    n = int(data.readline())
    total = 0
    for _ in range(n):
        total += int(data.readline())
    print("total =", total)

main()
```
```cpp title="정수 n개를 읽어 합 구하기 — 빠른 입력"
#include <iostream>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(nullptr);
    int n;
    cin >> n;
    long long total = 0;
    for (int i = 0; i < n; ++i) {
        int x;
        cin >> x;
        total += x;
    }
    cout << "total = " << total << "\n";
    return 0;
}
```
:::

**복잡도:** 시간 $O(n)$ — 각 정수를 정확히 한 번 파싱한다. 공간 $O(1)$ — 한 번에 정수 하나만 들고 있고 배열에 쌓지 않는다. 상수가 이 절의 주제다. 같은 $O(n)$이 4배 갈린다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 느린 기본 입력 | `input()` — 프롬프트 처리 + 개행 제거 | `cin` — C stdio와의 문자 단위 동기화 |
| 고치는 법 | `sys.stdin.readline`으로 함수를 바꾼다 | 함수는 그대로 두고 `sync_with_stdio(false)`로 설정을 바꾼다 |
| 개행 | `readline()`은 `'\n'`을 **남긴다.** `int()`는 무시하지만 문자열은 `.rstrip()` 필요 | `>>`는 공백·개행을 먼저 건너뛰고 읽는다 |
| 누적 변수 | `total`은 임의 정밀도라 그냥 둔다 | `total`은 `long long`이어야 한다. `int`면 넘친다 |
| 한 번에 읽기 | `sys.stdin.buffer.read().split()` (0.168초) | 드물게 `fread` + 직접 파싱. 보통은 불필요 |

Python 쪽 상세는 [0-2 Python 입출력과 기본 타입](#/0-2)에 있다.

## 5. `int`가 넘치는 자리

| 타입 | 크기 | 범위 | 안전한 상한 |
|---|---|---|---|
| `int` | 4바이트 | 약 $-2.1 \times 10^9$ ~ $2.1 \times 10^9$ | 21억 |
| `long long` | 8바이트 | 약 $\pm 9.2 \times 10^{18}$ | 900경 |
| `unsigned int` | 4바이트 | 0 ~ 약 $4.3 \times 10^9$ | 43억 |
| `double` | 8바이트 | 정수는 $2^{53}$까지 정확 | 약 $9 \times 10^{15}$ |

넘치는 자리는 정해져 있다. **곱셈, 누적합, 그리고 좌표.**

::: dual
```python title="누적합이 int 범위를 넘는 순간"
a = [10**9] * 5
total = 0
for x in a:
    total += x
print("total =", total)
```
```cpp title="누적합이 int 범위를 넘는 순간"
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> a(5, 1000000000);
    int total = 0;
    for (int x : a) total += x;
    cout << "total = " << total << "\n";
    return 0;
}
```
:::

**복잡도:** 시간 $O(n)$, 공간 $O(1)$ — 원소를 한 번씩 더할 뿐이다. 복잡도는 같은데 **답이 다르다.**

```console
Python:  total = 5000000000
C++:     total = 705032704
```

여기가 두 언어가 정면으로 갈리는 지점이다. Python 정수는 자릿수가 모자라면 알아서 늘어나고, C++ `int`는 늘어나지 않는다. `705032704`는 $5 \times 10^9$에서 $2^{32}$를 뺀 값이다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 정수 범위 | 임의 정밀도. 메모리가 허락하는 한 무한 | 타입이 고정 폭. `int`는 32비트 |
| 넘칠 때 | 자릿수가 늘어난다. 대신 큰 수 연산이 느려진다 | **미정의 동작.** 값이 잘리거나 최적화가 코드를 바꾼다 |
| 대비 | 없어도 된다 | 상한을 손으로 계산해 `long long`을 고른다 |
| 비용 | 큰 정수는 연산마다 자릿수 처리 | `long long`은 64비트 레지스터라 `int`와 거의 같은 속도 |

::: pitfall
- **곱셈은 대입 전에 넘친다.** `long long ans = 1000000 * 1000000;`은 `long long`에 담아도 `-727379968`이다. 오른쪽이 `int × int`로 먼저 계산되고 그 결과가 대입된다. `1LL * 1000000 * 1000000`처럼 **한쪽을 먼저 넓혀라.**
- **`(lo + hi) / 2`.** 둘 다 20억 근처면 합이 넘어 음수 인덱스가 된다. `lo + (hi - lo) / 2`로 쓴다([0-11](#/0-11)).
- **`1 << 31`.** `1`은 `int`라 부호 비트를 침범한다. `1LL << 31` 또는 `1u << 31`을 쓴다. 비트마스크는 [III-3 비트마스크로 집합 다루기](#/iii-3)에서 다시 나온다.
- **좌표 제곱.** 좌표가 $10^5$면 `x*x + y*y`는 $2 \times 10^{10}$이다. 기하([X-5](#/x-5))에서 흔히 터진다.
- **`size()`는 부호가 없다.** `for (int i = 0; i < v.size() - 1; ++i)`는 `v`가 비었을 때 `v.size() - 1`이 `0 - 1`이 되어 약 $1.8 \times 10^{19}$로 돈다. 루프가 통째로 폭주한다.
:::

## 6. UB는 "쓰레기 값이 나온다"가 아니다

부호 있는 정수 오버플로에 대한 가장 흔한 오해는 **"넘치면 음수로 돌아간다"**이다. 관찰로는 자주 맞다. 하지만 표준은 그것을 정의하지 않았고, 컴파일러는 정의되지 않은 일이 **일어나지 않는다고 가정하고** 코드를 다시 쓴다.

두 함수를 g++ 13에서 `-O0`과 `-O2`로 각각 컴파일해 돌린 결과다.

```cpp title="UB 실험 (전문은 tools/bench/cpp_signed_overflow_ub.cpp)"
bool always_true(int x) {
    return x + 1 > x;          // 오버플로가 없다면 항상 참
}

int count_up_to(int n) {
    int cnt = 0;
    for (int i = 0; i <= n; ++i) {   // n == INT_MAX 면 끝날 수 없는 조건
        cnt = cnt + 1;
        if (cnt < 0) break;          // 넘치면 빠져나가려고 둔 가드
    }
    return cnt;
}
```

`x = INT_MAX`를 넣으면 `x + 1`은 `INT_MIN`이고 `INT_MIN > INT_MAX`는 거짓이다. 그런데 `always_true(INT_MAX)`는 **`-O0`에서도 `true`를 돌려준다.** 생성된 기계어를 보면 이유가 분명하다.

```text nolines
  -O0:  mov  %edi,-0x4(%rbp)     <- 인자를 스택에 저장하고
        mov  $0x1,%eax           <- 그냥 1 을 돌려준다. 덧셈도 비교도 없다
  -O2:  mov  $0x1,%eax           <- 같다
```

`x + 1 > x`는 **최적화를 끄든 켜든** 상수 `true`로 접힌다. "안전하게 `-O0`으로 돌리면 되지 않느냐"가 통하지 않는다는 뜻이다.

두 번째가 더 극적이다. `count_up_to(INT_MAX)`는 `-O0`에서 21억 번을 실제로 돌고 **5.28초** 뒤에 `-2147483648`을 돌려준다. `-O2`에서는 **0.002초**에 같은 값을 돌려준다. 루프가 통째로 사라졌기 때문이다.

```text nolines
  -O2 의 count_up_to 전문:
        test  %edi,%edi
        mov   $0xffffffff,%eax
        cmovs %eax,%edi          <- n 이 음수면 -1 로
        lea   0x1(%rdi),%eax     <- 답은 n + 1
        ret
```

컴파일러는 이렇게 추론했다. `i`는 오버플로하지 않는다(그렇게 가정해도 된다). 그러면 이 루프는 정확히 `n + 1`번 돈다. `cnt`도 오버플로하지 않으므로 `cnt < 0`은 절대 참이 아니다. **그러니 가드를 지우고 답을 `n + 1`로 계산하면 된다.**

==오버플로를 막으려고 넣은 가드가, 오버플로가 없다는 가정 때문에 삭제되었다.== 이것이 UB가 부수는 방식이다. 값이 이상해지는 것이 아니라 **코드가 없어진다.**

::: deep
왜 표준은 이것을 정의하지 않았나. 정의해 버리면 위와 같은 추론이 전부 불법이 된다. `for (int i = 0; i <= n; ++i)`의 반복 횟수를 컴파일러가 `n + 1`로 확정할 수 없고, 루프 언롤링·벡터화·인덕션 변수 승격이 줄줄이 막힌다. 부호 있는 오버플로를 UB로 남긴 대가로 **정수 루프의 최적화 여지**를 산 것이다.

부호 **없는** 정수는 다르다. `unsigned`의 오버플로는 $2^{32}$로 나눈 나머지로 **정의되어 있다.** 해시 함수가 `unsigned`나 `uint64_t`로 곱셈을 굴리는 이유가 이것이다 — 넘치는 것이 버그가 아니라 설계다([II-6 해시](#/ii-6)).

필요하면 가정을 끌 수 있다.

- `-fwrapv` — 부호 있는 오버플로를 2의 보수 순환으로 **정의**한다. 최적화 일부를 포기하는 대신 예측 가능해진다.
- `-fsanitize=undefined` — 넘치는 순간 런타임에 잡아 위치를 찍는다. 디버그 빌드 전용이다.

둘 다 근본 해법은 아니다. **타입을 제대로 고르는 것이 해법이다.**
:::

::: hist
1996년 Ariane 5 로켓의 첫 비행은 발사 37초 뒤 파괴됐다. 원인은 64비트 부동소수 수평 속도 값을 16비트 부호 있는 정수로 변환하는 코드였다. 값이 범위를 넘었고, 예외가 처리되지 않아 관성 항법 장치가 정지했다. 그 코드는 Ariane 4에서 검증된 것이었고 Ariane 4의 속도 범위에서는 넘칠 수 없었다.

==타입은 값의 크기가 아니라 값의 **가정**을 적어 놓는 자리다.== 가정이 바뀌면 검증된 코드도 틀린다.
:::

::: warn
임베디드·제어 코드에서 실제로 자주 터지는 오버플로는 **시간 값**이다. 밀리초를 `int`(32비트 부호 있음)에 담으면 약 24.8일 만에 넘고, `unsigned`여도 49.7일이다. 장비를 재부팅 없이 오래 돌리면 그때 처음 드러난다.

경과 시간을 비교할 때 `if (now > deadline)`이 아니라 `if (now - start > timeout)`으로 쓰면 부호 없는 순환에서도 옳게 동작한다. 타이머 자료구조는 [XI-8 타이머 휠과 지연 큐](#/xi-8)에서 다룬다.
:::

## 7. `auto`와 범위 기반 for

`auto`는 "아무 타입"이 아니라 **초기값에서 타입을 유도하라**는 지시다. 유도 규칙에 하나 함정이 있다. `auto`는 참조와 최상위 `const`를 **떼어 낸다.**

```cpp title="auto 의 유도 규칙 (조각)"
vector<int> v = {1, 2, 3};
auto        x = v[0];   // int        — 복사본. x 를 바꿔도 v 는 그대로다
auto&       r = v[0];   // int&       — 원본을 가리킨다
const auto& c = v[0];   // const int& — 복사 없이 읽기만
```

범위 기반 for에도 그대로 적용된다. `for (auto x : v)`는 **원소를 매번 복사한다.** `int`면 상관없지만 `string`이나 구조체면 복사 비용이 그대로 든다.

```cpp title="범위 기반 for 의 세 가지 형태 (조각)"
for (auto x : words)        { /* 복사. string 이면 매번 힙 할당 가능 */ }
for (const auto& x : words) { /* 읽기 전용. 기본으로 삼을 형태 */ }
for (auto& x : words)       { /* 수정. x 를 바꾸면 원본이 바뀐다 */ }
```

::: pitfall
- **`for (auto& x : v)` 안에서 `v.push_back`.** 재할당이 일어나면 순회 중인 참조가 전부 죽는다. [0-6 C++ 컨테이너 세트](#/0-6)의 주제다.
- **`vector<bool>`에는 `auto&`가 안 붙는다.** `vector<bool>`은 비트를 압축해 담는 특수화라 원소가 `bool&`가 아니라 프록시 객체다. `for (auto& b : bits)`는 컴파일되지 않는다. `for (auto b : bits)` 또는 애초에 `vector<char>`를 쓴다.
- **`auto`로 받은 `size()`.** `auto n = v.size();`의 `n`은 `size_t`(부호 없음)다. `n - 1`을 쓰기 전에 비었는지 확인하라.
- **`auto`가 정수 나눗셈을 숨긴다.** `auto ratio = a / b;`에서 `a`와 `b`가 `int`면 `ratio`도 `int`다. 0.5는 0이 된다.
:::

## 8. 어디에 쓰이는가

**로그 라이브러리의 flush 정책이 §3 그대로다.** 운영 시스템의 로거는 대개 줄마다 flush 하지 않고 버퍼에 모았다가 일정 크기나 주기로 내보낸다. 그러면 초당 수만 줄을 감당할 수 있지만 프로세스가 죽는 순간 마지막 몇 줄이 사라진다. 그래서 로그 레벨이 `ERROR` 이상일 때만 즉시 flush 하는 절충이 흔하다. **"성능이냐 사후 추적이냐"의 교환이고, `endl` 대 `'\n'`이 그 교환의 최소 형태다.** 버퍼가 넘칠 때의 대응은 [XI-7 이벤트 루프와 백프레셔](#/xi-7)에서 다룬다.

**타입 폭의 선택은 프로토콜 설계의 첫 결정이다.** 장비와 주고받는 메시지에서 시퀀스 번호를 16비트로 잡을지 32비트로 잡을지, 타임스탬프를 밀리초 32비트로 둘지 마이크로초 64비트로 둘지가 여기서 갈린다. 한 번 배포되면 바꾸기 어렵고, 넘치는 시점은 대개 배포 몇 달 뒤다. 메시지 파싱은 [II-2 문자열 처리](#/ii-2)에서 이어진다.

::: quiz
코드를 짜기 전에 **어느 타입에 담아야 하는지부터** 계산하라.

**1. 백준 15552 빠른 A+B (브론즈 4)** — https://www.acmicpc.net/problem/15552
- 신호: 문제 자체가 "입출력 방식이 느리면 시간 초과"라고 명시한다. 테스트 케이스 100만 줄.
- 상태: 없다. 한 줄 읽고 한 줄 쓴다.
- 왜 이 도구인가: 알고리즘이 없는 문제라 입출력 설정만 남는다. §2·§3의 두 설정을 각각 빼고 넣으며 시간을 직접 비교해 보라.

**2. 백준 10757 큰 수 A+B (브론즈 5)** — https://www.acmicpc.net/problem/10757
- 신호: 입력이 10000자리 정수다. `long long`으로도 안 된다.
- 상태: 자릿수 배열과 올림 하나.
- 왜 이 도구인가: Python은 그냥 `a + b`로 끝나고 C++은 자릿수 덧셈을 직접 짜야 한다. **두 언어의 정수 모델 차이가 문제 난이도를 바꾸는 지점**이다. 이 차이를 실제로 겪어 두면 §5의 표가 지식이 아니라 감각이 된다.

**3. 백준 2338 긴 자리 계산 (브론즈 1)** — https://www.acmicpc.net/problem/2338
- 신호: 덧셈·뺄셈·곱셈을 모두 큰 수로. 곱셈에서 자릿수가 두 배가 된다.
- 상태: 부호와 자릿수 배열.
- 왜 이 도구인가: `int × int`가 대입 전에 넘친다는 §5의 함정이 가장 크게 드러나는 형태다.

**4. 손으로 계산할 것.** `int x = 2000000000;`일 때 `x + x`, `x * 2`, `1LL * x + x`, `(long long)(x + x)` 네 표현의 값을 각각 예측하고 그 이유를 한 줄로 쓴 뒤 실제로 돌려 비교하라.

::: answer
`x + x`와 `x * 2`는 둘 다 `int` 연산이라 UB다. g++ 13 `-O2`에서 관찰되는 값은 `-294967296`이지만 **그 값에 기대면 안 된다.** §6이 보인 것처럼 최적화는 이 식을 근거로 코드를 다시 쓸 수 있다.

`1LL * x + x`는 왼쪽 곱셈이 `long long`이 되고, 그러면 오른쪽 덧셈도 `long long`으로 승격된다. `4000000000`이 정확히 나온다.

`(long long)(x + x)`는 **소용없다.** 괄호 안이 이미 `int` 연산으로 끝난 뒤 그 결과를 넓히는 것이라 `-294967296`이 그대로 넓혀진다. ==넓히기는 계산 **전에** 해야 한다.== 이 한 칸의 차이가 §5 첫 번째 함정의 전부다.
:::

## 요약

- `ios_base::sync_with_stdio(false)`와 `cin.tie(nullptr)`는 `cin`의 C stdio 동기화를 끊는다. 정수 100만 개 읽기가 0.379초에서 0.094초로 줄었다. 대신 `printf`와 섞으면 출력 순서가 무너진다.
- `endl`은 개행 + flush다. 줄마다 flush 하면 100만 줄에서 10배 느려진다. **기본은 `'\n'`, 진단 출력과 대화형에만 flush.**
- `int`는 21억, `long long`은 900경이 상한이다. 넘치는 자리는 **곱셈, 누적합, 좌표 제곱, `(lo+hi)/2`** 넷이 거의 전부다.
- **곱셈은 대입 전에 넘친다.** `1LL *`을 곱셈의 **앞**에 붙여라. 캐스팅을 나중에 하면 아무 소용이 없다.
- 부호 있는 오버플로는 순환이 아니라 **미정의 동작**이다. g++ 13은 `x + 1 > x`를 `-O0`에서도 상수 `true`로 접고, `-O2`에서는 오버플로 가드가 달린 루프를 통째로 지웠다.
- `auto`는 참조와 `const`를 뗀다. 범위 기반 for의 기본형은 `for (const auto& x : v)`다.
