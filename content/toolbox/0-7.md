# 0-7 C++ 알고리즘 함수 세트

::: lead
표준 알고리즘을 쓰는 이유는 짧아서가 아니라, 직접 짜면 지기 때문이다.
:::

## 1. 문제

교과서에 나오는 퀵소트를 그대로 짠다. 피벗은 마지막 원소, 재귀 두 번. 무작위 입력에서는 잘 돈다. 그런데 **이미 정렬된 입력**을 넣으면 이렇게 된다.

| 입력 | 순진한 퀵소트 | `std::sort` |
|---|---|---|
| 정렬된 10만 개 | 4.96초, 비교 **50억 회**, 재귀 깊이 10만 | 0.0010초 |
| 정렬된 20만 개 | **Segmentation fault** (스택 초과) | 0.0021초 |

> (Linux x86-64 / g++ 13 `-O2` 실측, 기본 스택 8MB. 측정 스크립트는 `tools/bench/cpp_introsort_guard.cpp`.)

피벗이 항상 최댓값이라 구간이 하나씩만 줄어든다. 비교는 $n(n-1)/2$회이고 재귀 깊이가 $n$이다. **정렬된 입력은 이상한 입력이 아니다.** 앞 단계에서 정렬해 넘긴 데이터, 시간순으로 쌓인 로그, 좌표 압축을 마친 배열이 전부 정렬된 입력이다.

`std::sort`는 같은 입력에서 무너지지 않는다. 이유가 이 절의 첫 주제다.

## 2. `sort`의 정체 — introsort

📖 `std::sort(first, last)` — 구간 `[first, last)`를 오름차순 정렬. 최악 $O(n \log n)$.
   **안정 정렬이 아니다.** 같은 값의 원래 순서가 보존되지 않는다.
   쓰는 곳: 거의 모든 곳. 좌표 압축([VI-5](#/vi-5)), 그리디 전처리([VI-2](#/vi-2)), 크루스칼([IX-4](#/ix-4)).
   Python 대응: `list.sort()` / `sorted()` — 이쪽은 **안정 정렬**이다. 반대다.

`std::sort`는 하나의 알고리즘이 아니라 셋의 합성이고, 이름이 **introsort**(introspective sort)다.

```text nolines
  sort(first, last)
    │
    ├─ 구간 크기 > 16 이고 깊이 여유 있음 ──▶ quicksort 분할 (평균이 가장 빠르다)
    │
    ├─ 재귀 깊이가 2*log2(n) 를 넘음 ───────▶ heapsort 로 전환 (최악을 O(n log n) 으로 묶는다)
    │
    └─ 구간 크기 <= 16 ────────────────────▶ 건드리지 않고 남긴다
                                             마지막에 전체를 삽입 정렬로 한 번
```

세 갈래가 각각 다른 문제를 푼다.

**퀵소트는 평균이 가장 빠르다.** 추가 메모리가 없고 안쪽 루프가 단순해 캐시에 잘 맞는다. 하지만 §1처럼 최악이 $O(n^2)$다.

**깊이 가드가 그 최악을 잘라 낸다.** 재귀 깊이가 $2\log_2 n$을 넘으면 그 구간을 힙 정렬로 넘긴다. 힙 정렬은 어떤 입력에서도 $O(n \log n)$이다. ==그래서 `std::sort`는 최악에도 이차가 될 수 없다.== 특정 입력을 골라 느리게 만드는 공격도 막힌다.

**삽입 정렬이 마무리를 맡는다.** 작은 구간은 정렬하지 않고 남겨 둔 뒤, 마지막에 배열 전체를 삽입 정렬로 한 번 훑는다. 이 시점의 배열은 "16칸 이내로만 어긋난" 상태이고, 삽입 정렬은 그런 배열에서 $O(n + \text{역순쌍})$이다. 재귀 호출 비용을 아끼면서 상수를 줄이는 설계다.

::: perf
같은 입력(무작위 정수 500만 개)에 대한 표준 함수들.

| 함수 | 시간 | `sort` 대비 |
|---|---|---|
| `sort` | 0.402초 | 1.0배 |
| `stable_sort` | 0.573초 | 1.43배 느림 |
| `nth_element` (중앙값 하나) | 0.034초 | **11.9배 빠름** |
| `partial_sort` (상위 100개) | 0.0033초 | **122배 빠름** |

입력 모양을 바꿔 `sort`만 다시 재면 §1의 주장이 확인된다.

| 입력 | `sort` |
|---|---|
| 무작위 500만 | 0.402초 |
| 이미 정렬된 500만 | 0.071초 |
| 역순 500만 | 0.052초 |
| 전부 같은 값 500만 | 0.054초 |

> (Linux x86-64 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 측정 스크립트는 `tools/bench/cpp_sort_bench.cpp`.)

**최악의 입력이라던 것들이 오히려 빠르다.** 정렬된 입력에서 퀵소트 분할은 여전히 불균형하지만, 깊이 가드가 곧바로 힙 정렬로 넘기고 이동이 거의 없어 무작위보다 빨리 끝난다. 순진한 구현이 50억 번 비교하던 그 입력이다.
:::

::: deep
비교 횟수를 직접 세면 두 구현의 차이가 수로 드러난다. 입력은 전부 **이미 정렬된 배열**이다.

| n | 순진한 퀵소트 | `std::sort` | 순진한 쪽 재귀 깊이 |
|---|---|---|---|
| 1,000 | 499,500 | 10,621 | 1,000 |
| 2,000 | 1,999,000 | 24,219 | 2,000 |
| 4,000 | 7,998,000 | 54,413 | 4,000 |
| 8,000 | 31,996,000 | 120,799 | 8,000 |

왼쪽 열은 `n`이 2배가 될 때마다 정확히 **4배**가 된다. $n(n-1)/2$의 모양이다. 오른쪽은 2.28배, 2.25배, 2.22배로 2배에 조금씩 붙는다. $n \log n$에서 $n$이 2배가 되면 $2n(\log n + 1)$이므로 배수는 $2(1 + 1/\log n)$이고, $n$이 커질수록 2에 수렴한다. **표의 배수 자체가 복잡도의 증거다.**

재귀 깊이 열도 봐야 한다. 순진한 쪽은 깊이가 $n$이라 $n = 200{,}000$에서 스택 8MB를 다 쓰고 죽는다. `std::sort`의 깊이는 $2\log_2 n$으로 묶여 있어 $n = 10^9$이어도 60 근처다. **깊이 가드는 성능 장치이면서 동시에 스택 안전 장치다.**
:::

## 3. 커스텀 정렬 — 비교자와 키

::: dual
```python title="점수 내림차순, 같으면 이름 오름차순"
students = [("bob", 90), ("amy", 95), ("cho", 90), ("dan", 95)]

students.sort(key=lambda s: (-s[1], s[0]))

for name, score in students:
    print(name, score)
```
```cpp title="점수 내림차순, 같으면 이름 오름차순"
#include <algorithm>
#include <iostream>
#include <string>
#include <vector>
using namespace std;

int main() {
    vector<pair<string, int>> students = {{"bob", 90}, {"amy", 95}, {"cho", 90}, {"dan", 95}};

    sort(students.begin(), students.end(), [](const auto& a, const auto& b) {
        if (a.second != b.second) return a.second > b.second;
        return a.first < b.first;
    });

    for (const auto& [name, score] : students) cout << name << " " << score << "\n";
    return 0;
}
```
:::

**복잡도:** 시간 $O(n \log n)$ — 비교 기반 정렬의 하한이고 두 구현 모두 이를 달성한다. 비교자 안에서 문자열을 비교하므로 실제로는 문자열 길이 $L$이 곱해져 $O(L n \log n)$이다. 공간은 `sort`가 $O(\log n)$(재귀 스택), Python `sort`는 $O(n)$(Timsort의 병합 버퍼)이다.

출력은 같다.

```console
amy 95
dan 95
bob 90
cho 90
```

| 언어 차이 | Python | C++ |
|---|---|---|
| 지정 방식 | **키 함수.** 각 원소를 비교 가능한 값으로 바꾼다 | **비교자.** 두 원소 중 앞이 먼저인지 답한다 |
| 호출 횟수 | 키는 원소당 **한 번**만 계산되고 저장된다 | 비교자는 비교마다 호출된다. $O(n \log n)$회 |
| 내림차순 | `reverse=True` 또는 키에 음수 | `>` 비교자 또는 `greater<>()` |
| 다중 키 | 튜플로 묶으면 사전식 비교가 공짜 | `if`를 층층이 쌓거나 `tie(a.x, a.y) < tie(b.x, b.y)` |
| 안정성 | `sort()`는 **안정**(Timsort) | `sort`는 **불안정**. 안정이 필요하면 `stable_sort` |
| 알고리즘 | Timsort — 실제 데이터의 정렬된 구간을 활용 | introsort — 최악 보장 우선 |

**키 함수와 비교자의 차이는 성능으로 나타난다.** 키가 비싼 계산이면(문자열 파싱, 거리 계산) Python은 한 번만 하고 C++은 매 비교마다 한다. C++에서 같은 효과를 얻으려면 키를 미리 계산해 `pair`로 묶어 정렬한다. 이 기법을 Python에서는 데코레이트-정렬-언데코레이트라 부르고, C++에서는 그냥 관용구다.

::: warn
`sort`가 불안정하다는 사실은 **다중 키 정렬을 두 번에 나눠 할 때** 드러난다.

```cpp
sort(v.begin(), v.end(), by_name);    // 먼저 이름순
sort(v.begin(), v.end(), by_score);   // ❌ 점수순으로 다시 — 이름 순서가 깨진다
```

Python에서는 이 방식이 동작한다. `list.sort()`가 안정이라 두 번째 정렬이 첫 번째 결과를 보존하기 때문이다. **같은 코드를 C++로 옮기면 조용히 틀린다.** C++에서는 비교자 하나에 두 조건을 다 넣거나 `stable_sort`를 쓴다.

같은 값이 섞였을 때 순서가 재현되지 않으면 채점기에서 **가끔 틀리는** 형태로 나타난다. 원인을 찾기 가장 어려운 종류다.
:::

📖 `std::stable_sort(first, last)` — 같은 값의 원래 순서를 보존하는 정렬. $O(n \log n)$.
   추가 메모리 $O(n)$을 쓴다. **메모리 할당에 실패하면 $O(n \log^2 n)$짜리 제자리 병합으로 물러난다.** 느려지지만 동작은 한다.
   쓰는 곳: 여러 기준으로 차례차례 정렬해야 할 때.
   Python 대응: `list.sort()` 자체가 이미 안정이라 따로 없다.

## 4. 이분 탐색 함수

📖 `std::lower_bound(first, last, x)` — `x` **이상**인 첫 원소의 이터레이터. $O(\log n)$ 비교.
📖 `std::upper_bound(first, last, x)` — `x` **초과**인 첫 원소의 이터레이터.
   구간이 **정렬되어 있어야 한다.** 아니면 결과가 정의되지 않는다.
   쓰는 곳: 좌표 압축([VI-5](#/vi-5)), LIS $O(n \log n)$ 구현([VIII-6](#/viii-6)), 매개변수 탐색([VII-3](#/vii-3)).
   Python 대응: `bisect.bisect_left` / `bisect.bisect_right`.

::: dual
```python title="정렬 배열에서 값의 개수 세기"
import bisect

a = [1, 3, 3, 3, 5, 7, 9]
x = 3

lo = bisect.bisect_left(a, x)
hi = bisect.bisect_right(a, x)

print("lower =", lo)
print("upper =", hi)
print("count =", hi - lo)
```
```cpp title="정렬 배열에서 값의 개수 세기"
#include <algorithm>
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> a = {1, 3, 3, 3, 5, 7, 9};
    int x = 3;

    int lo = lower_bound(a.begin(), a.end(), x) - a.begin();
    int hi = upper_bound(a.begin(), a.end(), x) - a.begin();

    cout << "lower = " << lo << "\n";
    cout << "upper = " << hi << "\n";
    cout << "count = " << hi - lo << "\n";
    return 0;
}
```
:::

**복잡도:** 시간 $O(\log n)$ — 매 단계 구간이 절반으로 줄고, 폭 $n$을 1까지 접는 횟수가 $\log_2 n$이다. 공간 $O(1)$. 다만 **비교 횟수가 $O(\log n)$인 것과 전체가 $O(\log n)$인 것은 다르다.** 다음 상자가 그 이야기다.

두 출력은 `lower = 1`, `upper = 4`, `count = 3`으로 같다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 반환값 | **인덱스** 정수 | **이터레이터.** 인덱스는 `- a.begin()`으로 뺀다 |
| 이름 | `bisect_left` / `bisect_right` | `lower_bound` / `upper_bound` |
| 없는 값 | 삽입 위치를 돌려준다. 존재 확인은 따로 | 같다. `it != end() && *it == x`로 확인 |
| 존재만 확인 | `a[i] == x` 직접 검사 | `binary_search(first, last, x)` |
| 비교자 지정 | `key=` (Python 3.10+) | 넷째 인자로 비교자 |

::: danger
`std::lower_bound`는 **정렬된 구간이면 어떤 이터레이터에도 쓸 수 있다.** `std::set`에도 컴파일된다. 그리고 $O(n)$이 된다.

| 호출 | 시간 (원소 20만, 질의 2000회) | 질의당 |
|---|---|---|
| `std::lower_bound(s.begin(), s.end(), x)` | 13.51초 | 6755 μs |
| `s.lower_bound(x)` | 0.0009초 | 0.5 μs |

> (Linux x86-64 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 측정 스크립트는 `tools/bench/cpp_lower_bound_set.cpp`.)

**약 12,000배다.** 이유는 [0-8 C++ 반복자·람다·비교자](#/0-8)의 주제인 반복자 카테고리에 있다. `std::lower_bound`는 구간의 중간으로 점프해야 하는데, `set`의 반복자는 점프를 못 하고 한 칸씩 걷는다. 비교는 여전히 $\log n$번이지만 이동이 $O(n)$이다.

==`set`과 `map`에는 반드시 **멤버 함수** `s.lower_bound(x)`를 써라.== 자유 함수는 컴파일 에러를 내지 않고 조용히 느려진다.
:::

## 5. 전부 정렬할 필요가 없을 때

📖 `std::nth_element(first, nth, last)` — `nth` 위치에 **정렬했을 때 올 원소**를 놓는다. 기대 $O(n)$.
   그 앞은 전부 그 값 이하, 뒤는 전부 이상이 되지만 **각각의 내부 순서는 정해지지 않는다.**
   쓰는 곳: 중앙값, K번째 수, 이상치 제거.
   Python 대응: 표준에는 없다. `heapq.nsmallest(k, it)`가 가장 가깝다.

📖 `std::partial_sort(first, middle, last)` — 앞에서 `middle - first`개만 제대로 정렬한다. $O(n \log k)$.
   쓰는 곳: 상위 K개 추출.
   Python 대응: `heapq.nlargest(k, it)`.

**전체 정렬이 필요 없는데 정렬하는 코드는 흔하다.** 500만 개 중 중앙값 하나가 필요할 때 `sort`는 0.402초, `nth_element`는 0.034초다. 상위 100개면 `partial_sort`가 0.0033초로 122배다.

$O(n)$의 근거는 이렇다. 퀵소트처럼 분할하되 **찾는 위치가 있는 쪽으로만** 재귀한다. 매번 절반씩 줄면 $n + n/2 + n/4 + \dots < 2n$이다. `std::nth_element`는 최악에도 이차가 되지 않도록 introsort와 같은 방식의 가드를 둔다.

::: warn
`nth_element` 뒤의 배열은 정렬되어 있지 않다. `nth` 앞뒤가 "이하/이상"으로 갈라져 있을 뿐이다. 중앙값을 얻은 뒤 정렬된 배열이 필요하다고 착각하면 결과가 어긋난다.

`n`이 짝수일 때의 중앙값처럼 **두 값이 필요하면 `nth_element`를 두 번** 부르거나, 두 번째 값은 `max_element(first, nth)`로 얻는다. 앞쪽이 전부 이하라는 성질을 쓰는 것이다.
:::

## 6. `unique`는 아무것도 지우지 않는다

가장 자주 틀리는 표준 함수다. `unique`는 **인접한** 중복을 앞으로 밀어 모으고 "여기까지가 유효하다"는 위치를 돌려줄 뿐, 컨테이너 크기를 바꾸지 않는다.

```console
정렬 후             size=11  [1, 1, 2, 3, 3, 4, 5, 5, 5, 6, 9]
unique 반환 위치: 앞에서 7번째
unique 만 호출      size=11  [1, 2, 3, 4, 5, 6, 9, 5, 5, 6, 9]
unique + erase         size=7  [1, 2, 3, 4, 5, 6, 9]
정렬 없이 unique+erase size=11  [3, 1, 4, 1, 5, 9, 2, 6, 5, 3, 5]
```

> (실행 출력. 재현 스크립트는 `tools/bench/cpp_unique_erase.cpp`.)

세 줄에서 세 가지를 읽는다. 첫째, `unique`만 부르면 **뒤쪽에 옛 값이 그대로 남는다.** 둘째, 크기를 줄이려면 `erase`를 붙여야 한다. 셋째, **정렬하지 않으면 인접 중복만 지운다** — 마지막 줄은 인접한 중복이 없어 하나도 지워지지 않았다.

```cpp title="erase-remove 관용구 (조각)"
sort(v.begin(), v.end());
v.erase(unique(v.begin(), v.end()), v.end());        // 중복 제거

v.erase(remove(v.begin(), v.end(), 0), v.end());     // 값 0 전부 제거
v.erase(remove_if(v.begin(), v.end(),
                  [](int x) { return x < 0; }), v.end());   // 조건부 제거
```

**`remove`도 지우지 않는다.** 표준 알고리즘은 이터레이터 두 개만 받으므로 컨테이너에 접근할 수 없고, 따라서 크기를 바꿀 수 없다. 원소를 옮기고 새 끝 위치를 돌려주는 것이 할 수 있는 전부다. ==알고리즘과 컨테이너를 분리한 설계의 대가이고, 이 분리 자체는 [0-8](#/0-8)의 주제다.==

## 7. 나머지 도구

| 함수 | 하는 일 | 복잡도 | 주의 |
|---|---|---|---|
| `accumulate(f, l, init)` | 누적 합 | $O(n)$ | **`init`의 타입이 결과 타입이다** |
| `max_element(f, l)` | 최댓값의 **이터레이터** | $O(n)$ | 값이 아니라 위치. `*max_element(...)` |
| `minmax_element(f, l)` | 최소·최대를 한 번에 | $O(n)$ | 비교 횟수가 각각 부르는 것보다 적다 |
| `fill(f, l, x)` | 구간을 `x`로 채움 | $O(n)$ | 2차원은 각 행마다 |
| `iota(f, l, start)` | `start`부터 1씩 증가로 채움 | $O(n)$ | `<numeric>` 헤더 |
| `reverse(f, l)` | 뒤집기 | $O(n)$ | |
| `rotate(f, mid, l)` | `mid`가 맨 앞에 오도록 회전 | $O(n)$ | |
| `count_if(f, l, pred)` | 조건을 만족하는 개수 | $O(n)$ | |
| `all_of` / `any_of` / `none_of` | 조건 검사 | $O(n)$ | 조기 종료한다 |
| `next_permutation(f, l)` | 사전순 다음 순열 | 분할상환 $O(1)$ | **정렬 상태에서 시작**해야 전부 돈다 |

::: danger
`accumulate`의 세 번째 인자는 초기값이면서 **누적 변수의 타입**이다.

```cpp
vector<int> v(5, 1000000000);
long long s1 = accumulate(v.begin(), v.end(), 0);     // ❌ 705032704
long long s2 = accumulate(v.begin(), v.end(), 0LL);   // ✅ 5000000000
```

`0`은 `int`라 내부 누적이 `int`로 일어난다. `long long`에 받아도 이미 넘친 값이 넓혀질 뿐이다. [0-5 §5](#/0-5)의 "넓히기는 계산 전에"가 그대로 재현된다. ==`accumulate`에는 `0LL`을 쓰는 것을 습관으로 만들어라.==
:::

`next_permutation`은 **현재 배열의 사전순 다음 순열**을 만들고 성공하면 `true`를 돌려준다. 이미 마지막(내림차순)이면 오름차순으로 되돌리고 `false`다. 그래서 모든 순열을 훑으려면 **정렬된 상태에서 시작해야 한다.** 정렬하지 않고 `do { ... } while (next_permutation(...))`를 돌리면 시작점 뒤쪽만 나온다. 순열 생성은 [III-2](#/iii-2)에서 재귀 구현과 함께 다룬다.

## 8. 어디에 쓰이는가

**중앙값 필터가 `nth_element`의 대표적인 실사용이다.** 영상에서 소금-후추 잡음을 제거할 때 각 픽셀을 주변 $3\times3$ 또는 $5\times5$ 창의 중앙값으로 바꾼다. 창마다 9개나 25개를 전부 정렬할 필요가 없고 가운데 하나만 있으면 된다. 픽셀이 100만 개면 이 선택이 그대로 프레임 레이트가 된다. 이미지 연산은 [XIII-8 이미지 기본 연산](#/xiii-8)에서 다룬다.

**상위 K개 추출은 `partial_sort`의 자리다.** 검색 결과 상위 10개, 로그에서 가장 느린 요청 20개, 후보 경로 중 비용이 낮은 K개. 전체를 정렬해 앞 K개만 쓰는 코드는 흔하고, 데이터가 커지는 순간 그 낭비가 드러난다. 경로 후보 선별은 [V-6 A\* 변형](#/v-6)에서 다시 나온다.

**`sort` + `unique` + `lower_bound` 세 줄이 좌표 압축의 전부다.** 값의 범위는 $10^9$인데 실제로 등장하는 값은 $10^5$개일 때, 값을 순서만 보존한 채 $0 \dots m-1$로 옮기는 기법이다. 세그먼트 트리와 스위핑이 이 전처리 위에서 돈다([VI-5 좌표 압축](#/vi-5), [IX-2 세그먼트 트리](#/ix-2)).

**1. 백준 2751 수 정렬하기 2 (실버 5)** — https://www.acmicpc.net/problem/2751

**2. 백준 11651 좌표 정렬하기 2 (실버 5)** — https://www.acmicpc.net/problem/11651
- 신호: y좌표 우선, 같으면 x좌표. 다중 키다.
- 상태: 점의 배열.
- 왜 이 도구인가: 비교자를 두 층으로 쌓는 연습. **두 번 정렬하는 방식으로 짜 보고 왜 C++에서 깨지는지 확인하라**(§3의 경고).

**3. 백준 18870 좌표 압축 (실버 2)** — https://www.acmicpc.net/problem/18870
- 신호: "자신보다 작은 서로 다른 좌표의 개수". 값의 범위는 $10^9$, 개수는 $10^6$.
- 상태: 정렬·중복 제거된 값 목록.
- 왜 이 도구인가: `sort` → `unique` + `erase` → `lower_bound` 세 단계가 그대로 답이 되는 원형 문제다. §6과 §4를 한 번에 쓴다.

**4. 손으로 계산할 것.** `vector<int> v = {5, 5, 1, 5, 1};`에 `sort` 없이 `v.erase(unique(v.begin(), v.end()), v.end());`를 적용하면 결과는 무엇인가. 그리고 `sort`를 먼저 하면 무엇인가. 두 결과의 크기가 다른 이유를 한 문장으로 쓰라.

::: answer
정렬 없이 적용하면 `{5, 1, 5, 1}`이다. 인접한 `5, 5`만 하나로 합쳐지고 떨어져 있는 `5`와 `1`은 그대로 남는다. 크기는 5에서 4로만 줄어든다.

`sort`를 먼저 하면 `{1, 1, 5, 5, 5}`가 되고, `unique` + `erase` 후 `{1, 5}`다. 크기는 2다.

이유 한 문장: ==`unique`는 전역 중복이 아니라 **인접 중복**만 제거하므로, 같은 값을 인접시키는 정렬이 전제 조건이다.== 그리고 이 성질은 결함이 아니라 설계다. 전역 중복 제거를 하려면 해시나 트리가 필요해 $O(n)$ 추가 메모리가 들지만, 인접 중복 제거는 한 번 훑기로 끝나고 추가 메모리가 $O(1)$이다. **정렬이 이미 되어 있다면 그쪽이 더 싸다.**
:::
:::

## 요약

- `std::sort`는 introsort다. 퀵소트로 달리다 재귀 깊이가 $2\log_2 n$을 넘으면 힙 정렬로 전환하고, 16개 이하 구간은 마지막에 삽입 정렬로 마무리한다. **그래서 최악에도 이차가 되지 않는다.** 순진한 퀵소트는 정렬된 20만 개에서 스택을 다 쓰고 죽었다.
- `sort`는 **불안정**이고 Python `sort()`는 **안정**이다. 다중 키를 두 번의 정렬로 나누는 방식은 Python에서만 동작한다.
- `stable_sort`는 안정성을 $O(n)$ 추가 메모리와 1.43배의 시간으로 산다.
- 전부 정렬할 필요가 없으면 `nth_element`(11.9배)나 `partial_sort`(122배)를 쓴다.
- **`unique`와 `remove`는 지우지 않는다.** 이터레이터만 받는 알고리즘은 컨테이너 크기를 바꿀 수 없다. `erase`를 붙이는 것이 관용구다.
- `set`·`map`에 `std::lower_bound`를 쓰면 컴파일은 되고 12,000배 느려진다. 멤버 함수를 써라.
- `accumulate`의 초기값은 누적 타입이다. `0`이 아니라 `0LL`.
