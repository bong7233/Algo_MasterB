# 0-6 C++ 컨테이너 세트

::: lead
컨테이너 선택은 복잡도 표가 아니라 메모리 배치가 정한다.
:::

## 1. 문제

원소 500만 개를 순회하며 전부 더한다. `vector`, `deque`, `list` 중 무엇에 담아도 알고리즘은 $O(n)$이고 명령어 수도 거의 같다. 실측은 이렇다.

| 컨테이너 | 시간 | `vector` 대비 |
|---|---|---|
| `vector<int>` | 0.0041초 | 1.0배 |
| `deque<int>` | 0.0046초 | 1.1배 |
| `list<int>` (순서대로 만든 것) | 0.0236초 | 5.8배 |
| `list<int>` (링크를 뒤섞은 것) | 0.8462초 | **206배** |

마지막 줄이 이 절의 존재 이유다. **복잡도 표에는 206배가 없다.** 셋 다 $O(n)$이고, 한 원소를 처리하는 데 드는 명령어도 몇 개 차이 나지 않는다. 갈리는 것은 그 명령어들이 **메모리의 어디를 찌르느냐**뿐이다.

"삽입이 $O(1)$이니까 `list`"라는 판단이 실전에서 거의 항상 틀리는 이유가 여기 있다.

## 2. 캐시 라인이 정하는 것

CPU는 메모리를 바이트 단위로 읽지 않는다. **캐시 라인**이라는 고정 크기 덩어리로 읽는다. x86-64에서 64바이트이고, `int` 하나가 4바이트이니 **한 번 읽으면 `int` 16개가 딸려 온다.**

```text nolines
  vector<int> — 연속 배치
  ┌────┬────┬────┬────┬────┬────┬────┬────┐
  │ 10 │ 20 │ 30 │ 40 │ 50 │ 60 │ 70 │ 80 │  <- 캐시 라인 하나에 16개가 실려 온다
  └────┴────┴────┴────┴────┴────┴────┴────┘
  0x1000 부터 연속. 다음 주소를 예측할 수 있다

  list<int> — 노드 배치
  ┌──────┬──────┬────┐   ┌──────┬──────┬────┐
  │ prev │ next │ 10 │──▶│ prev │ next │ 20 │  <- 노드 하나가 24바이트(+할당자 몫)
  └──────┴──────┴────┘   └──────┴──────┴────┘
  0x2000                 0x7f40                <- 주소는 할당 순서가 정한다
```

차이는 세 겹이다.

**첫째, 밀도.** `vector`는 캐시 라인 64바이트에 `int` 16개가 들어간다. `list`는 노드가 24바이트라 실제로 쓰는 값은 4바이트뿐이고, 라인 하나에 값이 2~3개 실린다. 같은 개수를 읽는 데 캐시 라인을 6배 넘게 소모한다.

**둘째, 예측.** CPU에는 **프리페처**가 있어 순차 접근을 감지하면 다음 라인을 미리 가져온다. `vector` 순회는 여기에 정확히 걸린다. `list`는 다음 주소가 현재 노드를 읽어야 나오므로 미리 가져올 대상을 알 수 없다. 이것을 **포인터 추적**(pointer chasing)이라 하고, 메모리 지연이 계산으로 가려지지 않고 그대로 드러난다.

**셋째, 순서.** 방금 만든 `list`는 노드 주소가 대체로 오르막이라 프리페처가 절반쯤 먹힌다(5.8배). 삽입·삭제를 반복해 오래 산 리스트는 노드가 힙 여기저기에 흩어진다. 그 상태를 재현한 것이 마지막 줄의 206배다.

::: perf
§1의 표를 만든 조건과 스크립트.

- 원소 500만 개, 값은 1..n. 네 컨테이너 모두 같은 값을 담았다.
- "링크를 뒤섞은 것"은 노드를 그대로 두고 연결 순서만 무작위로 다시 이었다. **노드 개수도 값도 같고 링크 순서만 다르다.**
- `vector` 0.82 ns/원소, `list`(뒤섞임) 169 ns/원소.

> (Linux x86-64 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 측정 스크립트는 `tools/bench/cpp_container_cache.cpp`.)

뒤섞은 쪽은 실행마다 0.65~0.91초로 흔들린다. 캐시와 TLB 적중이 그때그때의 메모리 배치에 좌우되기 때문이다. **이 흔들림 자체가 신호다.** 연속 배치 쪽은 0.0038~0.0041초로 거의 흔들리지 않는다.
:::

## 3. `vector`는 어떻게 자라는가

`vector`에는 두 개의 크기가 있다. `size()`는 지금 들어 있는 원소 수, `capacity()`는 재할당 없이 담을 수 있는 최대 수다. `push_back`은 `size() == capacity()`인 순간에만 새 메모리를 잡고 **전부 옮긴다.**

::: dual
```python title="용량이 언제 늘어나는가"
import sys


def capacity(v):
    return (sys.getsizeof(v) - sys.getsizeof([])) // 8


v = []
cap = capacity(v)
for i in range(1, 18):
    v.append(i)
    if capacity(v) != cap:
        cap = capacity(v)
        print(f"size={len(v):3d} capacity={cap:3d}")
```
```cpp title="용량이 언제 늘어나는가"
#include <cstdio>
#include <vector>
using namespace std;

size_t capacity(const vector<int>& v) { return v.capacity(); }

int main() {
    vector<int> v;
    size_t cap = capacity(v);
    for (int i = 1; i <= 17; ++i) {
        v.push_back(i);
        if (capacity(v) != cap) {
            cap = capacity(v);
            printf("size=%3zu capacity=%3zu\n", v.size(), cap);
        }
    }
    return 0;
}
```
:::

**복잡도:** `push_back` 한 번은 **분할상환 $O(1)$** — 용량이 찰 때마다 2배로 잡으면 $n$개를 넣는 동안 총 복사량이 $1 + 2 + 4 + \dots + n < 2n$이므로, 원소당 평균 상수 회 복사다. 다만 **개별 호출의 최악은 $O(n)$**이고 그 호출이 하필 실시간 루프 안에 걸리면 그때 지연이 튄다.

출력이 갈린다.

```console
Python:  size=  1 capacity=  4     C++:  size=  1 capacity=  1
         size=  5 capacity=  8           size=  2 capacity=  2
         size=  9 capacity= 16           size=  3 capacity=  4
         size= 17 capacity= 24           size=  5 capacity=  8
                                         size=  9 capacity= 16
                                         size= 17 capacity= 32
```

| 언어 차이 | Python `list` | C++ `vector` |
|---|---|---|
| 증가 방식 | 약 1.125배 + 상수. 원소 1000개에 재할당 **28번** | 2배(libstdc++). 원소 1000개에 재할당 **11번** |
| 용량 조회 | 공식 API 없음. `sys.getsizeof`로 역산 | `capacity()` |
| 미리 잡기 | 없다. `[None] * n`으로 만들어 채운다 | `reserve(n)` |
| 저장하는 것 | 객체 **포인터** 8바이트. 값은 딴 데 있다 | 값 자체. `vector<int>`는 4바이트씩 연속 |
| 표준 규정 | 구현 세부 | 배수는 표준이 정하지 않는다. 2배는 libstdc++의 선택 |

**저장하는 것이 다르다는 마지막 줄이 §2와 이어진다.** `vector<int>`를 순회하면 값이 캐시 라인에 실려 오지만, Python `list`를 순회하면 포인터를 따라 객체로 한 번 더 가야 한다. Python 쪽 상세는 [0-3 Python 내장 자료구조의 실제 비용](#/0-3)에 있다.

📖 `v.reserve(n)` — 용량을 미리 `n`으로 잡는다. `size()`는 바뀌지 않는다.
   개수를 미리 아는 경우 재할당과 복사를 전부 없앤다. 실측으로 1000개 삽입의 재할당이 11번에서 **0번**이 됐다.
   쓰는 곳: 입력 개수를 먼저 읽는 모든 문제, 인접 리스트 구성([IV-1](#/iv-1)).
   Python 대응: 없다. 크기를 알면 `[0] * n`으로 만들고 인덱스로 채운다.

::: tip
`reserve`와 `resize`는 다르다. `v.reserve(10)` 뒤의 `v[0]`은 **범위 밖 접근**이다. 원소가 없기 때문이다. `v.resize(10)`은 원소를 실제로 10개 만들고 `0`으로 채운다. 인덱스로 쓰려면 `resize`, `push_back`으로 채울 거면 `reserve`다.

용량을 되돌리는 방법은 `clear()`가 아니다. `clear()`는 `size()`만 0으로 만들고 메모리는 쥐고 있다. 반납하려면 `vector<int>().swap(v)` 또는 `v.shrink_to_fit()`이다.
:::

## 4. 재할당이 참조를 죽인다

재할당은 새 메모리를 잡고 옮기고 옛 메모리를 해제한다. **그 순간 옛 메모리를 가리키던 포인터·참조·이터레이터가 전부 죽는다.**

```cpp title="죽은 참조로 읽기 (전문은 tools/bench/cpp_iterator_invalidation.cpp)"
vector<int> v;
v.push_back(10);
v.push_back(20);
int& first = v[0];                              // 지금은 유효하다
for (int i = 0; i < 100; ++i) v.push_back(i);   // 이 사이에 재할당
printf("first=%d  v[0]=%d\n", first, v[0]);     // 여기서 죽은 메모리를 읽는다
```

`-O2`로 컴파일해 돌린 실제 출력이다.

```console
재할당 전: first=10  data=0x55c4e96482d0  capacity=2
재할당 후: data=0x55c4e9649520  capacity=128  주소 바뀜
죽은 참조 읽기: first=1548654152  (v[0] 의 진짜 값은 10)
```

`first`는 `10`이어야 하는데 `1548654152`가 나왔다. 값은 실행마다 다르다. **프로그램은 죽지 않았고 오류 메시지도 없다.** 같은 코드를 `-fsanitize=address`로 다시 빌드하면 정체가 드러난다.

```console
ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000030
READ of size 4 at 0x502000000030 thread T0
```

::: danger
무효화 규칙은 컨테이너마다 다르다. 외워야 하는 표다.

| 컨테이너 | 삽입 시 | 삭제 시 |
|---|---|---|
| `vector` | 재할당되면 **전부** 무효. 아니면 삽입 위치 뒤가 무효 | 삭제 위치 뒤가 무효 |
| `deque` | 이터레이터는 **전부** 무효. 양끝 삽입이면 **참조는 유효** | 양끝 삭제면 그 원소만, 중간 삭제면 전부 무효 |
| `list` | 무효화 없음 | 삭제된 원소만 무효 |
| `map` / `set` | 무효화 없음 | 삭제된 원소만 무효 |
| `unordered_map` / `unordered_set` | 리해싱되면 **이터레이터 전부** 무효. **참조는 유효** | 삭제된 원소만 무효 |

`deque`와 `unordered_map`의 "이터레이터는 무효, 참조는 유효"가 특히 함정이다. 노드(혹은 청크)는 그 자리에 있는데 이터레이터가 들고 있던 관리 정보가 낡기 때문이다.

**실전 규칙 하나로 줄이면:** ==컨테이너를 수정하는 루프 안에서는 이터레이터·참조·포인터를 루프 밖으로 들고 나가지 마라.== `erase`는 반환값을 받아 `it = v.erase(it);`로 이어 간다.
:::

## 5. 컨테이너 카탈로그

| 컨테이너 | 내부 | 조회 | 끝 삽입 | 중간 삽입 | 메모리(원소당 실측) |
|---|---|---|---|---|---|
| `array<T,N>` | 스택 위 고정 배열 | $O(1)$ | 불가 | 불가 | `sizeof(T)` 정확히 |
| `vector<T>` | 힙 위 연속 배열 | $O(1)$ | 분할상환 $O(1)$ | $O(n)$ | 4.3바이트 |
| `deque<T>` | 청크 배열 + 청크 목록 | $O(1)$ | $O(1)$ | $O(n)$ | 4.3바이트 |
| `list<T>` | 양방향 연결 | $O(n)$ | $O(1)$ | $O(1)$(위치를 알 때) | 32.1바이트 |
| `set` / `map` | 레드-블랙 트리 | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | 48.1바이트 |
| `unordered_set` / `unordered_map` | 버킷 배열 + 노드 체인 | 평균 $O(1)$ | 평균 $O(1)$ | 평균 $O(1)$ | 43.7바이트 |

> (원소당 메모리는 `int` 100만 개를 넣고 프로세스의 상주 메모리 증가분을 잰 값이다. Linux x86-64 / g++ 13 `-O2` 실측. 측정 스크립트는 `tools/bench/cpp_container_memory.cpp`. `map`은 `map<int,int>`, `set`은 `set<int>`인데 둘 다 48.1바이트인 것은 glibc 할당자가 요청 크기를 16바이트 단위로 올려 잡기 때문이다.)

**`int` 하나를 담는 데 `set`은 48바이트를 쓴다.** 값 4바이트에 색 정보와 포인터 세 개, 그리고 할당자 몫이 붙는다. 메모리 제한이 256MB인 문제에서 `set<int>`에 500만 개를 넣으려는 계획은 이 표에서 이미 실패한다.

### deque의 정체

`deque`는 "양끝 삽입이 $O(1)$인 배열"로 소개되지만 내부는 **청크의 배열**이다. libstdc++은 원소 크기가 작으면 512바이트 청크를 쓴다. 앞에 삽입할 때 전체를 미는 대신 앞쪽 청크를 하나 더 붙인다.

```text nolines
  map(청크 포인터 배열)
  ┌────┬────┬────┬────┐
  │ p0 │ p1 │ p2 │ p3 │
  └─┬──┴─┬──┴─┬──┴─┬──┘
    │    │    │    └──▶ [ ... ]                <- 각 청크는 연속 512바이트
    │    │    └───────▶ [ ... ]
    │    └────────────▶ [ ... ]
    └─────────────────▶ [ ... ]
```

그래서 `&d[0] + i`는 `d[i]`가 아니다. **`deque`의 원소는 전체가 연속이 아니다.** C 함수에 넘길 버퍼로 쓸 수 없고, 순회 성능이 `vector`에 1.1배로 붙는 것은 청크 안이 연속이기 때문이다.

### 어댑터: `stack`, `queue`, `priority_queue`

이 셋은 컨테이너가 아니라 **어댑터**다. 자기 저장소가 없고 다른 컨테이너를 감싸 인터페이스만 제한한다. `stack`과 `queue`의 기본 저장소는 `deque`이고, `priority_queue`는 `vector`다.

📖 `priority_queue<T>` — 이진 힙. `push` $O(\log n)$, `top` $O(1)$, `pop` $O(\log n)$.
   **기본이 최대 힙이다.** 최소 힙은 `priority_queue<T, vector<T>, greater<T>>`.
   쓰는 곳: 다익스트라([V-1](#/v-1)), 실시간 태스크 스케줄러([XI-5](#/xi-5)).
   Python 대응: `heapq` — 이쪽은 **최소 힙 전용**이다. 방향이 반대다.

::: warn
`stack`과 `queue`에는 이터레이터가 없다. 순회하려면 꺼내야 하고, 꺼내면 사라진다. **BFS에서 큐 내용을 찍어 보며 디버깅하려면 `deque`를 직접 쓰는 편이 낫다.** 손추적([0-11](#/0-11))의 관찰 대상을 코드로 옮길 때 이 제약이 걸린다.

`pop()`은 값을 돌려주지 않는다. `int x = q.front(); q.pop();` 두 줄로 쓴다. 예외 안전성 때문에 그렇게 설계됐다.
:::

## 6. 해시냐 트리냐

빈도를 세는 코드로 둘의 차이를 본다.

::: dual
```python title="단어 빈도 세기 — 정렬된 출력"
words = ["pear", "apple", "pear", "fig", "apple", "pear"]

count = {}
for w in words:
    count[w] = count.get(w, 0) + 1

for k in sorted(count):
    print(k, count[k])
```
```cpp title="단어 빈도 세기 — 정렬된 출력"
#include <iostream>
#include <map>
#include <string>
#include <vector>
using namespace std;

int main() {
    vector<string> words = {"pear", "apple", "pear", "fig", "apple", "pear"};

    map<string, int> count;
    for (const string& w : words) count[w] += 1;

    for (const auto& [k, v] : count) cout << k << " " << v << "\n";
    return 0;
}
```
:::

**복잡도:** 시간 $O(n \log m)$ — 단어 $n$개를 각각 트리에 넣고, 트리 높이가 서로 다른 단어 수 $m$에 대해 $O(\log m)$이다. 문자열 비교 비용이 곱해지므로 실제로는 $O(n L \log m)$($L$은 단어 길이)이다. 공간 $O(m)$. Python `dict`로 짜면 평균 $O(n)$이지만 정렬 출력에 $O(m \log m)$이 붙어 결과는 비슷하다.

두 출력은 같다.

```console
apple 2
fig 1
pear 3
```

| 언어 차이 | Python | C++ |
|---|---|---|
| 기본 사상 | `dict` = 해시. **삽입 순서**를 유지한다 | `map` = 트리(정렬), `unordered_map` = 해시(순서 없음) |
| 정렬 출력 | `sorted(count)`로 그때 정렬한다 | `map`이면 이미 정렬. `unordered_map`이면 따로 뽑아 정렬 |
| 없는 키 조회 | `count[k]`는 **KeyError**. `get(k, 0)`을 쓴다 | `count[k]`는 **0을 만들어 넣는다.** 조회가 삽입이다 |
| 존재 확인 | `if k in count` | `if (count.count(k))` 또는 `count.find(k) != count.end()` |

::: danger
`m[k]`는 **키가 없으면 만든다.** 값 타입의 기본값(정수면 0)으로 삽입하고 그 참조를 돌려준다. 그래서 다음 코드는 조회만 하는 것처럼 보이지만 `map`을 키로 채운다.

```cpp title="조회처럼 보이는 삽입 (조각)"
if (m[key] > 0) { ... }   // ❌ key 가 없으면 0 으로 삽입된다
if (m.count(key) && m.at(key) > 0) { ... }   // ✅ 삽입하지 않는다
```

인접 리스트를 `map<int, vector<int>>`로 들고 `if (!graph[v].empty())`를 돌리면 정점 수가 조용히 늘어난다. 순회 중이면 그 자체로 무효화 사고가 된다.

`at()`은 없으면 예외를 던지고 삽입하지 않는다. **읽기에는 `at`, 쓰기에는 `[]`.**
:::

::: perf
키 100만 개(짝수만), 질의 100만 번(절반은 없는 키).

| 자료구조 | 시간 | 질의당 | `unordered_map` 대비 |
|---|---|---|---|
| 직접 인덱스 `vector` | 0.0077초 | 7.7 ns | **13.8배 빠름** |
| `unordered_map` | 0.107초 | 107 ns | 1.0배 |
| 정렬 `vector` + `lower_bound` | 0.228초 | 228 ns | 2.1배 느림 |
| `map` | 1.459초 | 1459 ns | **13.7배 느림** |

> (Linux x86-64 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 측정 스크립트는 `tools/bench/cpp_container_lookup.cpp`.)

읽을 것이 셋 있다.

**`map`이 `unordered_map`의 13.7배다.** $O(\log n)$과 $O(1)$의 차이는 $\log_2 10^6 \approx 20$이지만 실제 배수는 그보다 작아야 정상이다. 더 벌어진 이유는 비교 횟수가 아니라 **매 비교가 다른 캐시 라인**이기 때문이다. 트리 노드는 힙에 흩어져 있고 §2의 포인터 추적이 20번 반복된다.

**정렬 `vector`가 `map`의 6배 이상 빠르다.** 같은 $O(\log n)$이고 비교 횟수도 같다. 다른 것은 배치뿐이다. 이분 탐색의 뒤쪽 절반은 좁은 구간을 훑어 같은 캐시 라인에 몰린다. ==삽입·삭제가 없고 정렬 순서만 필요하면 `map`이 아니라 정렬된 `vector`다.==

**같은 $O(1)$인 직접 인덱스가 `unordered_map`의 13.8배다.** 해시 계산, 버킷 인덱스 계산, 노드 포인터 추적, 키 비교가 전부 상수에 들어 있다. **키가 조밀한 정수면 배열을 써라.** 방문 배열을 `unordered_map<int,bool>`로 잡는 것이 느린 이유가 이것이다([IV-3 BFS](#/iv-3)).
:::

::: deep
`unordered_map`은 왜 이 이상 빨라지지 못하나. 표준이 **버킷 인터페이스**(`bucket_count`, `begin(n)`)와 **참조 안정성**을 요구하기 때문이다. 리해싱을 해도 원소의 주소가 바뀌면 안 되므로 구현이 사실상 **체이닝**으로 고정된다. 원소마다 노드를 따로 할당하고 포인터로 잇는 구조에서 캐시 지역성은 원리적으로 나올 수 없다.

개방 주소법(모든 원소를 한 배열에)으로 짜면 훨씬 빠르지만 그것은 표준 인터페이스를 만족하지 않는다. 성능이 중요한 코드베이스가 표준 대신 자체 해시 맵을 쓰는 이유가 이것이다. 개방 주소법의 원리는 [0-3](#/0-3)과 [II-6 해시](#/ii-6)에 있다.

`map`의 레드-블랙 트리는 [II-9 이진 탐색 트리와 균형 트리](#/ii-9)에서, 같은 문제를 디스크에서 푸는 B-Tree는 [XV-2](#/xv-2)에서 다룬다. **캐시 라인을 블록으로 바꾸면 `map`과 B-Tree는 같은 이야기다.**
:::

## 7. 무엇을 고를 것인가

| 상황 | 선택 | 이유 |
|---|---|---|
| 개수를 알고 인덱스로 접근 | `vector` + `reserve` | 재할당 0, 캐시 최적 |
| 크기가 컴파일 시점에 고정 | `array` | 힙 할당 없음 |
| 양끝에서만 넣고 빼기 | `deque` | 앞 삽입 $O(1)$, 순회도 준수 |
| 뒤에서만 넣고 빼기 | `vector` | `deque`보다 단순하고 빠르다 |
| 키가 조밀한 정수 | `vector`를 표로 | 13.8배 |
| 키가 희소하고 순서 불필요 | `unordered_map` | |
| 순서가 필요하고 삽입·삭제가 잦음 | `map` / `set` | |
| 순서가 필요하고 다 넣은 뒤 조회만 | 정렬 `vector` + `lower_bound` | `map`의 6배 |
| 최솟값·최댓값만 반복해서 꺼냄 | `priority_queue` | 전체 정렬 불필요 |
| 중간 삽입·삭제가 지배적이고 위치를 이미 알고 있음 | `list` | 이 조건이 전부 맞을 때만 |

**`list`의 조건이 셋 다 맞는 경우는 드물다.** "위치를 이미 알고 있다"가 특히 그렇다. 위치를 찾는 데 $O(n)$이 들면 삽입이 $O(1)$인 것은 의미가 없다.

## 8. 어디에 쓰이는가

**LRU 캐시가 `list` + `unordered_map`의 교과서적 조합이다.** 접근한 항목을 목록 맨 앞으로 옮기고 넘치면 맨 뒤를 버린다. 목록 중간에서 노드를 떼어 앞으로 붙이는 것이 $O(1)$이어야 하고, 그 노드의 위치를 키로 즉시 찾아야 한다. `list`의 이터레이터가 **삽입·삭제에도 무효화되지 않는다**는 §4의 성질이 여기서 값을 한다. 교체 정책 자체는 [XV-9 캐시 교체 정책](#/xv-9)에서 다룬다.

**대규모 그래프는 인접 리스트를 `vector<vector<int>>`가 아니라 CSR로 담는다.** 정점마다 `vector`를 하나씩 두면 정점 100만 개에 힙 할당이 100만 번이고 간선 순회가 §2의 포인터 추적이 된다. CSR은 모든 인접 정점을 하나의 연속 배열에 이어 붙이고 정점별 시작 위치만 따로 둔다. 같은 그래프, 같은 복잡도, 다른 배치다. [XI-10 그래프의 메모리 표현](#/xi-10)에서 다룬다.

전부 "복잡도는 같은데 자료구조 선택이 결과를 가르는" 유형이다.

**1. 백준 10828 스택 (실버 4)** — https://www.acmicpc.net/problem/10828
- 신호: 명령 5개를 그대로 구현. 명령 수 1만.
- 상태: 스택 하나. `top`은 마지막 원소, `empty`는 크기 0.
- 왜 이 자료구조인가: `stack`을 써도 되고 `vector`를 써도 된다. **`vector`로 짜 보고 `stack`으로 바꿔 보라.** 어댑터가 무엇을 막아 주고 무엇을 불편하게 하는지가 §5의 요점이다.

**2. 백준 10866 덱 (실버 4)** — https://www.acmicpc.net/problem/10866
- 신호: 앞뒤 양쪽에서 넣고 뺀다.
- 상태: 덱 하나.
- 왜 이 자료구조인가: `vector`로 앞 삽입을 흉내 내면 매번 $O(n)$이다. 청크 구조가 왜 필요한지가 여기서 나온다.

**3. 백준 10815 숫자 카드 (실버 5)** — https://www.acmicpc.net/problem/10815
- 신호: N, M이 각각 50만. "가지고 있는 숫자인가"를 M번 묻는다.
- 상태: 가진 카드의 집합.
- 왜 이 자료구조인가: 값 범위가 $\pm 10^7$이라 직접 인덱스 배열, `unordered_set`, 정렬 후 이분 탐색이 전부 가능하다. **셋 다 짜서 시간을 비교하라.** §6의 표를 직접 재현하는 문제다.

**4. 손으로 계산할 것.** `vector<int>`에 `reserve` 없이 원소 100만 개를 `push_back`했다. 재할당은 몇 번 일어났고, 그동안 **복사된 원소는 총 몇 개**인가. 그리고 그 총합이 100만의 몇 배인가.

::: answer
용량은 0에서 시작해 1, 2, 4, 8, …로 2배씩 간다. 100만은 $2^{19} = 524288$과 $2^{20} = 1048576$ 사이이므로 마지막 용량은 $2^{20}$이고 재할당은 **21번**이다.

복사된 원소의 총합은 재할당 직전의 크기들을 더한 것이다.

$$1 + 2 + 4 + \dots + 2^{19} = 2^{20} - 1 = 1048575$$

약 **105만 개**, 즉 원소 수의 **1.05배**다. 재할당이 무서워 보여도 총 복사량은 $2n$을 넘지 않는다. 이것이 분할상환 $O(1)$의 실체다. $1 + 2 + 4 + \dots$가 마지막 항의 2배를 넘지 않는 등비급수이기 때문이다.

**그런데도 `reserve`를 쓰는 이유는 총량이 아니라 분포다.** 21번의 재할당 중 마지막 한 번이 52만 개를 옮긴다. 그 한 번이 제어 주기 안에 걸리면 그 주기만 지연이 튄다. 평균이 좋다는 것과 최악이 없다는 것은 다른 말이고, 실시간 코드에서 문제가 되는 것은 언제나 최악이다([XI-5](#/xi-5)).
:::
:::

## 요약

- 같은 $O(n)$ 순회가 `vector`와 흩어진 `list` 사이에서 **206배** 갈린다. 원인은 캐시 라인 밀도, 프리페치 가능성, 노드 배치 순서 셋이다.
- `vector`는 용량이 찰 때마다 2배로 늘리고 전부 복사한다. 분할상환 $O(1)$이지만 개별 호출의 최악은 $O(n)$이다. 개수를 알면 `reserve`.
- **재할당은 그 컨테이너를 가리키던 참조·이터레이터를 전부 죽인다.** 죽은 참조를 읽어도 프로그램은 대개 죽지 않고 쓰레기를 돌려준다. 그래서 더 위험하다.
- `m[k]`는 **없으면 만든다.** 읽기에는 `at`이나 `count`를 쓴다.
- `int` 하나를 `set`에 담으면 48바이트다. 메모리 한도는 개수가 아니라 원소당 바이트로 계산한다.
- $O(\log n)$인 정렬 `vector`가 $O(\log n)$인 `map`보다 6배 빠르고, $O(1)$인 `unordered_map`보다 $O(1)$인 배열 첨자가 13.8배 빠르다. **복잡도가 같으면 배치가 정한다.**
