# 0-8 C++ 반복자·람다·비교자

::: lead
표준 알고리즘이 컨테이너를 모르고도 도는 구조, 그리고 그 구조가 조용히 무너지는 두 지점.
:::

## 1. 문제

정렬 비교자에 등호 하나를 더 붙인다. 내림차순도 오름차순도 아니고 그냥 실수다.

```cpp title="등호 하나 (조각)" {2}
vector<int> v(n, 42);                                  // 전부 같은 값
sort(v.begin(), v.end(), [](int a, int b) { return a <= b; });   // < 가 아니라 <=
```

`n`을 바꿔 가며 돌린 결과다. 정렬 구간 앞뒤에 감시용 칸을 16개씩 두고 그 값이 바뀌는지 확인했다.

| `n` | 결과 |
|---|---|
| 8, 16 | 아무 일도 없음 |
| **17** | **Segmentation fault** (3회 실행 모두) |
| 32, 100, 1000, 100000 | 죽지 않음. **정렬 구간 밖 16칸이 덮어써짐** |

> (Linux x86-64 / g++ 13 `-O2` 실측. 재현 스크립트는 `tools/bench/cpp_strict_weak_ordering.cpp`.)

가장 나쁜 줄은 세 번째다. **죽지 않았다.** 프로그램은 계속 돌고, 정렬 결과도 얼추 맞아 보이고, 대신 배열 밖의 남의 메모리 16칸이 조용히 바뀌었다. 그 메모리가 무엇이었는지에 따라 증상은 몇 시간 뒤 엉뚱한 곳에서 나타난다.

`<`와 `<=`의 차이가 왜 이런 결과를 내는지가 이 절의 마지막 주제다. 먼저 그 밑에 깔린 구조부터 본다.

## 2. 반복자 — 알고리즘과 컨테이너를 잇는 규약

알고리즘이 $M$개, 컨테이너가 $N$개 있다. 각 알고리즘이 각 컨테이너를 직접 알면 구현이 $M \times N$개 필요하다. 표준 라이브러리는 그 사이에 **반복자**라는 규약을 두어 $M + N$으로 줄였다. 알고리즘은 반복자만 알고, 컨테이너는 반복자만 제공한다.

```text nolines
  sort  find  accumulate  unique       <- 알고리즘: 반복자만 안다
    │     │       │         │
    └─────┴───┬───┴─────────┘
              │  반복자 (규약)
    ┌─────┬───┴───┬─────────┐
    │     │       │         │
  vector list    set     istream       <- 컨테이너: 반복자만 제공한다
```

대가가 두 개 있다. **첫째, 알고리즘은 컨테이너를 수정할 수 없다.** `unique`와 `remove`가 아무것도 지우지 못하는 이유가 이것이다([0-7 §6](#/0-7)). **둘째, 비용이 인터페이스에 드러나지 않는다.** 같은 함수 호출이 컨테이너에 따라 $O(\log n)$이거나 $O(n)$이다.

### 카테고리 다섯 종류

| 카테고리 | 할 수 있는 것 | 대표 |
|---|---|---|
| 입력(input) | 한 방향 진행, **한 번만** 읽기 | `istream_iterator` |
| 출력(output) | 한 방향 진행, 쓰기만 | `back_insert_iterator` |
| 순방향(forward) | 한 방향 진행, 여러 번 읽기 | `forward_list`, `unordered_map` |
| 양방향(bidirectional) | `++`와 `--` | `list`, `set`, `map` |
| 임의 접근(random access) | `it + n`, `it2 - it1`, `it[n]` | `vector`, `deque`, `array`, 포인터 |

위에서 아래로 갈수록 할 수 있는 일이 늘어난다. **표준 알고리즘은 필요한 최소 카테고리를 요구한다.** `find`는 입력 반복자로 충분하고, `sort`는 임의 접근을 요구한다. 그래서 `list.sort()`는 멤버 함수로 따로 있다 — `std::sort`에 `list`의 반복자를 넘기면 컴파일되지 않는다.

::: dual
```python title="한 번 쓰면 사라지는 반복자"
data = (int(x) for x in "1 2 3 4 5".split())

first = sum(data)
second = sum(data)

print("first =", first)
print("second =", second)
```
```cpp title="한 번 쓰면 사라지는 반복자"
#include <iostream>
#include <iterator>
#include <numeric>
#include <sstream>
using namespace std;

int main() {
    istringstream data("1 2 3 4 5");

    int first = accumulate(istream_iterator<int>(data), istream_iterator<int>(), 0);
    int second = accumulate(istream_iterator<int>(data), istream_iterator<int>(), 0);

    cout << "first = " << first << "\n";
    cout << "second = " << second << "\n";
    return 0;
}
```
:::

**복잡도:** 시간 $O(n)$ — 각 원소를 한 번씩 읽는다. 공간 $O(1)$ — 원소를 저장하지 않는 것이 입력 반복자의 요점이다. 그래서 두 번째 순회는 $O(1)$에 끝나고 답은 0이다.

두 출력이 같다.

```console
first = 15
second = 0
```

**두 언어가 같은 함정을 공유한다.** Python 제너레이터와 C++ 입력 반복자는 둘 다 "한 번만 읽을 수 있는" 자료원이다. 다 쓰고 나면 비어 있다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 한 번만 읽히는 것 | 제너레이터, `map`/`filter`/`zip`의 결과 | 입력 반복자(`istream_iterator` 등) |
| 다시 쓰려면 | `list(...)`로 실체화 | `vector`에 담아 두기 |
| 다 썼는지 확인 | 방법이 없다. 소진되면 조용히 빈 것이 된다 | 같다. 끝 반복자와 같아질 뿐 |
| 카테고리 개념 | 없다. 전부 단일 패스 | 다섯 단계로 구분되고 알고리즘이 요구 수준을 정한다 |

### 카테고리는 비용의 이름이다

📖 `std::distance(first, last)` — 두 반복자 사이의 원소 수.
   임의 접근이면 뺄셈 한 번, 아니면 `++`를 세면서 걷는다.
   Python 대응: 없다. `len()`이 컨테이너에게 직접 묻는다.

| 호출 | 시간 (원소 20만, 500회) | 회당 |
|---|---|---|
| `distance(v.begin(), v.end())` — `vector` | 0.0000초 | 뺄셈 한 번 |
| `distance(l.begin(), l.end())` — `list` **전체** | 0.0000초 | 아래 상자 참고 |
| `distance(l.begin(), mid)` — `list` **절반** | 0.098초 | 195 μs |
| `distance(s.begin(), s.end())` — `set` | 1.25초 | 2509 μs |

> (Linux x86-64 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 측정 스크립트는 `tools/bench/cpp_iterator_category.cpp`.)

::: deep
`list` 전체 구간이 0초로 나온 것은 측정 실수가 아니다. libstdc++은 `std::distance`가 **리스트 전체 길이를 재는 경우**를 따로 잡아낸다. `bits/stl_list.h`에 이런 특수화가 있다.

```cpp title="libstdc++ 13, bits/stl_list.h (발췌)"
// Detect when distance is used to compute the size of the whole list.
_List_iterator<_Tp> __beyond = __last;
++__beyond;
bool __whole = __first == __beyond;
if (__builtin_constant_p (__whole) && __whole)
  return static_cast<const _Sentinel*>(__last._M_node)->_M_size;
```

C++11부터 `list::size()`가 $O(1)$이어야 해서 리스트가 원소 수를 들고 다니는데, 전체 길이를 구하는 호출이면 그 값을 그냥 돌려준다. **부분 구간에는 이 지름길이 없고, 그때 195 μs가 나온다.** 카테고리의 진짜 비용은 그쪽에 있다.

이 측정에는 함정이 하나 더 있었다. 컨테이너를 만든 함수 안에서 바로 재면 컴파일러가 "방금 $n$개를 넣었으니 답은 $n$"이라고 판정해 순회를 통째로 지운다. 처음 측정이 실제로 그렇게 나왔고, 어셈블리에는 저장된 크기를 읽는 명령 하나만 남아 있었다. 측정 함수를 `noinline, noipa`로 떼어 낸 뒤에야 숫자가 나왔다. ==벤치마크에서 0이 나오면 빠른 것이 아니라 지워진 것을 먼저 의심하라.==
:::

`set`이 2509 μs인 것이 [0-7 §4](#/0-7)에서 본 `std::lower_bound`의 12,000배를 설명한다. 이분 탐색은 구간 중간으로 가야 하는데, 양방향 반복자에게 "중간으로 가라"는 곧 "절반만큼 한 칸씩 걸어라"다. 비교는 여전히 $\log n$번이고 **이동이 $O(n)$이다.**

::: warn
`v.end()`는 **마지막 원소가 아니라 마지막 다음**을 가리킨다. 역참조하면 미정의 동작이다. 반열림 구간 `[first, last)` 관례가 표준 전체에 일관되게 쓰인다([0-11 §4](#/0-11)).

이 관례가 주는 이득은 세 가지다. 빈 구간이 `first == last` 하나로 표현되고, 원소 수가 `last - first`로 바로 나오며, 구간을 이어 붙일 때 경계가 중복되지 않는다.

반복자를 무효화시키는 조건은 컨테이너마다 다르다. 표는 [0-6 §4](#/0-6)에 있다.
:::

## 3. 람다 — 그 자리에서 만드는 함수 객체

람다는 문법 설탕이 아니다. 컴파일러가 **익명 클래스를 하나 만들고 `operator()`를 정의한 뒤 그 객체를 만드는 것**이다. 캡처한 변수는 그 클래스의 멤버가 된다.

```cpp title="람다와 그 정체 (조각)"
int threshold = 10;
auto pred = [threshold](int x) { return x > threshold; };

// 컴파일러가 만드는 것과 대체로 같다
struct __lambda {
    int threshold;                                   // 캡처가 멤버가 된다
    bool operator()(int x) const { return x > threshold; }
};
auto pred2 = __lambda{threshold};
```

| 캡처 | 뜻 |
|---|---|
| `[]` | 아무것도 캡처하지 않는다. 함수 포인터로 변환 가능 |
| `[x]` | `x`를 **값으로** 복사. 기본이 `const`라 수정 불가 |
| `[&x]` | `x`를 **참조로**. 원본을 읽고 쓴다 |
| `[=]` | 쓰인 것을 전부 값으로 |
| `[&]` | 쓰인 것을 전부 참조로 |
| `[this]` | 멤버 함수 안에서 객체 자신을 참조로 |
| `[y = expr]` | 초기화 캡처(C++14). 새 이름에 계산 결과를 담는다 |
| `[x]() mutable` | 값 캡처한 복사본을 수정할 수 있게 한다 |

실행 결과로 확인한다.

```console
값 캡처:  pred(5)=0 pred(50)=1
참조 캡처: pred(5)=1 pred(50)=1  (값은 실행마다 달라질 수 있다)
mutable 값 캡처: 1 2 3, 바깥 count=0
참조 캡처(같은 스코프): total=10
```

> (실행 출력. 재현 스크립트는 `tools/bench/cpp_lambda_capture.cpp`.)

::: danger
둘째 줄이 사고다. `threshold = 10`을 참조로 캡처한 람다를 **그 변수가 사는 함수 밖으로 반환**했다. `pred(5)`는 거짓이어야 하는데 참이 나왔다. 죽은 스택 자리에 남아 있던 쓰레기와 5를 비교한 것이다.

```cpp
function<bool(int)> make_pred() {
    int threshold = 10;
    return [&threshold](int x) { return x > threshold; };   // ❌ threshold 는 곧 죽는다
}
```

`-fsanitize=address`로 빌드하면 정체가 드러난다.

```console
ERROR: AddressSanitizer: stack-use-after-scope
READ of size 4 ... in std::_Function_handler<bool (int), make_pred()::{lambda(int)#1}>
```

규칙: ==클로저가 그것을 만든 스코프보다 오래 살면 참조 캡처를 쓰지 마라.== 콜백으로 등록하는 람다, 스레드에 넘기는 람다, 작업 큐에 넣는 람다가 전부 여기 해당한다. 그런 자리에는 값 캡처나 `[p = shared_ptr]` 초기화 캡처를 쓴다.

`[&]`가 위험한 이유도 같다. 무엇을 캡처했는지 코드에 안 적혀 있어 수명 검토를 눈으로 할 수 없다.
:::

::: dual
```python title="루프 변수를 담은 클로저 세 개"
funcs = []
for i in range(3):
    funcs.append(lambda: i)

for f in funcs:
    print(f(), end=" ")
print()
```
```cpp title="루프 변수를 담은 클로저 세 개"
#include <functional>
#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<function<int()>> funcs;
    for (int i = 0; i < 3; ++i) {
        funcs.push_back([i]() { return i; });
    }

    for (const auto& f : funcs) cout << f() << " ";
    cout << "\n";
    return 0;
}
```
:::

**복잡도:** 시간 $O(k)$ — 클로저 $k$개를 만들고 각각 한 번 호출한다. 공간 $O(k)$ — 클로저마다 캡처한 값을 따로 들고 있다. 여기서 두 언어의 답이 갈린다.

```console
Python:  2 2 2
C++:     0 1 2
```

| 언어 차이 | Python | C++ |
|---|---|---|
| 기본 캡처 | **변수 자체를 참조.** 호출 시점의 값을 본다(늦은 바인딩) | 캡처 방식을 **명시**해야 한다. `[i]`는 만든 시점의 값 |
| 루프에서 | 세 클로저가 같은 `i`를 공유해 전부 `2` | `[i]`면 각자 복사본을 들어 `0 1 2` |
| 값을 고정하려면 | `lambda i=i: i` — 기본 인자로 그 시점 값을 박는다 | 기본이 그 동작이다 |
| 참조로 하려면 | 기본이 그 동작이다 | `[&i]`. 그리고 루프가 끝나면 죽는다 |
| 수명 관리 | 참조 카운트가 알아서 살려 둔다 | **직접 책임진다.** 위 `::: danger`가 그 결과 |

==Python의 기본은 C++의 `[&]`에 가깝고, C++의 관용적 기본은 `[=]`에 가깝다.== 두 언어를 오갈 때 클로저에서 사고가 나는 자리가 정확히 여기다.

::: perf
비교자를 어떤 형태로 넘기느냐가 정렬 속도를 바꾼다. 무작위 정수 500만 개, 비교 내용은 넷 다 `x < y`로 동일하다.

| 비교자 | 시간 | 기본 대비 |
|---|---|---|
| 기본 (`operator<`) | 0.429초 | 1.00배 |
| 람다 | 0.415초 | 0.97배 |
| 함수 포인터 | 0.582초 | 1.35배 |
| `std::function` | 0.763초 | **1.78배** |

> (Linux x86-64 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 측정 스크립트는 `tools/bench/cpp_comparator_overhead.cpp`.)

**람다가 기본과 같다.** 람다는 타입마다 고유한 클래스라 `sort` 템플릿이 그 타입으로 실체화되고 `operator()`가 통째로 인라인된다. 호출이 사라진다.

**`std::function`은 1.78배다.** `std::function`은 타입 소거 장치다. 어떤 호출 가능 객체든 담을 수 있는 대신, 실제 호출은 가상 함수 호출 한 겹을 거친다. 인라인이 불가능하고 그 비용이 비교마다, 즉 $O(n \log n)$번 든다.

정렬 비교자, 우선순위 큐 비교자, 안쪽 루프의 콜백에는 `std::function`을 쓰지 마라. **`std::function`은 "타입이 다른 것들을 한 컨테이너에 담아야 할 때"의 도구다.**
:::

## 4. strict weak ordering — 비교자가 지켜야 하는 것

이제 §1로 돌아간다. 표준은 비교자에 네 가지를 요구하고, 이것을 묶어 **strict weak ordering**이라 부른다.

| 조건 | 뜻 | `<=`가 어기는가 |
|---|---|---|
| 비반사성 | `cmp(a, a)`는 항상 거짓 | **어긴다.** `a <= a`는 참 |
| 비대칭성 | `cmp(a, b)`가 참이면 `cmp(b, a)`는 거짓 | **어긴다.** 같은 값이면 양쪽 다 참 |
| 추이성 | `a < b`이고 `b < c`면 `a < c` | 지킨다 |
| 동등의 추이성 | `a`와 `b`가 동등하고 `b`와 `c`가 동등하면 `a`와 `c`도 동등 | 지킨다 |

"동등"은 `cmp(a, b)`와 `cmp(b, a)`가 **둘 다 거짓**인 상태로 정의된다. `<=`를 쓰면 같은 값에 대해 둘 다 참이 되어 이 정의 자체가 무너진다.

::: deep
왜 그것이 배열 밖 접근으로 이어지나. `std::sort`의 삽입 정렬 단계에는 `__unguarded_linear_insert`라는 함수가 있고, 이름 그대로 **경계 검사를 하지 않는다.**

```cpp
while (comp(val, *(it - 1))) { *it = *(it - 1); --it; }   // 경계 검사가 없다
```

검사를 뺄 수 있는 근거는 앞쪽 어딘가에 `val`보다 작거나 같은 원소가 반드시 있다는 것이다. 그 원소에서 `comp`가 거짓이 되어 루프가 멈춘다. 퀵소트 분할이 남긴 피벗이 그 **보초** 역할을 한다.

비교자가 비반사적이지 않으면 보초에서도 `comp`가 참이 된다. 루프는 멈추지 않고 배열 앞으로 계속 걸어 나간다. 경계 검사를 넣으면 되지 않느냐는 반문에는 답이 있다 — 그 검사는 안쪽 루프에서 원소마다 든다. **표준은 "비교자가 규약을 지킨다"를 전제로 그 비용을 없앤 것이고, 규약을 어기면 그 전제의 대가를 치른다.**

이것이 C++ 전반의 설계다. 검사할 수 있는 것을 검사하지 않고 요구 사항으로 문서화한다. 지키면 공짜, 어기면 미정의 동작이다([0-5 §6](#/0-5)).
:::

`n = 17`에서만 죽고 `n = 100`에서는 살아남은 이유도 여기서 나온다. 원소가 16개 이하면 `sort`는 경계 검사가 있는 삽입 정렬만 쓴다. 17개부터 introsort 경로로 들어가고, 어디까지 걸어 나가느냐는 그때의 메모리 배치가 정한다. **크기와 값 분포에 따라 죽기도 하고 조용히 남의 메모리를 덮기도 한다.** 재현되지 않는 버그의 전형이다.

두 도구가 이것을 잡는다.

```console
$ g++ -std=c++17 -O2 -D_GLIBCXX_DEBUG swo.cpp && ./a.out
Error: comparison doesn't meet irreflexive requirements, assert(!(a < a)).

$ g++ -std=c++17 -O2 -fsanitize=address swo.cpp && ./a.out
ERROR: AddressSanitizer: heap-buffer-overflow
  in std::__introsort_loop<...>
0x516000000290 is located 0 bytes after 528-byte region
```

`-D_GLIBCXX_DEBUG`는 **비교자 자체를 검사해 원인을 그대로 말해 준다.** 제출용 빌드에는 넣지 않지만(느려진다) 로컬에서 정렬 관련 버그를 만나면 첫 번째로 켜 볼 스위치다.

::: pitfall
실제로 나오는 위반들이다.

- **`return a.score >= b.score;`** — 내림차순을 만들려다 등호를 붙인 경우. `>`만 쓰면 된다.
- **`return a.x < b.x || a.y < b.y;`** — 다중 키를 `||`로 이었다. 추이성이 깨진다. 올바른 형태는 `if (a.x != b.x) return a.x < b.x; return a.y < b.y;`다.
- **`double`에 NaN이 섞임.** NaN은 어떤 값과 비교해도 거짓이라 비대칭성은 지키지만 동등의 추이성이 깨진다. NaN이 있는 배열을 `sort`에 넘기지 마라. 부동소수 비교는 [X-7](#/x-7)에서 다룬다.
- **비교자 안에서 상태를 바꿈.** 비교자는 호출 순서와 횟수가 보장되지 않는다. 카운터를 증가시키거나 캐시를 갱신하면 결과가 재현되지 않는다.
- **`priority_queue`의 비교자 방향 착각.** `priority_queue`는 비교자가 "우선순위가 낮다"를 뜻해 `less`가 최대 힙이 된다. `sort`와 반대 방향으로 읽힌다.
:::

::: interview
정렬 비교자를 짜게 한 뒤 이어지는 질문은 대개 이것이다.

**"이 비교자가 만족해야 하는 조건이 무엇입니까."**
답변 뼈대는 이름과 네 조건이다. "strict weak ordering입니다. 비반사성, 비대칭성, 추이성, 동등 관계의 추이성 넷이고, 실무에서 깨지는 것은 거의 항상 첫 번째입니다. `<=`를 쓰면 `cmp(a, a)`가 참이 되고, `std::sort`의 삽입 정렬 단계가 경계 검사를 생략하고 있어서 배열 밖으로 걸어 나갑니다."

**"어기면 어떻게 됩니까."**
"미정의 동작입니다. 관찰로는 크래시가 나기도 하고 정렬 구간 밖 메모리가 조용히 덮이기도 합니다. 원소가 16개 이하면 아무 일도 안 일어나서 작은 테스트로는 안 잡힙니다. `-D_GLIBCXX_DEBUG`로 빌드하면 비교자 자체를 검사해 줍니다."

크래시 여부를 단정하지 않는 것이 중요하다. **미정의 동작의 핵심은 "무엇이 일어나는지 정해져 있지 않다"이지 "크래시한다"가 아니다.**
:::

## 5. 어디에 쓰이는가

**이벤트 콜백의 수명 관리가 §3의 `::: danger` 그대로다.** 구독자가 핸들러를 등록하면 그 클로저는 구독을 해지할 때까지 살아 있다. 그 사이에 클로저가 참조로 잡은 객체가 먼저 파괴되면 이벤트가 발생하는 순간 죽은 메모리를 읽는다. 그래서 이벤트 버스 구현은 대개 약한 참조를 들고 있다가 호출 직전에 살아 있는지 확인한다. 이 구조는 [XII-7 Observer / Publish-Subscribe](#/xii-7)에서 다룬다.

**스레드 풀에 넘기는 작업이 같은 문제의 더 나쁜 버전이다.** 작업 큐에 람다를 넣으면 그것은 다른 스레드에서, 넣은 함수가 이미 반환한 뒤에 실행된다. `[&]`로 캡처한 작업은 거의 확실히 죽은 스택을 읽는다. 여기서는 값 캡처가 규칙이고, 큰 객체는 소유권째로 옮긴다. 작업 큐는 [XI-4 스레드 풀과 작업 큐](#/xi-4)에서 다룬다.

**우선순위 큐의 비교자가 스케줄링 정책 그 자체다.** 마감이 이른 순, 우선순위가 높은 순, 둘을 조합한 순 — 정책을 바꾸는 것이 비교자를 바꾸는 일이고, 그래서 비교자를 갈아 끼울 수 있게 만드는 것이 [XII-6 Strategy](#/xii-6) 패턴이다. 그 비교자가 strict weak ordering을 어기면 스케줄러가 미정의 동작으로 들어간다. 실시간 스케줄링은 [XI-5](#/xi-5)에 있다.

## 연습

::: quiz
비교자와 반복자 선택이 그대로 정답을 가르는 유형이다.

**1. 백준 1181 단어 정렬 (실버 5)** — https://www.acmicpc.net/problem/1181
- 신호: 길이 우선, 같으면 사전순, 중복 제거.
- 상태: 단어 배열.
- 왜 이 도구인가: 다중 키 비교자와 `unique` + `erase`가 한 문제에 같이 나온다. **비교자를 `||`로 잇는 실수를 실제로 해 보고** 결과가 어떻게 어긋나는지 확인하라(§4의 두 번째 함정).

**2. 백준 11650 좌표 정렬하기 (실버 5)** — https://www.acmicpc.net/problem/11650
- 신호: x 우선, 같으면 y. 점 10만 개.
- 상태: 점의 배열.
- 왜 이 도구인가: `pair`의 기본 비교가 이미 사전식이라 비교자가 필요 없다. **필요 없는 비교자를 안 쓰는 것도 판단이다.**

**3. 백준 11279 최대 힙 (실버 2)** — https://www.acmicpc.net/problem/11279
- 신호: 최댓값을 반복해서 꺼낸다. 전체 정렬이 필요 없다.
- 상태: 힙 하나.
- 왜 이 도구인가: `priority_queue`의 기본이 최대 힙이라 그대로 되고, 최소 힙 문제(백준 1927)로 바꾸면 비교자를 뒤집어야 한다. **§4 마지막 함정을 몸으로 확인하는 자리**다. Python `heapq`는 정반대라 부호를 뒤집는다.

**4. 손으로 판정할 것.** 다음 비교자 셋이 strict weak ordering을 만족하는지 각각 판정하고, 어기는 것은 어느 조건을 어기는지 쓰라.

```cpp
auto c1 = [](const P& a, const P& b) { return a.x <= b.x; };
auto c2 = [](const P& a, const P& b) { return a.x < b.x || a.y < b.y; };
auto c3 = [](const P& a, const P& b) { return abs(a.x - b.x) > 1e-9 ? a.x < b.x : a.y < b.y; };
```

::: answer
**`c1`은 비반사성과 비대칭성을 어긴다.** `c1(a, a)`는 `a.x <= a.x`라 참이다. `x`가 같은 두 점에 대해 양방향 모두 참이 되어 동등 관계가 정의되지 않는다. §1의 크래시가 이것이다.

**`c2`는 추이성을 어긴다.** `a = (1, 5)`, `b = (2, 1)`, `c = (3, 0)`을 넣어 보라. `c2(a, b)`는 `1 < 2`라 참, `c2(b, c)`는 `2 < 3`이라 참인데 `c2(c, a)`도 `0 < 5`라 **참**이다. `a < b < c < a`라는 순환이 생긴다. 순서 관계라면 있을 수 없는 상태이고, 정렬 결과는 입력 순서에 따라 달라진다.

**`c3`은 동등의 추이성을 어긴다.** `x`의 차이가 `1e-9` 이하면 같은 것으로 보고 `y`를 비교한다. `a.x = 0`, `b.x = 1e-9`, `c.x = 2e-9`이면 `a`와 `b`는 `x`가 동등, `b`와 `c`도 동등인데 `a`와 `c`는 차이가 `2e-9`라 동등하지 않다. ==허용 오차로 동등을 정의하면 동등 관계의 추이성이 깨진다.== 부동소수를 정렬 키로 쓸 때 EPS 비교를 넣으면 안 되는 이유가 이것이고, 실제 해법은 값을 정수로 스케일링하거나 EPS 없이 그냥 `<`로 비교하는 것이다([X-7](#/x-7)).

셋 중 둘은 "그럴듯해 보이는" 코드다. **비교자는 눈으로 읽어서 맞아 보이는 것과 규약을 만족하는 것이 다르고, 그 차이가 미정의 동작으로 나온다.**
:::
:::

## 요약

- 반복자는 알고리즘 $M$개와 컨테이너 $N$개를 $M \times N$이 아니라 $M + N$으로 잇는 규약이다. 대가는 **알고리즘이 컨테이너를 수정할 수 없다는 것**과 **비용이 인터페이스에 안 보인다는 것**이다.
- 카테고리는 성능의 이름이다. 임의 접근이 아니면 `distance`와 이분 탐색이 걷는다. `set` 전체 순회가 `vector`의 뺄셈 한 번과 같은 함수로 표현된다.
- 람다는 컴파일러가 만든 익명 클래스이고 캡처는 그 멤버다. **클로저가 스코프보다 오래 살면 참조 캡처는 죽은 메모리를 읽는다.**
- Python 클로저의 기본은 C++의 `[&]`에 가깝다. 같은 루프 코드가 `2 2 2`와 `0 1 2`로 갈린다.
- `std::function`은 타입 소거의 대가로 인라인을 포기한다. 정렬 비교자에 쓰면 1.78배 느려진다. 람다는 기본과 같다.
- 비교자는 **strict weak ordering**을 만족해야 한다. `<=`는 비반사성을 어기고, `std::sort`는 경계 검사가 없는 삽입 정렬 단계에서 배열 밖으로 걸어 나간다. 원소 17개에서 죽었고 100개에서는 **죽지 않고 남의 메모리 16칸을 덮었다.**
- 정렬이 이상하면 `-D_GLIBCXX_DEBUG`로 다시 빌드하라. 비교자 위반을 이름 그대로 말해 준다.
