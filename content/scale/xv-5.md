# XV-5 스킵 리스트

::: lead
정렬을 유지하며 로그 시간에 탐색하는 문제에 회전 없이 답할 수 있는가.
:::

## 1. 문제

[XV-2 B-Tree](#/xv-2)와 [XV-3 LSM](#/xv-3)이 디스크로 넘어간 상황을 다뤘다면, 이 챕터는 그 전 단계 — **메모리 안에 다 들어가지만 정렬 순서와 락 경합이 함께 문제가 되는 상황**을 다룬다.

정렬된 순서를 유지하면서 삽입·삭제·탐색을 전부 $O(\log n)$에 하고 싶다. [II-9](#/ii-9)는 이 문제를 균형 이진 트리로 풀었다 — 레드-블랙 트리가 삽입·삭제 때마다 회전을 돌려 높이를 $O(\log n)$으로 묶는다. 회전 로직은 정확하지만 까다롭다. 삽입 하나가 노드 하나를 넣는 것으로 안 끝나고, 조상 몇 개의 색을 바꾸고 방향을 뒤집는 연쇄 반응으로 번질 수 있다.

동시성 환경에서 이게 더 아파진다. Redis의 Sorted Set처럼 여러 스레드가 같은 정렬 구조를 동시에 건드려야 하는 상황을 생각해 보자. 회전은 트리의 여러 노드를 한 번에 재배선하는 연산이다. 회전 도중에 다른 스레드가 그 서브트리를 읽으면 반쯤 재배선된 상태를 보게 된다. 이걸 락 없이 안전하게 하려면 회전 자체를 원자적으로 만들어야 하는데, 포인터 여러 개를 동시에 바꾸는 연산은 원자적으로 만들기 어렵다. 락을 걸면 되지만, 그러면 [XI-3](#/xi-3)에서 본 것처럼 동시성을 포기하는 대가를 치른다.

**회전이 없는 정렬 구조는 없을까.** 삽입이 그 자리 하나만 건드리고 끝나는 구조라면, 락프리 구현이 훨씬 쉬워진다.

## 2. 아이디어

스킵 리스트는 균형을 **계산으로 맞추지 않고 동전 던지기로 맞춘다.** 기본은 그냥 정렬된 연결 리스트다 — 0층이라 부른다. 여기에 원소를 하나 넣을 때마다 동전을 던져서, 앞면이 나오는 동안 그 원소를 한 층 더 위로 올린다. 앞면 확률이 $\frac{1}{2}$이면 한 층 더 올라갈 확률이 매번 절반이므로, 위층으로 갈수록 원소 수가 지수적으로 줄어든다. 원소 $n$개 중 대략 $n/2$개가 1층에 있고, $n/4$개가 2층에, $n/8$개가 3층에 있는 식이다.

이 구조로 탐색이 빨라지는 이유는 고속도로와 국도의 관계와 같다. **맨 위층은 원소가 몇 개 없는 대신 한 걸음에 멀리 건너뛴다.** 탐색은 맨 위층에서 시작해서, 다음 노드의 키가 찾는 값보다 작으면 오른쪽으로 가고, 크거나 없으면 한 층 내려온다. 매번 내려올 때마다 "이 구간 안에 답이 있다"는 범위가 좁혀져 있는 채로 더 촘촘한 층에서 다시 찾는다. 층마다 원소 수가 절반씩 줄므로 층수는 $O(\log n)$이고, 각 층에서 옆으로 움직이는 횟수도 기댓값이 상수에 가깝게 억제된다 — 그래서 탐색 전체가 기대 $O(\log n)$이다.

**회전이 없다는 것이 핵심이다.** 삽입은 "이 값이 몇 층까지 올라가는가"를 동전으로 정한 뒤, 그 층까지 각 층의 연결 리스트에 노드 하나를 끼워 넣는 것으로 끝난다. 트리처럼 삽입 하나가 먼 조상까지 건드리며 재배선하는 연쇄가 없다. 각 층의 삽입은 그 층의 앞뒤 포인터 두 개만 바꾸면 되고, 이것은 원자적 포인터 교체(compare-and-swap) 하나로 표현할 수 있는 크기다 — 락프리 스킵 리스트가 락프리 균형 트리보다 훨씬 흔하게 구현되는 이유다.

균형이 확률적이라는 것은 **최악의 경우가 이론적으로는 존재한다**는 뜻이다. 동전이 계속 앞면만 나와서 모든 원소가 맨 위층까지 올라가면 탐색이 $O(n)$으로 무너진다. 하지만 그 확률은 $n$이 커질수록 지수적으로 작아진다. 레드-블랙 트리가 회전으로 **최악의 경우까지 보장**하는 것과 달리, 스킵 리스트는 **평균적으로, 압도적인 확률로** 보장한다. 이 교환을 받아들이는 대가로 회전 로직 전체를 지운다 — 삽입·삭제 코드가 균형 트리보다 훨씬 짧아지는 것은 그 대가의 직접적인 대금이다.

**층수의 상한을 어떻게 정하는가**도 실전에서 자주 나오는 질문이다. 원소가 최대 $n$개까지 들어온다고 예상되면 $\log_{1/p} n$을 상한으로 잡는다 — 앞면 확률 $p = \frac{1}{2}$일 때는 $\log_2 n$이다. 원소 100만 개를 예상한다면 상한은 20 근방이면 충분하다. 이보다 훨씬 크게 잡아도 틀리지는 않지만, 대부분의 층이 텅 빈 채로 포인터 배열만 차지해 메모리를 낭비한다.

## 4. 구현

::: dual
```python title="스킵 리스트 — 삽입·탐색"
MAX_LEVEL = 4
MASK32 = 0xFFFFFFFF
_state = 88172645463325252 & MASK32


def xorshift_bit():
    """레벨을 정하는 동전. xorshift32로 비트 하나를 뽑는다 — 표준 난수
    생성기 대신 쓰는 이유는 두 언어의 결과를 정확히 일치시키기 위해서다."""
    global _state
    x = _state
    x ^= (x << 13) & MASK32
    x ^= (x >> 17)
    x ^= (x << 5) & MASK32
    _state = x & MASK32
    return _state & 1


def random_level():
    lv = 0
    while lv < MAX_LEVEL and xorshift_bit() == 1:
        lv += 1
    return lv


class Node:
    __slots__ = ("key", "next")

    def __init__(self, key, level):
        self.key = key
        self.next = [None] * (level + 1)


head = Node(None, MAX_LEVEL)   # 모든 층을 관통하는 시작점


def search(key):
    x = head
    hops = 0                    # 옆으로 이동한 횟수 — 탐색 비용의 증거
    for lv in range(MAX_LEVEL, -1, -1):
        while x.next[lv] is not None and x.next[lv].key < key:
            x = x.next[lv]
            hops += 1
    x = x.next[0]
    return (x is not None and x.key == key), hops


def insert(key):
    update = [head] * (MAX_LEVEL + 1)   # 각 층에서 새 노드 직전에 올 노드
    x = head
    for lv in range(MAX_LEVEL, -1, -1):
        while x.next[lv] is not None and x.next[lv].key < key:
            x = x.next[lv]
        update[lv] = x
    lv = random_level()
    node = Node(key, lv)
    for i in range(lv + 1):
        node.next[i] = update[i].next[i]
        update[i].next[i] = node
    return lv


KEYS = [3, 6, 7, 9, 12, 17, 19, 21, 25, 26]
levels = [(k, insert(k)) for k in KEYS]
print("삽입한 레벨:", levels)
for q in [9, 20]:
    found, hops = search(q)
    print("search(%d) -> found=%s hops=%d" % (q, found, hops))
```
```cpp title="스킵 리스트 — 삽입·탐색"
#include <cstdio>
#include <cstdint>
#include <string>
#include <vector>
using namespace std;

const int MAX_LEVEL = 4;
uint32_t g_state = 88172645463325252ULL & 0xFFFFFFFFu;

// 레벨을 정하는 동전. xorshift32로 비트 하나를 뽑는다 — 표준 난수 생성기
// 대신 쓰는 이유는 두 언어의 결과를 정확히 일치시키기 위해서다.
int xorshift_bit() {
    uint32_t x = g_state;
    x ^= (x << 13);
    x ^= (x >> 17);
    x ^= (x << 5);
    g_state = x;
    return (int)(g_state & 1u);
}

int random_level() {
    int lv = 0;
    while (lv < MAX_LEVEL && xorshift_bit() == 1) lv++;
    return lv;
}

struct Node {
    int key;
    vector<Node*> next;
    Node(int k, int level) : key(k), next(level + 1, nullptr) {}
};

Node* head = new Node(-1, MAX_LEVEL);   // 모든 층을 관통하는 시작점

pair<bool, int> search(int key) {
    Node* x = head;
    int hops = 0;                       // 옆으로 이동한 횟수 — 탐색 비용의 증거
    for (int lv = MAX_LEVEL; lv >= 0; lv--) {
        while (x->next[lv] != nullptr && x->next[lv]->key < key) {
            x = x->next[lv];
            hops++;
        }
    }
    x = x->next[0];
    bool found = x != nullptr && x->key == key;
    return {found, hops};
}

int insert(int key) {
    vector<Node*> update(MAX_LEVEL + 1, head);   // 각 층에서 새 노드 직전에 올 노드
    Node* x = head;
    for (int lv = MAX_LEVEL; lv >= 0; lv--) {
        while (x->next[lv] != nullptr && x->next[lv]->key < key) x = x->next[lv];
        update[lv] = x;
    }
    int lv = random_level();
    Node* node = new Node(key, lv);
    for (int i = 0; i <= lv; i++) {
        node->next[i] = update[i]->next[i];
        update[i]->next[i] = node;
    }
    return lv;
}

int main() {
    vector<int> KEYS = {3, 6, 7, 9, 12, 17, 19, 21, 25, 26};
    printf("삽입한 레벨: [");
    bool first = true;
    for (int k : KEYS) {
        int lv = insert(k);
        printf("%s(%d, %d)", first ? "" : ", ", k, lv);
        first = false;
    }
    printf("]\n");
    for (int q : {9, 20}) {
        auto [found, hops] = search(q);
        printf("search(%d) -> found=%s hops=%d\n", q, found ? "True" : "False", hops);
    }
    return 0;
}
```

search(9) -> found=True hops=3

(Linux x86-64 / CPython 3.13 / g++ 13 `-O2` 실측. xorshift 시드가 고정이라 이 실행 결과는 항상 재현된다.) 무작위로 뽑은 300개 키를 삽입하고 1~2000 전 범위를 조회해 `set` 기준 정답과 대조했을 때 전부 일치했다 — 탐색이 반환하는 존재 여부가 정렬된 참조 구조와 어긋나지 않는다.

**복잡도:** 삽입·탐색 모두 기대 시간 $O(\log n)$ — 층마다 원소 수가 절반으로 줄어 층수의 기댓값이 $O(\log n)$이고, 각 층에서 옆으로 도는 횟수의 기댓값도 상수로 억제된다(레벨이 그 층까지 온 노드는 다음 동전에서 앞면이 나올 확률이 $\frac{1}{2}$이므로, 기하분포의 기댓값이 상수가 된다). 공간은 기대 $O(n)$ — 레벨 $i$에 있는 기대 노드 수가 $n/2^i$이므로 전체 층의 노드 수 합이 $2n$에 수렴한다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 레벨별 포인터 배열 | `self.next = [None] * (level+1)` — 리스트 | `vector<Node*> next(level+1, nullptr)` |
| `update` 배열 초기화 | `[head] * (MAX_LEVEL+1)` — 같은 객체를 참조하는 리스트라도 이후 전부 개별 대입되므로 안전하다 | `vector<Node*> update(MAX_LEVEL+1, head)` |
| 메모리 해제 | 가비지 컬렉터가 처리 | `new`로 만든 `Node`를 예제는 해제하지 않는다. 실전 구현은 소유권을 `unique_ptr` 사슬이나 [XI-11](#/xi-11)의 아레나로 관리해야 한다 |

::: pitfall
- **최대 레벨을 원소 수에 안 맞춰 고정한다.** 프로토타입 단계의 상수를 운영 규모까지 그대로 끌고 가는 경우가 흔하다. 레벨이 $\log_2 n$보다 너무 낮으면 위층이 없는 것과 같아져 $O(n)$에 가까워진다. 반대로 너무 높으면 대부분의 층이 텅 비어 메모리만 낭비한다. 원소 수의 예상 상한에서 $\log_2 n$을 계산해 정한다.
- **`update` 배열을 안 채우고 삽입한다.** 탐색하며 내려올 때 각 층에서 "새 노드 직전에 올 노드"를 기록해 둬야 그 층의 연결을 끊지 않고 끼워 넣을 수 있다. 이걸 빼먹으면 상위 층의 연결이 끊긴 채로 방치된다.
- **동전 확률을 무작위성 없이 재현하려다 진짜 표준 난수를 그대로 안 쓴다.** 위 코드의 xorshift는 이 챕터가 두 언어의 출력을 맞추기 위한 장치다. 실전 구현은 언어 표준 난수 생성기(`random`, `<random>`)를 쓰면 된다 — 재현성이 중요한 것은 교재의 지면이지, 실제 스킵 리스트의 정확성이 아니다.
:::

:::

## 5. 어디에 쓰이는가

**Redis의 Sorted Set(ZSET)이 스킵 리스트로 만들어져 있다.** 순위·랭킹 보드, 지연된 작업 큐(실행 시각을 점수로 쓰는 것), 리더보드 같은 기능이 전부 이 자료구조 위에서 동작한다고 알려져 있다. 점수(score) 순으로 정렬된 원소 집합에 삽입·삭제·범위 조회가 전부 자주 섞여 들어오는데, 균형 트리의 회전 로직 없이 이 성능을 낸다는 점이 Redis가 스킵 리스트를 선택한 이유로 알려져 있다. 값 하나를 삽입할 때 건드리는 포인터 수가 적어 구현이 단순하고, 락 경합이 걸리는 범위도 좁다.

**락프리 동시성 인덱스**에서도 스킵 리스트가 자주 등장한다. 락프리 균형 트리도 이론적으로는 존재하지만, 회전이 여러 포인터를 한 번에 바꾸는 연산이라 그 전체를 원자적으로 만들기가 까다롭다. 스킵 리스트는 애초에 삽입이 층마다 독립적인 포인터 교체로 쪼개지므로, 그 하나하나를 compare-and-swap으로 구현하는 정도로 락프리성을 얻을 수 있다. 회전이 없다는 성질이 [XI-3](#/xi-3)에서 다룬 원자적 연산과 잘 맞는다 — 삽입이 한 층의 포인터 하나를 compare-and-swap으로 바꾸는 것으로 축소될 수 있어서, 트리 회전을 락프리로 구현하는 것보다 훨씬 다루기 쉽다. Java의 `ConcurrentSkipListMap`이 이 발상을 그대로 표준 라이브러리에 옮긴 예다.

## 6. 같은 문제의 세 가지 답

"정렬을 유지하며 $O(\log n)$에 탐색한다"는 질문에 이 책은 이미 두 번 답했다. [II-9 균형 트리](#/ii-9)는 회전으로 높이를 강제한다 — 최악의 경우까지 보장하지만 삽입 하나가 여러 노드를 재배선할 수 있다. [XV-2 B-Tree](#/xv-2)는 노드 하나에 여러 키를 채워 높이를 낮추는 것으로 같은 문제를 디스크 I/O 관점에서 다시 푼다 — 여기서는 회전이 아니라 분할·병합이 재배선을 대신한다. 스킵 리스트는 셋 중 유일하게 **결정론적 재배선을 포기하고 확률에 맡긴다.** 세 구조 모두 "삽입 하나가 얼마나 넓게 파급되는가"라는 같은 축 위에서 서로 다른 지점을 고른 것이다 — 회전(국소적이지만 결정론적 연쇄), 분할(더 큰 단위지만 드물게), 동전(파급이 아예 없는 대신 확률적 보장).

- 어떤 구조이고 무엇을 대가로 치르는가: 스킵 리스트는 삽입·삭제·탐색이 전부 기대 $O(\log n)$이면서 구현이 균형 트리보다 짧다. 대가는 회전 트리 대비 최악의 경우 보장이 확률적이라는 것과, 포인터 배열(레벨마다 하나)로 인한 캐시 지역성 손해다.

- 무엇이 병목이거나 깨지는가: 메모리 안에서는 최선인 구조가 디스크로 넘어가면 최악이 될 수 있다. 포인터 기반 구조(균형 트리, 스킵 리스트)는 노드 하나하나가 흩어진 메모리 주소라 디스크 블록 하나에 실효 데이터가 거의 없다.

## 요약

- "정렬 유지 + $O(\log n)$ 탐색"이라는 같은 문제에 [II-9 균형 트리](#/ii-9)는 회전으로, [XV-2 B-Tree](#/xv-2)는 노드 분할로, 스킵 리스트는 **동전 던지기**로 답한다. 셋 다 "삽입 하나가 얼마나 넓게 파급되는가"라는 같은 축 위의 서로 다른 지점이다.
- 원소를 넣을 때마다 동전을 던져 앞면이 나오는 동안 층을 올린다. 위층일수록 원소가 지수적으로 적어져 큰 구간을 한 번에 건너뛸 수 있다.
- 탐색은 위층에서 시작해 다음 노드가 목표보다 크면 한 층 내려오는 식으로, 기대 $O(\log n)$에 끝난다.
- **회전이 없다.** 삽입은 각 층에서 포인터 두 개만 바꾸면 끝나고, 이 국소성 때문에 락프리 구현이 균형 트리보다 쉽다.
- 균형이 확률적이므로 이론상 최악의 경우가 있지만 그 확률은 $n$이 커질수록 지수적으로 작아진다 — 트리가 주는 "항상 보장"과는 다른 "거의 항상 보장"이다.
- Redis의 Sorted Set과 자바의 `ConcurrentSkipListMap`이 이 구조를 그대로 쓴다. [XI-3](#/xi-3)의 락프리 동시성 논의와 직접 연결된다.
- 층수 상한은 예상 원소 수 $n$에서 $\log_{1/p} n$으로 계산해 정한다. 너무 낮으면 $O(n)$에 가까워지고, 너무 높으면 빈 층이 메모리만 차지한다.
