# XV-11 복제와 합의 입문

::: lead
같은 데이터를 서버 세 대에 복사해 뒀을 때, "지금 진짜 값이 뭔가"를 누가 어떻게 정하는가.
:::

## 1. 문제

키-값 저장소를 서버 한 대로 운영하면 그 한 대가 죽는 순간 서비스가 멈춘다. 세 대로 복제하면 한 대가 죽어도 나머지가 버틴다 — 그런데 이제 새로운 문제가 생긴다. 클라이언트가 서버 A에 `x=1`을 쓰고, 곧이어 다른 클라이언트가 서버 B에서 `x`를 읽었는데 아직 복제가 안 됐다면 뭐가 보이는가. 서버 A와 서버 B가 동시에 `x`에 서로 다른 값을 쓰라는 요청을 받으면 어느 것이 이기는가. 서버 하나가 응답 없이 멈췄다면 그게 느린 것인지 죽은 것인지 어떻게 구별하는가.

이 질문들이 어려운 이유는 네트워크와 프로세스가 이상적으로 동작하지 않기 때문이다. **메시지는 유실되고, 늦게 도착하고, 순서가 뒤바뀐다. 노드는 멈추고, 재시작하고, 재시작한 뒤에는 자신이 얼마나 오래 멈춰 있었는지조차 모른다.** "서버가 응답하지 않는다"는 관찰만으로는 그 서버가 죽었는지, 네트워크가 끊겼는지, 단지 느린지 구별할 수 없다 — 관찰하는 쪽에서는 세 상황이 똑같이 보인다. 이 전제 없이는 왜 복제와 합의에 전용 알고리즘이 필요한지 이해가 안 된다. "그냥 최신 값을 쓰면 되지 않나"는 **무엇이 최신인지 노드마다 다르게 볼 수 있다**는 사실 앞에서 무너진다.

::: note
**분산 시스템 이론의 두 명제를 한 문단으로 요약한다.** FLP 불가능성 정리(Fischer, Lynch, Paterson, 1985)는 메시지 지연에 상한이 없는 비동기 네트워크에서는 단 하나의 노드가 고장 나도 절대 안전하게 합의에 도달하는 결정적 알고리즘이 존재하지 않는다는 것을 증명했다. CAP 정리는 네트워크 분단이 실제로 일어나면(P) 일관성(C)과 가용성(A) 중 하나를 포기해야 한다고 말한다. 두 정리 모두 "이상적으로는 안 된다"는 한계를 긋고, 실무 시스템은 그 한계 안에서 타임아웃·재시도·과반수 투표 같은 실용적 타협으로 동작한다. 이 챕터가 다루는 것이 그 타협의 대표적인 형태다.
:::

## 2. 아이디어

### 리더 선출 — 왜 "다수결로 대표를 뽑는다"가 답인가

노드 여러 개가 각자 판단하면 값이 갈린다. 그래서 한 노드를 **리더**로 세우고, 모든 쓰기를 리더를 거치게 한다. 문제는 리더를 어떻게 뽑느냐다 — 사람이 정하면 그 사람이 죽었을 때 아무도 못 뽑는다. Raft는 **텀(term)**이라는 논리적 시간 단위와 **과반수 투표**로 이 문제를 푼다.

```text nolines
follower  -- heartbeat timeout -->  candidate
candidate -- majority votes    -->  leader
candidate -- election fails    -->  follower   (다음 텀에 재시도)
leader    -- higher term seen  -->  follower
```

모든 노드는 팔로워로 시작한다. 리더로부터 오는 하트비트가 일정 시간 끊기면 그 노드는 스스로 **후보**가 되어 텀을 하나 올리고, 다른 모든 노드에 투표를 요청한다. 텀은 절대 되돌아가지 않는 정수이고, 더 높은 텀을 가진 메시지를 보면 무조건 그 텀을 받아들인다 — **텀이 "누구 말이 더 최신인가"를 가르는 유일한 기준**이다. 노드는 한 텀에 한 표만 던지므로, 과반의 표를 받은 후보는 **그 텀에서 유일**하게 리더가 된다(과반끼리는 겹칠 수밖에 없으므로 두 후보가 동시에 과반을 받을 수 없다). 이 성질이 "리더가 둘 생기는" 상황을 텀 단위로 막는다.

### 로그 복제 — 왜 "과반이 받아 적으면 확정"인가

리더가 정해지면 클라이언트의 쓰기는 리더의 로그에 먼저 append되고, 리더가 팔로워들에게 그 엔트리를 전파한다. **과반수(자기 자신 포함)가 그 엔트리를 자신의 로그에 적었다고 확인하면, 그 엔트리는 커밋된 것으로 본다.** 커밋된 엔트리는 이후 어떤 리더가 새로 뽑히더라도 절대 사라지지 않는다 — 새 리더를 뽑을 때 "가장 로그가 앞선 노드"만 표를 받을 수 있게 제한해 두었기 때문에(투표 요청에 후보의 로그 길이를 실어 보내고, 자기 로그가 더 길면 거부한다), 커밋된 엔트리를 가진 노드 없이는 과반을 모을 수 없다.

이 두 아이디어 — **텀으로 시간을 쪼개고, 과반으로 유일성을 만드는 것** — 이 Raft의 전부다. 멤버십 변경(노드 추가·제거), 스냅샷(로그가 무한히 길어지는 것을 막는 압축), 로그 압축 최적화는 이 뼈대 위에 얹히는 확장이고, 이 챕터의 범위 밖이다.

## 3. 손으로 따라가기 — 벡터 시계

리더 선출과 별개로, "이벤트 A가 이벤트 B보다 먼저 일어났다"를 노드들이 무엇을 근거로 판단할지도 문제다. 벽시계는 노드마다 어긋나므로 쓸 수 없다. **벡터 시계**는 각 노드가 "노드별 카운터 배열"을 들고 다니며, 자신의 카운터만 올리고 메시지를 주고받을 때 상대의 벡터와 원소별 최댓값을 취해 병합한다.

::: trace
노드 A, B, C가 각각 벡터 `[A, B, C]`를 `[0,0,0]`에서 시작한다. 규칙은 둘뿐이다. **로컬 이벤트**: 자기 칸만 1 증가. **메시지 수신**: 자기 칸을 1 증가시킨 뒤, 상대가 보내온 벡터와 원소별 최댓값을 취한다(송신 시에는 보내는 시점의 자기 벡터를 그대로 실어 보낸다).

| 스텝 | 사건 | A의 벡터 | B의 벡터 | C의 벡터 |
|---|---|---|---|---|
| 1 | A에서 로컬 이벤트 | [1,0,0] | [0,0,0] | [0,0,0] |
| 2 | A → B로 메시지 전송(A는 [1,0,0]을 실어 보냄) | [1,0,0] | [1,1,0] | [0,0,0] |
| 3 | B에서 로컬 이벤트 | | | |
| 4 | B → C로 메시지 전송 | | | |
:::

::: answer
| 스텝 | 사건 | A의 벡터 | B의 벡터 | C의 벡터 |
|---|---|---|---|---|
| 1 | A에서 로컬 이벤트 | [1,0,0] | [0,0,0] | [0,0,0] |
| 2 | A → B로 메시지 전송(A는 [1,0,0]을 실어 보냄) | [1,0,0] | [1,1,0] | [0,0,0] |
| 3 | B에서 로컬 이벤트 | [1,0,0] | [1,2,0] | [0,0,0] |
| 4 | B → C로 메시지 전송(B는 [1,2,0]을 실어 보냄) | [1,0,0] | [1,2,0] | [1,2,1] |

스텝 2가 핵심이다. B는 수신 시 **먼저 자기 칸(두 번째)을 `[0,0,0]`에서 `[0,1,0]`로 올리고, 그 다음 A가 실어 보낸 `[1,0,0]`과 원소별 최댓값**을 취한다 — `max([0,1,0], [1,0,0]) = [1,1,0]`. 자기 칸 증가와 병합은 **한 벡터 위에서 순서대로** 일어나는 두 단계지 서로 다른 결과를 내는 두 가지 방법이 아니다.

스텝 4에서 C의 벡터 `[1,2,1]`은 "C가 이 사건 이전에 A의 이벤트 1개와 B의 이벤트 2개를 인과적으로 안다"는 뜻이다. 두 벡터 $V_1, V_2$ 사이에 $V_1 \le V_2$(모든 칸에서 이하이고 적어도 하나는 미만)이면 $V_1$이 가리키는 사건이 $V_2$가 가리키는 사건보다 **인과적으로 먼저** 일어난 것이다. 최종 상태에서 A의 `[1,0,0]`과 C의 `[1,2,1]`을 비교하면 $[1,0,0] \le [1,2,1]$이 성립해 A의 이벤트가 C의 이벤트보다 먼저다. 반면 A의 `[1,0,0]`과 B의 로컬 이벤트 직후 `[1,2,0]`을 비교해도 마찬가지로 A가 먼저다 — 이 예제에는 동시적(concurrent) 사건 쌍이 없다. 두 벡터가 서로 어느 방향으로도 $\le$를 만족하지 않을 때만 "인과관계 없음"이라고 판정하며, 벡터 시계가 답하는 질문은 정확히 이것이지 "몇 시 몇 분에 일어났는가"가 아니다.
:::

### CRDT — 병합 순서를 신경 쓰지 않아도 되는 자료구조

리더 없이 여러 노드가 각자 쓰기를 받고 나중에 상태를 합치는 방식(멀티 마스터)에서는 "합칠 때 충돌이 안 나는 자료구조"가 필요하다. **CRDT(Conflict-free Replicated Data Type)**는 병합 연산이 교환·결합·멱등 법칙을 만족하도록 설계되어, **어떤 순서로 병합해도 결과가 같다.**

가장 단순한 예가 **G-Counter(증가 전용 카운터)**다. 각 노드가 "자신이 증가시킨 횟수"만 따로 든 배열을 유지한다 — 벡터 시계와 구조가 같다. 노드 A가 5번, B가 3번 증가시켰다면 A는 `[5,0]`, B는 `[0,3]`을 들고, 병합은 원소별 최댓값이다. 전체 값은 병합된 벡터의 합이다. 두 노드가 동시에 증가시켜도 각자 자기 칸만 건드리므로 **충돌이 구조적으로 발생하지 않는다** — 조율(coordination) 없이 병합해도 값이 유실되지 않는다. 감소가 필요하면 증가용 벡터와 감소용 벡터를 따로 두고 차를 낸다(PN-Counter).

집합이 필요하면 **OR-Set(Observed-Remove Set)**을 쓴다. 원소를 추가할 때마다 고유 태그를 붙이고, 삭제는 "그 시점까지 관찰된 태그들"을 제거 목록에 넣는 방식으로 처리한다 — 그래야 "A가 원소를 추가하는 동시에 B가 그 원소를 삭제"하는 상황에서 삭제가 자신이 보지 못한 추가까지 지워버리는 사고를 막는다. 두 자료구조 모두 이 챕터에서는 **존재와 병합 규칙까지만** 다룬다. 실제 구현은 태그 관리와 가비지 컬렉션(삭제된 태그를 언제 버려도 안전한가)이 얽혀 상당히 커지므로 범위 밖이다.

## 4. 구현 — 리더 선출과 로그 복제의 뼈대

3개 노드가 텀을 두고 투표해 리더를 뽑고, 리더가 로그 한 엔트리를 복제해 커밋하기까지를 시뮬레이션한다. 실제 네트워크·타이머 대신 **호출 순서를 코드에서 직접 정한 결정적 시뮬레이션**이다 — 메시지 유실이나 타임아웃 경합은 다루지 않는다.

::: dual
```python title="Raft 뼈대 — 리더 선출과 로그 복제"
class Node:
    def __init__(self, node_id):
        self.id = node_id
        self.term = 0
        self.voted_for = None
        self.role = "follower"
        self.log = []  # list of (term, value)
        self.votes = 0
        self.commit_index = -1

    def start_election(self):
        self.term += 1
        self.role = "candidate"
        self.voted_for = self.id
        self.votes = 1
        return self.term

    def request_vote(self, candidate_id, candidate_term, candidate_log_len):
        if candidate_term < self.term:
            return False
        if candidate_term > self.term:
            self.term = candidate_term
            self.voted_for = None
            self.role = "follower"
        my_log_len = len(self.log)
        log_ok = candidate_log_len >= my_log_len
        if (self.voted_for in (None, candidate_id)) and log_ok:
            self.voted_for = candidate_id
            return True
        return False

    def become_leader(self):
        self.role = "leader"

    def append_entries(self, leader_term, entries):
        if leader_term < self.term:
            return False
        self.term = leader_term
        self.role = "follower"
        self.log.extend(entries)
        return True


def majority(count, n):
    return count > n // 2


if __name__ == "__main__":
    nodes = [Node(i) for i in range(3)]
    candidate = nodes[0]
    term = candidate.start_election()
    print(f"node{candidate.id} 후보 등록, term={term}, 자기 표 1개")

    for follower in nodes:
        if follower.id == candidate.id:
            continue
        granted = follower.request_vote(candidate.id, term, len(candidate.log))
        if granted:
            candidate.votes += 1
        print(f"node{follower.id} 투표 요청 수신 -> {'승인' if granted else '거부'}")

    if majority(candidate.votes, len(nodes)):
        candidate.become_leader()
        print(f"node{candidate.id} 과반({candidate.votes}/{len(nodes)}) 확보, 리더 등극")
    else:
        print("과반 실패, 다음 텀 대기")

    entry = (term, "x=1")
    candidate.log.append(entry)
    acks = 1
    for follower in nodes:
        if follower.id == candidate.id:
            continue
        ok = follower.append_entries(candidate.term, [entry])
        if ok:
            acks += 1
        print(f"node{follower.id} AppendEntries 수신 -> {'복제 성공' if ok else '거부'}, log={follower.log}")

    if majority(acks, len(nodes)):
        candidate.commit_index = 0
        print(f"엔트리 커밋(과반 {acks}/{len(nodes)}): {entry}")
```
```cpp title="Raft 뼈대 — 리더 선출과 로그 복제"
#include <cstdio>
#include <vector>
#include <string>

struct Entry {
    int term;
    std::string value;
};

struct Node {
    int id;
    int term = 0;
    int voted_for = -1;  // -1 = 미투표
    std::string role = "follower";
    std::vector<Entry> log;
    int votes = 0;
    int commit_index = -1;

    int start_election() {
        term += 1;
        role = "candidate";
        voted_for = id;
        votes = 1;
        return term;
    }

    bool request_vote(int candidate_id, int candidate_term, int candidate_log_len) {
        if (candidate_term < term) return false;
        if (candidate_term > term) {
            term = candidate_term;
            voted_for = -1;
            role = "follower";
        }
        int my_log_len = (int)log.size();
        bool log_ok = candidate_log_len >= my_log_len;
        if ((voted_for == -1 || voted_for == candidate_id) && log_ok) {
            voted_for = candidate_id;
            return true;
        }
        return false;
    }

    void become_leader() { role = "leader"; }

    bool append_entries(int leader_term, const std::vector<Entry>& entries) {
        if (leader_term < term) return false;
        term = leader_term;
        role = "follower";
        for (const auto& e : entries) log.push_back(e);
        return true;
    }
};

bool majority(int count, int n) { return count > n / 2; }

std::string log_str(const std::vector<Entry>& log) {
    std::string s = "[";
    for (size_t i = 0; i < log.size(); ++i) {
        if (i) s += ", ";
        s += "(" + std::to_string(log[i].term) + ", '" + log[i].value + "')";
    }
    s += "]";
    return s;
}

int main() {
    std::vector<Node> nodes(3);
    for (int i = 0; i < 3; ++i) nodes[i].id = i;
    Node& candidate = nodes[0];
    int term = candidate.start_election();
    printf("node%d 후보 등록, term=%d, 자기 표 1개\n", candidate.id, term);

    for (auto& follower : nodes) {
        if (follower.id == candidate.id) continue;
        bool granted = follower.request_vote(candidate.id, term, (int)candidate.log.size());
        if (granted) candidate.votes += 1;
        printf("node%d 투표 요청 수신 -> %s\n", follower.id, granted ? "승인" : "거부");
    }

    if (majority(candidate.votes, (int)nodes.size())) {
        candidate.become_leader();
        printf("node%d 과반(%d/%d) 확보, 리더 등극\n", candidate.id, candidate.votes, (int)nodes.size());
    } else {
        printf("과반 실패, 다음 텀 대기\n");
    }

    Entry entry{term, "x=1"};
    candidate.log.push_back(entry);
    int acks = 1;
    for (auto& follower : nodes) {
        if (follower.id == candidate.id) continue;
        bool ok = follower.append_entries(candidate.term, {entry});
        if (ok) acks += 1;
        printf("node%d AppendEntries 수신 -> %s, log=%s\n", follower.id,
               ok ? "복제 성공" : "거부", log_str(follower.log).c_str());
    }

    if (majority(acks, (int)nodes.size())) {
        candidate.commit_index = 0;
        printf("엔트리 커밋(과반 %d/%d): (%d, '%s')\n", acks, (int)nodes.size(), entry.term, entry.value.c_str());
    }
}
```
:::

```console title="Raft 시뮬레이션 출력"
node0 후보 등록, term=1, 자기 표 1개
node1 투표 요청 수신 -> 승인
node2 투표 요청 수신 -> 승인
node0 과반(3/3) 확보, 리더 등극
node1 AppendEntries 수신 -> 복제 성공, log=[(1, 'x=1')]
node2 AppendEntries 수신 -> 복제 성공, log=[(1, 'x=1')]
엔트리 커밋(과반 3/3): (1, 'x=1')
```

**복잡도:** 시간 $O(n)$(노드 수 $n$) — 선출과 복제 각각 후보/리더가 나머지 $n-1$개 노드에 한 번씩 메시지를 보내므로 라운드당 $O(n)$, 라운드 수는 상수(선출 1회, 복제 1회)다. 공간 $O(n + L)$ — 노드당 로그 길이 $L$을 저장하며 실제 Raft에서는 이 로그가 무한히 자라는 것을 스냅샷으로 막는다(이 챕터 범위 밖).

| 언어 차이 | Python | C++ |
|---|---|---|
| "미투표" 표현 | `voted_for = None` | `voted_for = -1`(정수 필드라 sentinel 값이 필요하다) |
| 로그 문자열화 | `f"{follower.log}"`가 튜플 리스트를 자동으로 `[(1, 'x=1')]` 형태로 찍는다 | `log_str()` 헬퍼로 같은 문자열을 직접 조립해야 한다 — C++ 컨테이너는 기본 문자열 표현이 없다 |

::: pitfall
**"과반"을 `count >= n // 2`로 짜면 짝수 노드에서 틀린다.** 4개 노드면 `n // 2 = 2`이고 `count >= 2`는 정확히 절반(2표)도 과반으로 인정해 버린다 — 두 후보가 각각 2표씩 받는 상황이 가능해지고 리더가 둘 생긴다. `count > n // 2`(정수 나눗셈은 내림이므로 4에서는 `count > 2`, 즉 3표 이상)여야 한다.

**텀 비교를 빠뜨리면 죽었다 살아난 리더가 과거 텀으로 계속 자신을 리더라고 우긴다.** `request_vote`와 `append_entries` 둘 다 들어오는 메시지의 텀이 자신보다 낮으면 무조건 거부하고, 높으면 무조건 자신의 텀을 올리고 팔로워로 강등되는 코드가 있어야 한다 — 이 규칙이 없으면 "지금 누가 진짜 리더인가"에 대한 합의 자체가 깨진다.

**투표 조건에서 로그 길이 비교를 빼면 커밋된 엔트리가 사라질 수 있다.** 위 구현의 `log_ok` 검사가 그것이다 — 로그가 자신보다 짧은 후보에게는 투표하지 않는다. 이게 없으면 커밋된 엔트리를 못 가진 노드가 리더가 될 수 있고, 그 리더는 존재하지 않는 과거로 시스템을 되돌린다.
:::

## 5. 어디에 쓰이는가

etcd, Consul, CockroachDB 같은 분산 KV 스토어가 Raft로 리더를 뽑고 설정값·메타데이터를 복제한다 — Kubernetes의 클러스터 상태가 etcd에, etcd가 Raft에 얹혀 있다. 벡터 시계는 여러 데이터센터에 흩어진 노드들이 "이 쓰기가 저 쓰기보다 먼저인지"를 판정해야 하는 멀티 마스터 복제(예: 예전 버전의 Amazon Dynamo, Riak)에서 쓰인다. CRDT는 리더 없이도 협업 편집기(여러 사용자가 동시에 문서를 고치는 상황)나 모바일 앱의 오프라인 동기화(네트워크가 끊긴 동안 각자 로컬에서 수정한 내용을 나중에 합치는 상황)에서 조율 비용 없이 병합하는 데 쓰인다.

## 연습

::: quiz
**1. 설정 서비스의 일관성**
- 상황: 마이크로서비스 수백 개가 공유하는 설정값(피처 플래그, 라우팅 규칙)을 저장하는 서비스를 만든다. 설정이 바뀌면 모든 서비스가 곧 같은 값을 봐야 하고, 서버 한 대가 죽어도 설정 조회가 멈추면 안 된다.
- 무엇이 병목이거나 깨지는가: 리더 없이 아무 노드나 쓰기를 받으면 두 서버가 같은 시각 다른 값으로 같은 플래그를 바꿀 때 어느 쪽이 이기는지 정할 방법이 없다.
- 어떤 구조이고 무엇을 대가로 치르는가: Raft 기반 복제(etcd류). 모든 쓰기가 리더를 거치므로 쓰기 처리량은 리더 한 대 성능에 묶이지만, 그 대가로 "설정값에 대해 노드마다 다른 답을 준다"는 상황이 구조적으로 없어진다.

**2. 여러 지역에 흩어진 사용자 세션 카운터**
- 상황: 전 세계 리전마다 서버가 있고, 각 리전은 자신에게 접속한 사용자 수를 센다. 전체 접속자 수를 실시간에 가깝게 보고 싶고, 리전 간 네트워크가 잠깐 끊겨도 각 리전은 자기 카운트를 계속 늘릴 수 있어야 한다.
- 무엇이 병목이거나 깨지는가: 리전마다 리더를 거쳐야 한다면 리전 간 지연 때문에 카운트 증가마다 대륙 간 왕복이 필요해진다. 실시간 카운터에 그 지연은 못 견딘다.
- 어떤 구조이고 무엇을 대가로 치르는가: G-Counter. 각 리전이 자기 칸만 독립적으로 늘리고, 네트워크가 복구되면 원소별 최댓값으로 병합한다. 대가는 "지금 이 순간의 정확한 합"이 아니라 "각 리전이 마지막으로 안 시점 기준의 합"이라는 근사다 — 리전이 끊긴 동안의 증가분은 복구 후에야 반영된다.

**3. 협업 문서 편집기의 오프라인 지원**
- 상황: 여러 사용자가 문서 하나를 동시에 편집한다. 네트워크가 끊긴 사용자도 로컬에서 계속 수정할 수 있어야 하고, 재접속하면 자동으로 병합돼야 한다. 사용자가 수동으로 충돌을 해결하는 UI는 만들지 않기로 했다.
- 무엇이 병목이거나 깨지는가: 리더에게 매 키 입력마다 확인받는 구조는 오프라인에서 아예 동작하지 않는다. 그렇다고 마지막에 쓴 사람이 이기는 방식(last-write-wins)을 쓰면 두 사용자가 각자 다른 문단을 추가했을 때 한쪽 작업이 통째로 사라진다.
- 어떤 구조이고 무엇을 대가로 치르는가: OR-Set류 CRDT(문서를 원소들의 집합으로 모델링). 추가·삭제가 조율 없이 병합되므로 오프라인 편집이 그대로 동작한다. 대가는 자료구조 자체의 복잡도와 메모리다 — 삭제된 원소의 태그를 무한정 못 지우면 문서 크기가 실제 내용보다 계속 불어난다(가비지 컬렉션이 필요하고, 이 챕터 범위 밖이다).
:::

## 요약

- 분산 합의가 어려운 이유는 알고리즘이 아니라 전제다 — 네트워크는 메시지를 잃고 늦추고 순서를 바꾸고, 노드는 멈췄다 재시작한다.
- Raft는 텀(되돌아가지 않는 논리적 시간)과 과반수 투표로 "리더는 한 텀에 하나"를 보장한다.
- 로그 엔트리는 과반이 받아 적어야 커밋되고, 리더 선출 시 로그가 짧은 후보는 표를 받지 못해 커밋된 엔트리가 보존된다.
- 이 챕터는 리더 선출과 로그 복제까지다 — 멤버십 변경, 스냅샷, 로그 압축은 다루지 않는다.
- 벡터 시계는 "몇 시에 일어났는가"가 아니라 "어느 사건이 어느 사건을 인과적으로 아는가"에 답한다.
- CRDT는 병합 연산 자체를 충돌이 나지 않게 설계한 자료구조다 — G-Counter는 원소별 최댓값으로, OR-Set은 태그 기반 추가·삭제로 조율 없이 병합된다.
- FLP와 CAP은 "완벽한 합의는 이상적 조건에서만 가능하다"는 한계선이고, 실무 시스템은 타임아웃과 과반수 투표로 그 한계 안에서 동작한다.
