# XV-12 메모리에 안 들어가는 데이터 처리

::: lead
10GB짜리 로그 파일을 4GB RAM으로 정렬하려면, 정렬 알고리즘 자체가 아니라 무엇을 바꿔야 하는가.
:::

## 1. 문제

`sorted()`나 `std::sort`는 데이터 전체가 메모리에 올라와 있다고 전제한다. [II-7 정렬](#/ii-7)에서 다룬 Timsort와 introsort 둘 다 "배열 하나를 통째로 손에 쥐고" 비교·교환한다. 로그 파일이 10GB인데 서버 메모리가 4GB라면, 파일을 통째로 읽어 들이는 순간 프로세스가 죽거나 스와핑으로 사실상 멈춘다. 정렬 알고리즘을 아무리 잘 골라도 **자료구조가 메모리 밖에 있다는 전제 자체를 바꾸지 않으면** 문제가 안 풀린다.

이 문제는 낯설지 않다. [XV-1](#/xv-1)이 이 Part 전체의 전제로 세운 것 — 메모리에 다 들어간다는 가정이 깨지는 순간 무엇이 달라지는가 — 를 정렬이라는 가장 기본적인 연산에 적용하면 무엇이 나오는가가 이 챕터다. 집계(합계·평균·최댓값)도 같은 문제를 겪는다. 네트워크에서 들어오는 로그 스트림은 애초에 "전체"라는 것이 없다 — 지금 이 순간까지 본 것만 있고, 두 번 읽을 수도 없다.

## 2. 아이디어

### 외부 정렬 — 자르고, 각자 정렬하고, 병합한다

```text nolines
input (10GB, RAM 4GB)
   |
   +- step 1: split into chunks (in-memory size, e.g. 1GB each)
   |     chunk0 --sort--> disk: chunk0.sorted
   |     chunk1 --sort--> disk: chunk1.sorted
   |     ...
   |     chunk9 --sort--> disk: chunk9.sorted
   |
   +- step 2: k-way merge
         chunk0.sorted --+
         chunk1.sorted --+
             ...         +--> [min-heap, size k] --> sorted output   (최종 정렬 결과)
         chunk9.sorted --+
```

1단계는 그냥 [II-7 정렬](#/ii-7)이다 — 다만 한 번에 전체가 아니라 메모리에 들어갈 만큼씩 나눠서 돌린다. 청크 하나하나는 정렬된 채로 디스크에 쌓인다.

2단계가 핵심이다. **정렬된 청크가 $k$개 있으면, 각 청크의 맨 앞을 가리키는 포인터가 $k$개 있는 것과 같다.** 모든 포인터가 가리키는 값 중 최솟값을 뽑아 출력하고, 그 값이 나온 청크의 포인터만 한 칸 전진시킨다 — 이것이 [VI-3 투 포인터](#/vi-3)의 정확히 그 아이디어를, 포인터 2개에서 $k$개로 늘린 것이다. "최솟값을 매번 골라야 한다"는 부분이 남는데, 포인터가 2개면 비교 한 번으로 끝나지만 $k$개면 매번 $k$개를 다 비교하는 건 낭비다. 여기서 [II-8 힙](#/ii-8)이 들어온다 — $k$개의 "현재 후보값"을 최소 힙에 넣어 두면, 최솟값을 뽑는 데 $O(\log k)$, 새 값을 넣는 데 $O(\log k)$다. **정렬은 II-7의 디스크 판이고, 병합은 VI-3의 다중 포인터 판이며, 그 다중 포인터를 빠르게 굴리는 엔진이 II-8이다** — 이 챕터가 세 챕터를 한 자리에 모은다.

메모리에는 각 청크의 "지금 값" $k$개와 청크별 읽기 버퍼만 있으면 된다. 전체 10GB 중 어느 순간에도 메모리에 실제로 올라와 있는 것은 청크 하나(정렬 단계)와 $k$개의 값(병합 단계)뿐이다.

### 스트리밍 집계 — 한 번 지나가면서 답을 다 만든다

합계·평균·최댓값 같은 값은 데이터 전체를 들고 있을 필요가 없다. `total += v`, `count += 1`, `maximum = max(maximum, v)`처럼 **지금까지 본 값들의 요약**만 유지하면 새 값이 올 때마다 요약을 갱신하고 원본은 버려도 된다. 이 방식이 필요한 이유는 메모리 절약만이 아니다 — 네트워크 스트림이나 실시간 로그는 "전체를 다시 읽는다"는 연산 자체가 없다. 한 번 지나간 데이터는 다시 오지 않는다. 두 번 이상 읽어야 하는 알고리즘(예: 정확한 중앙값)은 스트림에서 그대로 못 쓴다 — [XV-6 카디널리티·빈도 추정](#/xv-6)이 그 한계를 확률적 자료구조로 우회하는 방법을 다룬다.

### MapReduce의 셔플 — 사실은 분산 외부 정렬

MapReduce에서 map 단계가 끝나면 각 map 태스크가 만든 `(key, value)` 쌍들을 reduce 태스크로 보내는 **셔플(shuffle)** 단계가 있다. 이 단계가 하는 일은 두 가지뿐이다. **① 키로 파티션한다**(어느 reduce 태스크로 보낼지 키의 해시로 정한다) **② 각 파티션 안에서 키로 정렬한다**(같은 키를 가진 값들이 reduce에서 한데 모이도록). 노드가 여러 대라는 것만 빼면 이것은 정확히 위에서 본 외부 정렬이다 — map 태스크 각각이 "청크를 정렬해 디스크에 쓰는" 역할을, 셔플이 "여러 정렬된 조각을 키 순서로 병합하는" 역할을 한다. 다른 점은 청크가 다른 서버에 있어서 병합 전에 네트워크로 옮겨야 한다는 것뿐이다. **분산 처리의 핵심 연산이 결국 정렬과 병합**이라는 사실이 이 절이 짚는 전부다 — 완전한 MapReduce 구현(태스크 스케줄링, 장애 복구, 컴바이너)은 이 챕터의 범위 밖이다.

## 4. 구현

청크 정렬과 $k$-way 병합을 실제 파일로 짠다. 청크를 임시 디렉터리에 파일로 쓰고, 병합할 때 각 파일에서 한 줄씩만 읽는다 — 어느 순간에도 파일 전체를 메모리에 올리지 않는다.

::: dual
```python title="외부 정렬 — 청크 정렬 + k-way 병합"
import heapq
import os
import tempfile


def split_and_sort_chunks(data, chunk_size, tmpdir):
    """데이터를 chunk_size씩 잘라 각각 정렬한 뒤 파일로 쓴다. 파일 경로 목록을 반환한다."""
    paths = []
    for i in range(0, len(data), chunk_size):
        chunk = sorted(data[i:i + chunk_size])
        path = os.path.join(tmpdir, f"chunk_{i // chunk_size}.txt")
        with open(path, "w") as f:
            for v in chunk:
                f.write(f"{v}\n")
        paths.append(path)
    return paths


def k_way_merge(paths, out_path):
    """각 청크 파일의 맨 앞을 가리키는 k개의 포인터 -- 힙으로 그중 최솟값을 매번 뽑는다."""
    files = [open(p) for p in paths]
    heap = []
    for i, f in enumerate(files):
        line = f.readline()
        if line:
            heapq.heappush(heap, (int(line), i))

    with open(out_path, "w") as out:
        while heap:
            val, i = heapq.heappop(heap)
            out.write(f"{val}\n")
            line = files[i].readline()
            if line:
                heapq.heappush(heap, (int(line), i))

    for f in files:
        f.close()


if __name__ == "__main__":
    data = [37, 12, 45, 3, 89, 21, 5, 67, 14, 99, 2, 58, 33, 76, 8]
    chunk_size = 4
    with tempfile.TemporaryDirectory() as tmpdir:
        paths = split_and_sort_chunks(data, chunk_size, tmpdir)
        print(f"청크 {len(paths)}개, 청크당 최대 {chunk_size}개")
        for p in paths:
            with open(p) as f:
                print(f"  {os.path.basename(p)}: {[int(x) for x in f.read().split()]}")

        out_path = os.path.join(tmpdir, "merged.txt")
        k_way_merge(paths, out_path)
        with open(out_path) as f:
            merged = [int(x) for x in f.read().split()]
        print(f"병합 결과: {merged}")
        print(f"정렬 확인(표준 정렬 결과와 대조): {merged == sorted(data)}")
```
```cpp title="외부 정렬 — 청크 정렬 + k-way 병합"
#include <cstdio>
#include <vector>
#include <algorithm>
#include <fstream>
#include <string>
#include <queue>
#include <filesystem>

namespace fs = std::filesystem;

std::vector<std::string> split_and_sort_chunks(const std::vector<int>& data, int chunk_size,
                                                 const fs::path& tmpdir) {
    std::vector<std::string> paths;
    for (size_t i = 0; i < data.size(); i += chunk_size) {
        std::vector<int> chunk(data.begin() + i, data.begin() + std::min(data.size(), i + chunk_size));
        std::sort(chunk.begin(), chunk.end());
        fs::path path = tmpdir / ("chunk_" + std::to_string(i / chunk_size) + ".txt");
        std::ofstream f(path);
        for (int v : chunk) f << v << "\n";
        paths.push_back(path.string());
    }
    return paths;
}

void k_way_merge(const std::vector<std::string>& paths, const std::string& out_path) {
    std::vector<std::ifstream> files(paths.size());
    for (size_t i = 0; i < paths.size(); ++i) files[i].open(paths[i]);

    // (값, 청크 인덱스) -- 최소 힙
    using Item = std::pair<int, int>;
    std::priority_queue<Item, std::vector<Item>, std::greater<Item>> heap;

    for (size_t i = 0; i < files.size(); ++i) {
        int v;
        if (files[i] >> v) heap.push({v, (int)i});
    }

    std::ofstream out(out_path);
    while (!heap.empty()) {
        auto [val, i] = heap.top();
        heap.pop();
        out << val << "\n";
        int v;
        if (files[i] >> v) heap.push({v, i});
    }
}

int main() {
    std::vector<int> data = {37, 12, 45, 3, 89, 21, 5, 67, 14, 99, 2, 58, 33, 76, 8};
    int chunk_size = 4;

    fs::path tmpdir = fs::temp_directory_path() / "algobook_extsort_demo";
    fs::remove_all(tmpdir);
    fs::create_directories(tmpdir);

    auto paths = split_and_sort_chunks(data, chunk_size, tmpdir);
    printf("청크 %zu개, 청크당 최대 %d개\n", paths.size(), chunk_size);
    for (auto& p : paths) {
        std::ifstream f(p);
        std::vector<int> vals;
        int v;
        while (f >> v) vals.push_back(v);
        std::string name = fs::path(p).filename().string();
        printf("  %s: [", name.c_str());
        for (size_t j = 0; j < vals.size(); ++j) {
            if (j) printf(", ");
            printf("%d", vals[j]);
        }
        printf("]\n");
    }

    std::string out_path = (tmpdir / "merged.txt").string();
    k_way_merge(paths, out_path);
    std::ifstream f(out_path);
    std::vector<int> merged;
    int v;
    while (f >> v) merged.push_back(v);
    printf("병합 결과: [");
    for (size_t j = 0; j < merged.size(); ++j) {
        if (j) printf(", ");
        printf("%d", merged[j]);
    }
    printf("]\n");

    std::vector<int> expect = data;
    std::sort(expect.begin(), expect.end());
    printf("정렬 확인(표준 정렬 결과와 대조): %s\n", (merged == expect) ? "True" : "False");

    fs::remove_all(tmpdir);
}
```

**복잡도:** 시간 $O(n \log B + n \log k)$ — $n$은 전체 원소 수, $B$는 청크 크기, $k$는 청크 개수($k = n/B$). 청크 정렬에 청크당 $O(B \log B)$이고 청크가 $k$개이므로 $O(kB\log B) = O(n \log B)$. 병합은 원소마다 힙에서 pop 한 번, push 한 번, 각 $O(\log k)$이므로 $O(n \log k)$. 공간 $O(B + k)$ — 어느 순간에도 메모리에는 정렬 중인 청크 하나($O(B)$)와 병합용 힙($O(k)$)만 있다. 원본 데이터 $n$이 아무리 커도 메모리 사용량은 $B$와 $k$로만 결정된다.

**디스크 접근**은 시간이 아니라 이 알고리즘의 진짜 단위다. 청크 생성 단계에서 원본을 한 번 순차로 읽고 청크를 한 번 순차로 쓴다(입력 1패스). 병합 단계에서 모든 청크를 한 번씩 순차로 읽고 결과를 한 번 순차로 쓴다(입력 1패스, 출력 1패스). **한 번의 청크 생성 + 한 번의 병합으로 끝나는 것을 2-패스 외부 정렬이라 부르는데, 이는 청크 개수 $k$가 한 번에 열어 둘 수 있는 파일 개수(운영체제 한도, 보통 수백~수천)를 넘지 않을 때만 성립한다.** $k$가 그 한도를 넘으면 병합을 여러 단계로 나눠야 하고(먼저 청크 몇 개씩 묶어 병합한 뒤 그 결과를 다시 병합), 그만큼 디스크를 더 여러 번 읽고 쓰게 된다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 파일 읽기 | `f.readline()`이 `""`(빈 문자열)을 반환하면 EOF | `files[i] >> v`가 스트림 상태를 `bool`로 반환하며, 실패하면 `if` 조건이 거짓 |
| 임시 디렉터리 | `tempfile.TemporaryDirectory()`가 `with` 블록을 벗어나면 자동 삭제 | `std::filesystem`에 자동 삭제 기능이 없어 `fs::remove_all()`을 직접 호출해야 한다 |
| 우선순위 큐 방향 | `heapq`는 최소 힙 고정이라 `(val, idx)` 튜플을 그대로 넣으면 값이 작은 것부터 나온다 | `priority_queue`는 최대 힙 기본이라 `std::greater<Item>`을 명시해야 최소 힙이 된다 |

::: pitfall
**청크 크기를 정할 때 "메모리에 들어가는 만큼 최대로" 잡고 싶은 유혹이 있는데, 청크가 커질수록 청크 개수는 줄고 개별 청크 정렬 비용은 늘어난다.** 청크가 지나치게 작으면 청크 개수 $k$가 폭발해 한 번에 열어야 하는 파일 수가 운영체제 한도를 넘는다. 실무에서는 가용 메모리의 상당 부분을 청크 하나에 쓰고, 나머지를 병합용 버퍼(각 청크 파일마다 조금씩 미리 읽어 두는 버퍼)에 배분한다.

**힙에 넣을 때 값만 넣고 어느 청크에서 왔는지(인덱스)를 빠뜨리면 다음에 어느 파일에서 읽어야 할지 알 수 없다.** 위 구현의 `(val, i)` 튜플에서 `i`가 그 역할이다 — 정렬 기준은 `val`이지만 진행 상태를 추적하는 열쇠는 `i`다.

**동점 값이 여러 청크에 걸쳐 있을 때 튜플 비교가 인덱스까지 비교하는 것은 무해하지만, 힙에 넣는 값이 비교 불가능한 타입(예: 딕셔너리)이면 동점에서 비교가 터진다.** `(val, i, payload)`처럼 payload를 힙 정렬 기준 밖으로 빼거나, `i`까지만 비교되도록 명시적으로 키를 지정해야 한다.
:::

이어서 스트리밍 집계다. 데이터를 한 번만 순회하며 개수·합·최댓값·평균을 계산한다 — 값을 리스트에 모아 두지 않는다.

::: dual
```python title="스트리밍 집계 — 한 번의 순회"
def streaming_stats(values):
    """한 번의 순회로 개수, 합, 최댓값, 평균을 계산한다. 값 전체를 저장하지 않는다."""
    count = 0
    total = 0
    maximum = None
    for v in values:
        count += 1
        total += v
        if maximum is None or v > maximum:
            maximum = v
    average = total / count if count else 0.0
    return count, total, maximum, average


def value_stream():
    """한 번만 순회 가능한 스트림을 흉내낸다 -- 제너레이터는 되감을 수 없다."""
    for v in [7, 3, 9, 1, 8, 4, 2]:
        yield v


if __name__ == "__main__":
    stream = value_stream()
    count, total, maximum, average = streaming_stats(stream)
    print(f"count={count} sum={total} max={maximum} avg={average:.4f}")
```
```cpp title="스트리밍 집계 — 한 번의 순회"
#include <cstdio>
#include <vector>

struct Stats {
    long long count;
    long long total;
    int maximum;
    double average;
};

template <typename Iter>
Stats streaming_stats(Iter begin, Iter end) {
    long long count = 0;
    long long total = 0;
    int maximum = 0;
    bool has_max = false;
    for (auto it = begin; it != end; ++it) {
        int v = *it;
        count += 1;
        total += v;
        if (!has_max || v > maximum) {
            maximum = v;
            has_max = true;
        }
    }
    double average = count ? (double)total / count : 0.0;
    return {count, total, maximum, average};
}

int main() {
    // 실제 스트림(소켓, 파일)은 한 번만 순회 가능하다. 여기서는 벡터로 흉내낸다.
    std::vector<int> stream = {7, 3, 9, 1, 8, 4, 2};
    Stats s = streaming_stats(stream.begin(), stream.end());
    printf("count=%lld sum=%lld max=%d avg=%.4f\n", s.count, s.total, s.maximum, s.average);
}
```
:::

```console title="스트리밍 집계 출력"
count=7 sum=34 max=9 avg=4.8571
```

**복잡도:** 시간 $O(n)$ — 값마다 상수 번의 연산(덧셈, 비교)만 하고 다시 들여다보지 않는다. 공간 $O(1)$ — `count`, `total`, `maximum` 세 값만 유지하며, $n$이 얼마든 메모리 사용량이 늘지 않는다. 이 $O(1)$ 공간이 스트리밍 집계의 존재 이유다 — 중앙값처럼 "정렬된 상태에서의 중간값"이 필요한 연산은 이 방식으로 정확히 계산할 수 없다. [XV-6](#/xv-6)의 근사 자료구조로 우회하거나, 값 전체를 보관해야 한다.

## 5. 어디에 쓰이는가

외부 정렬은 데이터베이스의 `ORDER BY`가 메모리 정렬 버퍼를 초과할 때 실행 계획에 등장하는 연산이고(`EXPLAIN` 결과에서 "external merge"로 표시되는 경우가 이것이다), Hadoop·Spark 같은 분산 처리 엔진의 셔플 단계 내부 구현이기도 하다. 스트리밍 집계는 로그 파이프라인(초당 수만 건의 이벤트에서 대시보드용 합계·평균을 실시간으로 갱신)과 ETL(추출-변환-적재 과정에서 원본을 두 번 읽지 않고 한 번에 집계와 변환을 끝내는 것)의 기본기다.

::: quiz
**1. 광고 클릭 로그 정렬**
- 상황: 하루치 광고 클릭 로그가 200GB이고, 사용자 ID로 정렬해 사용자별 클릭 이력을 이어 붙여야 한다. 처리 서버는 32GB RAM이다.
- 무엇이 병목이거나 깨지는가: 200GB를 한 번에 정렬 버퍼에 올리면 즉시 메모리가 터진다. 정렬 알고리즘의 선택(Timsort냐 introsort냐)은 이 문제와 무관하다.
- 어떤 구조이고 무엇을 대가로 치르는가: 외부 정렬. 32GB 중 정렬용으로 쓸 수 있는 부분(예: 20GB)만큼씩 청크로 잘라 정렬해 디스크에 쓰고, 나머지 메모리로 병합한다. 대가는 디스크 I/O — 데이터를 최소 두 번(청크 쓰기, 병합 읽기) 디스크에서 오간다는 것이고, 이 비용이 순수 메모리 정렬보다 몇 자릿수 크다는 것을 받아들여야 한다.

**2. 실시간 매출 대시보드**
- 상황: 결제 이벤트가 초당 수천 건 들어오고, 대시보드는 "지난 5분간 매출 합계"를 1초마다 갱신해 보여줘야 한다. 결제 이벤트 전체를 저장하는 별도 DB가 있지만 매번 거기서 집계 쿼리를 돌리면 DB에 부하가 몰린다.
- 무엇이 병목이거나 깨지는가: 매초 DB에 "지난 5분" 범위 쿼리를 날리면 쿼리 자체가 무거워지고, 이벤트가 몰릴 때 DB가 대시보드 갱신의 병목이 된다.
- 어떤 구조이고 무엇을 대가로 치르는가: 스트리밍 집계 — 이벤트가 들어올 때마다 합계를 갱신하는 인메모리 카운터를 두고 대시보드는 그 카운터만 읽는다. "지난 5분"이라는 슬라이딩 구간을 정확히 유지하려면 5분이 지난 이벤트를 빼는 로직이 필요해 완전한 $O(1)$ 공간은 아니게 되지만(5분치 이벤트 큐는 유지해야 한다), DB 부하는 완전히 없앤다.

**3. 여러 지역 서버의 접속 로그 병합**
- 상황: 리전 10곳의 서버가 각자 시간순으로 정렬된 접속 로그를 남긴다. 전 세계 시간순으로 통합된 로그 하나가 필요하다. 로그 전체를 한 서버로 복사해 다시 정렬하기엔 네트워크 대역폭이 부담스럽다.
- 무엇이 병목이거나 깨지는가: 이미 각 리전 로그는 시간순으로 정렬돼 있다 — 처음부터 다시 정렬하는 것은 이미 가진 정렬 정보를 버리는 낭비다.
- 어떤 구조이고 무엇을 대가로 치르는가: k-way 병합만 하면 된다(10개 리전 = 10개의 이미 정렬된 "청크"). 각 리전 로그를 스트리밍으로 열어 두고 최소 힙으로 다음 항목을 고르면, 전체를 한 곳에 모아 재정렬할 필요 없이 병합 단계만으로 끝난다. 대가는 10개 리전으로의 동시 네트워크 연결을 유지해야 한다는 것과, 한 리전의 연결이 느려지면 병합 전체가 그 리전을 기다려야 한다는 것이다.

## 요약

- 외부 정렬은 청크 단위로 잘라 각자 정렬해 디스크에 쓰고, 정렬된 청크들을 힙으로 k-way 병합한다.
- k-way 병합은 [VI-3 투 포인터](#/vi-3)를 포인터 $k$개로 일반화한 것이고, [II-8 힙](#/ii-8)이 그 $k$개 중 최솟값을 $O(\log k)$에 뽑는 엔진이다.
- 메모리 사용량은 원본 데이터 크기가 아니라 청크 크기와 청크 개수로 결정된다 — 이것이 "메모리 밖 데이터"를 다루는 핵심 트릭이다.
- 스트리밍 집계는 값을 저장하지 않고 요약만 갱신한다. $O(1)$ 공간을 요구하는 대가로, 두 번 이상 읽어야 하는 연산(정확한 중앙값 등)은 이 방식으로 풀 수 없다.
- MapReduce의 셔플은 "키로 파티션한 뒤 각 파티션을 정렬"하는 분산 외부 정렬이다.
- **Part XV의 흐름을 마지막으로 되짚는다.** Part II는 데이터가 메모리에 다 들어간다고 가정했다. 그 가정이 깨지자 [XV-2](#/xv-2)·[XV-3](#/xv-3)이 디스크로 내려가 높이와 쓰기 방식을 다시 설계했고, [XV-4](#/xv-4)·[XV-6](#/xv-6)은 정확성을 확률로 양보해 공간을 줄였고, [XV-8](#/xv-8)·[XV-11](#/xv-11)은 노드 하나를 여러 대로 늘리며 재배치와 합의의 문제를 열었고, 이 챕터는 데이터가 한 노드 안에서도 한 번에 다 볼 수 없을 때 — 디스크보다 크거나, 애초에 스트림이라 다시 볼 수 없을 때 — 무엇이 남는지를 보였다.
