# IX-1 유니온 파인드

::: lead
간선이 하나씩 추가되는 동안 "이 둘이 이미 같은 그룹인가"를 매번 물어야 한다면, 그 답을 거의 상수 시간에 내는 방법은 무엇인가.
:::

## 1. 문제

컴퓨터 $N$대가 있고, 케이블이 하나씩 연결된다. 케이블이 연결될 때마다 "지금 $a$번과 $b$번 컴퓨터가 (직접이든 간접이든) 통신 가능한가"를 즉시 답해야 한다. 연결과 질의가 최대 $10^5$번 섞여서 온라인으로 들어온다.

[IV-2 DFS](#/iv-2)로 풀면 이렇게 된다. 질의가 들어올 때마다 $a$에서 시작해 DFS로 도달 가능한 정점을 전부 훑고 그 안에 $b$가 있는지 본다. 질의 한 번에 $O(V+E)$이고, 질의가 $M$번이면 $O(M(V+E))$다. $V, M$이 각각 $10^5$이면 최악의 경우 $10^{10}$번 넘게 도는 셈이라 시간 안에 끝나지 않는다.

문제는 DFS 자체가 느려서가 아니다. **매 질의마다 그래프 전체를 다시 훑는다는 것**이 낭비다. 케이블이 연결될 때 두 그룹이 합쳐진다는 사실은 그 순간 한 번만 계산하면 되는 정보인데, DFS는 그 정보를 저장해 두지 않고 질의가 올 때마다 처음부터 다시 계산한다.

필요한 것은 두 연산만 빠르게 지원하는 자료구조다. **합치기(union)** — 두 그룹을 하나로 만든다. **찾기(find)** — 이 원소가 속한 그룹의 대표를 알아낸다. 두 원소의 대표가 같으면 같은 그룹이다. 이 둘을 각각 $O(1)$에 가깝게 해내는 자료구조가 **유니온 파인드**(Union-Find, Disjoint Set Union)다.

::: note
"서로소 집합"이라는 이름으로도 부른다. 처음에는 원소 $N$개가 각자 자기 혼자만의 집합이고, union이 그 집합들을 하나씩 합쳐 나간다 — 집합끼리는 항상 겹치지 않는다(서로소).
:::

## 2. 아이디어

각 그룹을 **트리 하나**로 표현한다. 트리의 뿌리가 그 그룹의 대표다. 원소마다 "내 부모가 누구인가"만 배열 하나에 저장한다. 자기 자신이 부모이면 그 원소가 뿌리다.

- **find(x)** — `parent[x]`를 계속 따라 올라가 부모가 자기 자신인 곳(뿌리)에 닿으면 그게 답이다.
- **union(a, b)** — `find(a)`와 `find(b)`로 두 뿌리를 구하고, 한쪽 뿌리의 부모를 다른 쪽 뿌리로 바꾼다. 트리 두 개가 하나로 붙는다.

여기까지만 구현해도 정답은 나온다. 문제는 속도다. **union을 아무 기준 없이 하면 트리가 사슬처럼 깊어질 수 있다.** 매번 뿌리 B를 뿌리 A 아래 붙이는 식으로 순서를 잘못 타면, $N$개를 다 합쳤을 때 트리 높이가 $N$에 달하고 find 한 번이 $O(N)$이 된다. 이러면 애초에 DFS로 매번 훑는 것과 다를 게 없다.

이 문제를 두 가지 독립적인 방법으로 고친다.

**첫째, union-by-rank(또는 union-by-size).** 두 트리를 합칠 때 **더 낮은 트리를 더 높은 트리 아래 붙인다.** 항상 낮은 쪽이 흡수되므로 트리 높이는 붙을 때마다 최대 1만 늘고, 그것도 두 트리의 높이가 같을 때뿐이다. 높이가 $h$인 트리가 가지려면 최소 $2^h$개의 원소가 필요하다는 것을 귀납적으로 보일 수 있고, 따라서 원소가 $N$개면 높이는 $O(\log N)$을 넘지 못한다. **이것만으로 find는 $O(\log N)$이 보장된다.**

**둘째, 경로 압축(path compression).** find(x)가 뿌리까지 가는 길에 지나친 노드들을 **전부 뿌리에 직접 매단다.** 다음에 같은 노드에서 find를 부르면 한 번에 뿌리에 닿는다. **이것만으로도 평균적으로 $O(\log N)$에 가까워진다.**

**둘을 같이 쓰면** 트리가 애초에 잘 안 깊어지는 데다 깊어진 부분도 find 한 번마다 계속 납작해진다. 이때의 분할 상환 복잡도가 $O(\alpha(N))$이고, $\alpha$는 **아커만 함수의 역함수**다. $\alpha(N)$은 $N$이 아무리 커져도 5를 넘지 않는다 — 우주에 있는 원자 수보다 큰 $N$을 넣어도 4다. 실무에서는 **상수로 취급한다.**

::: widget union-find {"n":6,"ops":[["union",1,0],["union",2,1],["union",3,2],["union",4,3],["find",0]],"strategy":"naive","pathCompression":true}
:::

이 위젯은 일부러 최악의 조건을 만든다. `strategy: "naive"`라 union이 랭크를 보지 않고 무조건 두 번째 인자의 뿌리를 첫 번째 인자의 뿌리 아래 붙인다. `union(1,0)`, `union(2,1)`, `union(3,2)`, `union(4,3)`을 순서대로 넣으면 매번 "지금까지의 뿌리"가 새 원소 아래로 들어가면서 사슬이 자란다 — 네 번의 union 뒤에 0에서 뿌리까지 가는 길이 다섯 칸(0→1→2→3→4)이나 된다.

그다음 `find(0)`을 누르면 두 프레임이 나온다. **압축 전** 프레임은 그 다섯 칸짜리 경로를 순서대로 밟는 모습이고, **압축 후** 프레임은 그 경로에 있던 노드 0, 1, 2, 3이 전부 뿌리 4에 직접 매달린 모습이다. 트리 높이가 4에서 1로 한 번의 find로 떨어진다. **다음에 0이나 1이나 2에서 find를 불러도 전부 즉시 뿌리에 닿는다** — 압축이 그 find 한 번만 빠르게 하는 게 아니라 앞으로의 모든 find를 빠르게 만든다는 것이 핵심이다.

## 3. 손으로 따라가기

::: trace
원소 6개(`0`~`5`), 전략은 위젯과 같은 **랭크 없는(naive) union** + **경로 압축**. 연산 순서: `union(1,0)`, `union(2,1)`, `union(3,2)`, `union(4,3)`, `find(0)`. `union(a,b)`는 "b의 뿌리를 a의 뿌리 아래 붙인다"는 뜻이다.

- [ ] 스텝 6에서 부모 배열의 몇 칸이 바뀌는가. 바뀌지 않는 칸이 있다면 어디이고 왜인가

::: answer
| 스텝 | 연산 | 부모 배열 `[0,1,2,3,4,5]` | 비고 |
|---|---|---|---|
| 0 | 시작 | `[0,1,2,3,4,5]` | 전부 자기 자신이 뿌리 |
| 1 | union(1,0) | `[1,1,2,3,4,5]` | 뿌리 0을 뿌리 1 아래로 |
| 2 | union(2,1) | `[1,2,2,3,4,5]` | 뿌리 1을 뿌리 2 아래로 — 0은 안 건드림 |
| 3 | union(3,2) | `[1,2,3,3,4,5]` | 뿌리 2를 뿌리 3 아래로 |
| 4 | union(4,3) | `[1,2,3,4,4,5]` | 뿌리 3을 뿌리 4 아래로. 이제 0→1→2→3→4가 사슬 |
| 5 | find(0) — 압축 전 | `[1,2,3,4,4,5]` | 경로 `[0,1,2,3,4]`, 다섯 칸을 전부 밟는다 |
| 6 | find(0) — 압축 후 | `[4,4,4,4,4,5]` | 0,1,2,3이 전부 뿌리 4에 직접 매달린다 |

**첫 번째.** 경로는 `0 → 1 → 2 → 3 → 4`, 다섯 칸(노드 5개, 간선 4개)이다. union 네 번이 전부 "새 원소 아래 지금까지의 뿌리를 붙이는" 순서였기 때문에 매번 사슬이 한 칸씩 자랐다.

**두 번째.** 바뀌는 칸은 0, 1, 2, 3 — 경로에서 뿌리를 제외한 전부다. **5번은 이 union들에 한 번도 등장하지 않았으므로 그대로 자기 자신이 뿌리다.** 압축은 find가 실제로 밟은 경로만 건드리고, 트리의 나머지 부분에는 손을 대지 않는다.

**세 번째.** 압축 후 `parent[1] = 4`이므로 `find(1)`은 `1 → 4` 한 칸 만에 끝난다. 압축 전이었다면 `1 → 2 → 3 → 4`로 세 칸이 걸렸을 것이다. **이번 find가 다음 find들의 비용까지 미리 깎아 놓았다.**

## 4. 구현

::: dual
```python title="유니온 파인드 — naive 대조와 union-by-rank + 경로 압축"
def find_naive(x, parent):
    """압축도 균형도 없다. 뿌리까지 그냥 올라간다."""
    while parent[x] != x:
        x = parent[x]
    return x


def union_naive(a, b, parent):
    """항상 b의 뿌리를 a의 뿌리 아래 붙인다 — 순서에 따라 사슬이 생긴다."""
    ra, rb = find_naive(a, parent), find_naive(b, parent)
    if ra != rb:
        parent[rb] = ra


def find(x, parent):
    """경로 압축 — 뿌리를 먼저 찾고, 지나온 길 전부를 뿌리에 직접 매단다."""
    root = x
    while parent[root] != root:
        root = parent[root]
    while parent[x] != root:
        parent[x], x = root, parent[x]
    return root


def union_(a, b, parent, rank):
    """union-by-rank — 랭크가 낮은 뿌리를 높은 뿌리 아래 붙인다."""
    ra, rb = find(a, parent), find(b, parent)
    if ra == rb:
        return
    if rank[ra] < rank[rb]:
        ra, rb = rb, ra
    parent[rb] = ra
    if rank[ra] == rank[rb]:
        rank[ra] += 1


OPS = [(1, 0), (2, 1), (3, 2), (4, 3)]   # 손추적·위젯과 같은 순서
N = 6

p_naive = list(range(N))
for a, b in OPS:
    union_naive(a, b, p_naive)
print("[압축도 랭크도 없음]")
print("  union 4번 후 부모 배열 =", p_naive)

path = [0]
while p_naive[path[-1]] != path[-1]:
    path.append(p_naive[path[-1]])
print("  find(0)이 밟는 경로 =", path, "(길이 %d)" % len(path))

p_compressed = p_naive[:]
root = find(0, p_compressed)
print("  find(0) 압축 후 부모 배열 =", p_compressed, "(뿌리 %d)" % root)

p_best = list(range(N))
rank = [0] * N
for a, b in OPS:
    union_(a, b, p_best, rank)
print("[union-by-rank]")
print("  같은 union 4번 후 부모 배열 =", p_best)
```
```cpp title="유니온 파인드 — naive 대조와 union-by-rank + 경로 압축"
#include <iostream>
#include <string>
#include <vector>
using namespace std;

string fmt(const vector<int>& v) {
    string s = "[";
    for (size_t i = 0; i < v.size(); i++) { if (i) s += ", "; s += to_string(v[i]); }
    return s + "]";
}

int find_naive(int x, vector<int>& parent) {
    // 압축도 균형도 없다. 뿌리까지 그냥 올라간다.
    while (parent[x] != x) x = parent[x];
    return x;
}

void union_naive(int a, int b, vector<int>& parent) {
    // 항상 b의 뿌리를 a의 뿌리 아래 붙인다 — 순서에 따라 사슬이 생긴다.
    int ra = find_naive(a, parent), rb = find_naive(b, parent);
    if (ra != rb) parent[rb] = ra;
}

int find(int x, vector<int>& parent) {
    // 경로 압축 — 뿌리를 먼저 찾고, 지나온 길 전부를 뿌리에 직접 매단다.
    int root = x;
    while (parent[root] != root) root = parent[root];
    while (parent[x] != root) { int nx = parent[x]; parent[x] = root; x = nx; }
    return root;
}

void union_(int a, int b, vector<int>& parent, vector<int>& rank_) {
    // union-by-rank — 랭크가 낮은 뿌리를 높은 뿌리 아래 붙인다.
    int ra = find(a, parent), rb = find(b, parent);
    if (ra == rb) return;
    if (rank_[ra] < rank_[rb]) swap(ra, rb);
    parent[rb] = ra;
    if (rank_[ra] == rank_[rb]) rank_[ra] += 1;
}

int main() {
    vector<pair<int, int>> OPS = {{1, 0}, {2, 1}, {3, 2}, {4, 3}};   // 손추적·위젯과 같은 순서
    int N = 6;

    vector<int> p_naive(N);
    for (int i = 0; i < N; i++) p_naive[i] = i;
    for (auto [a, b] : OPS) union_naive(a, b, p_naive);
    printf("[압축도 랭크도 없음]\n");
    printf("  union 4번 후 부모 배열 = %s\n", fmt(p_naive).c_str());

    vector<int> path = {0};
    while (p_naive[path.back()] != path.back()) path.push_back(p_naive[path.back()]);
    printf("  find(0)이 밟는 경로 = %s (길이 %d)\n", fmt(path).c_str(), (int)path.size());

    vector<int> p_compressed = p_naive;
    int root = find(0, p_compressed);
    printf("  find(0) 압축 후 부모 배열 = %s (뿌리 %d)\n", fmt(p_compressed).c_str(), root);

    vector<int> p_best(N), rank_(N, 0);
    for (int i = 0; i < N; i++) p_best[i] = i;
    for (auto [a, b] : OPS) union_(a, b, p_best, rank_);
    printf("[union-by-rank]\n");
    printf("  같은 union 4번 후 부모 배열 = %s\n", fmt(p_best).c_str());
    return 0;
}
```

```console

  union 4번 후 부모 배열 = [1, 2, 3, 4, 4, 5]
  find(0)이 밟는 경로 = [0, 1, 2, 3, 4] (길이 5)
  find(0) 압축 후 부모 배열 = [4, 4, 4, 4, 4, 5] (뿌리 4)

```

마지막 줄이 이 챕터의 요점을 숫자로 보여준다. **같은 union 네 번인데** naive 판은 사슬(높이4)이 생기고, union-by-rank 판은 처음부터 별 모양(높이1)이다. 랭크 하나가 애초에 사슬을 못 만들게 막는다.

**복잡도:** union-by-rank만 쓰면 시간 $O(\log N)$ — 높이가 $h$인 트리는 원소가 최소 $2^h$개이므로 $N$개를 다 합쳐도 $h \le \log_2 N$이다. 경로 압축만 쓰면 분할 상환 $O(\log N)$ — 한 번의 깊은 find가 앞으로의 find들을 얕게 만들어 평균을 끌어내린다. **둘을 같이 쓰면** 분할 상환 $O(\alpha(N))$이고, $\alpha(N) \le 4$가 사실상 모든 $N$에서 성립하므로 실무에서는 $O(1)$로 취급한다. 공간은 $O(N)$ — 부모 배열(과 랭크 배열) 하나씩.

| 언어 차이 | Python | C++ |
|---|---|---|
| 스왑 | `ra, rb = rb, ra` | `swap(ra, rb)` |
| 재귀 깊이 | `find`를 재귀로 짜면 사슬이 깊을 때 `RecursionError`가 날 수 있다([0-2](#/0-2)) — 그래서 이 코드는 반복문으로 짰다 | 스택이 더 크지만 재귀도 안전을 보장하지 않는다. 실전에서는 양쪽 다 반복문 find를 쓴다 |
| 배열 초기화 | `list(range(N))` | `for (int i = 0; i < N; i++) parent[i] = i;` — `iota(parent.begin(), parent.end(), 0)`로도 쓴다 |

::: pitfall
- **`find`를 압축 없이 짜 놓고 "경로 압축을 썼다"고 착각한다.** 뿌리를 반환하기만 하고 부모 배열을 갱신하지 않으면 압축이 아니다. 반드시 찾은 뿌리를 경로의 모든 노드에 다시 써 줘야 한다.
- **union에서 이미 같은 집합인지 확인하지 않는다.** `find(a) == find(b)`인데 그대로 `parent[rb] = ra`를 실행하면 자기 자신을 자기 부모로 놓는 꼴은 아니지만, 크루스칼([IX-4](#/ix-4))처럼 "합쳐졌으면 True, 이미 같으면 False"를 반환값으로 써야 하는 경우 이 확인을 빼먹으면 사이클 판정이 깨진다.
- **union-by-rank 없이 매번 같은 방향으로만 합친다.** 예를 들어 항상 번호가 작은 쪽 아래 큰 쪽을 붙이면, 입력이 `union(0,1), union(1,2), union(2,3), ...` 순서로 들어올 때 정확히 사슬이 만들어진다. 입력 순서를 통제할 수 없는 이상 랭크나 크기 기준은 선택이 아니라 필수다.
- **랭크를 "지금까지 합쳐진 원소 수"로 착각한다.** 랭크는 **트리 높이의 상한**이지 원소 개수가 아니다. 원소 개수를 쓰려면 그것은 별도의 union-by-size이고, 갱신 규칙이 다르다(둘 다 갱신하는 것이 아니라 어느 한쪽만 쓴다).
:::

## 5. 어디에 쓰이는가

**이미지의 연결 요소 라벨링(connected component labeling)이 유니온 파인드의 정석적인 용례다.** 이진 이미지를 위에서 아래로, 왼쪽에서 오른쪽으로 한 번만 훑으면서 각 픽셀에 임시 라벨을 붙이다가, 왼쪽 픽셀과 위쪽 픽셀의 라벨이 다른데 둘 다 전경이면 그 두 라벨을 유니온으로 합친다. 스캔이 끝난 뒤 각 라벨의 뿌리를 find로 구하면 그것이 최종 blob(연결된 덩어리) 번호다. 이 두 번 훑기(two-pass) 알고리즘이 [IV-5 플러드필과 연결 요소 라벨링](#/iv-5)의 BFS/DFS 방식보다 이미지를 순차적으로 한 방향으로만 스캔해도 되는 하드웨어 친화적인 대안이고, 유니온 파인드가 그 접합부를 담당한다.

**맵 병합도 같은 구조다.** 여러 로봇이나 여러 센서가 각자 부분 지도를 만들다가 겹치는 영역을 발견하면, 그 두 지도가 실은 같은 공간이라는 것을 유니온으로 기록한다. 이후 "이 두 관측이 같은 실제 지점을 가리키는가"를 find로 즉시 답할 수 있다. 지도가 몇 번이고 부분적으로 합쳐지는 온라인 상황이라는 점에서 정확히 이 챕터가 다룬 문제 형태다.

**[IX-4 최소 신장 트리](#/ix-4)의 크루스칼 알고리즘은 유니온 파인드 없이는 성립하지 않는다.** 간선을 가중치 순으로 정렬해 하나씩 보면서 "이 간선의 양 끝이 이미 같은 집합인가"만 물으면 사이클 여부를 즉시 알 수 있고, 그 질의가 바로 find다.

## 6. 이 유형을 알아보는 법

::: classify
- 신호어: "같은 그룹에 속해 있는가", "합집합 연산", "친구 네트워크", "연결되어 있는지", "이 둘을 합쳐라", 그래프에 간선을 하나씩 추가하면서 "사이클이 생기는가"를 묻는 문장
- 제약조건: 원소(정점) 수 $N$과 연산(union·find) 수 $M$이 각각 $10^5 \sim 10^6$까지 허용된다. **연산이 시간순으로 온라인으로 섞여 들어오는 것**이 결정적 조건이다 — 질의마다 그래프 상태가 바뀐다
- 혼동 주의: 그래프가 끝까지 다 만들어진 뒤에 한 번만 연결성을 묻는다면 [IV-2 DFS](#/iv-2)나 [IV-3 BFS](#/iv-3) 한 번으로 충분하다. 최단 거리나 경로 자체를 구해야 하면 이건 유니온 파인드가 아니라 BFS·다익스트라([V-1](#/v-1))다. 유니온 파인드는 "같은 집합인가"만 답할 뿐 **두 정점 사이의 실제 경로는 복원하지 못한다**
- 반례 함정: union에 랭크나 크기 기준을 안 넣으면 특정 입력 순서(사슬형 union 순서)에서 트리가 $O(N)$까지 깊어진다. 예제 데이터가 무작위 순서라 우연히 통과하다가, 정렬된 순서로 들어오는 큰 입력(크루스칼처럼 간선을 가중치 순으로 정렬한 뒤 union하는 경우)에서 시간 초과가 난다
:::

::: interview
**"경로 압축이 왜 시간 복잡도를 낮추는지 설명해 보라."**
"find(x)가 뿌리까지 가는 길에 지나친 모든 노드의 부모를 뿌리로 직접 바꿉니다. 그 노드들에서 다시 find를 부르면 한 번에 끝나므로, 한 번의 비싼 find가 앞으로의 find들을 싸게 만듭니다. union-by-rank와 함께 쓰면 분할 상환 복잡도가 $O(\alpha(N))$까지 내려가고, 아커만 역함수 $\alpha$는 사실상 모든 입력 크기에서 4를 넘지 않아 상수로 취급합니다."
:::

## 연습

::: quiz
**1. 백준 1717 집합의 표현 (골드 4)** — https://www.acmicpc.net/problem/1717
- 신호: "합집합 연산"과 "두 원소가 같은 집합에 속해 있는지 확인하는 연산"이 순서 없이 섞여 온다. $N \le 10^6$, $M \le 10^5$.
- 상태: 원소마다 대표(뿌리) 하나.
- 자료구조: 유니온 파인드 그 자체. $M$번의 질의마다 DFS를 돌리면 $O(NM)$이라 시간 안에 안 끝나고, 매 질의를 union 또는 find 한 번으로 처리해야 $O(M \alpha(N))$이 된다.

**2. 백준 1976 여행 가자 (골드 4)** — https://www.acmicpc.net/problem/1976
- 신호: 도시 간 연결 정보가 인접 행렬로 주어지고, 주어진 여행 순서의 도시들이 전부 같은 그룹인지 묻는다. 같은 도시를 다시 지나가도 된다는 조건이 "경로"가 아니라 "연결성"만 확인하면 된다는 신호다.
- 상태: 도시마다 대표(뿌리) 하나.
- 자료구조: 유니온 파인드. 인접 행렬에서 연결된 두 도시를 전부 union한 뒤, 여행 순서의 도시들이 전부 같은 뿌리를 갖는지만 확인한다. 경로를 실제로 찾을 필요가 없다는 것이 이 문제와 BFS 문제를 가르는 지점이다.

**3. 백준 1043 거짓말 (골드 5)** — https://www.acmicpc.net/problem/1043
- 신호: "진실을 아는 사람이 파티에 한 명이라도 있으면 그 파티에서는 거짓말을 할 수 없다"는 **파티 참석자 목록이 곧 그룹**이라는 신호다. 한 파티에 참석한 사람들은 전부 같은 그룹으로 묶인다.
- 상태: 사람마다 대표(뿌리) 하나. 그 뿌리가 "진실을 아는 그룹"에 속하는지 별도 배열로 표시한다.
- 자료구조: 유니온 파인드. 각 파티의 참석자를 전부 하나로 union한 뒤, 처음에 진실을 아는 사람들이 속한 뿌리를 전부 "진실 그룹"으로 표시하고, 그 어떤 뿌리에도 속하지 않는 파티만 거짓말이 가능한 파티로 센다.
:::

## 요약

- 온라인으로 섞여 들어오는 union·find 질의를 매번 DFS로 풀면 $O(M(V+E))$다. 유니온 파인드는 두 연산을 각각 거의 $O(1)$로 줄인다.
- 원소마다 부모만 저장하는 트리 숲으로 집합을 표현한다. 뿌리가 그 집합의 대표다.
- **union-by-rank(또는 size)만 있으면 $O(\log N)$**이 보장된다 — 높이 $h$인 트리는 최소 $2^h$개의 원소를 요구하므로 높이가 로그 이상 자랄 수 없다.
- **경로 압축만 있어도 분할 상환 $O(\log N)$**에 가까워진다 — find 한 번이 지나친 경로 전부를 뿌리에 직접 매달아 다음 find들을 값싸게 만든다.
- **둘을 같이 쓰면 분할 상환 $O(\alpha(N))$**이고 $\alpha(N) \le 4$가 사실상 모든 입력에서 성립해 실무에서는 상수로 취급한다.
- 실측 코드에서 같은 union 순서인데도 naive 판은 사슬(높이4), union-by-rank 판은 별 모양(높이1)이 나왔다. **트리가 깊어지는 것은 데이터가 아니라 union 순서의 문제다.**
- 이미지 연결 요소 라벨링과 지도 병합이 실무의 대표 용례이고, [IX-4 최소 신장 트리](#/ix-4)의 크루스칼은 유니온 파인드 없이 성립하지 않는다.
