# IX-6 트라이

::: lead
문자열을 집합에 통째로 넣는 해시셋은 "이 문자열이 있는가"는 즉시 답하면서 "이 접두사로 시작하는 문자열이 있는가"는 왜 못 답하는가.
:::

## 1. 문제

터미널에 `gi`까지 입력하고 <kbd>Tab</kbd>을 누르면 `git`, `give`처럼 `gi`로 시작하는 명령어 후보가 뜬다. 셸이 아는 명령어를 전부 해시셋에 넣어 뒀다고 하자. `git`이 명령어인지는 `"git" in commands`로 즉시 답할 수 있다. 그런데 **"gi로 시작하는 명령어가 있는가"는 다르다.** 해시셋에는 완성된 문자열만 들어 있고, 그 문자열이 "gi"로 시작하는지는 문자열 하나하나를 꺼내 `startswith("gi")`로 확인하는 수밖에 없다. 명령어가 수천 개면 키 입력 한 번마다 수천 번의 문자열 비교가 일어난다.

원인은 해시 함수의 성질에 있다. 해시 함수는 문자열 전체를 뭉개서 숫자 하나로 만든다([II-6](#/ii-6)). `"git"`과 `"give"`는 앞 두 글자가 같지만 해시값은 서로 아무 관계가 없는 곳으로 흩어진다. **해시셋은 "같은 문자열인가"만 빠르게 답할 수 있을 뿐, "일부가 같은가"라는 질문 자체를 표현할 방법이 없다.**

필요한 것은 접두사 관계를 자료구조의 모양 자체로 표현하는 구조다. 문자열 집합 `{"car", "cat", "cap"}`을 생각하면, 셋 다 `"ca"`까지는 완전히 같은 경로를 지난다. 그 공유된 경로를 한 번만 저장해 두고, 갈라지는 지점부터만 따로 두면 어떨까. 그러면 "ca로 시작하는 단어가 있는가"는 문자열을 하나씩 훑을 필요 없이 **"ca"라는 경로가 이 구조 안에 존재하는가**로 바뀐다. 이 발상을 그대로 자료구조로 만든 것이 트라이다.

## 2. 아이디어

```text nolines
   (root)
     ├── t ── e ── n *          (ten)
     │         ├── a *          (tea)
     │         └── d *          (ted)
     └── i ── n ── n *          (inn)
```

네 단어 `ten`, `tea`, `ted`, `inn`을 넣은 트라이다. **노드 하나가 문자 하나가 아니라 "여기까지 온 문자열", 즉 접두사 하나를 나타낸다.** 뿌리는 빈 문자열이다. 간선은 문자 하나의 전이이고, `*` 표시는 그 노드까지의 경로가 **온전한 단어로 등록되어 있다**는 뜻이다.

`t`와 `e`를 지나는 노드는 `ten`, `tea`, `ted` 세 단어가 공유한다. 이 공유가 트라이의 전부다. `ten`을 넣은 뒤 `tea`를 넣으면 `t`, `e` 노드는 이미 있으므로 그대로 재사용하고 `a` 노드 하나만 새로 생긴다. **삽입한 단어가 많아져도 이미 있는 접두사를 지나가는 동안은 새 노드가 생기지 않는다.**

여기서 두 가지 질문이 갈린다.

**"ted가 등록된 단어인가"**는 `t → e → d`를 따라가 봤을 때 그 경로가 끝까지 존재하고 **그 마지막 노드가 `*`인가**로 답한다.

**"te로 시작하는 단어가 있는가"**는 `t → e`를 따라가 봤을 때 **경로가 존재하기만 하면** 된다. 마지막 노드가 `*`인지는 상관없다 — `te` 자체가 단어가 아니어도 `ten`, `tea`, `ted`가 그 아래 있으므로 답은 "있다"다.

**같은 자료구조, 같은 이동 방식으로 두 가지 다른 질문에 답한다.** 차이는 딱 하나, 끝에서 `*`를 확인하느냐 마느냐뿐이다.

### 2.1 자식을 무엇으로 들 것인가

노드 하나가 다음 문자로 가지는 전이를 어떻게 저장할지는 언어마다 유리한 쪽이 다르다. 후보로 삼는 알파벳이 소문자 26개뿐이라면, **고정 크기 배열** `children[26]`에 문자를 인덱스로 바로 꽂아 넣을 수 있다. 배열 인덱싱은 해시 계산이 필요 없는 $O(1)$이고, C++에서는 이 배열이 메모리에 연속으로 붙어 캐시에 올라가기 좋다. 대신 노드 하나가 실제로 쓰는 자식이 한둘뿐이어도 26칸을 전부 예약해야 한다 — 포인터 26개면 64비트 환경에서 노드 하나에 208바이트다.

Python에서는 사정이 다르다. Python의 리스트·정수 하나하나가 이미 힙에 흩어진 객체라서([0-3](#/0-3)) 배열을 고정 크기로 잡아도 C++만큼의 캐시 이득이 나지 않는다. 그 대신 **딕셔너리**로 자식을 두면 실제로 쓰는 문자만 저장해 메모리가 절약되고, 코드가 알파벳 크기에 얽매이지 않아 대문자·숫자·유니코드가 섞여도 그대로 동작한다. **알파벳이 커질수록(예: 모든 유니코드 문자) 배열은 C++에서도 불리해진다** — 그때는 C++도 `unordered_map<char, Node*>`로 돌아간다. 이 절의 구현은 Python은 딕셔너리, C++은 소문자 26개 배열을 쓴다. 어느 쪽이 맞는 선택인지는 알파벳 크기와 삽입될 문자열의 수에 달렸다.

## 3. 손으로 따라가기

::: trace
`ten`, `tea`, `ted`, `inn`을 이 순서로 삽입한 뒤 `ted`, `te`, `tex`를 검색한다. **경로 열은 지금까지 지나온 노드를 문자로 표시하고, `새 노드` 열은 이번 동작에서 새로 만든 노드 수를 센다.** 검색 행의 `실패 지점`은 경로를 더 이상 따라갈 수 없게 된 문자다.

- [ ] 4번 행(`inn` 삽입)에서 새로 만든 노드는 몇 개인가. `t` 노드를 재사용하는 3번 행과 무엇이 다른가
- [ ] 6번 행(`te` 검색)은 경로를 끝까지 따라갈 수 있는데도 왜 "단어로 존재"가 아닌가
- [ ] 7번 행(`tex` 검색)은 몇 번째 문자에서 멈추는가. `t`, `e`까지는 존재하는데 그다음이 왜 없는가

::: answer
| 순서 | 동작 | 대상 | 경로 | 새 노드 | 실패 지점 |
|---|---|---|---|---|---|
| 1 | 삽입 | ten | (root)→t→e→n* | t, e, n (3개) | — |
| 2 | 삽입 | tea | (root)→t→e→a* | a (1개, t·e는 재사용) | — |
| 3 | 삽입 | ted | (root)→t→e→d* | d (1개, t·e는 재사용) | — |
| 4 | 삽입 | inn | (root)→i→n→n* | i, n, n (3개) | — |
| 5 | 검색 | ted | (root)→t→e→d* | — | 없음. `*`이므로 단어로 존재 |
| 6 | 검색 | te | (root)→t→e | — | 없음. 경로는 있지만 `*`가 아님 |
| 7 | 검색 | tex | (root)→t→e→(x 없음) | — | 세 번째 문자 `x`에서 실패 |

첫 번째. `inn` 삽입은 노드 3개를 전부 새로 만든다. 이전까지 삽입된 `ten`, `tea`, `ted`가 전부 `t`로 시작해 `i` 쪽 경로가 하나도 없었기 때문이다. **공유는 접두사가 실제로 겹칠 때만 일어난다.** `t`로 시작하는 단어끼리는 `t`, `e` 두 노드를 계속 나눠 쓰지만, `i`로 시작하는 순간 뿌리부터 새 가지가 시작된다.

두 번째. `te`는 `t → e`까지 경로가 온전히 존재하므로 접두사로는 "있다". 그런데 이 경로의 마지막 노드 `e`는 `ten`, `tea`, `ted`로 가는 도중일 뿐 그 자체가 등록된 단어가 아니다. `*` 표시가 없다. ==경로가 있다는 것과 그 경로 끝이 단어라는 것은 서로 다른 조건이고, 트라이는 둘을 노드 하나의 서로 다른 필드로 구별한다.==

세 번째. `t`, `e`까지는 `ten`이 만든 경로를 그대로 따라간다. 세 번째 문자 `x`에서 `e` 노드의 자식 중 `x`가 없다 — `e` 노드의 자식은 `n`, `a`, `d`뿐이다. **검색은 실패한 지점까지만 걷고 즉시 멈춘다.** 남은 문자를 마저 비교할 필요가 없다는 것이 O(1) 자식 조회의 이점이다.
:::

## 4. 구현

::: dual
```python title="트라이 — 삽입·검색·접두사 존재"
class TrieNode:
    """문자 하나의 전이를 표현하는 노드. children 은 문자 -> TrieNode."""
    __slots__ = ("children", "is_end")

    def __init__(self):
        self.children = {}
        self.is_end = False


def insert(root, word):
    node = root
    for ch in word:
        if ch not in node.children:
            node.children[ch] = TrieNode()
        node = node.children[ch]
    node.is_end = True


def search(root, word):
    """word 전체가 등록된 단어인가."""
    node = root
    for ch in word:
        if ch not in node.children:
            return False
        node = node.children[ch]
    return node.is_end


def starts_with(root, prefix):
    """prefix 로 시작하는 단어가 하나라도 있는가."""
    node = root
    for ch in prefix:
        if ch not in node.children:
            return False
        node = node.children[ch]
    return True


words = ["ten", "tea", "ted", "inn"]
root = TrieNode()
for w in words:
    insert(root, w)

for q in ["ted", "te", "tex"]:
    print(f"search({q!r}) = {search(root, q)}   starts_with({q!r}) = {starts_with(root, q)}")
```
```cpp title="트라이 — 삽입·검색·접두사 존재"
#include <cstdio>
#include <string>
#include <vector>
using namespace std;

// 알파벳 소문자 26개 고정. children[i] 는 i 번째 문자로의 전이
struct TrieNode {
    TrieNode* children[26] = {};
    bool is_end = false;
};

void insert(TrieNode* root, const string& word) {
    TrieNode* node = root;
    for (char ch : word) {
        int idx = ch - 'a';
        if (!node->children[idx]) node->children[idx] = new TrieNode();
        node = node->children[idx];
    }
    node->is_end = true;
}

bool search(TrieNode* root, const string& word) {
    // word 전체가 등록된 단어인가
    TrieNode* node = root;
    for (char ch : word) {
        int idx = ch - 'a';
        if (!node->children[idx]) return false;
        node = node->children[idx];
    }
    return node->is_end;
}

bool starts_with(TrieNode* root, const string& prefix) {
    // prefix 로 시작하는 단어가 하나라도 있는가
    TrieNode* node = root;
    for (char ch : prefix) {
        int idx = ch - 'a';
        if (!node->children[idx]) return false;
        node = node->children[idx];
    }
    return true;
}

int main() {
    vector<string> words = {"ten", "tea", "ted", "inn"};
    TrieNode* root = new TrieNode();
    for (const string& w : words) insert(root, w);

    for (const string& q : {"ted", "te", "tex"}) {
        printf("search(\"%s\") = %s   starts_with(\"%s\") = %s\n",
               q.c_str(), search(root, q) ? "true" : "false",
               q.c_str(), starts_with(root, q) ? "true" : "false");
    }
    return 0;
}
```
:::

두 언어의 출력은 같다(참·거짓 표기의 대소문자만 다르다).

```console
search('ted') = True   starts_with('ted') = True
search('te') = False   starts_with('te') = True
search('tex') = False   starts_with('tex') = False
```

**복잡도:** 삽입·검색·접두사 존재 확인 모두 시간 $O(L)$ — $L$은 대상 문자열의 길이다. **트리 깊이가 아니라 문자열 길이가 상한이라는 것이 핵심이다.** 저장된 단어가 10개든 100만 개든, `"ted"`를 찾는 데 걷는 칸 수는 3으로 고정되어 있다 — 한 걸음마다 정확히 문자 하나씩만 소비하고, 자식 조회 자체는 $O(1)$(배열 인덱싱이거나 평균 $O(1)$의 딕셔너리 조회)이기 때문이다. 공간은 $O(\sum L_i)$ — 삽입한 모든 문자열의 길이 합이 상한이고, 접두사가 겹칠 때마다 그보다 적게 든다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 자식 저장 | `dict` — 실제로 쓰는 문자만 저장 | 소문자 26개 고정 배열 — 인덱스는 `ch - 'a'` |
| 없는 자식 확인 | `ch not in node.children` | `node->children[idx] == nullptr` (배열 초기값이 `{}`라 자동으로 `nullptr`) |
| 노드 해제 | 참조가 없어지면 GC가 자동 회수 | `new`로 만든 노드를 해제하는 코드가 없다 — 실전 코드라면 소멸자나 스마트 포인터가 필요하다 |
| 알파벳 확장 | 대문자·숫자·유니코드가 섞여도 코드 변경 없음 | 인덱스 계산식과 배열 크기를 알파벳에 맞춰 다시 잡아야 한다 |

::: pitfall
- **대소문자를 섞어 배열 인덱스를 계산한다.** `'A' - 'a'`는 음수라 C++ 배열 밖을 가리키고 정의되지 않은 동작(UB)이 된다. 배열 기반 구현은 입력을 미리 한쪽 대소문자로 통일해야 한다.
- **`search`를 `starts_with`로 착각한다.** 마지막 노드의 `is_end`를 확인하지 않으면 "ca"만 넣어도 "ca"라는 단어가 존재한다고 잘못 답한다. 이 챕터의 트레이스 6번 행이 정확히 이 실수를 잡는 지점이다.
- **빈 문자열을 특별 취급하지 않는다.** 빈 문자열을 삽입한다는 것은 **뿌리 자체를 `is_end`로 표시**한다는 뜻이다. 뿌리를 건너뛰는 삽입 코드는 이 경우를 조용히 무시한다.
- **트라이가 항상 이긴다고 가정한다.** 접두사 공유가 거의 없는 무작위 문자열을 많이 넣으면 노드 수가 총 문자 수에 근접하고, 특히 C++ 배열 기반은 노드 하나가 208바이트라 해시셋보다 메모리를 더 쓸 수 있다. **접두사가 실제로 겹치는 문제인지 먼저 확인한다.**
:::

## 5. 어디에 쓰이는가

**자동완성이 트라이의 표준 응용이다.** 입력된 접두사까지 트라이를 내려간 뒤, 그 노드를 뿌리 삼아 서브트리를 DFS로 훑으면서 `is_end`인 노드를 전부 모으면 그것이 후보 목록이다 — `starts_with`가 멈춘 자리에서 탐색을 한 번 더 이어가는 것뿐이다. 더 나아가 **어떤 노드의 자식이 정확히 하나뿐이면 다음 글자는 사용자가 누르지 않아도 확정된다.** 휴대폰 자판이나 셸의 자동 완성이 타이핑 중간에 다음 글자를 미리 채워 주는 동작이 바로 이 판정이다 — 자식이 둘 이상으로 갈라지는 노드에서만 실제로 선택이 필요하다.

**IP 라우팅 테이블도 트라이다.** 라우터는 목적지 주소와 가장 길게 일치하는 규칙(longest prefix match)을 골라야 하는데, IP 주소를 비트 문자열로 보면 이 절의 트라이와 완전히 같은 구조가 된다. 주소의 비트를 하나씩 따라 내려가다가 등록된 규칙 노드를 지날 때마다 기록해 두고, 더 내려갈 수 없는 지점에서 **가장 마지막으로 기록한 규칙**을 쓰면 longest prefix match다. IPv4는 32비트로 깊이가 고정되어 있어, 주소가 아무리 많이 등록돼도 조회는 항상 32단계 이내로 끝난다 — 이 절의 "트리 깊이가 아니라 문자열(비트열) 길이가 상한"이라는 성질이 그대로 성능 보장으로 이어지는 지점이다.

## 6. 이 유형을 알아보는 법

::: classify
- 신호어: "접두사로 시작하는 단어가 있는지", "다른 문자열의 접두사가 되면 안 된다", "자동완성", "사전에서 특정 단어를 찾아라", 여러 문자열을 한꺼번에 등록해 두고 반복해서 조회하는 상황
- 제약조건: 삽입할 문자열 길이의 총합이 $10^6$ 안팎이면 여유롭다([0-9](#/0-9)). 알파벳이 소문자뿐이면 배열 기반이 유리하고, 알파벳이 크거나 섞여 있으면 딕셔너리·해시맵 기반이 낫다
- 혼동 주의: **정확히 일치하는 문자열의 존재 여부만 묻는다면 해시셋으로 충분하다** — 접두사 관계 자체가 문제일 때만 트라이가 필요하다. 하나의 긴 문자열 안에서 패턴을 찾는 문제는 트라이가 아니라 [IX-7 문자열 매칭](#/ix-7)의 KMP다 — 트라이는 **여러 문자열의 집합**을 다루고, KMP는 **하나의 문자열 안에서의 반복 구조**를 다룬다
- 반례 함정: 입력에 대소문자나 숫자가 섞여 있는데 소문자 26개 배열로 짜면 인덱스가 범위를 벗어난다. 그리고 "문자열이 다른 문자열의 접두사가 되면 안 된다"는 조건은 삽입 도중에도 검사해야 한다 — 모든 삽입이 끝난 뒤에 한 번에 검사하면, **먼저 넣은 짧은 단어가 나중에 넣은 긴 단어의 접두사인 경우**를 놓친다
:::

## 요약

- 해시셋은 문자열 전체를 뭉개서 저장하므로 "같은 문자열인가"는 답해도 "접두사가 같은가"는 답할 수 없다.
- 트라이는 노드 하나가 문자 하나가 아니라 **접두사 하나**를 나타낸다. 접두사가 겹치는 동안은 노드를 공유한다.
- "단어로 존재하는가"는 경로 끝의 `is_end`까지 확인해야 하고, "접두사로 존재하는가"는 경로만 있으면 된다 — 이 둘을 헷갈리는 것이 가장 흔한 실수다.
- 자식을 배열로 둘지 딕셔너리로 둘지는 알파벳 크기와 언어 특성이 정한다. 알파벳이 작고 고정이면 C++ 배열이, 알파벳이 크거나 가변이면 딕셔너리·해시맵이 유리하다.
- 삽입·검색·접두사 확인 모두 $O(L)$이다. 저장된 문자열의 개수가 아니라 **질의 문자열 자신의 길이**가 비용을 정한다.
- 자동완성은 접두사 노드에서 서브트리를 DFS로 훑어 `is_end` 노드를 모으는 것이고, 다음 글자 자동 입력은 자식이 하나뿐인 노드를 판정하는 것이다.
- IP 라우팅의 최장 접두사 일치는 비트열을 문자로 보는 트라이이고, IPv4는 깊이가 32로 고정되어 등록된 규칙 수와 무관하게 조회 비용이 일정하다.

**다음 절**: [IX-7 문자열 매칭](#/ix-7) — 여러 문자열의 집합이 아니라 하나의 문자열 안에서 패턴이 반복되는 구조를 본다. 트라이가 접두사를 공유했다면, 이번에는 접두사와 접미사가 겹치는 지점을 이용한다.
