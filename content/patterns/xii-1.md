# XII-1 패턴을 왜 배우는가

::: lead
같은 구조를 설명하는 데 3분이 드는 팀과 한 단어가 드는 팀의 차이는 어디서 오는가.
:::

## 1. 문제

코드 리뷰에 이런 코멘트가 달렸다고 하자.

> 지금은 상위 함수가 장비 종류를 문자열로 받아서 분기하고 있는데, 장비가 늘 때마다 이 함수를 고치게 됩니다. 상위가 자기한테 필요한 동작만 정의해 두고, 장비별로 그 동작에 맞춰 주는 얇은 껍데기를 하나씩 만들어서, 상위는 그 껍데기들만 목록으로 들고 도는 쪽이 낫지 않을까요. 그러면 장비가 늘어도 껍데기 하나만 새로 쓰면 됩니다.

문장은 정확하고 제안도 옳다. 문제는 **이 문단을 쓰는 데 3분이 들고 읽는 데 1분이 든다**는 것이다. 그리고 다음 리뷰에서 같은 구조를 제안할 때 같은 3분을 다시 쓴다. 같은 팀의 다른 사람은 같은 것을 조금 다른 문장으로 쓴다.

이 코멘트에 이름이 있으면 이렇게 줄어든다.

> 여기 Adapter 하나 두죠.

여섯 글자다. 그리고 여섯 글자가 위 문단 전체를 실어 나른다. 상위가 인터페이스를 소유한다는 것, 껍데기가 벤더당 하나씩 붙는다는 것, 상위 로직은 그 뒤로 고쳐지지 않는다는 것까지 전부 딸려 온다. ==설계 대화의 비용은 구조의 복잡도가 아니라 그 구조를 매번 처음부터 서술해야 한다는 데 있다.==

이름이 없을 때 벌어지는 두 번째 일이 더 비싸다. **같은 구조가 한 코드베이스 안에서 세 번 다시 발명되고, 세 번 다르게 생긴다.** 한 곳은 `DeviceWrapper`, 한 곳은 `SensorBridge`, 한 곳은 `hw_compat` 모듈이다. 같은 것에 세 이름이 붙으면 검색으로 찾히지 않고, 찾히지 않으면 네 번째가 또 만들어진다.

그런데 이름이 생기는 순간 반대 방향의 사고가 시작된다. 어제까지 함수 하나였던 것이 오늘 이렇게 된다.

```text nolines
  before                          after
  render(rec)                     render(rec)
    -> to_plain(rec)                -> FormatterFactory.create("plain")
                                    -> FormatterRegistry.lookup("plain")
                                    -> PlainFormatter.format(rec)
                                    -> BaseFormatter.render_impl(rec)
```

오른쪽에는 인터페이스가 있고 팩토리가 있고 등록기가 있다. **그리고 구현체는 여전히 하나다.** 이 코드는 확장성을 얻지 않았다. 얻은 것은 파일 다섯 개와 스택 네 겹이고, 잃은 것은 진입점이다. 새로 온 사람이 "plain 형식이 실제로 어디서 만들어지는가"를 알아내는 데 걸리는 시간이 함수 하나였을 때보다 길다.

두 장면은 같은 도구의 양면이다. **패턴은 코드가 아니라 어휘다.** 어휘는 대화를 압축하고, 압축된 대화는 남용된다. 이 Part는 그 두 가지를 같은 무게로 다룬다.

## 2. 무엇이 달라져야 하는가

모든 설계 패턴이 하는 일은 하나다. **변하는 것과 변하지 않는 것을 갈라서, 변하는 쪽이 변할 때 변하지 않는 쪽을 건드리지 않게 한다.** 앞의 리뷰 코멘트에서 변하는 것은 장비 종류이고 변하지 않는 것은 "온도를 하나 읽는다"는 상위의 요구다. 카탈로그의 스물세 개는 무엇을 그 자리에 넣느냐의 차이일 뿐이다.

가름이 공짜가 아니라는 것이 두 번째 절반이다. 간접 계층 하나를 끼울 때의 회계는 이렇다.

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 확장 | 호출부를 고치지 않고 종류를 늘린다 | 종류가 늘지 않으면 아무것도 얻지 않는다 |
| 읽기 | 각 조각이 짧아진다 | 흐름이 파일 여러 개에 흩어진다 |
| 디버깅 | 갈아 끼워서 격리할 수 있다 | 스택이 깊어지고 진입점이 사라진다 |
| 테스트 | 대역을 넣을 자리가 생긴다 | 대역과 진짜가 갈라져 통합 결함이 늦게 드러난다 |

오른쪽 열은 **지금 즉시** 지불되고 왼쪽 열은 **두 번째 구현체가 나타났을 때** 회수된다. 두 번째가 영영 나타나지 않으면 회수는 없다. 그래서 이 Part 전체를 관통하는 판정 기준이 하나 선다.

==구현체가 정확히 하나인 추상화는 아직 비용만 치른 것이다.==

이것은 "추상화하지 마라"가 아니다. **언제 회수가 시작되는지를 묻는 기준**이다. 셋 중 하나에 해당하면 추상화는 그 자리에서 값을 한다. ① 두 번째 구현체가 이미 코드에 있다. ② 두 번째가 요구사항 문서에 적혀 있고 일정이 있다. ③ 테스트가 진짜 대신 대역을 넣어야 하고, 그 대역이 두 번째 구현체다. 셋 다 아니면 함수 하나로 두고 두 번째가 올 때 가른다. 세 번째 조건 때문에, 외부 세계에 닿는 경계(장비·네트워크·파일)는 구현체가 하나뿐이어도 추상화가 정당해지는 경우가 많다.

세 번째로 봐야 할 것이 있다. **언어가 이 회계를 바꾼다.** 같은 요구가 한 언어에서는 클래스 계층을 부르고 다른 언어에서는 함수 하나로 끝난다. 다음 절이 그 장면이다.

## 3. 구현

로그 한 줄을 여러 형식으로 내보내는 코드다. 지금 필요한 형식은 `plain`과 `csv` 두 가지다. 나쁜 판은 형식 이름으로 분기하고, 좋은 판은 형식 이름을 만드는 함수에 대응시킨다. 두 판을 한 프로그램에서 나란히 돌린다.

::: dual
```python title="로그 형식 — 분기 사슬과 이름-함수 대응"
class Record:
    def __init__(self, ts, level, msg, value):
        self.ts, self.level, self.msg, self.value = ts, level, msg, value


def write_bad(fmt, rec):
    if fmt == "plain":
        return f"{rec.ts} {rec.level} {rec.msg} {rec.value}"
    elif fmt == "csv":
        return f"{rec.ts},{rec.level},{rec.msg},{rec.value}"
    else:                                   # 모르는 형식은 기본값으로 — 여기가 함정이다
        return f"{rec.ts} {rec.level} {rec.msg} {rec.value}"


FORMATTERS = {}                             # 형식 이름 -> 한 줄을 만드는 함수


def register(name, fn):
    FORMATTERS[name] = fn


def write_good(fmt, rec):
    fn = FORMATTERS.get(fmt)
    if fn is None:
        return None                         # 모르는 형식은 결과가 없다. 호출부가 알게 된다
    return fn(rec)


register("plain", lambda rec: f"{rec.ts} {rec.level} {rec.msg} {rec.value}")
register("csv", lambda rec: f"{rec.ts},{rec.level},{rec.msg},{rec.value}")

rec = Record("2026-01-01T00:00:00", "WARN", "disk", 91)

print("[1] plain 과 csv 만 있을 때 — 두 판이 같다")
for fmt in ("plain", "csv"):
    print(f"  bad  {fmt:5} : {write_bad(fmt, rec)}")
    print(f"  good {fmt:5} : {write_good(fmt, rec)}")

print("[2] json 요구가 들어왔다. 아직 아무것도 고치지 않고 그대로 부른다")
out_bad = write_bad("json", rec)
out_good = write_good("json", rec)
print(f"  bad  json  : {out_bad}")
print(f"  good json  : {out_good if out_good is not None else '<미등록 — 호출 즉시 드러난다>'}")

print("[3] json 을 붙인다")
register("json", lambda rec: '{"ts":"%s","level":"%s","msg":"%s","value":%d}'
         % (rec.ts, rec.level, rec.msg, rec.value))
print(f"  bad  json  : {write_bad('json', rec)}")
print(f"  good json  : {write_good('json', rec)}")
```
```cpp title="로그 형식 — 분기 사슬과 이름-함수 대응"
#include <functional>
#include <iomanip>
#include <iostream>
#include <optional>
#include <string>
#include <unordered_map>
using namespace std;

struct Record {
    string ts, level, msg;
    int value;
};

string write_bad(const string& fmt, const Record& rec) {
    if (fmt == "plain")
        return rec.ts + " " + rec.level + " " + rec.msg + " " + to_string(rec.value);
    else if (fmt == "csv")
        return rec.ts + "," + rec.level + "," + rec.msg + "," + to_string(rec.value);
    else                                    // 모르는 형식은 기본값으로 — 여기가 함정이다
        return rec.ts + " " + rec.level + " " + rec.msg + " " + to_string(rec.value);
}

unordered_map<string, function<string(const Record&)>> FORMATTERS;  // 형식 이름 -> 함수

void register_fmt(const string& name, function<string(const Record&)> fn) {
    FORMATTERS[name] = move(fn);
}

optional<string> write_good(const string& fmt, const Record& rec) {
    auto it = FORMATTERS.find(fmt);
    if (it == FORMATTERS.end())
        return nullopt;                     // 모르는 형식은 결과가 없다. 호출부가 알게 된다
    return it->second(rec);
}

int main() {
    register_fmt("plain", [](const Record& rec) {
        return rec.ts + " " + rec.level + " " + rec.msg + " " + to_string(rec.value);
    });
    register_fmt("csv", [](const Record& rec) {
        return rec.ts + "," + rec.level + "," + rec.msg + "," + to_string(rec.value);
    });

    Record rec{"2026-01-01T00:00:00", "WARN", "disk", 91};

    cout << "[1] plain 과 csv 만 있을 때 — 두 판이 같다\n";
    for (const string& fmt : {string("plain"), string("csv")}) {
        cout << "  bad  " << left << setw(5) << fmt << " : " << write_bad(fmt, rec) << "\n";
        cout << "  good " << left << setw(5) << fmt << " : " << *write_good(fmt, rec) << "\n";
    }

    cout << "[2] json 요구가 들어왔다. 아직 아무것도 고치지 않고 그대로 부른다\n";
    string out_bad = write_bad("json", rec);
    optional<string> out_good = write_good("json", rec);
    cout << "  bad  json  : " << out_bad << "\n";
    cout << "  good json  : "
         << (out_good ? *out_good : string("<미등록 — 호출 즉시 드러난다>")) << "\n";

    cout << "[3] json 을 붙인다\n";
    register_fmt("json", [](const Record& rec) {
        return "{\"ts\":\"" + rec.ts + "\",\"level\":\"" + rec.level +
               "\",\"msg\":\"" + rec.msg + "\",\"value\":" + to_string(rec.value) + "}";
    });
    cout << "  bad  json  : " << write_bad("json", rec) << "\n";
    cout << "  good json  : " << *write_good("json", rec) << "\n";
    return 0;
}
```
:::

두 언어의 출력은 한 글자도 다르지 않다.

```console
[1] plain 과 csv 만 있을 때 — 두 판이 같다
  bad  plain : 2026-01-01T00:00:00 WARN disk 91
  good plain : 2026-01-01T00:00:00 WARN disk 91
  bad  csv   : 2026-01-01T00:00:00,WARN,disk,91
  good csv   : 2026-01-01T00:00:00,WARN,disk,91
[2] json 요구가 들어왔다. 아직 아무것도 고치지 않고 그대로 부른다
  bad  json  : 2026-01-01T00:00:00 WARN disk 91
  good json  : <미등록 — 호출 즉시 드러난다>
[3] json 을 붙인다
  bad  json  : 2026-01-01T00:00:00 WARN disk 91
  good json  : {"ts":"2026-01-01T00:00:00","level":"WARN","msg":"disk","value":91}
```

**복잡도:** 나쁜 판의 형식 판정은 시간 $O(k)$ — 형식이 $k$가지면 최악의 경우 문자열 비교를 $k$번 한다. 좋은 판은 평균 $O(1)$ — 해시 조회 한 번이다. 둘 다 공간 $O(k)$로 같다. **하지만 이 복잡도 차이는 이 절의 요점이 아니다.** $k$는 열을 넘는 일이 드물고 비교 열 번은 아무 데서도 문제가 되지 않는다.

요점은 `[2]`다. 형식이 하나 늘었을 때 나쁜 판은 **함수 본체를 고쳐야 하고, 고치기 전까지 조용히 틀린 답을 낸다.** `else` 가지가 plain을 돌려주므로 json을 요청한 호출부는 plain을 받고도 그 사실을 모른다. 좋은 판은 미등록을 값으로 돌려주어 호출 즉시 드러나고, 확장은 `register` 한 줄이며 `write_good`은 손대지 않는다. ==수정해야 할 지점의 개수가 복잡도보다 자주 시스템을 결정한다.==

| 언어 차이 | Python | C++ |
|---|---|---|
| 함수를 값으로 | 함수·람다가 그대로 값이다. `dict`에 바로 넣는다 | `std::function`으로 감싼다. 타입 소거 비용이 붙는다([0-8](#/0-8)) |
| 없는 키 | `dict.get(k)`이 `None`을 돌려준다 | `find()`가 `end()` 반복자를 돌려준다. `[]`로 읽으면 **없는 키가 생성된다** |
| 값 없음 표현 | `None` 하나로 끝난다 | `std::optional<T>`(C++17). `nullopt`가 없음이다 |
| 조회 비용 | `dict`는 해시, 평균 $O(1)$ | `unordered_map`은 평균 $O(1)$, `map`은 균형 트리라 $O(\log k)$ |
| 등록 시점 | 모듈이 임포트될 때 실행된다 | 전역 초기화 순서가 번역 단위 간에 정해지지 않는다. `main` 안에서 등록하는 이유다 |

::: danger
나쁜 판의 진짜 결함은 `else` 가지다. **모르는 입력에 기본값을 돌려주는 코드는 틀린 답을 정상 응답으로 위장한다.** 위 출력에서 `bad json`은 예외도 로그도 없이 plain을 돌려준다. 이 값을 받아 파싱하는 쪽은 형식이 어긋난 이유를 자기 코드에서 찾게 된다.

모르는 입력에는 값을 만들지 말고 **모른다는 사실을 값으로 돌려주거나 예외를 던져라.** 좋은 판이 `None` / `nullopt`를 돌려준 것이 그것이다. 같은 함정을 다른 얼굴로 [XII-15 안티패턴](#/xii-15)에서 다시 본다.
:::

## 4. 이제 이름을 붙인다

좋은 판이 한 일에는 이름이 있다. 형식마다 달라지는 부분을 **교체 가능한 조각**으로 떼어 내 바깥에서 주입한 것이 **Strategy**이고, 이름으로 그 조각을 찾아 주는 `FORMATTERS` 표가 **등록기(registry)**다. 각각 [XII-6 Strategy](#/xii-6), [XII-5 Factory Method / Abstract Factory / Builder](#/xii-5)에서 본체를 다룬다.

이제 Python 판을 다시 보라. **클래스가 하나도 없다.** 1994년의 GoF 카탈로그에서 Strategy는 `Strategy` 추상 클래스, `ConcreteStrategyA`, `ConcreteStrategyB`, 그리고 그것을 들고 있는 `Context`로 그려진다. Python 판에는 그 넷 중 어느 것도 없고 함수 두 개와 `dict` 하나가 있다. C++ 판에는 `std::function`이 그 자리를 대신한다 — 클래스 계층이 사라진 것은 언어에 일급 함수와 타입 소거가 있기 때문이지 설계가 달라서가 아니다.

**GoF 카탈로그의 상당수는 1994년 C++과 Smalltalk의 제약에서 나온 우회로다.** 이 명제가 Part XII 전체의 축이다.

::: hist
패턴이라는 발상은 소프트웨어에서 나오지 않았다. 건축가 Christopher Alexander가 1977년 *A Pattern Language*에서 "되풀이되는 문제와 그에 대한 해법의 핵심"에 이름을 붙여 목록으로 만들었고, 그 목적은 설계도를 배포하는 것이 아니라 **건축주와 건축가가 같은 단어로 말하게 하는 것**이었다.

Gamma·Helm·Johnson·Vlissides가 1994년 *Design Patterns*에서 스물세 개를 카탈로그로 묶을 때도 목적은 같았다. 그 책은 패턴을 복사해 쓸 코드가 아니라 **설계 어휘**로 제시했다. 카탈로그가 코드 템플릿 모음으로 읽히기 시작한 것은 그다음의 일이고, 이 Part가 이름을 매번 4절에 두는 이유가 그 오독을 되풀이하지 않기 위해서다.

반론도 오래됐다. Peter Norvig는 1996년 강연 *Design Patterns in Dynamic Languages*에서 스물세 개 중 상당수가 동적 언어에서는 보이지 않거나 훨씬 단순해진다고 지적했다. 다음 표가 그 주장의 요약에 가깝다.
:::

| 패턴 | C++에서 필요한 것 | Python에서 접히는 지점 |
|---|---|---|
| Strategy | 추상 클래스 + 구현체 계층 | 함수를 인자로 넘긴다 |
| Command | 실행 인터페이스 + 구현체 | 클로저 하나 |
| Template Method | 순수 가상 훅을 가진 기반 클래스 | 고차 함수의 인자 |
| Abstract Factory | 팩토리 인터페이스 + 제품군 인터페이스 | 덕 타이핑이면 팩토리 인터페이스가 불필요할 때가 많다 |
| Singleton | 정적 인스턴스 + 접근 제어 | 모듈이 이미 싱글톤이다 |
| Iterator | 반복자 클래스 | `__iter__` / 제너레이터가 언어에 있다 |

**여기서 "Python에서는 필요 없다"로 끝내면 잘못 읽은 것이다.** 접히는 것은 **구조**이지 **문제**가 아니다. 접힘이 풀리는 경계가 셋 있다.

- **조각에 상태가 붙을 때.** 형식기가 설정을 들고 있고 그 설정이 실행 중에 바뀌면 함수로는 부족하다. 상태를 가진 호출 가능한 객체가 필요하고, 그것이 곧 클래스다.
- **등록·발견이 필요할 때.** 조각이 여러 파일·여러 플러그인에 흩어져 있으면 "어디에 무엇이 있는지"를 관리하는 표가 필요하다. 위 코드의 `FORMATTERS`가 이미 그 표다.
- **타입 검사가 필요할 때.** 덕 타이핑은 잘못된 조각을 호출 시점까지 통과시킨다. `typing.Protocol`이나 ABC로 계약을 코드에 적어 두면 실행 전에 걸린다. 다음 절이 그 예다.

그리고 무엇보다, **이름은 구조가 사라져도 남는다.** Python 판에 `Strategy`라는 클래스가 없어도 리뷰에서 "여기는 Strategy로 가죠"는 그대로 통한다. ==패턴의 값어치는 클래스 다이어그램이 아니라 그 단어다.==

## 5. 어디에 박혀 있는가

**표준 라이브러리의 이름 자체에 패턴이 박혀 있다.** Java의 `InputStreamReader`는 바이트 스트림을 문자 스트림으로 맞추는 Adapter이고, `BufferedInputStream`은 같은 인터페이스를 유지한 채 버퍼링을 얹는 Decorator다. 이름만 읽고도 무엇을 하는 클래스인지 짐작되는 이유가 패턴 어휘다. Python의 `io.TextIOWrapper`는 같은 자리에 있는 같은 것이다 — 이진 버퍼를 감싸 텍스트 인터페이스로 내놓는다.

**C++ 표준 라이브러리는 패턴을 이름 대신 타입으로 쓴다.** `std::sort`의 세 번째 인자인 비교자는 Strategy이고, `std::function`은 호출 가능한 온갖 것을 하나의 호출 인터페이스로 맞추는 어댑터다. `std::priority_queue`의 세 번째 템플릿 인자로 `greater<int>`를 넘겨 최소 힙을 만드는 것도([II-8 힙과 우선순위 큐](#/ii-8)) 같은 구조다. 정렬 기준이라는 변하는 축과 정렬 알고리즘이라는 변하지 않는 축을 갈라 놓은 것이다.

**설계 문서와 리뷰에서 이름은 반박 가능한 단위를 만든다.** "이 클래스가 좀 커진 것 같은데요"는 반박도 동의도 어렵다. "이건 Facade로 시작했는데 지금 God Object로 자라고 있습니다"는 검증할 수 있는 주장이다 — 파사드가 서브시스템의 인터페이스를 얼마나 다시 노출하고 있는지 세어 보면 된다. 이름은 대화를 짧게 만드는 데 그치지 않고 **대화를 판정 가능하게 만든다.**

## 6. 언제 쓰지 말아야 하는가

**첫째, 구현체가 하나일 때.** §2의 기준이 그대로 적용된다. 인터페이스 하나에 구현체 하나, 팩토리 하나, 등록기 하나를 만들어 놓고 "나중에 늘어날 것"이라고 말하는 코드가 가장 흔한 낭비다. 늘어날 때 가르는 비용은 미리 가르는 비용보다 대개 싸다. 이미 짜인 코드를 갈라내는 일은 기계적이지만, 잘못 그은 경계를 지우는 일은 그렇지 않기 때문이다.

**둘째, 이름을 먼저 정하고 코드를 거기 맞출 때.** "이번 모듈은 Strategy로 갑시다"가 요구사항보다 먼저 나오면 순서가 뒤집힌 것이다. 패턴은 문제의 형태를 보고 붙이는 이름이지 설계의 출발점이 아니다. 이 Part의 모든 챕터가 이름을 4절에 두는 이유가 그것이다.

**셋째, 이름이 틀렸을 때.** 서브시스템 전부를 그대로 다시 노출하는 클래스에 `XxxFacade`라는 이름이 붙어 있으면, 그 이름이 리뷰를 막는다. 이름은 "이미 검토된 설계"라는 신호를 보내기 때문이다. ==틀린 이름은 없는 이름보다 나쁘다.== 없는 이름은 질문을 부르지만 틀린 이름은 질문을 막는다.

성능은 이 목록에 없다. 간접 호출 한 번의 기계 비용은 다음 절에서 실측하는데, 결론만 미리 말하면 나노초 단위이고 거의 언제나 무시할 만하다. **간접 계층의 비용은 CPU가 아니라 사람이 치른다.** 그래서 판정 기준도 사이클이 아니라 "이 추상화가 회수를 시작했는가"다.

::: note
GoF는 스물세 개를 세 갈래로 묶었다. **생성**(객체를 어떻게 만드는가), **구조**(객체를 어떻게 조립하는가), **행위**(객체가 책임을 어떻게 나누는가)다. 이 Part는 그 순서를 따르지 않는다. 구조 쪽인 Adapter·Facade·Bridge·Proxy·Decorator를 먼저 두고([XII-2](#/xii-2)~[XII-4](#/xii-4)), 생성 쪽을 그다음에([XII-5](#/xii-5)), 행위 쪽을 뒤에 둔다([XII-6](#/xii-6)~[XII-11](#/xii-11)).

이유는 하나다. **구조 패턴은 "무엇을 무엇 앞에 끼우는가"만 이해하면 되지만, 행위 패턴은 그 앞에 객체 사이의 책임 분배를 먼저 이해해야 한다.** 분류는 카탈로그를 정리하는 축이고, 학습 순서는 의존성의 축이다. 둘은 같지 않다.
:::

::: interview
패턴은 기술 면접에서 두 가지 방식으로 물어진다. 둘의 기대 답변이 정반대다.

**"아는 디자인 패턴을 말해 보세요."**
이름을 나열하면 지식 확인으로 끝난다. 한 걸음 더 나가는 답변은 **자기 코드에서 그 패턴이 해결한 문제와 그때 치른 대가**를 같이 말하는 것이다. "장비 종류가 세 개로 늘면서 상위 로직이 벤더별로 분기하고 있어서 Adapter를 뒀습니다. 대신 벤더 고유의 오류 코드를 공통 인터페이스에서 어떻게 표현할지 정해야 했고, 그 결정을 미루면 어댑터가 새기 시작합니다." 이 답변은 이름 대신 **판단**을 보인다.

**"이 코드를 개선해 보세요."**
여기서 패턴 이름을 먼저 꺼내면 감점 요인이 된다. 순서는 언제나 같다. ① 무엇이 반복해서 고쳐지는가 ② 변하는 축이 실재하는가 ③ 그래서 무엇을 가를 것인가 ④ 그 구조의 이름은 이것이다. 이름이 ④에 오지 않고 ①에 오면 요구 없이 추상화를 얹는 사람으로 읽힌다.

가장 자주 나오는 후속 질문은 **"그럼 언제 쓰지 말아야 합니까"** 다. 답의 뼈대는 §2의 기준이다. 구현체가 하나뿐이고, 두 번째가 일정에도 없고, 테스트가 대역을 요구하지도 않으면 아직 이르다.
:::

## 연습

::: quiz
설계 질문이다. 코드를 짜지 마라. 세 가지를 적어라.

**1. 결제 수단이 카드 하나뿐인 서비스.** 결제 모듈은 카드사 API를 직접 호출한다. 다음 분기에 계좌이체를 붙인다는 계획이 로드맵 문서에 있고, 지금 테스트는 실제 카드사 샌드박스에 붙어서 느리고 자주 실패한다.
- 상황: 구현체가 지금 몇 개인가. §2의 세 조건 중 몇 개가 참인가.
- 무엇이 변하고 무엇이 고정인가:
- 어떤 패턴이고, 무엇을 대가로 치르는가:

**2. 이미지 파일 형식 변환기.** 입력 형식 판정이 `if ext == "png" ... elif ext == "jpg" ...` 사슬이고 분기가 아홉 개다. 새 형식을 추가한 사람이 사슬 중간에 넣는 바람에 순서 의존 버그가 두 번 났다.
- 상황: 무엇이 반복해서 고쳐지는가. `else` 가지는 무엇을 돌려주는가.
- 무엇이 변하고 무엇이 고정인가:
- 어떤 패턴이고, 무엇을 대가로 치르는가:

**3. 사내 도구의 알림 발송기.** `Notifier` 추상 클래스, `SlackNotifier` 구현체 하나, `NotifierFactory`, 설정 파일에서 이름을 읽어 팩토리를 부르는 부트스트랩 코드가 있다. 이 도구는 3년째 슬랙에만 보낸다.
- 상황: 지금 회수되고 있는 비용이 있는가.
- 무엇이 변하고 무엇이 고정인가:
- 어떤 패턴이고, 무엇을 대가로 치르는가:

::: answer
**1.** 구현체는 지금 하나지만 §2의 조건 ②(로드맵에 두 번째가 있다)와 ③(테스트가 대역을 요구한다)이 둘 다 참이다. 변하는 것은 결제 수단별 호출 규약이고 고정된 것은 "금액과 주문 번호를 주면 성공/실패가 돌아온다"는 상위의 요구다. 상위가 소유하는 결제 인터페이스를 두고 카드사 호출을 그 뒤로 옮긴다 — [XII-2 Adapter](#/xii-2)다. 대가는 호출 한 겹과, 카드사 고유의 오류 코드를 인터페이스가 어떻게 표현할지 지금 정해야 한다는 것이다. 이 결정을 미루면 어댑터가 새기 시작한다.

**2.** 반복해서 고쳐지는 것은 분기 사슬 하나이고, 형식이 늘 때마다 같은 함수가 열린다. `else` 가지가 무엇을 돌려주는지가 이 문제의 핵심이다 — 기본 형식을 돌려주면 미지원 파일이 조용히 잘못 처리된다. 변하는 것은 형식별 판정·디코딩이고 고정된 것은 "확장자를 주면 디코더가 나온다"는 요구다. 이름-구현 대응표로 바꾸면 순서 의존이 사라진다. 본문의 좋은 판과 같은 구조이고, 등록 쪽은 [XII-5](#/xii-5), 교체 쪽은 [XII-6](#/xii-6)이다. 대가는 아홉 개 디코더가 아홉 파일로 흩어져 전체 흐름을 한 화면에서 볼 수 없게 되는 것이다.

**3.** 회수되는 비용이 없다. 3년간 구현체는 하나였고 로드맵에도 두 번째가 없다. 여기서 "변하는 축"은 실재하지 않는 축이며, 실재하지 않는 축을 가른 것이 이 코드의 결함이다. 추상 클래스·팩토리·부트스트랩을 걷어 내고 함수 하나로 되돌리는 것이 옳다. 단 예외가 하나 있다 — 테스트가 실제 슬랙에 붙지 않기 위해 대역을 쓰고 있다면 조건 ③이 참이고 인터페이스는 남긴다. 그 경우에도 팩토리와 설정 기반 조회는 근거가 없다. **추상화를 세 겹 쌓았을 때는 각 겹이 각자 근거를 대야 한다.**

## 요약

- 패턴은 코드가 아니라 **어휘**다. 값어치의 대부분은 클래스 다이어그램이 아니라 설계 대화를 한 단어로 압축하는 데서 나온다.
- 이름이 없으면 같은 구조가 한 코드베이스에서 여러 번 다시 발명되고, 다른 이름이 붙어 검색되지 않는다.
- 모든 패턴이 하는 일은 하나다. **변하는 것과 변하지 않는 것을 가른다.** 카탈로그의 차이는 무엇을 그 자리에 넣느냐뿐이다.
- 간접 계층의 비용은 **지금** 지불되고 이득은 **두 번째 구현체가 나타났을 때** 회수된다. ==구현체가 정확히 하나인 추상화는 아직 비용만 치른 것이다.==
- 회수가 시작되는 조건은 셋이다. 두 번째 구현체가 이미 있다 / 일정과 함께 예정되어 있다 / 테스트가 대역을 요구한다.
- **GoF 카탈로그의 상당수는 1994년 C++·Smalltalk의 제약에서 나온 우회로다.** Python에서는 Strategy·Command·Singleton·Template Method가 함수·클로저·모듈로 접힌다. 접히는 것은 구조이지 문제가 아니다.
- 접힘이 풀리는 경계는 상태가 붙을 때, 등록·발견이 필요할 때, 타입 검사가 필요할 때다.
- 남용의 세 얼굴: 구현체가 하나인 추상화, 이름을 먼저 정하는 설계, 그리고 **틀린 이름**. 틀린 이름은 없는 이름보다 나쁘다 — 질문을 막기 때문이다.

**다음 절**: [XII-2 Adapter](#/xii-2) — 벤더마다 다른 장비 SDK를 상위 로직이 직접 분기하면 무엇이 무너지는지 보고, 의존 방향을 뒤집어 상위가 인터페이스를 소유하게 만든다.
