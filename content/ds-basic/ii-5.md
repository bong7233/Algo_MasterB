# II-5 큐와 덱

::: lead
먼저 들어온 것을 먼저 꺼낸다는 규칙 하나가 자료구조를 어디까지 결정하는가.
:::

## 1. 문제

장비 제어기가 상위 시스템에서 명령을 받는다. 초당 수천 개가 들어오고, 처리 순서는 **도착 순서**여야 한다. 나중에 온 명령을 먼저 실행하면 "집었다가 놓는다"가 "놓았다가 집는다"가 된다.

가장 먼저 떠오르는 구현은 배열이다. 뒤에 붙이고 앞에서 꺼낸다.

```python title="큐로 쓰면 안 되는 구현 (조각)"
buf = []
buf.append(cmd)          # 뒤에 붙인다 — O(1)
cmd = buf.pop(0)         # ❌ 앞에서 꺼낸다 — O(n)
```

`pop(0)`은 첫 원소를 지운 뒤 **뒤의 모든 원소를 한 칸씩 앞으로 민다.** 명령 10만 개를 넣고 빼면 미는 일만 50억 번이다. [0-3 Python 내장 자료구조의 실제 비용](#/0-3)의 실측으로 `list.pop(0)` 10만 회가 0.738초, `deque.popleft()`는 0.0045초다. **165배다.** 알고리즘은 그대로인데 자료구조 한 줄이 전부를 결정한다.

여기까지는 "앞을 건드리지 마라"로 요약된다. 그런데 큐를 제대로 쓰기 시작하면 곧 두 번째 장면이 온다.

같은 제어기가 최근 `k`개의 센서 값 중 **최댓값**을 매 스텝 알아야 한다. 값이 하나 들어올 때마다 창이 한 칸 밀린다. 창마다 다시 훑으면 $O(nk)$다. $n = 200{,}000$, $k = 1{,}600$이면 3억 2천만 번이고, 실측으로 C++이 0.67초, Python이 4.6초다(§4).

두 장면의 요구가 다르다. 첫 번째는 **한쪽 끝에 넣고 반대쪽 끝에서 뺀다.** 두 번째는 **양쪽 끝에서 넣고 뺀다.** 앞의 것이 큐이고, 뒤의 것이 덱이다. 그리고 둘은 같은 구조 위에 선다.

## 2. 아이디어

### 2.1 링 버퍼 — 앞을 빼는 대신 앞을 옮긴다

앞에서 꺼내는 것이 비싼 이유는 **꺼낸 자리를 메우려 하기 때문**이다. 메우지 않으면 된다. 배열은 그대로 두고 "지금 앞이 어디인가"를 가리키는 인덱스만 옮긴다.

```text nolines
   cap = 8,  head = 2,  size = 3

     0     1     2     3     4     5     6     7
   +-----+-----+-----+-----+-----+-----+-----+-----+
   |  -  |  -  |  A  |  B  |  C  |  -  |  -  |  -  |
   +-----+-----+-----+-----+-----+-----+-----+-----+
               ^                 ^
               head              head + size        <- 다음에 넣을 자리
```

꺼내면 `head`가 하나 늘고, 넣으면 `head + size` 자리에 쓴다. 둘 다 상수 시간이다. 배열 끝에 닿으면 다시 0으로 돌아온다 — 인덱스를 항상 `% cap`으로 접기 때문이다. 논리적으로는 원이고 물리적으로는 배열이다. 그래서 **링 버퍼**다.

::: warn
`head`와 `tail` 두 인덱스만 들면 **빈 것과 꽉 찬 것을 구분할 수 없다.** 둘 다 `head == tail`이기 때문이다. 해법은 둘 중 하나다. 원소 수 `size`를 따로 세거나, 한 칸을 영구히 비워 둬서 `tail + 1 == head`를 "꽉 참"으로 쓴다. 앞쪽이 읽기 쉽고, 뒤쪽은 인덱스 둘만으로 끝나 락 없는 구현에 유리하다([XI-3](#/xi-3)).
:::

용량이 고정이라는 점은 결함이 아니라 성질이다. **큐가 넘칠 때 무엇을 버릴지 강제로 결정하게 만든다.** 무한히 커지는 큐는 메모리가 다 찰 때까지 문제를 미룰 뿐이다. 이 선택이 백프레셔이고 [XI-7 이벤트 루프와 백프레셔](#/xi-7)의 주제다.

### 2.2 덱 — 큐의 일반화

덱(deque, double-ended queue)은 양쪽 끝 전부가 $O(1)$인 큐다. 큐가 할 수 있는 일은 전부 하고 하나를 더 한다. **방금 넣은 것을 취소할 수 있다.**

두 언어의 구현이 다르다. 그 차이가 곧 성능 특성의 차이다.

| | Python `collections.deque` | C++ `std::deque` |
|---|---|---|
| 구조 | 고정 크기 블록들의 이중 연결 리스트 | 블록 배열 + 블록 포인터 표(map) |
| 양 끝 삽입·삭제 | $O(1)$ | $O(1)$ |
| `d[i]` 인덱싱 | **$O(n)$** — 블록을 세어 간다 | $O(1)$ — 표에서 블록을 바로 찾는다 |
| 슬라이싱 | 없다 | 없다(반복자로 대신) |

📖 `collections.deque()` — 양쪽 끝 연산이 $O(1)$인 양방향 큐.
　 `append` / `appendleft` / `pop` / `popleft` 넷이 전부 $O(1)$이고, `d[0]`과 `d[-1]`은 양 끝이라 예외적으로 $O(1)$이다. 중간 인덱싱은 $O(n)$이다.
　 쓰는 곳: BFS의 큐([IV-3](#/iv-3)), 슬라이딩 윈도우(이 절, [VI-3](#/vi-3)), 0-1 BFS([IV-4](#/iv-4)).
　 C++ 대응: `std::deque` — 인덱싱까지 $O(1)$이라는 점이 다르다. 자세한 메모리 배치는 [0-6 C++ 컨테이너 세트](#/0-6)에.

### 2.3 왜 덱이 필요한가 — 슬라이딩 윈도우 최댓값

큐만 있으면 되는 문제에 덱을 쓸 이유는 없다. 덱이 아니면 안 되는 대표 문제가 이것이다.

::: widget two-pointer {"array":[1,3,-1,-3,5,3,6,7],"window":3,"mode":"max","monotonic":true}
:::

위젯은 창이 오른쪽으로 한 칸씩 밀릴 때 덱 안에 무엇이 남고 무엇이 버려지는지를 한 스텝씩 보인다. 창이 밀릴 때마다 두 종류의 원소가 사라진다. **창 밖으로 나간 것**은 앞에서 빠지고, **새 값보다 작은 것**은 뒤에서 빠진다.

두 번째가 핵심이다. 새 값 `x`가 들어왔을 때, 덱 뒤쪽에 `x` 이하인 값이 있으면 그것은 **영원히 답이 될 수 없다.** 그 값은 `x`보다 앞에 있으므로 창에서 `x`보다 먼저 나가고, 그때까지는 `x`가 그 값을 가린다. 살아 있는 동안 한 번도 최댓값이 되지 못하는 원소를 들고 있을 이유가 없다.

버리고 나면 덱에는 **값이 내림차순인 인덱스만** 남는다. 이것이 불변식이고, 그래서 창의 최댓값은 항상 덱의 맨 앞이다. 최댓값을 찾는 것이 아니라 **찾을 필요가 없게 유지하는 것**이 이 기법의 정체다.

비용을 세면 왜 $O(n)$인지 나온다. 각 인덱스는 덱에 **정확히 한 번 들어가고 많아야 한 번 나온다.** 안쪽 `while` 루프가 한 스텝에서 여러 번 돌 수는 있지만, 전체를 합치면 pop 횟수가 push 횟수를 넘지 못한다. 이런 논증을 분할상환 분석이라고 부른다.

### 2.4 스택은 배열로 충분한데 큐는 왜 아닌가

두 자료구조의 차이는 규칙 한 줄인데 구현 난도는 크게 갈린다.

**스택은 넣는 곳과 빼는 곳이 같다.** 둘 다 배열의 뒤끝이므로 동적 배열 하나면 끝이고, 실제로 Python의 `list`와 C++의 `vector`가 그대로 스택이다([II-4](#/ii-4)).

**큐는 넣는 곳과 빼는 곳이 반대다.** 그래서 두 위치가 배열 위를 **서로 다른 속도로 오른쪽으로 기어간다.** 그냥 두면 앞쪽에 쓰지 않는 칸이 계속 쌓여 배열이 무한히 자란다. 이 낭비를 막는 방법이 둘인데, 앞을 메우면 $O(n)$이고 **끝을 처음에 이어 붙이면 $O(1)$이다.** 후자가 링 버퍼다.

::: note
C++의 `std::queue`와 `std::stack`은 자료구조가 아니라 **어댑터**다. 다른 컨테이너를 감싸 인터페이스만 제한한다. `stack`의 기본 바탕은 `deque`이고 `vector`로 바꿔 끼울 수 있지만, `queue`는 `vector`를 바탕으로 쓸 수 없다 — `vector`에 `pop_front`가 없기 때문이다. **인터페이스가 이미 그 자료구조의 비용 구조를 말하고 있다**([0-6](#/0-6)).
:::

## 3. 손으로 따라가기

::: trace
입력: `a = [1, 3, -1, -3, 5, 3, 6, 7]`, `k = 3`.

규칙은 셋이다. ① 덱 뒤에서 `a[뒤] <= a[i]`인 동안 버린다. ② 인덱스 `i`를 뒤에 넣는다. ③ 앞이 `i - k` 이하면 만료라 버린다. `i >= k - 1`부터 답이 나온다.

덱에는 **인덱스**가 들어간다. 값 열은 그 인덱스가 가리키는 값이다.

| i | a[i] | 뒤에서 버림 | 앞에서 만료 | 덱(인덱스) | 덱(값) | 창의 최댓값 |
|---|---|---|---|---|---|---|
| 0 | 1 | — | — | [0] | [1] | — |
| 1 | 3 | 0 (1 ≤ 3) | — | [1] | [3] | — |
| 2 | -1 | — | — | [1,2] | [3,-1] | 3 |
| 3 | -3 |  |  |  |  |  |
| 4 | 5 |  |  |  |  |  |
| 5 | 3 |  |  |  |  |  |
| 6 | 6 |  |  |  |  |  |
| 7 | 7 |  |  |  |  |  |

세 가지를 확인하라.

- [ ] 덱(값) 열이 매 줄 **내림차순**인가. 한 줄이라도 깨지면 규칙 ①을 빠뜨린 것이다
- [ ] 만료가 실제로 일어나는 줄은 어디인가. 몇 번뿐인가
- [ ] 전체를 통틀어 push는 몇 번, pop은 몇 번인가
:::

::: answer
| i | a[i] | 뒤에서 버림 | 앞에서 만료 | 덱(인덱스) | 덱(값) | 창의 최댓값 |
|---|---|---|---|---|---|---|
| 0 | 1 | — | — | [0] | [1] | — |
| 1 | 3 | 0 (1 ≤ 3) | — | [1] | [3] | — |
| 2 | -1 | — | — | [1,2] | [3,-1] | 3 |
| 3 | -3 | — | — | [1,2,3] | [3,-1,-3] | 3 |
| 4 | 5 | 3, 2, 1 | — | [4] | [5] | 5 |
| 5 | 3 | — | — | [4,5] | [5,3] | 5 |
| 6 | 6 | 5, 4 | — | [6] | [6] | 6 |
| 7 | 7 | 6 | — | [7] | [7] | 7 |

답은 `[3, 3, 5, 5, 6, 7]`이다.

덱(값) 열은 여덟 줄 전부 내림차순이다. 이것이 "맨 앞이 곧 최댓값"의 근거다.

**만료는 한 번도 일어나지 않았다.** 앞에서 버리는 규칙이 필요 없었다는 뜻이 아니다. `i = 4`에서 인덱스 1을 뒤에서 버렸기 때문에 만료될 기회가 없었을 뿐이다. `a = [9, 1, 1, 1]`, `k = 3`이면 `i = 3`에서 인덱스 0이 창 밖으로 나가고, 그때는 뒤에서 버리는 규칙이 손대지 않는다. **두 규칙은 서로를 대신하지 못한다.**

push는 여덟 번, pop은 여섯 번이다(0, 3, 2, 1, 5, 4). 합이 열넷으로 $2n$을 넘지 않는다. 안쪽 `while`이 `i = 4`에서 세 번 돌았지만 그 세 번은 이미 push된 것을 갚은 것이다. **한 스텝의 최악이 $O(k)$여도 전체는 $O(n)$이다.**
:::

## 4. 구현

먼저 링 버퍼다. `%` 하나로 원을 만든다.

::: dual
```python title="링 버퍼 큐 — 고정 용량, 양 끝 O(1)"
class RingQueue:
    def __init__(self, cap):
        self.buf = [None] * cap
        self.cap = cap
        self.head = 0     # 다음에 꺼낼 자리
        self.size = 0     # head 하나로는 빈 것과 꽉 찬 것을 구분 못 한다

    def push(self, x):
        if self.size == self.cap:
            return False                          # 오버런 정책은 XI-1 에서 다룬다
        self.buf[(self.head + self.size) % self.cap] = x
        self.size += 1
        return True

    def pop(self):
        if self.size == 0:
            return None
        x = self.buf[self.head]
        self.buf[self.head] = None                # 참조를 남기면 객체가 안 죽는다
        self.head = (self.head + 1) % self.cap
        self.size -= 1
        return x


def dump(q):
    cells = []
    live = {(q.head + j) % q.cap for j in range(q.size)}
    for i in range(q.cap):
        cells.append(str(q.buf[i]) if i in live else "_")
    return "[" + " ".join(cells) + "]"


q = RingQueue(4)
for x in (10, 20, 30):
    q.push(x)
    print("push", x, "head =", q.head, "size =", q.size, dump(q))
for _ in range(2):
    print("pop ", q.pop(), "head =", q.head, "size =", q.size, dump(q))
for x in (40, 50):
    q.push(x)
    print("push", x, "head =", q.head, "size =", q.size, dump(q))
```
```cpp title="링 버퍼 큐 — 고정 용량, 양 끝 O(1)"
#include <iostream>
#include <set>
#include <string>
#include <vector>
using namespace std;

struct RingQueue {
    vector<int> buf;
    int cap, head = 0, size = 0;   // head 하나로는 빈 것과 꽉 찬 것을 구분 못 한다

    RingQueue(int cap) : buf(cap, 0), cap(cap) {}

    bool push(int x) {
        if (size == cap) return false;            // 오버런 정책은 XI-1 에서 다룬다
        buf[(head + size) % cap] = x;
        size += 1;
        return true;
    }

    int pop() {
        if (size == 0) return -1;
        int x = buf[head];
        buf[head] = 0;                            // 흔적을 남기지 않는다
        head = (head + 1) % cap;
        size -= 1;
        return x;
    }
};

string dump(const RingQueue& q) {
    set<int> live;
    for (int j = 0; j < q.size; j++) live.insert((q.head + j) % q.cap);
    string s = "[";
    for (int i = 0; i < q.cap; i++) {
        if (i) s += " ";
        s += live.count(i) ? to_string(q.buf[i]) : "_";
    }
    return s + "]";
}

int main() {
    RingQueue q(4);
    for (int x : {10, 20, 30}) {
        q.push(x);
        cout << "push " << x << " head = " << q.head << " size = " << q.size << " " << dump(q) << "\n";
    }
    for (int i = 0; i < 2; i++) {
        int x = q.pop();
        cout << "pop  " << x << " head = " << q.head << " size = " << q.size << " " << dump(q) << "\n";
    }
    for (int x : {40, 50}) {
        q.push(x);
        cout << "push " << x << " head = " << q.head << " size = " << q.size << " " << dump(q) << "\n";
    }
    return 0;
}
```
:::

두 언어의 출력은 같다.

```console
push 10 head = 0 size = 1 [10 _ _ _]
push 20 head = 0 size = 2 [10 20 _ _]
push 30 head = 0 size = 3 [10 20 30 _]
pop  10 head = 1 size = 2 [_ 20 30 _]
pop  20 head = 2 size = 1 [_ _ 30 _]
push 40 head = 2 size = 2 [_ _ 30 40]
push 50 head = 2 size = 3 [50 _ 30 40]
```

마지막 줄이 링 버퍼의 전부다. 논리적 순서는 `30 40 50`인데 물리적 배치는 `50 _ 30 40`이다. **원소는 한 칸도 움직이지 않았고 `head`만 0에서 2로 갔다.**

**복잡도:** `push`·`pop` 모두 시간 $O(1)$ — 나머지 연산 한 번과 대입 한 번뿐이고 원소를 미는 루프가 없다. 공간 $O(\text{cap})$ — 원소 수와 무관하게 처음 잡은 배열 하나다. 상수도 작다. 배열이 연속 메모리라 `head`가 훑는 방향이 캐시 라인과 맞는다 — 같은 $O(1)$이어도 연결 리스트 큐보다 실측이 빠른 이유가 이것이다([II-3](#/ii-3)).

| 언어 차이 | Python | C++ |
|---|---|---|
| 빈 자리 표시 | `None`을 넣어 참조를 끊는다. 안 끊으면 GC가 객체를 못 회수한다 | `int` 값이라 회수할 것이 없다. 포인터를 담는 큐라면 같은 문제가 생긴다 |
| 실패 통지 | `False` / `None` 반환 | `false` / 센티넬 반환. 실무에서는 `std::optional`(C++17)이 낫다 |
| 나머지 연산 | `%`는 항상 음이 아닌 값 | `%`는 피연산자가 음수면 음수. 인덱스가 음수가 될 수 있으면 `(i % cap + cap) % cap` |

이제 슬라이딩 윈도우 최댓값이다. 손추적 표의 세 규칙을 그대로 옮긴다.

::: dual
```python title="슬라이딩 윈도우 최댓값 — 단조 감소 덱"
from collections import deque


def window_max(a, k):
    dq = deque()          # 인덱스를 담는다. 값은 a[i] 로 읽는다
    out = []
    for i, x in enumerate(a):
        while dq and a[dq[-1]] <= x:
            dq.pop()      # ① 나보다 작은 뒤쪽은 영원히 답이 못 된다
        dq.append(i)      # ②
        if dq[0] <= i - k:
            dq.popleft()  # ③ 창 밖으로 나갔다
        if i >= k - 1:
            out.append(a[dq[0]])   # 불변식: 덱은 값 내림차순이라 앞이 최댓값
    return out


a = [1, 3, -1, -3, 5, 3, 6, 7]
print(window_max(a, 3))
```
```cpp title="슬라이딩 윈도우 최댓값 — 단조 감소 덱"
#include <deque>
#include <iostream>
#include <vector>
using namespace std;

vector<int> window_max(const vector<int>& a, int k) {
    deque<int> dq;        // 인덱스를 담는다. 값은 a[i] 로 읽는다
    vector<int> out;
    for (int i = 0; i < (int)a.size(); i++) {
        int x = a[i];
        while (!dq.empty() && a[dq.back()] <= x)
            dq.pop_back();     // ① 나보다 작은 뒤쪽은 영원히 답이 못 된다
        dq.push_back(i);       // ②
        if (dq.front() <= i - k)
            dq.pop_front();    // ③ 창 밖으로 나갔다
        if (i >= k - 1)
            out.push_back(a[dq.front()]);  // 불변식: 덱은 값 내림차순이라 앞이 최댓값
    }
    return out;
}

int main() {
    vector<int> a = {1, 3, -1, -3, 5, 3, 6, 7};
    cout << "[";
    vector<int> r = window_max(a, 3);
    for (size_t i = 0; i < r.size(); i++) cout << (i ? ", " : "") << r[i];
    cout << "]\n";
    return 0;
}
```
:::

둘 다 `[3, 3, 5, 5, 6, 7]`을 출력한다.

**복잡도:** 시간 $O(n)$ — 각 인덱스가 덱에 한 번 push되고 많아야 한 번 pop되므로 안쪽 `while`의 총 반복 횟수가 $n$을 넘지 못한다. 공간 $O(k)$ — 덱에는 창 안의 인덱스만 남는다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 양 끝 읽기 | `dq[0]`, `dq[-1]` | `dq.front()`, `dq.back()` |
| 뒤에서 빼기 | `dq.pop()` — 값을 **반환**한다 | `dq.pop_back()` — 반환하지 않는다. 읽고 빼는 것이 두 단계 |
| 빈 검사 | `while dq:` — 빈 컨테이너가 거짓 | `while (!dq.empty())` — 컨테이너에 참·거짓 변환이 없다 |
| 중간 인덱싱 | `dq[i]`가 $O(n)$ | `dq[i]`가 $O(1)$ |

::: perf
같은 입력에 대해 창마다 다시 훑는 방법과 덱을 비교한 값이다. `n = 200,000` 고정, `k`만 바꾼다.

| k | Python 훑기 | Python 덱 | C++ 훑기 | C++ 덱 |
|---|---|---|---|---|
| 100 | 0.340초 | 0.071초 | 0.0361초 | 0.0029초 |
| 400 | 1.177초 | 0.068초 | 0.1620초 | 0.0028초 |
| 1,600 | 4.644초 | 0.068초 | 0.6747초 | 0.0030초 |

> (Linux x86-64 / CPython 3.13 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 측정 스크립트는 `tools/bench/window_max_deque.py` 와 `.cpp` 다.)

읽을 것은 배수가 아니라 **기울기**다. 훑기 쪽은 `k`가 4배가 될 때마다 시간이 3.5~4.2배가 된다. $O(nk)$의 모양이다. 덱 쪽은 `k`를 16배로 키워도 0.071 → 0.068초, 0.0029 → 0.0030초로 **움직이지 않는다.** 창의 크기가 비용에 안 들어간다는 $O(n)$의 정의가 표에 그대로 있다.
:::

::: pitfall
- **덱에 값을 넣는다.** 인덱스를 넣어야 만료 판정(`dq[0] <= i - k`)이 가능하다. 값만 들고 있으면 창 밖으로 나간 것을 알아볼 방법이 없다.
- **`<=` 대신 `<`를 쓴다.** 같은 값이 여러 개일 때 `<`는 덱에 중복을 남긴다. 답은 같지만 덱이 최악에 `k`까지 커지고, 최솟값 버전으로 부등호를 뒤집을 때 실수의 진원지가 된다.
- **만료를 먼저 검사한다.** ③을 ①·②보다 앞에 두면 이번 스텝에 push한 인덱스를 검사하지 못한다. `k = 1`에서 즉시 틀린다.
- **`list`를 덱으로 쓴다.** `pop(0)`이 $O(n)$이라 전체가 $O(nk)$로 되돌아간다. 자료구조를 바꾼 이유가 통째로 사라진다.
- **`% cap`을 빠뜨린다.** 링 버퍼에서 `head + size`가 배열 끝을 넘어가는 순간 조용히 인덱스 오류가 난다. C++에서는 조용히 남의 메모리를 읽는다.
:::

## 5. 어디에 쓰이는가

**메시지 큐가 큐다.** 브로커는 생산자와 소비자의 속도가 다르다는 전제 위에 선다. 둘을 직접 잇지 않고 가운데 유계 큐를 두면 소비자가 잠깐 느려져도 생산자가 멈추지 않는다. 큐가 차면 무엇을 할지가 시스템의 성격을 정한다 — 생산자를 막을지, 오래된 것을 버릴지, 새 것을 거부할지. [XI-2 생산자-소비자와 유계 큐](#/xi-2)와 [XI-7 이벤트 루프와 백프레셔](#/xi-7)가 이 결정을 다룬다.

**센서 스트림과 로그 버퍼는 링 버퍼다.** 최근 N개만 필요하고 오래된 것은 덮어써도 된다. 고정 크기라 실행 중에 메모리를 할당하지 않는다는 점이 제어 루프에서 결정적이다 — 할당은 시간이 얼마나 걸릴지 보장되지 않는 연산이라 실시간 경로에서 금지된다. [XI-1 링 버퍼(원형 큐)](#/xi-1)가 오버런 정책까지 이어받는다.

**명령 버퍼는 큐에 담긴 커맨드 객체다.** "지금 실행"과 "나중에 실행"을 같은 형태로 다루면 실행 취소와 재시도가 공짜로 따라온다. 자료구조가 큐이고 그 위의 설계가 [XII-9 Command](#/xii-9)다.

**스레드 풀의 작업 큐가 같은 구조다.** 작업을 큐에 넣고 놀고 있는 워커가 앞에서 꺼낸다. 여기서 덱이 한 번 더 값을 한다 — 워커마다 자기 덱을 두고 자기 작업은 **뒤에서** 꺼내고 남의 작업은 **앞에서** 훔쳐 가면 경합이 크게 준다. 워크 스틸링이라고 부르고 [XI-4 스레드 풀과 작업 큐](#/xi-4)에서 다룬다. **양 끝이 열려 있다는 성질 하나가 동시성 설계의 선택지를 만든다.**

**BFS의 엔진이 큐다.** 큐가 거리 순서를 유지한다는 성질 하나로 최단 거리가 나온다([IV-3](#/iv-3)). 가중치가 0과 1뿐이면 큐를 덱으로 바꾸는 것만으로 다익스트라 없이 풀린다 — 비용 0인 간선은 앞에, 1인 간선은 뒤에 넣는다([IV-4](#/iv-4)). **자료구조를 한 단계 일반화한 것이 알고리즘 하나를 만든다.**

## 6. 이 유형을 알아보는 법

::: interview
**"고정 크기 배열로 큐를 구현해 보세요."**
화이트보드 단골이고, 채점 지점은 코드가 아니라 세 가지 답이다. ① `head`와 원소 수를 든다(또는 `tail`을 들고 한 칸을 비운다). 왜 인덱스 둘만으로는 안 되는지를 **빈 상태와 꽉 찬 상태가 같은 식이 된다**로 설명한다. ② 인덱스는 `% cap`으로 접는다. ③ 꽉 찼을 때의 정책을 되묻는다 — 거부할지, 오래된 것을 버릴지, 생산자를 막을지는 자료구조가 아니라 요구사항이 정한다.

**"`std::queue`와 `std::deque` 중 무엇을 쓰겠습니까."**
"둘 다 됩니다"가 아니라 기준을 답한다. 인터페이스를 큐로 제한해 오용을 막고 싶으면 `queue`, 양 끝이 다 필요하면 `deque`다. 그리고 **양쪽 다 아닌 답이 있다** — 크기가 정해져 있고 실시간 경로라면 실행 중 할당이 없는 고정 크기 링 버퍼다.
:::

::: classify
- 신호어: "먼저 들어온 순서대로", "차례대로 처리", "앞뒤로 뺀다", "회전시킨다", "연속한 K개 중 최대/최소", "각 위치에서 최근 K개의"
- 제약조건: $N \le 10^6$ 수준이라 $O(n)$ 또는 $O(n \log n)$만 허용된다. 창 크기 $K$가 $N$에 비례해 커질 수 있으면 $O(NK)$ 훑기는 탈락이다
- 혼동 주의: 꺼내는 순서가 도착 순서가 아니라 **우선순위**면 힙이다([II-8](#/ii-8)). 나중에 들어온 것부터면 스택이다([II-4](#/ii-4)). 창 안의 최댓값이 아니라 **합**이면 덱이 필요 없고 누적합으로 끝난다([VI-4](#/vi-4))
- 반례 함정: 창의 최댓값을 힙으로 풀면 창을 벗어난 원소가 힙 안에 남아 답을 오염시킨다. 지연 삭제를 붙이면 $O(n \log n)$이 되고, 덱이면 $O(n)$이다
:::

## 연습

::: quiz
앞의 둘은 큐 그 자체이고, 뒤의 둘은 "덱이 아니면 안 되는" 이유를 만든다.

**1. 백준 2164 카드2 (실버 4)** — https://www.acmicpc.net/problem/2164
- 신호: "제일 위 카드를 버리고, 다음 카드를 제일 아래로 옮긴다". 앞에서 빼서 뒤에 넣는 동작이 지문에 그대로 있다.
- 상태: 남은 카드의 순서 하나. 다른 정보가 없다.
- 자료구조: 큐. `list.pop(0)`으로 짜면 $N = 500{,}000$에서 $O(n^2)$이라 넘는다. 자료구조 선택이 곧 통과 여부다.

**2. 백준 1966 프린터 큐 (실버 3)** — https://www.acmicpc.net/problem/1966
- 신호: "뒤에 더 중요한 문서가 있으면 맨 뒤로 보낸다". 조건부 재삽입이라 순서가 큐로 유지된다.
- 상태: (중요도, 원래 인덱스) 쌍의 큐 + 남은 중요도의 개수.
- 자료구조: 큐. "더 중요한 것이 있는가"를 매번 훑어도 $N \le 100$이라 통과한다. **$N$이 커지면 이 판정에 힙이 필요해진다** — 그 경계를 계산해 보는 것이 이 문제의 훈련 가치다.

**3. 백준 1021 회전하는 큐 (실버 3)** — https://www.acmicpc.net/problem/1021
- 신호: "왼쪽으로 한 칸", "오른쪽으로 한 칸". 양방향 회전이 연산으로 주어진다.
- 상태: 원소들의 현재 배치와 뽑아야 할 위치.
- 자료구조: 덱. 회전은 한쪽 끝에서 빼서 반대쪽 끝에 넣는 것이고, 양쪽이 $O(1)$이어야 매 회전이 상수 시간이다.

**4. 백준 2346 풍선 터뜨리기 (실버 3)** — https://www.acmicpc.net/problem/2346
- 신호: 적힌 수만큼 **양방향으로** 이동한다. 음수면 왼쪽이다.
- 상태: (풍선 번호, 적힌 수) 쌍의 원형 배치.
- 자료구조: 덱. 이동을 회전으로 바꾸면 현재 위치를 항상 맨 앞으로 정규화할 수 있다. 인덱스 계산으로 풀려 들면 이미 터진 풍선을 건너뛰는 처리에서 무너진다.
:::

## 요약

- 큐의 정체는 자료구조가 아니라 **규칙**이다. 먼저 들어온 것이 먼저 나간다. 그 규칙을 $O(1)$로 지키는 구현이 링 버퍼다.
- 앞에서 빼는 것이 비싼 이유는 **꺼낸 자리를 메우기 때문**이다. 메우지 않고 `head`만 옮기면 상수 시간이 된다.
- `head`와 `tail`만으로는 빈 것과 꽉 찬 것을 구분할 수 없다. `size`를 세거나 한 칸을 비워 둔다.
- 덱은 양 끝이 $O(1)$인 큐다. Python `deque`는 중간 인덱싱이 $O(n)$이고 C++ `std::deque`는 $O(1)$이다.
- 슬라이딩 윈도우 최댓값의 덱은 **값 내림차순**을 불변식으로 유지한다. 새 값보다 작은 뒤쪽 원소는 영원히 답이 될 수 없으므로 버린다.
- 각 원소가 한 번 들어가고 많아야 한 번 나오므로 안쪽 `while`이 있어도 전체가 $O(n)$이다. 실측에서 `k`를 16배로 키워도 시간이 움직이지 않는다.
- 큐가 넘칠 때 무엇을 버리는가가 시스템의 성격을 정한다. 그 결정을 강제하는 것이 고정 용량의 존재 이유다.
