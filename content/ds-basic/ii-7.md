# II-7 정렬

::: lead
정렬은 구현 문제가 아니라 선택 문제다. 무엇을 보고 고르고, 잘못 고르면 무엇이 조용히 틀리는가.

## 1. 문제

대회 순위표를 만든다. 규칙은 두 줄이다. **점수가 높은 사람이 위**, 점수가 같으면 **먼저 제출한 사람이 위**.

기준이 둘이니 정렬을 두 번 한다. 약한 기준으로 먼저 정렬해 두고, 강한 기준으로 다시 정렬한다. 나중 정렬이 앞 정렬의 결과를 흐트러뜨리지 않으니 두 기준이 겹쳐진다. 널리 쓰이는 관용구이고, Python에서는 언제나 맞는다.

같은 코드를 C++로 옮기고 예제로 열여섯 명을 넣으면 통과한다. 그런데 실제 데이터에서 순위가 뒤집힌다. **열일곱 명부터다.**

```console
Python  100점 구간의 제출 시각: [0, 2, 4, 6, 8, 10, 12, 14, 16]
C++     100점 구간의 제출 시각: [8, 16, 14, 12, 10, 0, 6, 4, 2]
```

여기서 나쁜 것은 틀렸다는 사실이 아니라 **틀린 것이 안 보인다**는 사실이다. 출력은 여전히 점수 내림차순으로 "정렬되어" 있다. 눈으로 훑으면 정상이고, 예제는 통과하고, 채점기만 틀렸다고 말한다.

원인은 `std::sort`가 **안정 정렬이 아니라는 것**이고, 열여섯까지 통과한 이유는 introsort가 원소 16개 이하인 구간을 삽입 정렬로만 마무리하기 때문이다([0-7](#/0-7)). ==예제의 크기가 버그를 가렸다.==

::: warn
"16"은 표준이 정한 값이 아니라 libstdc++의 구현 상수다. 다른 표준 라이브러리는 다른 문턱을 쓰고, 같은 라이브러리도 판을 올리며 바꿀 수 있다. **경계가 정확히 어디인지는 의존할 값이 아니고, 의존할 값은 "보장이 없다"는 사실 하나다.**
:::

정렬 함수를 고르는 일이 이런 결과를 낳는다. 이 절은 그 선택에 필요한 축 세 개를 다룬다. **비교하는가**, **안정한가**, **비교자가 계약을 지키는가.**

## 2. 아이디어

### 2.1 비교로는 $n \log n$ 밑으로 못 내려간다

원소 $n$개의 가능한 배치는 $n!$가지다. 정렬 알고리즘은 그중 정답 하나를 골라내는 절차이고, 비교 하나가 주는 정보는 참·거짓 **한 비트**다. 비트 $k$개로 구별할 수 있는 경우는 $2^k$가지이므로 $2^k \ge n!$이어야 하고, 양변에 로그를 취하면 이렇게 된다.

$$k \ge \log_2 (n!) \approx n \log_2 n - 1.44n$$

**어떤 비교 기반 정렬도 최악에 이보다 적게 비교할 수 없다.** 특정 알고리즘의 한계가 아니라 "비교만으로 정보를 얻는다"는 규칙 자체의 한계다.

:::

위젯은 같은 배열에 네 알고리즘을 동시에 걸고 비교 횟수와 교환 횟수를 세면서 진행한다. 무작위 입력에서 병합·퀵·힙 정렬의 비교 횟수는 전부 $n \log_2 n$ 근처에 모이고 삽입 정렬만 $n^2/4$ 쪽으로 벌어진다. 입력을 "이미 정렬됨"으로 바꾸면 순서가 뒤집힌다 — 삽입 정렬이 $n-1$번으로 끝나고 나머지는 그대로다.

마지막 관찰이 하한의 조건을 드러낸다. **하한은 "$n!$가지가 전부 가능한 입력"에 대한 명제다.** 이미 정렬된 입력은 후보가 그만큼 많지 않으므로 하한이 걸리지 않는다. Timsort가 실전 데이터에서 이론값보다 훨씬 빠른 이유가 이것이고, 실측은 [0-4 Python 표준 라이브러리 세트](#/0-4) §7.1에 있다.

### 2.2 비교를 안 하면 하한이 걸리지 않는다

하한을 깨는 방법은 하나뿐이다. **비교를 하지 않는 것.**

**계수 정렬**은 값 자체를 배열 인덱스로 쓴다. 값 $v$가 몇 개인지 세고, 누적합으로 "값 $v$가 끝나는 위치"를 구한 뒤, 원소를 그 위치에 직접 놓는다. 원소끼리 한 번도 비교하지 않으므로 $O(n + K)$다. $K$는 값의 범위다.

조건이 붙는다. **값이 정수여야 하고 범위가 좁아야 한다.** $K$가 $n$보다 훨씬 크면 카운트 배열을 만드는 비용이 정렬 비용을 잡아먹는다. 32비트 정수 전체를 담으려면 카운트 배열만 8GB다.

**기수 정렬**이 그 제약을 푼다. 값을 자릿수로 쪼개고 낮은 자리부터 계수 정렬을 반복한다. 8비트씩 끊으면 32비트 정수를 네 번의 계수 정렬로 끝낸다. 비용은 $O(d(n + B))$이고, $d$는 자릿수, $B$는 진법이다.

기수 정렬이 성립하려면 **각 자리의 계수 정렬이 안정해야 한다.** 낮은 자리에서 정한 순서를 높은 자리 정렬이 보존해야 전체가 맞기 때문이다. 안정성이 편의가 아니라 **정확성의 조건**이 되는 첫 자리다.

### 2.3 안정성은 언제 답을 바꾸는가

**안정 정렬**은 키가 같은 원소들의 원래 순서를 보존한다. 정의는 한 줄인데, 이것이 답을 바꾸는 자리는 정확히 하나다. **키가 여러 개일 때.**

두 기준으로 정렬하는 방법은 둘이다.

- **한 번에 비교한다.** 비교자가 `(점수 내림, 시각 오름)`을 튜플로 본다. 안정성과 무관하게 항상 맞는다.
- **두 번 정렬한다.** 약한 기준 먼저, 강한 기준 나중. **나중 정렬이 안정일 때만 맞는다.**

Python의 `sort`는 항상 안정(Timsort)이라 둘 다 통한다. C++의 `std::sort`는 안정이 아니라 두 번째 방법이 깨진다. §1의 출력이 그 결과다.

::: warn
두 번 정렬하는 방법을 버릴 필요는 없다. **기준을 하나의 비교자로 합칠 수 없을 때**는 이쪽이 유일한 방법이다. 예를 들어 기준 하나가 외부 시스템에서 오는 순위이고 나중에야 알 수 있다면, 안정 정렬을 쌓는 것 말고는 방법이 없다.

판단 기준은 하나다. **합칠 수 있으면 합쳐라. 합칠 수 없으면 안정 정렬을 명시하라.** C++에서 그것은 `std::stable_sort`다.
:::

📖 `std::stable_sort(first, last[, cmp])` — 안정 정렬. 시간 $O(n \log n)$, 추가 메모리 $O(n)$(못 잡으면 $O(n \log^2 n)$으로 떨어진다).
　 `std::sort`보다 실측이 1.4배가량 느리고, 그 차이가 **안정성의 값**이다([0-7](#/0-7)).
　 쓰는 곳: 다중 키를 두 번에 나눠 정렬할 때, 기수 정렬의 각 자리.
　 Python 대응: 없다. `list.sort` / `sorted`가 **이미 안정**이라 따로 고를 것이 없다.

### 2.4 비교자는 계약이다

커스텀 비교자를 넘길 때 지켜야 하는 규칙이 있다. **strict weak ordering**이다. 핵심은 `cmp(a, a)`가 반드시 거짓이어야 한다는 것 — "자기 자신보다 작다"가 참이 되는 순간 정렬은 배열 밖을 읽는다.

`<=`를 쓰는 비교자가 전형적인 위반이다. 이것은 잘못된 순서를 내는 것으로 끝나지 않고 **정의되지 않은 동작**이라 크래시하거나 조용히 남의 메모리를 밟는다. [0-8 C++ 반복자·람다·비교자](#/0-8) §4에 그 실측이 있다.

Python은 이 함정이 훨씬 얕다. `key=`가 기본 문법이고, 키를 뽑아 표준 비교로 정렬하므로 계약을 어길 여지가 애초에 적다. `functools.cmp_to_key`로 비교자를 직접 쓸 때만 같은 위험이 돌아온다.

::: deep
`std::sort`가 안정성을 포기한 것은 게으름이 아니라 **교환의 결과**다.

퀵소트의 분할은 멀리 떨어진 두 원소를 맞바꾸며 진행한다. 값이 같은 원소 둘이 그 교환에 걸리면 순서가 뒤집히고, 뒤집힌 것을 되돌리려면 원래 위치를 어딘가에 적어 두어야 한다. 그 "어딘가"가 $O(n)$의 추가 메모리다. 안정성을 지키는 병합 정렬 계열이 병합 버퍼를 요구하는 것과 같은 이유다.

그래서 표준은 두 함수를 나눠 놓았다. `sort`는 추가 메모리 $O(\log n)$(재귀 스택뿐)에 상수가 작고, `stable_sort`는 $O(n)$을 쓰고 실측 1.4배를 낸다. **버퍼를 못 잡으면 `stable_sort`는 $O(n \log^2 n)$으로 떨어지되 여전히 안정을 지킨다** — 표준이 무엇을 먼저 포기하는지가 여기서 드러난다. 속도를 포기하고 안정성을 지킨다.

Python에는 이 선택지가 없다. Timsort가 병합 기반이라 버퍼를 이미 쓰고 있고, 그래서 안정성이 공짜로 따라온다. **한쪽 언어의 "기본값"이 다른 쪽에서는 선택지라는 것이 이 절의 언어 차이 표 전체를 설명한다.**
:::

### 2.5 그래서 무엇을 고를 것인가

앞의 네 절이 축이었고, 실제 판단은 표 한 장으로 접힌다.

| 입력·요구 | 고를 것 | 근거 |
|---|---|---|
| 특별한 성질이 없다 | 언어 기본 정렬 | Python `sort`, C++ `sort`. 고민할 이유가 없다 |
| 다중 키를 나눠 정렬해야 한다 | Python 기본 / C++ `stable_sort` | 안정성이 정확성의 조건이 된다(§2.3) |
| 값이 정수이고 범위가 $n$ 수준 | 계수 정렬 | 비교를 안 하므로 $O(n+K)$ |
| 값이 정수인데 범위가 넓다 | 기수 정렬 | 자릿수로 쪼개 계수 정렬을 반복 |
| 메모리가 수 MB로 좁다 | 계수 정렬 | 입력을 안 들고 세기만 하면 된다(§4) |
| 상위 K개만 필요하다 | `partial_sort` / 힙 | 전부 정렬할 이유가 없다([II-8](#/ii-8)) |
| K번째 값 하나만 필요하다 | `nth_element` | 평균 $O(n)$([0-7](#/0-7)) |
| 매 시점 최솟값이 필요하다 | 우선순위 큐 | 정렬은 정적이고 힙은 동적이다([I-5](#/i-5)) |

표의 위 세 줄이 이 절의 본문이고, 아래 세 줄은 **정렬을 쓰지 않는 선택지**다. 정렬 유형을 물었을 때 아래 세 줄이 먼저 떠오르면 판별이 한 단계 올라간 것이다.

## 3. 손으로 따라가기

::: trace
계수 정렬을 손으로 돌린다. 입력은 `(키, 표식)` 여섯 쌍이다. 표식은 원래 순서를 눈으로 따라가려고 붙였을 뿐 정렬에는 안 쓴다.

입력: `3a 1b 3c 2d 1e 3f`, 키의 범위는 1~3.

1단계 — 개수: `cnt[1]=2`, `cnt[2]=1`, `cnt[3]=3`
2단계 — 누적합: `cnt[1]=2`, `cnt[2]=3`, `cnt[3]=6`  ← "그 값이 끝나는 위치"
3단계 — **입력을 뒤에서부터** 훑으며 `cnt[키]`를 1 줄이고 그 자리에 놓는다.

| 훑는 i | a[i] | cnt[키] 전 → 후 | 놓는 자리 | out 배열 |
|---|---|---|---|---|
| 5 | 3f | 6 → 5 | 5 | `_ _ _ _ _ 3f` |
| 4 | 1e | 2 → 1 | 1 | `_ 1e _ _ _ 3f` |
| 3 | 2d | 3 → 2 | 2 | `_ 1e 2d _ _ 3f` |
| 2 | 3c |  |  |  |
| 1 | 1b |  |  |  |
| 0 | 3a |  |  |  |

세 가지를 확인하라.

- [ ] 다 채웠을 때 `1b`와 `1e` 중 어느 쪽이 앞인가. 입력에서는 `1b`가 앞이었다
- [ ] 3단계를 **앞에서부터**(i = 0, 1, 2, …) 훑으면 같은 질문의 답이 어떻게 바뀌는가
- [ ] 이 알고리즘은 키를 몇 번 비교했는가
:::

::: answer
| 훑는 i | a[i] | cnt[키] 전 → 후 | 놓는 자리 | out 배열 |
|---|---|---|---|---|
| 5 | 3f | 6 → 5 | 5 | `_ _ _ _ _ 3f` |
| 4 | 1e | 2 → 1 | 1 | `_ 1e _ _ _ 3f` |
| 3 | 2d | 3 → 2 | 2 | `_ 1e 2d _ _ 3f` |
| 2 | 3c | 5 → 4 | 4 | `_ 1e 2d _ 3c 3f` |
| 1 | 1b | 1 → 0 | 0 | `1b 1e 2d _ 3c 3f` |
| 0 | 3a | 4 → 3 | 3 | `1b 1e 2d 3a 3c 3f` |

결과는 `1b 1e 2d 3a 3c 3f`다. **`1b`가 `1e`보다 앞이고, `3a 3c 3f`도 입력 순서 그대로다. 안정하다.**

앞에서부터 훑으면 `1e 1b 2d 3f 3c 3a`가 된다. 같은 키를 가진 원소들의 순서가 **정확히 뒤집힌다.** `cnt`는 끝 위치를 들고 있고 놓을 때마다 왼쪽으로 한 칸씩 물러나므로, 먼저 놓인 것이 더 오른쪽에 앉는다. 입력을 뒤에서부터 읽어야 "먼저 온 것이 먼저" 앉는다.

==안정성이 한 줄에서 나온다.== 루프의 방향 하나다. 계수 정렬을 직접 짜면서 이 방향을 뒤집으면, 그것을 자릿수마다 반복하는 기수 정렬은 통째로 틀린 답을 낸다.

키 비교는 **0번**이다. `cnt[키]`로 배열을 인덱싱했을 뿐 두 원소를 견준 적이 없다. §2.1의 하한이 이 알고리즘에 걸리지 않는 이유가 여기 있다 — 하한을 깬 것이 아니라 하한이 걸리는 게임을 하지 않은 것이다.
:::

## 4. 구현

먼저 §1의 사고를 코드로 재현한다. 두 언어가 **같은 알고리즘을 같은 순서로** 수행하는데 결과가 다르다.

::: dual
```python title="다중 키를 두 번 정렬로 — 나중 정렬이 안정이어야 한다"
N = 17
rows = [(100 if i % 2 == 0 else 90, i) for i in range(N)]   # (점수, 제출 시각)

rows.sort(key=lambda r: r[1])      # ① 약한 기준: 제출 시각 오름차순
rows.sort(key=lambda r: -r[0])     # ② 강한 기준: 점수 내림차순

top = [t for s, t in rows if s == 100]
print("100점 구간의 제출 시각:", top)
print("동점자가 제출 순인가:", top == sorted(top))
```
```cpp title="다중 키를 두 번 정렬로 — 나중 정렬이 안정이어야 한다"
#include <algorithm>
#include <iostream>
#include <vector>
using namespace std;

int main() {
    const int N = 17;
    vector<pair<int, int>> rows;                 // (점수, 제출 시각)
    for (int i = 0; i < N; i++) rows.push_back({i % 2 == 0 ? 100 : 90, i});

    // ① 약한 기준: 제출 시각 오름차순
    sort(rows.begin(), rows.end(), [](const auto& a, const auto& b) { return a.second < b.second; });
    // ② 강한 기준: 점수 내림차순
    sort(rows.begin(), rows.end(), [](const auto& a, const auto& b) { return a.first > b.first; });

    vector<int> top;
    for (auto [s, t] : rows) if (s == 100) top.push_back(t);

    cout << "100점 구간의 제출 시각: [";
    for (size_t i = 0; i < top.size(); i++) cout << (i ? ", " : "") << top[i];
    cout << "]\n";
    cout << "동점자가 제출 순인가: " << (is_sorted(top.begin(), top.end()) ? "True" : "False") << "\n";
    return 0;
}
```
:::

**출력이 다르다. 그것이 이 블록의 요점이다.**

```console
Python  100점 구간의 제출 시각: [0, 2, 4, 6, 8, 10, 12, 14, 16]
        동점자가 제출 순인가: True

C++     100점 구간의 제출 시각: [8, 16, 14, 12, 10, 0, 6, 4, 2]
        동점자가 제출 순인가: False
```

**복잡도:** 둘 다 시간 $O(n \log n)$ — 정렬을 두 번 하지만 상수 2가 붙을 뿐 항이 바뀌지 않는다. 공간은 Python이 $O(n)$(Timsort의 병합 버퍼), C++ `sort`가 $O(\log n)$(재귀 스택)이다. **복잡도는 같고 답만 다르다.** 성능 문제로 드러나지 않는 결함이 가장 늦게 발견된다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 기본 정렬 | `sort()` = Timsort, **안정** | `std::sort` = introsort, **불안정** |
| 위 코드의 결과 | 항상 맞는다 | 이 입력에서는 **n = 17부터 틀린다.** 16 이하는 introsort가 전체를 삽입 정렬로만 끝내므로 어떤 입력이어도 안정하게 나온다 |
| 고치는 법 | 고칠 것이 없다 | `stable_sort`로 바꾸거나, 두 기준을 비교자 하나로 합친다 |
| 내림차순 | `key=lambda r: -r[0]` 또는 `reverse=True` | 비교자에서 `>`. `reverse` 인자가 없다 |
| 다중 키 관용구 | `key=lambda r: (-r[0], r[1])` — 튜플이 사전순 비교 | `return a.first != b.first ? a.first > b.first : a.second < b.second;` |

```cpp title="고치는 두 가지 방법 (조각)"
// ✅ 방법 1 — 안정 정렬을 명시한다. 두 번 정렬 관용구가 그대로 산다
stable_sort(rows.begin(), rows.end(), [](const auto& a, const auto& b) { return a.first > b.first; });

// ✅ 방법 2 — 기준을 하나의 비교자로 합친다. 안정성과 무관해진다
sort(rows.begin(), rows.end(), [](const auto& a, const auto& b) {
    if (a.first != b.first) return a.first > b.first;   // 점수 내림차순
    return a.second < b.second;                          // 동점이면 시각 오름차순
});
// ❌ return a.first >= b.first;  <- strict weak ordering 위반. 크래시한다(0-8 §4)
```

두 번째가 더 안전하다. **안정성에 의존하지 않는 코드는 정렬 함수를 바꿔도 안 깨진다.**

이제 비교하지 않는 정렬이다. 손추적 표의 세 단계를 그대로 옮긴다.

::: dual
```python title="계수 정렬 — 비교 0회, 그리고 안정성은 루프 방향에서 나온다"
def counting_sort(a, K, backward):
    cnt = [0] * (K + 1)
    for key, _ in a:
        cnt[key] += 1                       # 값마다 몇 개인지 센다. 비교는 한 번도 없다
    for v in range(1, K + 1):
        cnt[v] += cnt[v - 1]                # 누적합 = 그 값이 끝나는 위치
    out = [None] * len(a)
    order = range(len(a) - 1, -1, -1) if backward else range(len(a))
    for i in order:
        key, tag = a[i]
        cnt[key] -= 1                       # 끝에서부터 채워 나간다
        out[cnt[key]] = (key, tag)
    return out


def show(a):
    return " ".join(f"{k}{t}" for k, t in a)


a = [(3, "a"), (1, "b"), (3, "c"), (2, "d"), (1, "e"), (3, "f")]
print("입력           :", show(a))
print("뒤에서부터 순회:", show(counting_sort(a, 3, True)))
print("앞에서부터 순회:", show(counting_sort(a, 3, False)))
```
```cpp title="계수 정렬 — 비교 0회, 그리고 안정성은 루프 방향에서 나온다"
#include <iostream>
#include <string>
#include <vector>
using namespace std;

vector<pair<int, char>> counting_sort(const vector<pair<int, char>>& a, int K, bool backward) {
    vector<int> cnt(K + 1, 0);
    for (auto [key, tag] : a)
        cnt[key] += 1;                      // 값마다 몇 개인지 센다. 비교는 한 번도 없다
    for (int v = 1; v <= K; v++)
        cnt[v] += cnt[v - 1];               // 누적합 = 그 값이 끝나는 위치
    vector<pair<int, char>> out(a.size());
    for (int j = 0; j < (int)a.size(); j++) {
        int i = backward ? (int)a.size() - 1 - j : j;
        auto [key, tag] = a[i];
        cnt[key] -= 1;                      // 끝에서부터 채워 나간다
        out[cnt[key]] = {key, tag};
    }
    return out;
}

string show(const vector<pair<int, char>>& a) {
    string s;
    for (size_t i = 0; i < a.size(); i++) {
        if (i) s += " ";
        s += to_string(a[i].first);
        s += a[i].second;
    }
    return s;
}

int main() {
    vector<pair<int, char>> a = {{3, 'a'}, {1, 'b'}, {3, 'c'}, {2, 'd'}, {1, 'e'}, {3, 'f'}};
    cout << "입력           : " << show(a) << "\n";
    cout << "뒤에서부터 순회: " << show(counting_sort(a, 3, true)) << "\n";
    cout << "앞에서부터 순회: " << show(counting_sort(a, 3, false)) << "\n";
    return 0;
}
```
:::

두 언어의 출력은 한 글자도 다르지 않다.

```console
입력           : 3a 1b 3c 2d 1e 3f
뒤에서부터 순회: 1b 1e 2d 3a 3c 3f
앞에서부터 순회: 1e 1b 2d 3f 3c 3a
```

**복잡도:** 시간 $O(n + K)$ — 원소를 두 번 훑고($n$) 카운트 배열을 한 번 훑는다($K$). 공간 $O(n + K)$ — 출력 배열과 카운트 배열. **$K$가 $n$보다 크면 이 알고리즘은 $O(K)$짜리 알고리즘이고, 그때는 쓰지 않는다.**

::: perf
`n = 2,000,000`에 대해 값 범위를 바꿔 가며 잰 값이다.

| 값 범위 | `std::sort` | 계수 정렬 | 기수 정렬(8비트×4) |
|---|---|---|---|
| $K = 10^4$ | 0.1278초 | **0.0207초 (6.2배)** | — |
| $2^{31}$ | 0.1616초 | 카운트 배열만 8GB — 불가능 | **0.0595초 (2.7배)** |

Python 쪽은 시간이 아니라 메모리가 결정한다.

| 방법 | 시간 | 최대 RSS |
|---|---|---|
| `list.sort()` | 0.607초 | 97.5 MB |
| 계수 정렬(리스트 보관) | 0.119초 | 101.7 MB |
| 계수 정렬(입력을 안 들고 세기만) | — | **11.3 MB** |

> (Linux x86-64 / CPython 3.13 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 측정 스크립트는 `tools/bench/counting_radix_bench.cpp` 와 `.py` 다.)

세 번째 줄이 Python에서 계수 정렬을 쓰는 진짜 이유다. **입력을 리스트로 들지 않고 읽으면서 바로 세면 메모리가 9분의 1로 줄어든다.** 정수 1,000만 개를 리스트로 들면 값 하나가 객체 하나라 수백 MB가 되고, 카운트 배열은 값의 범위에만 비례한다. 백준 10989가 이 차이를 그대로 묻는 문제다.
:::

::: pitfall
- **누적합을 빠뜨리고 개수만으로 위치를 정한다.** 그러면 값별 시작 위치를 모른다. 개수 배열과 위치 배열은 다른 것이다.
- **계수 정렬을 앞에서부터 훑는다.** 같은 키의 순서가 뒤집힌다. 단독으로 쓸 때는 티가 안 나고, **기수 정렬의 부품으로 쓰는 순간 전체가 틀린다.**
- **음수에 계수 정렬을 쓴다.** 인덱스가 음수가 된다. 최솟값만큼 평행이동(`v - min`)해야 한다.
- **`std::sort`로 두 번 정렬한다.** 예제에서는 통과한다. n = 17부터 깨진다.
- **비교자에 `<=`를 쓴다.** strict weak ordering 위반이라 크래시한다. "같으면 앞" 같은 규칙은 **비교자의 두 번째 기준**으로 표현한다.
- **정렬이 필요 없는데 정렬한다.** 최댓값 하나면 $O(n)$, 상위 K개면 `partial_sort`, K번째 값 하나면 `nth_element`가 $O(n)$이다([0-7](#/0-7)).
:::

## 5. 어디에 쓰이는가

**데이터베이스의 `ORDER BY`가 안정성 문제를 그대로 안고 있다.** 정렬 키가 같은 행들의 순서를 표준이 보장하지 않으므로, 페이지 넘김이 있는 목록에서 같은 행이 두 번 나오거나 아예 빠질 수 있다. 실무의 방어는 §2.3의 두 번째 방법과 같다 — **정렬 키에 고유 식별자를 마지막 기준으로 덧붙여 동점을 없앤다.**

**외부 정렬은 계수·기수 정렬과 같은 발상 위에 있다.** 메모리에 안 들어가는 데이터를 조각으로 나눠 각각 정렬한 뒤 병합하는데, 이때 조각을 어떻게 나눌지가 곧 "값의 범위를 어떻게 쪼갤 것인가"다([XV-12](#/xv-12)).

**정렬은 다른 알고리즘의 전처리로 더 자주 쓰인다.** 좌표 압축([VI-5](#/vi-5)), 구간 스케줄링([VI-2](#/vi-2)), 크루스칼의 간선 정렬([IX-4](#/ix-4)), 스위핑([VI-6](#/vi-6))이 전부 "정렬해 두면 뒤가 단순해진다"는 같은 이유로 정렬을 부른다. 그래서 정렬의 복잡도 $O(n \log n)$이 이 알고리즘들의 하한을 정하는 일이 잦다.

**그래픽 파이프라인의 반투명 물체 정렬이 안정성을 요구한다.** 깊이가 같은 물체들의 그리는 순서가 프레임마다 달라지면 화면이 미세하게 깜빡인다. 프레임 사이에 순서가 바뀌지 않아야 하고, 그 보장을 주는 것이 안정 정렬이다.

## 6. 이 유형을 알아보는 법

::: classify
- 신호어: "오름차순으로 출력", "~순으로 정렬하되 같으면 ~순으로", "K번째로 작은", "가장 많이 등장한 순서로"
- 제약조건: $N \le 10^6$이면 $O(N \log N)$ 표준 정렬로 충분하다. $N \ge 10^7$이거나 메모리 제한이 수 MB면 표준 정렬이 안 들어가고 **값의 범위 $K$를 봐야 한다.** $K \le 10^6$이면 계수 정렬
- 혼동 주의: 전부 정렬할 필요가 없으면 정렬이 아니다. 상위 K개면 힙([II-8](#/ii-8)), K번째 값 하나면 `nth_element`. **매 시점 최솟값이 필요하면** 정렬이 아니라 우선순위 큐다([I-5](#/i-5))
- 반례 함정: 동점 처리가 지문에 있는데 `std::sort`로 두 번 정렬하는 것. n ≤ 16인 예제는 전부 통과하고 실제 데이터에서만 깨진다. 그리고 값에 음수가 섞인 계수 정렬
:::

::: interview
**"`std::sort`와 `stable_sort`의 차이가 무엇입니까."**
"안정성"만 답하면 절반이다. 뼈대는 셋이다. ① `sort`는 introsort라 추가 메모리가 $O(\log n)$, `stable_sort`는 $O(n)$이다. ② 실측 차이는 1.4배 정도이고 그것이 안정성의 값이다. ③ **안정성이 답을 바꾸는 경우는 다중 키를 두 번에 나눠 정렬할 때뿐이고**, 비교자 하나로 합치면 무관해진다.

**"$O(n \log n)$보다 빠른 정렬이 있습니까."**
"계수 정렬이 $O(n)$입니다"로 끝내면 안 된다. 하한이 **비교 기반**에만 걸린다는 점, 계수·기수 정렬은 비교를 하지 않는다는 점, 대신 키가 정수이고 범위가 제한되어야 한다는 조건을 함께 말한다.
:::

**1. 백준 10989 수 정렬하기 3 (브론즈 1)** — https://www.acmicpc.net/problem/10989

- 자료구조: 크기 10,001짜리 카운트 배열. 메모리 제한이 좁아 입력을 리스트로 들면 그것만으로 넘는다. §4의 세 번째 줄이 이 문제의 답이다.

- 상태: (국어, 영어, 수학, 이름) 튜플.
- 자료구조: 배열 + 비교자 하나. 기준을 전부 합쳐 한 번에 비교한다. 네 번 나눠 정렬하면 C++에서 `stable_sort`가 필수가 되고, 그럴 이유가 없다.

**3. 백준 10814 나이순 정렬 (실버 5)** — https://www.acmicpc.net/problem/10814
- 신호: "나이가 같으면 **먼저 가입한 순서**로". 동점의 순서가 곧 답이다.
- 상태: (나이, 가입 순서, 이름).
- 자료구조: 배열. Python은 `sort(key=...)`가 이미 안정이라 끝난다. **C++에서 `sort`로 짜면 §1의 사고가 그대로 재현된다** — 가입 순서를 두 번째 기준으로 넣거나 `stable_sort`를 쓴다.

**4. 백준 1431 시리얼 번호 (실버 3)** — https://www.acmicpc.net/problem/1431
- 신호: 길이 → 자릿수 합 → 사전순의 **3단 기준**. 각 단계의 정의가 지문에 문장으로 주어진다.
- 상태: 문자열과 그 파생값 두 개(길이, 숫자 합).
- 자료구조: 배열 + 비교자. 파생값을 매 비교마다 다시 계산하면 비교 횟수만큼 곱해진다. **미리 계산해 튜플로 만들어 두는 것**이 이 문제의 훈련 가치다.

## 요약

- 비교 기반 정렬은 최악에 $\log_2(n!) \approx n \log_2 n$번의 비교가 필요하다. **비교 하나가 1비트**라는 사실에서 곧바로 나온다.
- 하한은 "모든 배치가 가능한 입력"에 대한 명제다. 이미 정렬된 입력에는 걸리지 않고, 그래서 Timsort가 $O(n)$에 끝낼 수 있다.
- 계수·기수 정렬은 하한을 깬 것이 아니라 **비교를 하지 않는다.** 대신 키가 정수이고 범위가 좁아야 한다는 조건을 받는다.
- 계수 정렬의 안정성은 **루프 방향 하나**에서 나온다. 입력을 뒤에서부터 훑어야 한다. 앞에서부터 훑으면 같은 키의 순서가 뒤집히고, 기수 정렬은 그 자리에서 무너진다.
- 안정성이 답을 바꾸는 자리는 **다중 키를 두 번에 나눠 정렬할 때**다. `std::sort`로 그렇게 짜면 **n ≤ 16은 통과하고 17부터 틀린다.**
- 가장 안전한 습관은 **기준을 비교자 하나로 합치는 것**이다. 안정성에 의존하지 않는 코드는 정렬 함수를 바꿔도 안 깨진다.
- 비교자는 strict weak ordering을 지켜야 한다. `<=`를 쓰면 잘못된 순서가 아니라 **정의되지 않은 동작**이다.
- 전부 정렬할 필요가 없는 문제에 정렬을 쓰지 않는다. 상위 K개, K번째 값, 매 시점 최솟값은 각각 다른 도구가 있다.

**다음 절**: [II-8 힙과 우선순위 큐](#/ii-8) — 전부 정렬하지 않고 "지금 가장 급한 것 하나"만 $O(\log n)$에 꺼내는 구조. 다익스트라의 엔진이 여기서 나온다.
