# II-3 연결 리스트

::: lead
배열이 원리적으로 못 하는 연산은 하나뿐이다. 그 하나가 값어치를 하는 자리는 어디이고, 그 밖에서는 왜 지는가.
:::

## 1. 문제

캐시가 항목 1,000개를 들고 있다. 새 항목이 들어올 자리가 없으면 **가장 오래 안 쓴 것**을 버린다. 그러려면 사용 순서를 유지해야 하고, 항목을 쓸 때마다 그것을 순서의 맨 앞으로 옮겨야 한다.

배열로 짜 본다. 항목이 어디 있는지는 안다고 하자 — 해시 테이블이 `키 → 위치`를 알려 준다. 그 위치의 원소를 맨 앞으로 옮기려면 앞의 원소들을 전부 한 칸씩 뒤로 민다. **위치를 아는데도 $O(n)$이다.** 캐시 접근이 100만 번이고 크기가 1,000이면 밀기만 5억 번이다.

여기서 배열의 한계가 정확히 드러난다. 배열은 **순서를 위치로 표현한다.** 순서를 바꾸려면 위치를 바꿔야 하고, 위치를 바꾼다는 것은 물리적으로 옮긴다는 뜻이다.

순서를 위치가 아닌 것으로 표현하면 어떻게 되는가. 각 원소가 "다음은 저기"라고 적어 두면, 순서를 바꾸는 일은 **적어 둔 주소 몇 개를 고치는 일**이 된다. 원소는 제자리에 있는다. 이것이 연결 리스트다.

그리고 여기부터가 이 절의 진짜 주제다. 이 자료구조는 거의 모든 교재에 배열 다음 순서로 실리는데 **실제 코드에서는 좀처럼 쓰이지 않는다.** 왜 배우고, 언제 쓰고, 왜 대개 지는가.

## 2. 아이디어

### 2.1 순서를 주소로 적는다

```text nolines
  ┌─────┬──────┐   ┌─────┬──────┐   ┌─────┬──────┐
  │  A  │  ●───┼──▶│  C  │  ●───┼──▶│  D  │ null │
  └─────┴──────┘   └─────┴──────┘   └─────┴──────┘
   0x1a40           0x7f20           0x0c80          <- allocated anywhere
```

값 옆에 다음 노드의 주소가 붙는다. 양방향이면 이전 주소도 함께 든다. 이 구조에서 나오는 성질이 셋이다.

**중간에서 떼어내는 데 값을 옮기지 않는다.** 앞 노드의 "다음"을 뒤 노드로 바꾸면 끝이다. 이중 연결이면 링크 두 개, 단일 연결이면 하나다. **몇 개가 남아 있든 고치는 링크의 개수는 같다.**

**$i$번째를 바로 찾을 수 없다.** 주소식이 없다. 앞에서부터 $i$번 따라가야 한다.

**메모리가 연속이 아니다.** 노드마다 값 외에 주소를 들고, 할당자가 준 자리에 흩어져 앉는다.

### 2.2 $O(1)$이 성립하는 조건

교재의 표는 대개 이렇게 적혀 있고, 그 표가 오해를 만든다.

| 연산 | 배열 | 연결 리스트 |
|---|---|---|
| $i$번째 읽기 | $O(1)$ | $O(i)$ |
| 맨 앞 삽입·삭제 | $O(n)$ | $O(1)$ |
| **위치를 아는** 중간 삭제 | $O(n)$ | $O(1)$ |
| **값을 찾아서** 중간 삭제 | $O(n)$ | $O(n)$ |
| 전체 순회 | $O(n)$ | $O(n)$ |

굵은 두 줄이 갈림길이다. ==연결 리스트의 $O(1)$은 "그 노드를 이미 손에 들고 있다"를 전제한다.== 위치를 모르면 찾는 데 $O(n)$이 들고, 그 순간 배열과 복잡도가 같아진다. 그리고 상수는 배열이 훨씬 낫다.

**그래서 질문이 뒤집힌다.** "삽입이 빠른가"가 아니라 **"위치를 공짜로 얻을 수 있는가"** 다. 얻을 수 있으면 리스트가 이기고, 매번 찾아야 하면 진다.

### 2.3 지는 쪽을 먼저 본다

같은 작업을 두 조건에서 재면 이 갈림길이 숫자로 나온다.

::: perf
원소 10만 개. `A`는 위치를 이미 손에 든 채 한가운데에서 5만 번 지우고, `B`는 값을 찾아서 2,000번 지운다.

| | `vector` | `list` | |
|---|---|---|---|
| **A. 위치를 아는 삭제** 5만 회 | 0.142초 | **0.0007초** | 리스트가 200배 빠름 |
| **B. 값을 찾아 삭제** 2,000회 | **0.0478초** | 0.192초 | 리스트가 4.0배 느림 |

> (Linux x86-64 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 측정 스크립트는 `tools/bench/ii3_list_vs_vector.cpp`.)

A는 복잡도가 다르다($O(1)$ 대 $O(n)$). B는 복잡도가 같은데($O(n)$ 대 $O(n)$) 상수만으로 4배가 갈렸다. **B의 4배는 전부 메모리 접근 패턴이다.**
:::

순회 자체의 비용 차이는 [0-6 C++ 컨테이너 세트](#/0-6)가 이미 쟀다. 같은 500만 개를 더하는 데 `vector`가 0.82ns/원소, 링크를 뒤섞은 `list`가 169ns/원소로 **206배**였다. 원인은 셋이다.

**밀도.** 64바이트 캐시 라인에 `int`가 16개 실린다. 노드는 값 4바이트에 포인터 16바이트가 붙어 24바이트 이상이고, 라인 하나에 값이 두세 개밖에 안 실린다.

**예측 불가.** CPU의 프리페처는 순차 접근을 감지해 다음 라인을 미리 가져온다. 리스트는 **다음 주소가 현재 노드를 읽어야 나온다.** 미리 가져올 대상을 알 수 없어 메모리 지연이 그대로 드러난다. 이것을 포인터 추적이라 한다.

**할당.** 노드마다 할당자를 부른다. 배열은 한 번에 통째로 잡는다.

### 2.4 그래도 이기는 자리

그럼에도 연결 리스트가 대체 불가능한 자리가 있다. 전부 §2.2의 조건을 만족하는 곳이다.

**① 다른 색인이 위치를 공짜로 준다.** LRU 캐시가 정확히 이 모양이다. 해시 테이블이 `키 → 노드`를 $O(1)$에 주고, 리스트가 순서를 관리한다. 탐색을 리스트가 하지 않으므로 약점이 발동하지 않는다. ==두 자료구조의 합작이지 리스트 혼자의 승리가 아니다.==

**② 원소가 자기 위치를 들고 있어야 한다.** 커널과 메모리 할당자의 연결 리스트는 노드를 따로 만들지 않는다. 링크 필드가 **데이터 구조체 안에 박혀 있다.** 그래서 어떤 객체든 자기 자신을 리스트에서 $O(1)$에 뺄 수 있고, 삭제하는 데 메모리 할당이 한 번도 일어나지 않는다. 이것을 intrusive list라 하고, 할당이 금지된 인터럽트 문맥에서 쓸 수 있는 유일한 형태다.

**③ 통째로 옮긴다.** `std::list::splice`는 리스트 하나를 다른 리스트의 중간에 통째로 끼워 넣는 데 링크 몇 개만 고친다 — 원소가 100만 개여도 $O(1)$이다. 배열은 이 연산이 항상 복사다.

**④ 원소의 주소가 절대 바뀌면 안 된다.** 다른 곳에서 원소를 가리키고 있으면 배열은 쓸 수 없다. 재할당 한 번에 그 포인터가 전부 죽는다([II-1](#/ii-1)). 리스트는 노드가 이사하지 않으므로 다른 노드를 지워도 남은 포인터가 유효하다.

### 2.5 실전의 타협 — 배열 위의 연결 리스트

포인터를 **배열 인덱스**로 바꾸면 둘의 장점이 섞인다.

```text nolines
  idx    0(sentinel)  1     2     3     4
  val         -       A     B     C     D
  nxt         1       2     3     4     0        <- "다음" 을 인덱스로 적는다
  prv         4       0     1     2     3
```

노드가 배열 세 개에 나뉘어 연속으로 앉는다. 할당이 한 번이고, 캐시 밀도가 회복되며, 링크 수정은 여전히 $O(1)$이다. 인덱스는 재할당해도 살아 있어 무효화 문제도 없다. **코딩테스트에서 연결 리스트가 필요한 문제는 대부분 이 형태로 짠다.** 남는 약점은 하나 — 삭제한 슬롯이 배열에 그대로 남아 메모리를 돌려주지 않는다.

## 3. 손으로 따라가기

::: trace
§2.5의 배열 기반 이중 연결 리스트다. 센티넬 0번이 원을 닫고 있어 빈 리스트든 한 개짜리든 같은 코드로 돈다.

삭제 규칙은 두 줄이다.

```text nolines
  nxt[prv[x]] = nxt[x]
  prv[nxt[x]] = prv[x]
```

삽입(`p` 뒤에 `x`)은 네 줄이다. `nxt[x] = nxt[p]`, `prv[x] = p`, `prv[nxt[p]] = x`, `nxt[p] = x`.

시작 상태: `nxt = [1, 2, 3, 4, 0]`, `prv = [4, 0, 1, 2, 3]`, 읽은 순서 `A B C D`.

| 연산 | nxt | prv | 0에서 따라 읽은 순서 |
|---|---|---|---|
| (시작) | [1, 2, 3, 4, 0] | [4, 0, 1, 2, 3] | A B C D |
| `remove(2)` | [1, 3, 3, 4, 0] | [4, 0, 1, 1, 3] | A C D |
| `move_to_front(4)` | | | |
| `remove(1)` | | | |

세 가지를 확인하라.

- [ ] `remove(2)` 뒤에도 `nxt[2]`는 3으로 남아 있다. **왜 지워도 되지 않는가**
- [ ] 모든 살아 있는 노드에서 `prv[nxt[x]] == x`가 성립하는가. 이것이 이 자료구조의 불변식이다
- [ ] `move_to_front(4)`는 삭제 후 삽입이다. **삽입의 네 줄 순서를 바꾸면** 어디서 깨지는가
:::

::: answer
| 연산 | nxt | prv | 0에서 따라 읽은 순서 |
|---|---|---|---|
| (시작) | [1, 2, 3, 4, 0] | [4, 0, 1, 2, 3] | A B C D |
| `remove(2)` | [1, 3, 3, 4, 0] | [4, 0, 1, 1, 3] | A C D |
| `move_to_front(4)` | [4, 3, 3, 0, 1] | [3, 4, 1, 1, 0] | D A C |
| `remove(1)` | [4, 3, 3, 0, 3] | [3, 4, 1, 4, 0] | D C |

**`nxt[2]`가 3으로 남아 있는 것은 버그가 아니다.** 살아 있는 노드 중 누구도 2를 가리키지 않으므로 0에서 출발해 따라가는 경로에 2는 등장하지 않는다. ==링크 자료구조에서 "지운다"는 것은 값을 지우는 일이 아니라 도달 불가능하게 만드는 일이다.== 그리고 남겨 두는 편이 유리하다 — 2를 나중에 되살릴 때(실행 취소) 그 자리에 다시 끼워 넣을 수 있다. 백준 5397 키로거류 문제에서 실제로 쓰는 성질이다.

불변식 `prv[nxt[x]] == x`는 살아 있는 노드 전부에서 성립한다. 마지막 줄로 확인하면 살아 있는 것은 0, 3, 4다. `nxt[0] = 4`이고 `prv[4] = 0`, `nxt[4] = 3`이고 `prv[3] = 4`, `nxt[3] = 0`이고 `prv[0] = 3`이다. **이 등식이 깨진 줄이 있으면 그 줄에서 연결이 끊어진 것이고, 대개 삽입 네 줄의 순서를 잘못 쓴 결과다.**

순서 문제가 그 네 줄에 있다. `nxt[p] = x`를 `prv[nxt[p]] = x`보다 **먼저** 쓰면, 뒷줄의 `nxt[p]`가 이미 `x`로 바뀌어 있어 `prv[x] = x`가 된다. 자기 자신을 이전으로 가리키는 노드가 생기고, 그 노드를 뒤에서 지우는 순간 리스트가 끊긴다. **증상은 삽입 시점이 아니라 한참 뒤 삭제에서 나온다.** 링크를 고칠 때는 항상 "아직 필요한 옛 값을 덮어쓰지 않았는가"를 먼저 본다.
:::

## 4. 구현

::: dual
```python title="배열 위의 이중 연결 리스트"
class ArrayList:
    """인덱스로 잇는 이중 연결 리스트. 0 번은 센티넬이고 원소는 1..n 이다."""

    def __init__(self, values):
        n = len(values)
        self.val = [None] + list(values)
        self.nxt = [(i + 1) % (n + 1) for i in range(n + 1)]   # 원형으로 이어 둔다
        self.prv = [(i - 1) % (n + 1) for i in range(n + 1)]   # 경계 분기가 사라진다

    def remove(self, x):
        self.nxt[self.prv[x]] = self.nxt[x]     # 고치는 링크는 정확히 두 개다
        self.prv[self.nxt[x]] = self.prv[x]

    def insert_after(self, p, x):
        self.nxt[x], self.prv[x] = self.nxt[p], p
        self.prv[self.nxt[p]] = x               # nxt[p] 를 덮기 전에 써야 한다
        self.nxt[p] = x

    def move_to_front(self, x):
        self.remove(x)
        self.insert_after(0, x)

    def order(self):
        out, cur = [], self.nxt[0]
        while cur != 0:
            out.append(self.val[cur])
            cur = self.nxt[cur]
        return out


L = ArrayList(["A", "B", "C", "D"])
print("초기            :", " ".join(L.order()))
L.remove(2)
print("remove(2)       :", " ".join(L.order()))
L.move_to_front(4)
print("move_to_front(4):", " ".join(L.order()))
L.remove(1)
print("remove(1)       :", " ".join(L.order()))
print("nxt =", L.nxt)
print("prv =", L.prv)
```
```cpp title="배열 위의 이중 연결 리스트"
#include <iostream>
#include <string>
#include <vector>
using namespace std;

// 인덱스로 잇는 이중 연결 리스트. 0 번은 센티넬이고 원소는 1..n 이다.
struct ArrayList {
    vector<string> val;
    vector<int> nxt, prv;

    ArrayList(const vector<string>& values) {
        int n = (int)values.size();
        val.assign(n + 1, "");
        for (int i = 0; i < n; i++) val[i + 1] = values[i];
        nxt.resize(n + 1);
        prv.resize(n + 1);
        for (int i = 0; i <= n; i++) {
            nxt[i] = (i + 1) % (n + 1);             // 원형으로 이어 둔다
            prv[i] = (i - 1 + n + 1) % (n + 1);     // 경계 분기가 사라진다
        }
    }

    void remove(int x) {
        nxt[prv[x]] = nxt[x];                       // 고치는 링크는 정확히 두 개다
        prv[nxt[x]] = prv[x];
    }

    void insert_after(int p, int x) {
        nxt[x] = nxt[p];
        prv[x] = p;
        prv[nxt[p]] = x;                            // nxt[p] 를 덮기 전에 써야 한다
        nxt[p] = x;
    }

    void move_to_front(int x) {
        remove(x);
        insert_after(0, x);
    }

    string order() const {
        string out;
        for (int cur = nxt[0]; cur != 0; cur = nxt[cur]) {
            if (!out.empty()) out += " ";
            out += val[cur];
        }
        return out;
    }
};

static void dump(const char* name, const vector<int>& a) {
    cout << name << " = [";
    for (size_t i = 0; i < a.size(); i++) cout << a[i] << (i + 1 == a.size() ? "" : ", ");
    cout << "]\n";
}

int main() {
    ArrayList L({"A", "B", "C", "D"});
    cout << "초기            : " << L.order() << "\n";
    L.remove(2);
    cout << "remove(2)       : " << L.order() << "\n";
    L.move_to_front(4);
    cout << "move_to_front(4): " << L.order() << "\n";
    L.remove(1);
    cout << "remove(1)       : " << L.order() << "\n";
    dump("nxt", L.nxt);
    dump("prv", L.prv);
    return 0;
}
```

```console
prv = [3, 4, 1, 4, 0]
```

**복잡도:** `remove`·`insert_after`·`move_to_front`는 시간 $O(1)$ — 고치는 배열 원소가 각각 2개, 4개로 **원소 수와 무관한 상수**다. `order`는 $O(k)$ — 살아 있는 노드 수만큼 링크를 따라간다. 공간 $O(n)$ — 값·`nxt`·`prv` 세 배열. 상수도 말해 둔다. 인덱스가 `int`면 노드 하나의 링크 비용이 8바이트이고, 64비트 포인터 두 개를 쓰는 표준 리스트의 절반이다. **캐시 라인에 두 배가 실린다는 뜻이다.**

| 언어 차이 | Python | C++ |
|---|---|---|
| 표준 연결 리스트 | 없다. `list`는 배열이고 `deque`는 블록의 연결이다 | `std::list`(이중), `std::forward_list`(단일) |
| 통째로 옮기기 | 없다. 슬라이스는 복사다 | `list::splice` — 원소 수와 무관하게 $O(1)$ |
| 노드 메모리 | 객체마다 GC가 관리. 순환 참조도 회수한다 | 직접 관리. `shared_ptr` 순환은 **회수되지 않는다**([XI-11](#/xi-11)) |
| 반복자 무효화 | 해당 없음 | `list`는 **지운 노드만** 무효. `vector`는 재할당 시 전부 무효 |
| 인덱스 기반 구현 | 리스트 세 개 | `vector` 세 개. 이쪽이 값을 연속으로 담아 이점이 더 크다 |

::: pitfall
- **위치를 매번 찾는다.** 연결 리스트로 짰는데 매 연산마다 앞에서부터 훑으면 전체가 $O(n^2)$이다. 자료구조를 바꿔도 복잡도가 안 바뀐 것이다 — **위치를 주는 색인이 따로 있어야 한다.**
- **삽입 네 줄의 순서를 바꾼다.** 아직 필요한 옛 링크를 먼저 덮어쓰면 자기 자신을 가리키는 노드가 생긴다. 증상은 한참 뒤에 나온다.
- **경계를 분기로 처리한다.** `head`·`tail`이 `None`인 경우를 `if`로 다 나누면 경우가 넷으로 늘고 그중 하나를 빠뜨린다. **센티넬 노드 하나면 분기가 사라진다.**
- **단일 연결 리스트에서 노드를 지우려 한다.** `prev`가 없으면 앞 노드를 알 수 없어 $O(n)$이다. 지울 일이 있으면 이중으로 만든다.
- **Python에서 노드 클래스로 짠다.** 노드마다 객체 하나라 메모리가 수십 바이트씩 붙고 순회가 느리다. 인덱스 배열 방식이 거의 항상 낫다.
:::

## 5. 어디에 쓰이는가

**LRU 캐시가 §2.4 ①의 원형이다.** 해시 테이블이 `키 → 노드 위치`를, 이중 연결 리스트가 `사용 순서`를 맡는다. 조회하면 해시가 노드를 $O(1)$에 주고, 리스트가 그 노드를 맨 앞으로 $O(1)$에 옮기고, 자리가 없으면 맨 뒤를 $O(1)$에 버린다. **세 연산이 모두 상수 시간인 것은 두 자료구조를 겹쳤기 때문이다.** 교체 정책의 비교와 구현은 [XV-9 캐시 교체 정책](#/xv-9)에 있다.

**커널과 할당자는 intrusive list로 만들어져 있다.** 빈 메모리 블록을 잇는 free list, 실행 대기 프로세스를 잇는 런 큐, 만료 시각별로 타이머를 잇는 버킷([XI-8 타이머 휠과 지연 큐](#/xi-8))이 전부 같은 모양이다. 링크가 데이터 안에 박혀 있어 삭제에 할당이 필요 없고, 그래서 **메모리를 할당할 수 없는 문맥에서도 동작한다.** 할당자 자신이 자기 자료구조를 위해 할당을 부를 수는 없다는 사정이 이 설계를 강제한다.

**텍스트 에디터의 커서**도 고전적인 자리다. 커서 위치에서의 삽입·삭제가 $O(1)$이고, 커서는 이미 노드를 손에 들고 있다. 다만 실제 에디터는 연결 리스트를 쓰지 않는다 — gap buffer나 rope처럼 **연속 메모리의 이점을 살리면서 국소 편집을 싸게 만드는** 구조가 표준이다. 커서가 한 곳에 머무르는 동안에는 연속 배열이 그냥 더 빠르기 때문이다.

**그리고 정직하게 말할 것이 있다.** 백준 1406 에디터는 "연결 리스트 문제"로 분류되지만, 실제로는 **스택 두 개**로 더 짧고 빠르게 풀린다. 커서 왼쪽을 한 스택에, 오른쪽을 다른 스택에 담으면 커서 이동이 한쪽에서 빼서 다른 쪽에 넣는 연산이 된다([II-4 스택](#/ii-4)). ==연결 리스트를 배우는 값어치는 그것을 쓰는 데 있는 것이 아니라, "위치를 손에 들고 있는가"라는 질문을 갖게 되는 데 있다.== 그 질문은 자료구조를 고를 때마다 다시 나온다.

## 6. 이 유형을 알아보는 법

::: classify
- 신호어: "커서", "커서 왼쪽/오른쪽", "중간에서 지운다", "지운 뒤에도 나머지 순서는 그대로", "원을 돌면서 K번째를 제거", "가장 오래 사용되지 않은"
- 제약조건: 삭제·이동 연산이 $10^5\!\sim\!10^6$회이고, **매 연산의 대상 위치가 직전 위치이거나 별도 색인으로 주어진다.** 위치를 매번 탐색해야 하면 이 유형이 아니다
- 혼동 주의: 양쪽 끝에서만 넣고 빼면 덱([II-5](#/ii-5)). 커서가 하나뿐이면 스택 두 개가 더 짧다([II-4](#/ii-4)). $k$번째 원소 접근이 잦으면 펜윅 트리([IX-3](#/ix-3)). 정렬 상태를 유지해야 하면 균형 트리([II-9](#/ii-9))
- 반례 함정: 연결 리스트로 짰는데 대상 위치를 매번 처음부터 찾아 전체가 $O(n^2)$이 되는 구현. 삭제된 노드를 다시 참조하는 입력(실행 취소). 원소가 하나 남았을 때와 전부 지워졌을 때의 경계
:::

::: interview
**"연결 리스트는 삽입이 $O(1)$인데 왜 실무에서 `vector`를 씁니까."**
답변 뼈대는 두 겹이다. ① **그 $O(1)$은 위치를 이미 알고 있을 때만이다.** 위치를 찾아야 하면 $O(n)$이고, 그러면 복잡도가 같아지면서 상수만 나빠진다. ② **상수가 자릿수로 나쁘다.** 포인터 추적이라 프리페처가 먹히지 않고 캐시 밀도가 낮아, 같은 $O(n)$ 순회가 실측으로 수십에서 수백 배 차이 난다. 마무리는 조건 제시다 — "해시가 노드를 주는 LRU나, 할당이 금지된 커널 문맥의 intrusive list처럼 **위치가 공짜로 주어지는 자리**에서는 여전히 이깁니다."
:::

## 연습

::: quiz
전부 **"대상 위치를 어떻게 공짜로 얻는가"** 가 본체인 문제다.

**1. 백준 1406 에디터 (실버 2)** — https://www.acmicpc.net/problem/1406
- 신호: "커서"와 명령 `L`·`D`·`B`·`P`. 삽입·삭제가 항상 **커서 자리**에서 일어난다. 초기 문자열 60만, 명령 50만.
- 상태: 커서 왼쪽의 글자들과 오른쪽의 글자들. 커서 이동은 한쪽 끝에서 빼서 다른 쪽 끝에 넣는 것이다.
- 자료구조: 스택 두 개가 정답에 가장 가깝다. 연결 리스트로도 되지만 코드가 길어진다. **배열 하나에 `insert`/`erase`로 짜면 명령마다 $O(n)$이라 시간 초과다.**

**2. 백준 5397 키로거 (실버 2)** — https://www.acmicpc.net/problem/5397
- 신호: 1406과 같은 구조인데 `<`, `>`, `-`가 섞인 입력 한 줄을 재생한다. 백스페이스가 커서 왼쪽을 지운다.
- 상태: 1406과 같다. 다른 것은 입력 형식뿐이다.
- 자료구조: 스택 두 개 또는 배열 기반 연결 리스트. **빈 상태에서의 `-`와 `<`** 를 어떻게 처리하는지가 이 문제의 경계 조건이다.

**3. 백준 1158 요세푸스 문제 (실버 4)** — https://www.acmicpc.net/problem/1158
- 신호: "원을 이루며 앉아 K번째 사람을 제거한다". 제거 후 **다음 시작점이 방금 지운 자리 다음**이다. 위치가 직전 연산에서 그대로 주어진다.
- 상태: 현재 위치와 남은 사람 수.
- 자료구조: 원형 연결 리스트가 개념적으로 가장 맞고, 덱을 `K-1`번 회전시키는 방법이 가장 짧다. **리스트를 `pop(i)`로 짜면 매 삭제가 $O(n)$** 이지만 `N ≤ 5,000`이라 그것도 통과한다 — 제약이 작으면 자료구조 선택이 티가 나지 않는다는 사실을 확인할 자리다.

**4. 백준 2346 풍선 터뜨리기 (실버 3)** — https://www.acmicpc.net/problem/2346
- 신호: 원형 배치에서 터뜨린 풍선의 값만큼 좌우로 이동한다. 값이 **음수일 수 있다**는 것이 핵심이다.
- 상태: 현재 위치와 남은 풍선들의 원형 순서.
- 자료구조: 원형 이중 연결 리스트, 또는 덱을 양방향으로 회전. 양방향 이동이 있으므로 **단일 연결로는 안 된다.** 이동 횟수를 남은 개수로 나머지 연산해 줄이지 않으면 최악에서 느려진다.
:::

## 요약

- 연결 리스트는 **순서를 위치가 아니라 주소로 표현한다.** 그래서 순서를 바꾸는 데 값을 옮기지 않는다.
- 그 $O(1)$은 **"노드를 이미 손에 들고 있을 때"** 만 성립한다. 위치를 찾아야 하면 $O(n)$이고, 그때는 복잡도가 배열과 같아지면서 상수만 나빠진다.
- 실측으로 두 얼굴이 다 나온다. 위치를 아는 삭제는 리스트가 200배 빠르고, 값을 찾는 삭제는 4배 느리다. 순회는 [0-6](#/0-6) 기준 최대 206배 느리다.
- 지는 이유는 복잡도가 아니라 **포인터 추적**이다. 프리페처가 먹히지 않고 노드 오버헤드로 캐시 밀도가 낮다.
- 이기는 자리는 넷이다. 다른 색인이 위치를 주는 경우(LRU), 링크가 데이터에 박힌 경우(intrusive), 통째로 옮기는 경우(splice), 원소 주소가 바뀌면 안 되는 경우.
- 실전에서는 **포인터 대신 배열 인덱스**로 잇는다. 할당 한 번, 캐시 밀도 회복, 무효화 없음, $O(1)$ 유지.
- 링크 자료구조에서 "지운다"는 값을 지우는 것이 아니라 **도달 불가능하게 만드는 것**이다. 남은 링크는 실행 취소에 그대로 쓰인다.
