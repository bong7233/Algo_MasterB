# II-2 문자열 처리

::: lead
문자열은 배열이다. 다만 **원소 하나가 무엇인가**가 언어마다 다르고, 그 차이는 한글 한 글자에서 즉시 드러난다.
:::

## 1. 문제

장비가 한 줄에 한 프레임씩 보낸다.

```text nolines
  SEQ|00421|MOVE|x=3,y=7|OK
```

필드를 뽑아 명령으로 해석해야 한다. `split('|')` 한 줄이면 끝나 보이고, 실제로 대부분의 줄에서 끝난다. 문제는 나머지 줄이다.

**필드 안에 구분자가 들어온다.** 경로를 담는 필드에 `C:\log|2024`가 실린다. 그 순간 `split`은 필드를 여섯 개로 쪼개고, 그 뒤 인덱스가 전부 한 칸씩 밀린다. 이것을 막는 표준 수단이 이스케이프 문자이고, 이스케이프가 들어오는 순간 `split`은 쓸 수 없다.

**필드가 고정폭인 프레임도 있다.** `00421`은 "421"이 아니라 "5자리 시퀀스 번호"다. 구분자가 아예 없는 형식이면 자르는 위치를 길이로 정한다.

**한글이 섞이면 길이가 두 가지가 된다.** 로그를 80자로 잘라 저장하는 코드가 있다. `"온도25도"`는 Python에서 5, C++에서 11이다. 어느 쪽이 맞느냐가 아니라 **둘이 다른 것을 세고 있다.** 자르는 위치가 글자 가운데에 떨어지면 저장된 로그는 깨진 바이트로 끝난다.

이 절이 답하는 것은 셋이다. **`s[i]`가 무엇을 돌려주는가, 구분자가 데이터에 섞일 때 어떻게 쪼개는가, 어디서 자르면 안전한가.**

::: note
`str`의 불변성과 `join` 관용구, `+=` 반복의 실제 비용은 [0-3 Python 내장 자료구조의 실제 비용](#/0-3) §5에 있다. C++ `string`의 메모리 배치는 [0-6 C++ 컨테이너 세트](#/0-6)에 있다. 이 절은 그 위층 — **문자열을 자료구조로 어떻게 다룰 것인가**다.
:::

## 2. 아이디어

### 2.1 원소가 무엇인가

문자열에는 층이 셋이다.

**바이트.** 파일과 소켓이 실제로 나르는 것. 인코딩을 정하기 전에는 뜻이 없다.

**코드포인트.** 유니코드가 문자 하나에 붙인 번호. `'온'`은 U+C628이다.

**사람이 세는 글자.** 코드포인트 여럿이 모여 한 글자로 보이는 경우가 있다. 결합 문자와 이모지가 그렇다.

세 층이 일치하는 세계가 ASCII다. 한 글자 = 한 코드포인트 = 한 바이트. **영어만 쓰는 동안 이 셋의 구분은 존재하지 않는다.** 한글이 들어오는 순간 갈라진다.

UTF-8은 코드포인트를 바이트로 옮기는 규칙이고, 규칙은 선두 바이트의 상위 비트가 전부 말해 준다.

```text nolines
  0xxxxxxx                              1 byte    ASCII
  110xxxxx 10xxxxxx                     2 bytes   latin extended
  1110xxxx 10xxxxxx 10xxxxxx            3 bytes   hangul, CJK
  11110xxx 10xxxxxx 10xxxxxx 10xxxxxx   4 bytes   emoji
```

핵심은 두 번째 이후 바이트가 전부 `10xxxxxx`라는 것이다. 이 패턴은 선두 바이트에 절대 나타나지 않는다. **따라서 바이트 하나만 보고 "여기가 글자 시작인가"를 판정할 수 있다.** 이 자기 동기화 성질이 UTF-8 설계의 핵심이고, 뒤에 나올 안전한 자르기가 전부 여기서 나온다.

```text nolines
  ec 98 a8 | eb 8f 84 | 32 | 35 | eb 8f 84       <- 11 bytes
  ^^         ^^         ^^   ^^   ^^
  |          |          |    |    +-- lead byte 0xeb, 3 bytes
  |          |          |    +------- '5' = 0x35, 1 byte
  |          |          +------------ '2' = 0x32, 1 byte
  |          +--------------------------- lead byte 0xeb, 3 bytes
  +------------------------------------- lead byte 0xec, 3 bytes
```

Python `str`은 코드포인트의 배열이라 위 문자열의 `len`이 5다. C++ `std::string`은 **바이트의 배열**이라 `size()`가 11이고 `s[0]`은 글자가 아니라 `0xec`라는 숫자다. ==두 언어의 `s[i]`는 이름만 같고 다른 것을 돌려준다.==

::: warn
C++에서 한글을 다루는 코드가 "일단 도는" 이유는 **대부분의 연산이 바이트 단위로도 옳기 때문**이다. 복사, 비교, 이어붙이기, 완전 일치 검색은 바이트로 해도 결과가 같다. 무너지는 것은 딱 셋이다. **글자 수 세기, 인덱스로 접근하기, 길이로 자르기.** 이 셋만 조심하면 나머지는 그대로 써도 된다.
:::

### 2.2 쪼개는 방법은 셋뿐이다

**① 구분자 분할.** `split(sep)`. 가장 싸고 가장 흔하다. 성립 조건이 하나 있다 — **구분자가 데이터 안에 절대 나타나지 않는다는 보장.** 그 보장은 코드가 아니라 프로토콜 명세가 준다. 명세에 없으면 없는 것이다.

**② 고정폭 필드.** 위치로 자른다. 구분자가 필요 없으니 데이터에 무엇이 들어와도 밀리지 않는다. 금융 전문과 이진 프레임 헤더가 이 방식이다. 대가는 필드 길이가 명세에 못 박혀 낭비가 생기는 것과, **한 필드가 밀리면 그 뒤가 전부 밀린다**는 것이다.

**③ 한 번 훑는 스캐너.** 상태를 들고 문자를 하나씩 본다. 이스케이프·따옴표·중첩이 있으면 이 방법뿐이다. `split` 뒤에 후처리를 붙여 고치려는 시도는 거의 항상 실패한다 — 쪼개는 순간 정보가 이미 사라졌기 때문이다.

판단은 한 줄로 끝난다. **구분자가 데이터에 나타날 수 있는가.** 없으면 ①, 있으면 ③, 구분자 자체가 없으면 ②다.

### 2.3 파서가 느린 이유는 알고리즘이 아니다

셋 다 $O(n)$이다. 그런데 실제 속도는 몇 배씩 갈리고, 갈리는 원인은 **필드마다 문자열을 새로 만드는가**다.

::: perf
필드 20만 개(약 2.3MB)짜리 한 줄을 쪼개 길이의 합을 구한다.

| C++17 `-O2` | 시간 | | Python 3.13 | 시간 |
|---|---|---|---|---|
| `istringstream` + `getline` | 0.0061초 | | `str.split('\|')` | 0.0287초 |
| `find` + `substr` | 0.0023초 | | 파이썬 레벨 문자 루프 | 0.249초 |
| `find` + `string_view` | 0.0014초 | | 정규식 `finditer` | 0.137초 |

> (Linux x86-64 / CPython 3.13 / g++ 13 `-O2` 실측, 3회 실행의 중앙값. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 측정 스크립트는 `tools/bench/ii2_parse.cpp` 와 `.py` 다.)

**교훈이 두 언어에서 정반대다.** C++에서는 표준 스트림이 느려서 직접 훑는 쪽이 4배 빠르다. Python에서는 `split`이 이미 C로 구현되어 있어 직접 훑는 순간 9배 느려진다. =="직접 짜면 빠르다"는 언어에 종속된 명제다.==
:::

📖 `std::string_view` — 문자열을 **복사하지 않고 가리키기만 하는** (포인터, 길이) 쌍. C++17.
　 `substr`이 새 `string`을 만들어 복사하는 데 비해 `string_view::substr`은 포인터와 길이만 조정한다. 그래서 위 표에서 4배가 나온다.
　 **원본이 살아 있는 동안만 유효하다.** 원본이 죽으면 매달린 참조가 되고, 이것은 정의되지 않은 동작이다.
　 쓰는 곳: 대용량 로그·프레임 파싱, 함수 인자로 문자열 받기.
　 Python 대응: 없다. 슬라이스 `s[a:b]`는 항상 새 `str`을 만든다. 복사를 피하려면 인덱스 쌍 `(a, b)`을 직접 들고 다닌다.

## 3. 손으로 따라가기

::: trace
이스케이프를 아는 스캐너다. 구분자는 `|`, 이스케이프 문자는 `\`이고 규칙은 둘이다.

- 이스케이프 상태에서 만난 글자는 **뜻을 잃고 데이터가 된다.**
- 이스케이프 문자 자신은 버퍼에 들어가지 않는다.

입력(원시 10글자): `a \ | b | c \ \ | d`

| i | ch | 직전 상태 | buf | 완성된 필드 | 다음 상태 |
|---|---|---|---|---|---|
| 0 | `a` | NORMAL | `a` | — | NORMAL |
| 1 | `\` | NORMAL | `a` | — | ESC |
| 2 | `\|` | ESC | `a\|` | — | NORMAL |
| 3 | `b` | NORMAL | | | |
| 4 | `\|` | NORMAL | | | |
| 5 | `c` | | | | |
| 6 | `\` | | | | |
| 7 | `\` | | | | |
| 8 | `\|` | | | | |
| 9 | `d` | | | | |

세 가지를 확인하라.

- [ ] `i = 2`에서 `|`가 필드를 끊지 **않은** 이유. 상태 열이 그것을 설명하는가
- [ ] 루프가 끝난 뒤에 남는 `buf`는 어떻게 처리해야 하는가. 필드는 몇 개인가
- [ ] 입력이 `\`로 끝나면(즉 마지막 상태가 ESC면) 그것은 무엇을 뜻하는가
:::

::: answer
| i | ch | 직전 상태 | buf | 완성된 필드 | 다음 상태 |
|---|---|---|---|---|---|
| 0 | `a` | NORMAL | `a` | — | NORMAL |
| 1 | `\` | NORMAL | `a` | — | ESC |
| 2 | `\|` | ESC | `a\|` | — | NORMAL |
| 3 | `b` | NORMAL | `a\|b` | — | NORMAL |
| 4 | `\|` | NORMAL | (비움) | `a\|b` | NORMAL |
| 5 | `c` | NORMAL | `c` | — | NORMAL |
| 6 | `\` | NORMAL | `c` | — | ESC |
| 7 | `\` | ESC | `c\` | — | NORMAL |
| 8 | `\|` | NORMAL | (비움) | `c\` | NORMAL |
| 9 | `d` | NORMAL | `d` | — | NORMAL |

필드는 `a|b`, `c\`, `d` **세 개**다. 그런데 표에는 두 개만 찍혀 있다 — `d`는 구분자를 만나서가 아니라 **입력이 끝나서** 완성되기 때문이다. ==루프가 끝난 뒤 버퍼를 한 번 더 비우는 줄을 빠뜨리는 것이 이 유형에서 가장 흔한 버그다.== 마지막 필드 하나가 조용히 사라진다.

`i = 2`의 `|`가 필드를 끊지 않은 것은 직전 상태가 ESC이기 때문이다. 상태 열을 지우면 이 줄과 `i = 4`의 줄이 구별되지 않는다. **같은 입력 글자가 상태에 따라 다른 뜻을 갖는 것**이 스캐너가 `split`보다 강한 이유이고, 동시에 손추적에서 상태를 반드시 열로 둬야 하는 이유다.

마지막 상태가 ESC라면 **프레임이 중간에 잘렸다**는 뜻이다. 이스케이프는 다음 글자를 요구하는데 그 글자가 오지 않았다. 실전에서 이것은 오류가 아니라 정상 상황이다 — TCP는 메시지 경계를 보장하지 않아 한 프레임이 두 번에 나뉘어 도착한다. 스캐너는 상태를 **다음 조각까지 들고 가야** 한다. 그래서 §4의 구현은 이 상태를 반환값으로 내보낸다.
:::

## 4. 구현

::: dual
```python title="이스케이프를 아는 스캐너 — 한 번 훑기"
def split_escaped(s, sep="|", esc="\\"):
    fields, buf, escaped = [], [], False
    for ch in s:                       # 문자를 정확히 한 번씩만 본다
        if escaped:
            buf.append(ch)             # 이스케이프 다음 글자는 무조건 데이터다
            escaped = False
        elif ch == esc:
            escaped = True             # 이스케이프 문자 자신은 버퍼에 넣지 않는다
        elif ch == sep:
            fields.append("".join(buf))
            buf = []
        else:
            buf.append(ch)
    fields.append("".join(buf))        # 마지막 필드는 루프가 끝난 뒤에 나온다
    return fields, escaped


raw = "a\\|b|c\\\\|d"
print("입력:", raw)
fields, dangling = split_escaped(raw)
for i, f in enumerate(fields):
    print(f"  field[{i}] = [{f}]")
print("끝이 이스케이프 상태인가:", dangling)

fields, dangling = split_escaped("a|b\\")
print("잘린 프레임:", fields, "dangling =", dangling)
```
```cpp title="이스케이프를 아는 스캐너 — 한 번 훑기"
#include <iostream>
#include <string>
#include <vector>
using namespace std;

pair<vector<string>, bool> split_escaped(const string& s, char sep = '|', char esc = '\\') {
    vector<string> fields;
    string buf;
    bool escaped = false;
    for (char ch : s) {                // 문자를 정확히 한 번씩만 본다
        if (escaped) {
            buf += ch;                 // 이스케이프 다음 글자는 무조건 데이터다
            escaped = false;
        } else if (ch == esc) {
            escaped = true;            // 이스케이프 문자 자신은 버퍼에 넣지 않는다
        } else if (ch == sep) {
            fields.push_back(buf);
            buf.clear();
        } else {
            buf += ch;
        }
    }
    fields.push_back(buf);             // 마지막 필드는 루프가 끝난 뒤에 나온다
    return {fields, escaped};
}

int main() {
    string raw = "a\\|b|c\\\\|d";
    cout << "입력: " << raw << "\n";
    auto [fields, dangling] = split_escaped(raw);
    for (size_t i = 0; i < fields.size(); i++)
        cout << "  field[" << i << "] = [" << fields[i] << "]\n";
    cout << "끝이 이스케이프 상태인가: " << (dangling ? "True" : "False") << "\n";

    auto [f2, d2] = split_escaped("a|b\\");
    cout << "잘린 프레임: ['" << f2[0] << "', '" << f2[1] << "'] dangling = "
         << (d2 ? "True" : "False") << "\n";
    return 0;
}
```
:::

두 언어의 출력은 같다.

```console
입력: a\|b|c\\|d
  field[0] = [a|b]
  field[1] = [c\]
  field[2] = [d]
끝이 이스케이프 상태인가: False
잘린 프레임: ['a', 'b'] dangling = True
```

**복잡도:** 시간 $O(n)$ — 문자마다 분기 하나를 타고 되돌아가지 않는다. 공간 $O(n)$ — 필드들의 총 길이가 입력 길이를 넘지 않는다. 상수도 말해 둔다. 버퍼에 한 글자씩 붙이는 것은 동적 배열의 `push`라 **분할상환 $O(1)$**이고([II-1](#/ii-1)), Python에서 `buf`를 `str`로 두고 `+=`하면 매번 새 문자열을 만들어 $O(n^2)$이 된다. 리스트에 모아 `join`하는 이유가 그것이다.

| 언어 차이 | Python | C++ |
|---|---|---|
| 소스에서 `\` 쓰기 | `"\\"`가 백슬래시 한 개. 원시 문자열 `r"\\"`는 두 개다 | 같다. `'\\'`가 문자 하나 |
| 버퍼 누적 | `list.append` + `join`. `str +=`는 $O(n^2)$ 위험 | `string +=`는 분할상환 $O(1)$. 그대로 써도 된다 |
| 여러 값 반환 | 튜플을 그대로 돌려준다 | `pair`/`tuple` + C++17 구조적 바인딩 `auto [a, b]` |
| 표준 분할 함수 | `str.split(sep)` 있음 | 없다. `getline(stream, tok, sep)` 또는 직접 짠다 |

이제 인코딩이다. 같은 문자열, 같은 규칙, 두 언어.

```python title="원소가 무엇인가 — 코드포인트와 바이트"
s = "온도25도"
data = s.encode("utf-8")                  # 바이트로 내리면 두 언어가 같은 것을 본다

print("원소 개수 =", len(s))              # Python 의 원소는 코드포인트다
print("첫 원소   =", s[0])
print("바이트 수 =", len(data))


def count_codepoints(data):
    # 연속 바이트(10xxxxxx)가 아닌 것만 세면 글자 수다
    return sum(1 for b in data if (b & 0xC0) != 0x80)


def safe_cut(data, limit):
    # limit 이하에서 글자가 끊기지 않는 가장 큰 경계
    if limit >= len(data):
        return len(data)
    k = limit
    while k > 0 and (data[k] & 0xC0) == 0x80:
        k -= 1
    return k


print("코드포인트 수 =", count_codepoints(data))
print("앞 3바이트 =", " ".join(f"{b:02x}" for b in data[:3]))
for limit in (3, 4, 7, 11):
    print(f"limit={limit:2d} -> 안전 경계 {safe_cut(data, limit)}바이트")
```
```cpp title="원소가 무엇인가 — 코드포인트와 바이트"
#include <cstdio>
#include <string>
using namespace std;

int count_codepoints(const string& data) {
    // 연속 바이트(10xxxxxx)가 아닌 것만 세면 글자 수다
    int n = 0;
    for (unsigned char b : data)
        if ((b & 0xC0) != 0x80) n++;
    return n;
}

int safe_cut(const string& data, int limit) {
    // limit 이하에서 글자가 끊기지 않는 가장 큰 경계
    if (limit >= (int)data.size()) return (int)data.size();
    int k = limit;
    while (k > 0 && ((unsigned char)data[k] & 0xC0) == 0x80) k--;
    return k;
}

int main() {
    string s = "온도25도";
    const string& data = s;                 // C++ 의 string 은 이미 바이트 배열이다

    printf("원소 개수 = %zu\n", s.size());   // C++ 의 원소는 바이트다
    printf("첫 원소   = 0x%02x\n", (unsigned char)s[0]);
    printf("바이트 수 = %zu\n", data.size());

    printf("코드포인트 수 = %d\n", count_codepoints(data));
    printf("앞 3바이트 =");
    for (int i = 0; i < 3; i++) printf(" %02x", (unsigned char)data[i]);
    printf("\n");
    int limits[] = {3, 4, 7, 11};
    for (int limit : limits)
        printf("limit=%2d -> 안전 경계 %d바이트\n", limit, safe_cut(data, limit));
    return 0;
}
```
:::

**복잡도:** `count_codepoints`와 `safe_cut` 모두 시간 $O(n)$과 $O(1)$이다 — 앞은 바이트를 한 번씩 보고, 뒤는 최대 3바이트만 뒤로 물러난다(UTF-8의 최대 길이가 4바이트이므로 연속 바이트는 연달아 3개를 넘지 못한다). **Python에서 `len(s)`가 $O(1)$인 것과 `count_codepoints`가 $O(n)$인 것의 차이가 곧 두 언어의 차이다** — Python은 만들 때 이미 세어 두었고, C++은 물어볼 때마다 세야 한다.

출력의 앞 두 줄만 다르고 나머지는 한 글자도 다르지 않다.

```console
Python: 원소 개수 = 5      C++: 원소 개수 = 11
        첫 원소   = 온           첫 원소   = 0xec
        바이트 수 = 11           바이트 수 = 11
        코드포인트 수 = 5        코드포인트 수 = 5
        앞 3바이트 = ec 98 a8    앞 3바이트 = ec 98 a8
        limit= 4 -> 3바이트      limit= 4 -> 3바이트
```

| 언어 차이 | Python `str` | C++ `std::string` |
|---|---|---|
| 원소 | 코드포인트 | **바이트** |
| `len` / `size()` | 글자 수. $O(1)$ | 바이트 수. $O(1)$이지만 **글자 수가 아니다** |
| `s[0]` | 글자 하나 | 바이트 하나(`char`). 한글이면 조각이다 |
| 뒤집기 | `s[::-1]`이 글자 단위로 옳다 | `reverse`는 **바이트를 뒤집어 문자열을 깨뜨린다** |
| 글자 수 세기 | `len(s)` | 선두 바이트를 직접 센다. $O(n)$ |
| 소스 파일 인코딩 | UTF-8이 기본 | 리터럴이 그대로 바이트로 들어간다. `u8"..."`로 명시 가능 |

::: danger
**바이트 길이로 자르면 언젠가 깨진다.** 세 자리가 실제 장애를 만든다.

- **로그 자르기.** "한 줄 최대 200바이트"로 자른 로그의 마지막 글자가 반토막 난다. 그 로그를 UTF-8로 읽는 뷰어는 줄 전체를 물음표로 렌더링하거나 예외를 던진다.
- **DB 칼럼 길이.** `VARCHAR(20)`이 20글자인지 20바이트인지는 DBMS와 문자셋 설정이 정한다. 바이트라면 한글은 6글자에서 넘친다. 저장 시점에 잘리는 것이 아니라 **에러로 거절되는** 쪽이 그나마 낫다.
- **화면 폭.** 고정폭 글꼴에서 한글은 두 칸을 차지한다. 글자 수로 맞춘 표는 한글이 섞이는 순간 어긋난다. **폭은 글자 수도 바이트 수도 아닌 세 번째 척도다.** 이 책의 아스키 다이어그램을 검사하는 `tools/check_diagrams.py`가 재는 것이 그 세 번째 척도다.

방어는 하나다. **자르기 전에 경계를 확인한다.** `safe_cut`이 그 열 줄이다.
:::

::: pitfall
- **마지막 필드를 빠뜨린다.** 루프가 끝난 뒤 버퍼를 비우는 줄이 없으면 필드 하나가 조용히 사라진다.
- **빈 필드를 없는 것으로 취급한다.** `a||b`는 필드 셋이고 가운데는 빈 문자열이다. 값이 없는 것과 필드가 없는 것은 다르다.
- **줄 끝 문자를 안 지운다.** `\r\n`으로 오는 프레임에서 마지막 필드에 `\r`이 붙어 비교가 전부 실패한다. Python `readline`은 `\n`을 남기고 `strip()`은 양쪽 공백을 다 지운다.
- **`s[i]`로 한글을 다룬다.** C++에서 조각이 나오고, 조각을 비교하면 조용히 틀린다.
- **`+=`로 문자열을 누적한다.** Python에서 $O(n^2)$이다. 리스트에 모아 `join`한다([0-3](#/0-3) §5).
- **대소문자와 전각 문자.** `'A'`와 `'a'`, `'１'`과 `'1'`은 다른 코드포인트다. 비교 전에 정규화 규칙을 정한다.
:::

## 5. 어디에 쓰이는가

**프로토콜 메시지 파싱이 이 절 그대로다.** GPS 수신기가 뱉는 NMEA 문장은 `$`로 시작해 쉼표로 필드를 나누고 `*`뒤에 체크섬이 붙는 구분자 형식이다. HTTP 헤더는 `이름: 값`을 줄 단위로 자르는 형식이고, CSV는 따옴표와 이스케이프가 있어 **①이 아니라 ③으로만 옳게 읽힌다.** 흔한 사고는 CSV를 `split(',')`으로 읽다가 값 안의 쉼표에서 무너지는 것이고, 이 사고는 데이터가 늘어난 뒤에야 나타난다.

**고정폭 형식은 아직 살아 있다.** 금융 전문, 산업 장비 프레임, 로그 포맷의 앞부분이 그렇다. 구분자 탐색이 없어 파싱이 슬라이스 몇 번으로 끝나고, 길이가 명세로 고정이라 **길이 검증이 곧 형식 검증**이 된다. 대신 필드 하나가 밀리면 그 뒤가 전부 밀린다.

**스트림 파서는 상태를 들고 있어야 한다.** TCP는 바이트 스트림이라 메시지 경계를 보장하지 않는다. 한 프레임이 두 번에 나뉘어 오고, 두 프레임이 한 번에 붙어 온다. §3의 `escaped` 반환값이 그래서 필요하다 — 다음 조각을 이어 붙일 때 상태를 복원해야 한다. 이 구조가 커지면 상태 기계가 되고([XI-6 상태 기계](#/xi-6)), 들어오는 속도가 처리 속도를 넘으면 백프레셔 문제가 된다([XI-7](#/xi-7)).

**같은 문자열을 반복해 검색한다면 이 절의 도구로는 부족하다.** 긴 텍스트에서 패턴을 찾는 것은 KMP·라빈-카프의 영역이고([IX-7 문자열 매칭](#/ix-7)), 접두사가 공유되는 문자열 집합은 트라이다([IX-6](#/ix-6)). 이 절은 **한 줄을 조각내는 일**까지다.

## 6. 이 유형을 알아보는 법

::: classify
- 신호어: "문자열이 주어졌을 때", "단어", "몇 개의 ~로 이루어져 있는지", "각 문자가 몇 번", "공백으로 구분된", "가장 많이 사용된 알파벳"
- 제약조건: 문자열 길이 ≤ $10^6$이고 한 번 훑어 끝나는 작업. 문자 종류가 알파벳 26개·아스키 128개처럼 작아 배열 하나로 세어진다. 입력이 ASCII로 한정된다는 문장이 있는가
- 혼동 주의: 같은 패턴을 여러 번 찾으면 KMP([IX-7](#/ix-7)). 접두사를 공유하는 문자열 집합이면 트라이([IX-6](#/ix-6)). 문자 개수만 세면 그냥 배열([II-1](#/ii-1)). 괄호·중첩이 있으면 스택([II-4](#/ii-4)). 단어를 정렬·비교하면 정렬([II-7](#/ii-7))
- 반례 함정: 빈 문자열과 길이 1. 겹치는 패턴(`"aaa"`에서 `"aa"`를 세면 2개인가 1개인가 — 지문이 정한다). 대소문자 혼용. 마지막 구분자 뒤의 빈 필드. 그리고 **입력에 ASCII 아닌 문자가 섞일 수 있는가**
:::

**2. 백준 1316 그룹 단어 체커 (실버 5)** — https://www.acmicpc.net/problem/1316

**3. 백준 2941 크로아티아 알파벳 (실버 5)** — https://www.acmicpc.net/problem/2941
- 신호: `c=`, `dz=`, `lj` 같은 **여러 글자가 알파벳 하나**다. 인코딩 절의 문제를 라틴 문자로 옮겨 놓은 형태다.
- 상태: 현재 위치 `i` 하나. 남은 길이가 충분하면 긴 것부터 맞춰 보고, 맞으면 그 길이만큼 건너뛴다.
- 자료구조: 문자열 목록. **긴 패턴을 먼저 검사해야 한다** — `dz=`를 `z=`보다 나중에 보면 앞의 `d`가 따로 세어진다. 이것이 최장 일치 원칙이고, 실제 인코더·토크나이저가 같은 규칙을 쓴다.

**4. 백준 2870 수학숙제 (실버 4)** — https://www.acmicpc.net/problem/2870
- 신호: 글자와 숫자가 섞인 줄에서 **숫자만 뽑아** 정렬한다. 앞의 0을 떼야 하고, 수가 100자리까지 간다.
- 상태: 현재 토큰의 시작 위치와 길이. 숫자가 아닌 글자를 만나면 토큰이 끝난다.
- 자료구조: 문자열 리스트. 값이 `long long`을 넘으므로 **문자열 상태로 비교**해야 한다 — 길이를 먼저 보고 같으면 사전순이다. Python은 정수로 바꿔도 임의 정밀도라 통과하고, C++은 그 순간 무너진다([0-5](#/0-5)).

## 요약

- 문자열은 배열이고, 원소가 무엇인지가 언어를 가른다. **Python `str`은 코드포인트 배열, C++ `std::string`은 바이트 배열이다.**
- UTF-8은 선두 바이트의 상위 비트가 길이를 말하고 연속 바이트는 전부 `10xxxxxx`다. 이 자기 동기화 성질이 **바이트 하나만 보고 글자 경계를 판정**할 수 있게 한다.
- 쪼개는 방법은 셋뿐이다. 구분자 분할, 고정폭 슬라이스, 한 번 훑는 스캐너. **구분자가 데이터에 나타날 수 있으면 스캐너 말고 답이 없다.**
- 스캐너는 상태를 들고 간다. 같은 글자가 상태에 따라 다른 뜻을 가지는 것이 `split`보다 강한 이유이고, 스트림 파싱에서 **상태를 다음 조각까지 넘겨야** 하는 이유다.
- 파서의 속도는 알고리즘이 아니라 **복사 횟수**가 정한다. C++에서는 `string_view`가 4배, Python에서는 표준 `split`이 직접 훑기보다 9배 빠르다. 방향이 반대다.
- 바이트 길이로 자르면 글자가 깨진다. 로그 잘림, `VARCHAR` 길이, 화면 폭이 전부 같은 사고다. **자르기 전에 경계를 확인한다.**
- 이 절은 한 줄을 조각내는 데까지다. 패턴을 반복해 찾는 것은 [IX-7 문자열 매칭](#/ix-7), 접두사 집합은 [IX-6 트라이](#/ix-6)다.
