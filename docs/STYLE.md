## 1. 독자와 목표

- 독자는 **일반 프로그래밍 경험이 있는 사람**이다. `for`, `if`, 배열, 함수 정의는 안다. Python과 C++ 중 최소 하나는 읽을 줄 안다.
- 목표는 *"코딩테스트를 통과하면서, 그 알고리즘이 실제 시스템 어디에 박혀 있는지도 설명할 수 있는 개발자"* 다.
- 도달 기준은 **시니어 개발자가 설명할 수 있어야 하는 수준**이다.
- 그러므로 **"~하는 법"이 아니라 "왜 그런가"** 를 쓴다. 사용법은 검색하면 나온다.
  검색으로 안 나오는 것을 써라: 내부 동작, 설계 이유, 함정, 실제 비용.

### 밀도의 기준

한 절은 **읽는 데 15~30분**, 본문 6,000~12,000자(코드 제외) 정도다.
짧으면 얕고, 길면 안 읽는다. 다만 **분량을 채우려고 늘리지 마라.** 할 말이 없으면 짧게 끝낸다.

## 2. 말투

- **평서형 반말체.** "~한다", "~이다". `~습니다`, `~해요` 금지.
- 독자를 부를 때는 "당신". 명령형은 "~하라", "~해라" 를 쓴다.
- **단정적으로 쓴다.** "~인 것 같다", "~일 수도 있다" 같은 헤지를 피한다.
  단, 모르면 모른다고 쓴다. 아는 척이 최악이다.
- 문장은 짧게. 한 문장에 한 가지만.
- **비유는 정확할 때만.** 틀린 비유는 잘못된 모델을 심는다.

### 좋은 예

> BFS가 최단 거리를 보장하는 이유는 큐가 거리 순으로 정렬되기 때문이다. 가중치가 생기는 순간 이 성질이 깨진다.

> `visited`를 큐에서 뺄 때 찍으면 같은 정점이 큐에 여러 번 들어간다. 넣을 때 찍어라.

### 나쁜 예

> BFS는 최단 거리를 구할 때 유용하게 사용될 수 있는 알고리즘입니다.

> visited 처리는 상황에 따라 다를 수 있으니 주의가 필요합니다.

## 3. 절의 구조 — 3단 서술 (강제)

모든 알고리즘 챕터는 **문제 → 아이디어 → 구현** 순서다. 예외 없다.

```
① 문제   — 이 알고리즘이 없으면 무엇이 안 되는가. 구체적 상황부터
② 아이디어 — 위젯 + 산문. 코드 없이 원리만. 여기서 이해가 끝나야 한다
③ 구현   — ::: trace → ::: dual → 복잡도 → ::: pitfall → ::: classify
```

**②와 ③ 사이에 `::: trace`가 없으면 그 챕터는 미완성이다.**

코드를 먼저 보여주고 설명하는 순서는 **금지**한다. 그 순서는 "읽으면 이해되는데 못 짜는" 상태를 재생산한다.

### 도입부 원칙

**정의부터 시작하지 마라.** 문제부터 보여라.

- 나쁨: "유니온 파인드는 서로소 집합을 관리하는 자료구조다."
- 좋음: 간선을 하나씩 추가하면서 "이 둘이 이미 연결되어 있나?"를 매번 물어야 하는 상황을 먼저 보인다. 그걸 DFS로 매번 풀면 왜 터지는지 보인 다음, 유니온 파인드로 간다.

### 파일 골격

`CLAUDE.md` §4-10의 템플릿을 그대로 쓴다.

- `# 제목` 은 `content/toc.json` 의 `num` + `title` 과 **정확히** 일치해야 한다.
- `::: lead` 로 시작한다 — 이 챕터가 답하는 질문 한 문장.
- `## 요약` 으로 닫는다 — 5~7개 불릿, 읽고 남아야 할 것만.
- 마지막 줄에 **다음 절** 링크.

## 4. 마크다운 확장 문법

### 코드 블록

````markdown
```python title="파일명.py"
실행 가능한 완결된 코드
```

```cpp title="설명" {3,5-7}
3번, 5~7번 줄이 강조된다
```

```text nolines
아스키 다이어그램 (줄 번호 없음)
```
````

지원 언어: `python` `cpp` `text` `bash` `json` `console`

### 이중 언어 블록 `::: dual` — 이 책의 핵심 장치

````markdown
::: dual
```python title="BFS — 최단 거리"
...
```
```cpp title="BFS — 최단 거리"
...
```
:::
````

**강제 규칙 (어기면 챕터 미완성):**

1. **Python이 먼저, C++이 뒤.** 순서 고정.
2. **동일한 알고리즘·동일한 변수명·동일한 줄 구조.** 한쪽에만 있는 최적화를 넣지 않는다.
3. **두 `title=` 이 같아야 한다.**
4. 갈라지는 지점은 **코드 바로 아래 "언어 차이" 표**로 명시한다. 갈라질 게 없으면 표를 생략해도 된다.
5. **C++은 C++17(`g++ -std=c++17 -O2`)에서 실제로 컴파일되어야 한다.** 조각이면 조각임을 밝힌다.
6. **Python은 CPython 3.13에서 실제로 실행되어야 한다.**

두 언어를 동시에 배울 때 가장 위험한 것은 "비슷해 보이는데 다른 것"이다. 그 지점을 침묵으로 넘기지 마라.

### 표시 상자

| 문법 | 쓰는 때 |
| --- | --- |
| `::: lead` | 절 머리말. 이 챕터가 답하는 질문 한 문장 |
| `::: note` | 알아두면 좋은 보충. 몰라도 진도는 나간다 |
| `::: tip` | 실무 요령 |
| `::: warn` | 틀리기 쉬운 지점 |
| `::: danger` | **버그를 만드는** 지점. 실제 장애로 이어지는 것만 |
| `::: deep` | 한 단계 아래 이야기. 내부 구현, 표준 문서, 설계 결정 |
| `::: perf` | 실행 속도·메모리. **반드시 실측치와 함께**(§6) |
| `::: hist` | 왜 이렇게 설계됐는가 |
| `::: trace` | **손추적 훈련.** §5 |
| `::: pitfall` | 실제로 틀리는 지점 모음 |
| `::: classify` | **유형 판별 상자.** §5 |
| `::: interview` | 기술 면접에서 이렇게 질문된다 + 답변 뼈대 |
| `::: quiz` | 연습문제 (대표문제 3~5개) |
| `::: answer` | 해설 (접혀서 나온다) |
| `::: widget {type} {json}` | 위젯 삽입 |

**한 절에 상자가 8~16개** 정도가 적당하다. 너무 많으면 본문이 사라진다.

`::: interview` 는 **실제로 질문되는 지점에만** 넣는다. 남발 금지.

## 5. 필수 상자의 형식

### 5.1 `::: trace` — 손추적

**필수 챕터**(생략 불가): BFS/DFS, 백트래킹, 다익스트라, 이분 탐색(경계 조건), **모든 DP 챕터**, 유니온 파인드(경로 압축), 세그먼트 트리(구간 분해), KMP(실패 함수), 투 포인터, B-Tree(분할), LSM(컴팩션), 일관성 해싱(노드 추가 시 재배치).

**형식:** 입력을 주고, 상태 표의 **앞 2~3행만 채워** 보인다. 나머지는 빈칸. 독자가 채운다. 전체 표는 바로 뒤 `::: answer` 에 넣는다.

```markdown
::: trace
입력: `n=5`, 간선 `(1,2) (1,3) (2,4) (3,4) (4,5)`, 시작 `1`

| 스텝 | 큐 | 방문 | dist |
|---|---|---|---|
| 0 | [1] | {1} | 1:0 |
| 1 | [2,3] | {1,2,3} | 1:0 2:1 3:1 |
| 2 | | | |
| 3 | | | |
:::

::: answer
(전체 표)
:::
```

**관찰 대상을 고르는 것이 핵심이다.** 모든 변수를 다 적으면 표가 죽는다. 그 알고리즘의 **불변식을 드러내는 것**만 열로 둔다.

### 5.2 `::: classify` — 유형 판별

**Part II~X의 모든 알고리즘 챕터에 필수.** 4항목 전부 있어야 한다.

```markdown
::: classify
- 신호어: "최소 이동 횟수", "몇 번 만에", "가장 가까운"
- 제약조건: 간선 가중치가 전부 1 또는 없음, 정점 ≤ 10^5
- 혼동 주의: 가중치가 다르면 → 다익스트라(V-1). 음수면 → 벨만-포드(V-2)
- 반례 함정: 시작점이 여러 개면 다중 시작 BFS(IV-4)
:::
```

| 항목 | 무엇을 쓰나 |
|---|---|
| **신호어** | 지문에 나오는 실제 표현. 추상적 설명이 아니라 문장 조각 |
| **제약조건** | N 범위, 가중치 유무, 메모리 한도 — 이 유형이 성립하는 수치 조건 |
| **혼동 주의** | 헷갈리는 이웃 알고리즘 + **무엇이 다르면 그쪽인지** + 챕터 링크 |
| **반례 함정** | 이 유형이 맞는데 순진하게 짜면 틀리는 변형 |

이 블록은 `build.py`가 수집해 Anki 덱과 Part I 부록을 만든다. **양식을 어기면 자동 수집이 깨진다.**

### 5.3 `::: quiz` — 대표문제

- **번호 + 제목 + 난도**만 표기. 백준은 `https://www.acmicpc.net/problem/{번호}` 규칙 URL만 허용. 다른 플랫폼은 **제목만**.
- **정답 코드 전문 금지.** 3단 사고과정만 쓴다:
  1. 어떤 신호로 이 유형임을 알아채는가
  2. 상태를 무엇으로 정의하는가
  3. 왜 이 자료구조인가
- 챕터당 3~5개. **유형의 원형(canonical)에 가까운 것.** 변형·꼼수 문제는 배제.

## 6. 절대 규칙

### 6.1 수치는 반드시 실행해서 확인한다

**추정한 수치를 쓰지 마라.** 측정 환경은 `CLAUDE.md` §1-3에 고정되어 있다.

| 항목 | 값 |
|---|---|
| OS | Ubuntu 24.04 LTS (x86-64) |
| Python | CPython 3.13.12 |
| C++ | g++ 13.3.0, `-std=c++17 -O2` |

수치를 적을 때 이 문장을 함께 둔다:

> (Linux x86-64 / CPython 3.13 / g++ 13 `-O2` 실측. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다.)

**측정 스크립트를 `tools/bench/` 에 남긴다.** 재현 불가능한 수치는 본문에 넣지 않는다.

### 6.2 복잡도에는 근거가 붙는다

`O(E log V)` 만 쓰고 끝내지 않는다.

- 나쁨: **복잡도:** 시간 $O(E \log V)$
- 좋음: **복잡도:** 시간 $O(E \log V)$ — 각 간선마다 힙에 최대 한 번 push되므로 힙 연산이 $O(E)$회, 각 연산이 $O(\log V)$.

**상수도 말한다.** $O(1)$ 이라고만 하지 말고 그 상수가 언제 문제가 되는지 쓴다.

### 6.3 아스키 다이어그램 안에는 ASCII만

한글은 고정폭 글꼴에서 **두 칸**을 차지한다. 선(`│ ─ ┌ └`)보다 **왼쪽에** 한글이 있으면 그림이 깨진다. 선보다 오른쪽의 꼬리 주석은 괜찮다.

```text nolines
   OK   ├── node        <- 설명은 한글이어도 된다
   OK   a ──▶ ┌──────────┐
   BAD  │ 정점 객체  │      <- 상자 안의 한글
```

`python tools/check_diagrams.py` 가 검사한다.

**그리고 — 시간에 따라 변하는 것은 다이어그램으로 그리지 마라.** 위젯으로 만든다(§7).

### 6.4 코드

- **모든 코드는 실행 가능해야 한다.** 조각이면 조각임을 밝힌다 — 앞 블록의 정의를 이어받아
  단독으로는 컴파일·실행되지 않는 코드는 **제목에 `(조각)` 을 붙이고** 본문에서도 무엇을
  이어받는지 한 줄로 말한다. 예: ```` ```cpp title="축소 (조각) — …" ````
  `tools/check_code.py` 가 이 표기를 보고 단독 실행 검사에서 제외한다. 표기가 없으면
  검사에서 실패로 잡히고, 그것이 옳다 — 독자는 실리는 코드가 도는 코드라고 믿는다.
- 주석은 **왜**를 쓴다. 무엇을 하는지는 코드가 이미 말한다.
- 나쁜 예/좋은 예는 `# ❌` / `# ✅` 로 표시한다.
- 변수명·주석은 한국어로 써도 된다. 단 **식별자는 영어**.
- Python 타입 힌트는 **필요할 때만.** 예제를 흐리면 뺀다.
- C++은 `using namespace std;` 를 허용한다 — 코테 코드의 실제 모습이고, 예제를 짧게 유지한다. 단 헤더는 개별 `#include` 로 명시한다(`bits/stdc++.h` 금지 — 표준이 아니고 무엇이 필요한지 가린다).

### 6.5 다른 절과 연결한다

이 책의 강점은 **연결**이다. 반드시 앞뒤 절을 링크로 건다.

> 이건 [V-5 A*](#/v-5)에서 다시 만난다.
> 힙의 내부는 [II-8 힙과 우선순위 큐](#/ii-8)에.

**단, 없는 id를 링크하지 마라.** `content/toc.json` 에 있는 id만 쓴다. `tools/check_links.py` 가 검사한다.

### 6.6 실무 연결은 필수, 억지는 금지

모든 알고리즘 챕터는 최소 한 번 **"이게 실제 시스템 어디에 박혀 있는가"** 를 짚는다.

**좋은 예:** 유니온 파인드 → 이미지 연결요소 라벨링 / 트라이 → IP 라우팅 테이블 / 위상 정렬 → 빌드 시스템 / 우선순위 큐 → 이벤트 시뮬레이션 / 스킵 리스트 → Redis Sorted Set / 머클 트리 → Git 오브젝트 그래프.

**나쁜 예:** "세그먼트 트리는 센서 데이터 구간 조회에 쓸 수도 있다" ← **쓰지 않는다.** 없으면 생략하고 마일스톤 보고에 "이 챕터는 실무 연결이 약하다"고 남긴다.

억지 연결은 독자의 신뢰를 깎는다. 하나라도 억지가 섞이면 진짜 연결까지 의심받는다.

### 6.7 외부 링크

**작성 시점에 실제로 접속해서 (1) 살아있는지 (2) 제목이 아니라 실제 내용이 주제와 일치하는지** 확인한 뒤에만 넣는다. 추측으로 만든 URL은 **넣지 않는다.** 확인이 안 되면 비워 둔다. **없는 것이 틀린 것보다 낫다.**

추가할 때마다 같은 커밋에 `docs/LINK_LOG.md` 에 한 줄(확인 날짜, URL, 확인 방법)을 남긴다.

논문은 **저자·연도·제목**만으로 인용할 수 있다. URL은 위 규칙을 통과했을 때만.

## 7. 위젯 우선 원칙

**시간에 따라 상태가 변하는 것은 예외 없이 위젯으로 만든다.**

탐색 순서, 테이블 채우기, 포인터 이동, 트리 회전, 힙 sift, 재귀 호출 트리, B-Tree 분할, LSM 컴팩션 — 전부 해당한다.

아스키 다이어그램은 **정적 구조**(그래프 모양, 트리 형태, 메모리 배치) 표기에만 쓴다.

**"글로 설명 가능하다"는 이 책에서 근거가 되지 않는다.** 글로 설명 가능한 것과 글만 읽고 머릿속에서 재생되는 것은 다르다.

삽입 문법:

```markdown
::: widget grid-search {"algo":"bfs","grid":"basic-maze","start":[0,0],"goal":[9,9]}
:::
```

위젯 뒤에는 **그 위젯을 말로 옮긴 산문**이 온다. 위젯이 안 뜨는 환경(단일 HTML을 텍스트로 읽는 경우 등)에서도 이해가 되어야 한다.

## 8. 서술 시점과 톤 (예외 없는 강제 규칙)

이 레포는 public이며 누구나 모든 문서·챕터·주석·커밋 메시지를 읽는다는 전제로 쓴다.

**절대 넣지 않는 것:**

- **저자 1인칭 서사 일체.** "나는 이걸 몰랐다", "처음엔 어려웠다", "계속 틀렸다" 류의 학습 경험 고백. **이 책은 독자를 위한 레퍼런스이지 저자의 학습 노트가 아니다.**
- 저자의 이력·학력·경력·나이·직무·과거 사용 기술·구직 활동에 대한 언급.
- 특정 회사명, 채용 시장 서술, 특정 시험·전형에 대한 개인적 평가.
- 자기 능력에 대한 방어적·변명적 서술.
- **AI 어트리뷰션.** 커밋 메시지·코드 주석·본문 어디에도 생성 도구를 언급하지 않는다.

**대신 쓰는 프레이밍:** 모든 서술은 **일반 명제 또는 콘텐츠 설계 근거**로 쓴다.

- 나쁨: "나는 유형 판별이 제일 어려웠다."
- 좋음: "알고리즘 학습의 실질 병목은 지식의 부재가 아니라 문제-알고리즘 매핑의 실패다."

앞 문장은 고백이고, 뒤 문장은 편집 방침의 근거다. 대상 독자층을 서술하는 것은 허용된다.

**적용 범위:** README, 챕터 본문, 코드 주석, 커밋 메시지, PR 본문, 부속 문서 전부.

## 9. 체크리스트

절을 끝내기 전에:

- [ ] `# 제목` 이 `toc.json` 의 `num` + `title` 과 정확히 같은가

- [ ] C++은 `g++ -std=c++17 -O2` 로 컴파일되는가. Python은 3.13에서 실행되는가
- [ ] 언어 차이 표를 붙였는가 (갈라지는 지점이 있다면)

- [ ] `::: trace` 가 있는가 (필수 챕터라면)
